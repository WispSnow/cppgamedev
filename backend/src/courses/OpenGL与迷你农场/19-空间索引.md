# 空间索引：静态瓦片网格 + 动态实体网格的组合

在进入 Part 4（空间索引与碰撞）之前，先盘点一下我们手里已有的材料：

- **地图加载**（后续课程会展开，但此刻你已经知道 Tiled `.tmj` 能被解析成运行时实体）：地图里既有静态的瓦片信息（SOLID、ARABLE、WATER…），也有动态的对象——角色、NPC、树木、石头。
- **ECS 系统编排**：系统每帧更新，玩法逻辑的本质是"读写组件数据"。
- **碰撞器组件**（`AABBCollider` / `CircleCollider`）和基础的移动/交互/耕作系统——它们都需要反复问同一类问题：
  - "这个位置能不能走？"
  - "玩家面前那格有什么可交互目标？"
  - "这一格能不能锄地？有没有被动态实体占用？"

问题在于：**谁来回答这些问题？**

如果没有统一的空间查询入口，实际项目往往会滑向两个死胡同：

1. **遍历一切**：每次判定都扫一遍场景里的所有实体，拿 Transform + Collider 逐个比较。当实体量过百，这条路的性能和可维护性都不可接受。
2. **各自为战**：移动系统自己缓存一份碰撞表，交互系统自己缓存一份目标表，耕作系统再来一份……切地图、读档、实体销毁时，数据一致性直接变成噩梦。

所以本节要做的事很明确：把"空间查询"做成一个**稳定的基础设施**，让所有玩法系统只关心**发起查询**与**消费结果**，而不必关心索引的维护细节。

## 核心概念

本节有三个关键概念。理解了它们，你就能读懂《迷你农场》里几乎所有空间相关的玩法逻辑。

### 1. 两张网格：静态（tile）与动态（entity）

我们用"网格"做空间索引，原因很直接：
- 游戏世界本身就是 2D 瓦片地图，天然是网格。
- 均匀网格（uniform grid）实现成本低、查询性能稳定、调试时可视化一目了然。

但一张网格不够用——因为我们需要索引的东西天生分成两类：

| 特征 | 静态瓦片信息 | 动态实体碰撞器 |
|------|------------|--------------|
| **典型数据** | SOLID/ARABLE/WATER 标志、soil/wet/crop 层实体 | 玩家、NPC、树木、石头的碰撞盒 |
| **生命周期** | 地图加载时写入，运行时几乎不变 | 实体移动时需要频繁更新 |
| **查询粒度** | 恰好一个 tile 一个 cell | 一个实体可能跨多个 cell |
| **典型问法** | "这格是否阻挡？""这格上有 crop 实体吗？" | "这个区域里有哪些碰撞体？" |

因此《迷你农场》把空间索引拆成两张网格，各自用最合适的数据结构：

**(1) StaticTileGrid（静态瓦片网格）**

每个瓦片对应一个 `TileCellData`，里面存两样东西：

- **`tile_type_`（`TileType` 位掩码）**：`BLOCK_N/S/W/E`、`SOLID`、`ARABLE`、`WATER`、`HAZARD`、`OCCUPIED` 等标志，用一个整数的不同 bit 表示。碰撞/属性判定靠位运算 `hasTileFlag()` / `hasAllTileFlags()` 完成——`SOLID` 实际上等于四向阻挡全部置位。
- **按 layer 分桶的实体列表**：同一瓦片上可以叠放多个"瓦片实体"（soil、wet、crop、rock、rest…），每个占一个 layer。内部用 `layer_to_index_` 哈希表做 O(1) 查找，所以 `getTileEntity(coord, layer_id)` 能按层精确定位。

> 为什么要按 layer 分桶？因为同一格上"土壤""湿润标记""作物"三者可以同时存在，查询时你需要按语义区分，而不是把它们混成一个列表。

关联阅读：`src/engine/spatial/static_tile_grid.h`（`TileCellData` 结构体定义）

**(2) DynamicEntityGrid（动态实体网格）**

- 把"带碰撞器的实体"按固定 cell size 分桶。一个实体的碰撞盒可能跨越多个 cell，因此同一个实体会被注册到所有覆盖的 cell 中。
- 内部维护 `entity→cells` 的双向映射（`entity_to_cells_`），更新时先移除旧 cell、再插入新 cell。
- 查询返回的是"候选集合"：所有与查询区域覆盖相同 cell 的实体。这个集合可能包含"靠得很近但并未真正相交"的实体——所以它只是 **broadphase**。

关联阅读：`src/engine/spatial/dynamic_entity_grid.h`（类声明 + 调试接口）

两张网格统一由 `SpatialIndexManager` 对外暴露。玩法系统不直接依赖底层网格，而是通过 Manager 的 API 发起查询——这是整个设计的核心约束。

### 2. Broadphase → Narrowphase（候选 → 真实命中）

动态网格返回的"候选集合"是一种**过度估计**：它告诉你"这些实体可能和查询区域相交"，但不保证每个都真的碰上了。这是均匀网格的天然特性——分桶精度取决于 cell 尺寸，而不是碰撞体的真实形状。

因此查询需要两个阶段：

```text
queryColliders(rect):
  candidates = dynamicGrid.queryEntities(rect)      // ← broadphase：快速缩小范围
  overlaps = []
  for e in candidates:
    shape = buildColliderShape(registry, e)          // 从 ECS 读 Transform + Collider，构造几何形状
    if shape intersects rect:                        // ← narrowphase：精确相交测试
      overlaps.push(e)
  return overlaps
```

两阶段各有分工：
- **Broadphase** 负责"缩小集合"，把 O(N) 全场遍历压缩到 O(K)，其中 K 是查询区域覆盖的 cell 内的实体数。
- **Narrowphase** 负责"精确判定"，剔除"同 cell 但不相交"的误报。

在代码里，narrowphase 的几何判定封装在 `collider_shape.h` 中——这是一个纯函数工具头文件（header-only，不持有状态）：

- `buildColliderShape(registry, entity)`：从 ECS 读取 `TransformComponent` + `AABBCollider`（或 `CircleCollider`），构造统一的 `ColliderShape`（内含 `Rect` 或 `Circle` 几何数据）
- `intersectsRectQuery(rect, shape)` / `intersectsCircleQuery(center, radius, shape)` / `intersectsPointQuery(point, shape)`：三种查询形状与 `ColliderShape` 的相交测试，内部根据碰撞器类型分发到 Rect-Rect、Rect-Circle、Circle-Circle 等具体判定函数

> `collider_shape.h` 的设计意图是让 `SpatialIndexManager`（本节）和 `CollisionResolver`（[碰撞解析与移动](20-碰撞解析与移动.md)）共用同一套判定逻辑，避免重复实现。

关联阅读：`src/engine/spatial/collider_shape.h`、`src/engine/spatial/spatial_index_manager.cpp`（`queryColliders()` 和 `filterOverlaps()` 模板）

<img src="https://theorhythm.top/gamedev/TF/L17_broadphase_narrowphase.webp" style='width: 960px;' />

### 3. 半开区间与"卡边"问题

空间索引里最容易踩坑的不是算法，而是**边界定义**：

- 一个点恰好落在两个格子的交界线上，算哪一边？
- 一个矩形的右下角刚好碰到下一格的左上角，要不要把下一格也算进覆盖范围？

如果边界定义不一致，你会遇到这些典型 bug：
- 角色贴墙移动时反复抖动（一帧判定为碰撞、一帧判定为不碰撞）
- 查询"误伤"隔壁格子的实体，导致不该触发的交互被触发
- Debug 面板里高亮的范围和实际玩法逻辑不一致，排错时给你传递错误信息

《迷你农场》的统一规则：

- **Point → tile/cell 映射**：使用 `floor` 函数，边界点归右/归下。代码实现在 `StaticTileGrid::worldToTileCoord()` 和 `DynamicEntityGrid::worldToCell()`。
- **Rect 覆盖范围**：按半开区间 `[pos, pos+size)` 解释。计算覆盖的 tile/cell 范围时，对 max 端做 epsilon 收缩（`pos + size - epsilon`），避免"矩形尺寸恰好等于 tile 尺寸时多算一格"的 off-by-one 错误。

这套规则被固化在 `tileRangeForRect()` 和 `getCellsForRect()` 中，并用单元测试锁定。

关联阅读：`src/engine/spatial/static_tile_grid.cpp`（`tileRangeForRect()`）、`src/engine/spatial/dynamic_entity_grid.cpp`（`getCellsForRect()`）

## 架构与数据流

用两张图把整个系统串起来：一张看"静态结构"，一张看"运行时数据怎么流动"。

### 结构图：SpatialIndexManager 组合两张网格

`SpatialIndexManager` 持有一个 `StaticTileGrid` 和一个 `DynamicEntityGrid`，并持有对 `entt::registry` 的非拥有指针（用于在 narrowphase 时读取碰撞器组件）。

它对外暴露三类 API：
- **静态查询**：`isSolidAt()` / `isArableAt()` / `getTileEntity()` 等——直接代理到 `StaticTileGrid`
- **动态查询**：`queryColliderCandidates()`（broadphase）和 `queryColliders()`（broadphase + narrowphase）
- **综合查询**：`checkCollision()`——同时查静态阻挡 + 动态碰撞体，返回一个 `CollisionResult`

<img src="https://theorhythm.top/gamedev/TF/L17_structure_diagram.webp" style='width: 960px;' />

### 数据流：加载阶段写静态，运行阶段更新动态

<img src="https://theorhythm.top/gamedev/TF/L17_data_flow.webp" style='width: 960px;' />

**加载阶段（Load Phase）**

地图加载时，`LevelLoader::loadTileLayer()` 会把每个瓦片的 `TileInfo.type_` 通过 `setTileType()` 写入静态网格，同时把瓦片实体通过 `addTileEntity()` 按 layer 注册。对象层的 `EntityBuilder` 也可以补充标注（例如休息区标记 `INTERACT` 标志并注册 layer 实体）。

关联阅读：`src/engine/loader/level_loader.cpp`、`src/game/loader/entity_builder.cpp`（`buildRestArea()`）

**运行阶段（Runtime Update）**

`SpatialIndexSystem` 负责维护动态网格。它的更新策略是 **dirty 驱动**：

```text
SpatialIndexSystem::update():
  view = registry.view<SpatialIndexTag, TransformDirtyTag, TransformComponent>()
  for entity in view:
    spatial_index.updateColliderEntity(entity)    // 重新计算碰撞盒，更新 cell 归属
    registry.remove<TransformDirtyTag>(entity)    // 清除 dirty 标记
```

三个组件缺一不可：
- `SpatialIndexTag`：标记"这个实体参与动态空间索引"（不是所有实体都需要被索引）
- `TransformDirtyTag`：标记"这个实体的位置发生了变化"（由 `MovementSystem` 等系统在修改 Transform 后添加）
- `TransformComponent`：提供位置数据

> 这种设计的好处是，只有**位置真正发生变化**的实体才会触发网格更新。如果场景里有 100 个带碰撞器的实体，但这一帧只有 3 个在移动，那么只需要更新 3 次——而不是重建整张动态网格。

关联阅读：`src/engine/system/spatial_index_system.cpp`、`src/engine/component/tags.h`

**系统更新顺序也很关键**：`SpatialIndexSystem` 必须在 `MovementSystem` 之后运行。如果顺序反了，你查到的碰撞器位置是上一帧的——这类 bug 的表现是"角色明明已经走到了新位置，但碰撞检测还在用旧位置"，很难排查。

你可以用这张数据流图回答两个常见排错问题：
- "某个数据从哪来？" → 看 Load Phase
- "为什么我移动了实体，查询结果却没变？" → 检查 dirty 标记是否被设置、系统更新顺序是否正确

## 玩法系统如何使用空间索引

理论讲完了，来看两个真实的消费端。它们展示了玩法系统如何**只依赖 `SpatialIndexManager` 的 API** 完成判定，而不需要关心底层网格的实现细节。

### 交互系统：在玩家面前找目标

`InteractionSystem::chooseFacingTarget()` 的核心逻辑：

1. 根据玩家朝向，在前方一格构建一个瓦片大小的"探测矩形"（probe rect）
2. 调用 `checkCollision(probe_rect)` 获取这个区域内的所有动态碰撞体
3. 在候选集合中按优先级筛选：NPC 对话 > 宝箱 > 休息区
4. 如果动态查询没有结果，回退到静态层查询 `getTileEntityAtWorldPos(pos, REST_LAYER)`

> 注意第 4 步的"回退"设计：休息区在地图中以瓦片层实体的形式存在（静态网格），而 NPC/宝箱以碰撞器形式存在（动态网格）。交互系统先查动态、再查静态，用一个 `SpatialIndexManager` 覆盖了两种数据源。

关联阅读：`src/game/system/interaction_system.cpp`

### 农场系统：锄地前的三重检查

`FarmSystem` 在玩家使用锄头时要回答的问题：

1. **这一格是否可耕作？** → `isArableAt(tile_coord)`（静态属性查询）
2. **这一格上是否已有土壤/作物？** → `getTileEntityAtWorldPos(pos, SOIL_LAYER)`（静态层实体查询）
3. **这一格是否被动态实体占用？** → `queryColliders(tile_rect)`（动态查询）——如果有 `AABBCollider` 类型的实体占着这格（比如一棵树），锄地操作应该被阻止

三个查询分别使用了 `SpatialIndexManager` 的静态属性 API、静态层实体 API 和动态查询 API。农场系统自身不需要知道底层网格的存在。

关联阅读：`src/game/system/farm_system.cpp`

## 调试与可视化

空间索引是"看不见"的基础设施，出了问题很难靠猜来排查。所以《迷你农场》提供了 `Spatial Index` 调试面板和对应的调试渲染叠加层：

**静态网格可视化**：开启后可以看到网格线和各类标志的瓦片高亮（SOLID 用一种颜色、ARABLE 用另一种）。你能直观确认"Tiled 里标记的属性是否正确写入了运行时网格"。

**动态网格可视化**：开启后可以看到动态网格线、有实体的 cell 高亮、以及每个碰撞器的包围盒。移动玩家或靠近 NPC 时，你能观察到 cell 归属的实时变化和候选数量。

**综合查询测试**：在面板中输入一个查询矩形或查询圆，观察静态碰撞结果 + 动态候选列表 + narrowphase 命中列表。这是验证"我的查询为什么没找到目标"的最直接手段。

关联阅读：`src/engine/debug/panels/spatial_index_debug_panel.*`、`src/engine/system/debug_render_system.cpp`

## 课后练习

### 练习 1：为 DynamicEntityGrid 增加运行时统计

**目标**：让你在不写 profiler 的情况下，也能回答"为什么这里候选这么多？查询这么频繁？更新是不是太贵了？"

**验收标准**：
- 在 `Spatial Index` 调试面板中能看到至少 3 个统计指标（例如：每帧 update 次数、每帧 query 次数、候选 candidates 峰值/均值、narrowphase overlaps 峰值/均值）
- 统计数据能随帧刷新，且不会无限增长（有 clear/reset 机制）
- 不影响 Release 逻辑（默认开销很低；建议只在 debug 构建或面板开启时采样）
- `ctest --test-dir build -R engine_tests --output-on-failure` 可通过

**提示线索**：
- `src/engine/spatial/dynamic_entity_grid.*`
- `src/engine/spatial/spatial_index_manager.*`（统计 query/candidates 的天然入口）
- `src/engine/debug/panels/spatial_index_debug_panel.*`

**提交方式**：GitHub PR（描述"新增了哪些指标 / 如何验证"）

### 练习 2（可选挑战）：优化 entity→cells 映射结构

**目标**：当前 `DynamicEntityGrid` 的 `entity_to_cells_` 类型是 `unordered_map<entity, unordered_set<cell>>`。在实体数量较多时，`unordered_set` 的内存分配和哈希开销较高。尝试替换为更轻量的结构。

**验收标准**：
- 保持对外行为一致：添加/更新/移除/查询结果不变
- 新增或更新必要的单元测试
- `ctest --test-dir build -R DynamicEntityGridTest --output-on-failure` 可通过

**提示思路**：
- 小向量（small vector）：大多数实体只占 1–4 个 cell，用定长数组 + 溢出堆分配
- 连续区间表示：如果碰撞盒是矩形，覆盖的 cell 一定是连续的矩形区域，可以只存 `min_cell` + `max_cell`
- 自定义轻量 cell 列表：避免 `unordered_set` 的节点分配开销

**提交方式**：GitHub PR（说明你选择的结构、trade-off、以及如何验证正确性）

## 小结

本节课完成了"空间查询基础设施"的工程化落地：

- **两张网格各司其职**：`StaticTileGrid` 回答瓦片属性和瓦片层实体查询，`DynamicEntityGrid` 提供碰撞器候选集合
- **统一入口**：`SpatialIndexManager` 把静态查询、broadphase、narrowphase、综合查询收敛成一套稳定 API
- **按需更新**：`SpatialIndexSystem` 只处理 dirty 实体，避免每帧全量重建
- **可视化排错**：调试面板和渲染叠加层让空间索引从"黑盒"变成"可观测"
