# 输入系统：动作映射、状态机与鼠标逻辑坐标

上节课我们把文本渲染工程化了：`config/text_render.json` 让样式变成可复现输入，`Text` 面板让调参实时生效，`Resource` 面板让 atlas 成本可观测。整条管线从 FreeType/HarfBuzz 到 UI/World 两条绘制通路，都有了清晰的分工和排查入口。

但是——文字画出来了，按钮也有了，玩家要怎么"用"它们？

你需要移动角色、打开背包、点击按钮、暂停游戏。这些操作的起点都是**键盘/鼠标输入**。然而 SDL 给你的只是底层事件流（`SDL_EVENT_KEY_DOWN`、`SDL_EVENT_MOUSE_BUTTON_DOWN`），它不知道"按下 A 键"意味着"向左移动"，也不知道"点击鼠标"应该优先给 UI 还是给世界。

更棘手的是坐标问题：当窗口大小和逻辑分辨率不一致（出现 letterbox 黑边）时，SDL 的鼠标坐标和你的 UI/世界坐标根本对不上。

所以这节课的目标不是"教你读 SDL_Event"，而是教你如何把底层输入变成一个**可配置、可观测、可组合**的工程化系统。

## 本节目标与问题定义

核心问题用一句话概括：

> 把"物理输入"（键盘/鼠标事件）翻译成"游戏动作"（ActionState），让它可配置（JSON 驱动映射）、有帧语义（状态机）、能分优先级（回调占用/转发），并统一鼠标坐标系（logical 映射），让 UI 与世界交互不再"打架"。

本节完成后你应该能回答这些问题：

- **动作映射**：为什么要把按键抽象成 action？`config/input.json` 如何驱动映射？
- **状态机**：`PRESSED/HELD/RELEASED` 的帧语义是什么？为什么需要 `HELD`？
- **两种使用方式**：什么时候 polling（`isActionDown`）更合适，什么时候 callback（`onAction(...).connect`）更合适？
- **输入占用/转发**：UI 为什么要"吃掉"点击？消费规则如何实现？
- **鼠标逻辑坐标**：为什么不能直接用 SDL 的鼠标坐标？letterbox/高 DPI 下怎么保证 UI 与世界交互稳定？
- **ImGui 隔离**：调试 UI 与游戏输入如何互不干扰？

## 核心概念

### 动作映射：从"按键"到"语义动作"

在工程里，"按下 A 键"并不是你真正想表达的需求，你真正想表达的是：

- "向左移动"
- "打开背包"
- "暂停/关闭菜单"

如果代码里到处写 `if (key == SDL_SCANCODE_A)`，那改一次键位就要改无数个地方。因此《迷你农场》用 `action_name`（动作名称）做"稳定 API"，把具体按键绑定交给配置文件：

```json
{
  "input_mappings": {
    "move_left": ["A", "Left"],
    "pause": ["P", "Escape"],
    "interact": ["F"],
    "inventory": ["I"],
    "hotbar_1": ["1"],
    "camera_reset_zoom": ["MouseMiddle"]
  }
}
```

好处非常直接：

- **改键位不改代码**——改 JSON 即可，不需要重新编译
- **多处系统共用同一个 action**——例如 `pause` 同时用于 `GameScene`（打开暂停菜单）和 `PauseMenuScene`（关闭暂停菜单）
- **一个 action 可以绑定多个键**——`move_left` 同时绑定了 A 和方向键左，也是将来扩展手柄支持的基础
- **一个按键也可以触发多个 action**——如果你把同一个键名写进两个不同的 action 数组里，两个 action 都会被激活

`InputManager` 在初始化时读取 `config/input.json`，把 `action_name → [key_names]` 翻译成内部的 `input → [action_id]` 映射表（`input_to_actions_`）。字符串键名通过 `SDL_GetScancodeFromName` 转成 `SDL_Scancode`；鼠标按钮名（`MouseLeft` / `MouseRight` / `MouseMiddle` / `MouseX1` / `MouseX2`）则通过硬编码映射转成 `SDL_BUTTON_*` 常量。

有一个值得注意的细节：`mouse_left` 和 `mouse_right` 是输入系统内部使用的**隐式 action**。如果配置文件里没有显式定义它们，`InputManager` 会在 `initializeMappings()` 中自动注入默认映射。这保证了 UI 层（`UIManager`）始终可以订阅鼠标点击事件，而不需要用户在配置中关心这些底层绑定。

### 动作状态机：把"事件"变成"帧语义"

SDL 的 KEY_DOWN/KEY_UP 是事件流——事件来了才有，不来就没有。但游戏逻辑更需要的是"每帧我处在什么状态"。

![动作状态机转换图](diagrams/L13_action_state_machine.png)

四种状态的含义：

| 状态 | 含义 | 类比 |
| --- | --- | --- |
| `PRESSED` | 本帧刚按下 | 边沿触发（上升沿） |
| `HELD` | 持续按住 | 电平保持（高电平） |
| `RELEASED` | 本帧刚松开 | 边沿触发（下降沿） |
| `INACTIVE` | 未激活 | 电平保持（低电平） |

其中 `HELD` 解决的是一个现实问题：**"按住不动"时 SDL 不会每帧都给你一个 KEY_DOWN 事件**。如果没有 `HELD`，按住方向键的第二帧开始，`isActionDown()` 就会返回 false，角色只动一帧就停了。所以 `InputManager` 必须在帧开始时主动把上一帧的 `PRESSED` 推进为 `HELD`——这就是状态机的核心意义。

对于键盘重复事件（`event.key.repeat == true`），`InputManager` 会设为 `HELD` 而不是重新触发 `PRESSED`——这避免了"长按时反复触发一次性动作"的问题（想象一下按住 F 键连续对话）。

还有一个容易忽略的防御措施：当收到 KEY_UP 事件时，`updateActionState` 会检查当前状态是否为 `INACTIVE`——如果从未按下却收到松开事件（比如 ImGui 捕获了按下事件但没捕获松开事件，或者窗口焦点切换），就跳过 `RELEASED` 状态，避免产生一次"幽灵释放"。

### InputManager 的三段式更新

`InputManager::update()` 每帧的工作可以拆成严格的三个阶段：

![三段式更新流程](diagrams/L13_three_phase_update.png)

**阶段 1：推进状态**

```
PRESSED  → HELD       // 按住不动时保持 HELD
RELEASED → INACTIVE   // 松开后回到空闲
```

同时重置滚轮 delta（滚轮数据只有单帧有效，不像按键有"持续按住"的概念）。

**阶段 2：处理 SDL 事件**

轮询所有 `SDL_PollEvent`，根据事件类型更新动作状态：

- **键盘事件**：`SDL_Scancode` → 查 `input_to_actions_` → `updateActionState`
- **鼠标按钮**：`SDL_BUTTON_*` → 查 `input_to_actions_` → `updateActionState`
- **鼠标移动/滚轮**：更新 `mouse_position_` 和 `mouse_wheel_delta_`
- **窗口事件**：通过 dispatcher 触发 `WindowResizedEvent`（区分窗口逻辑尺寸变化与像素尺寸变化，后者对应高 DPI 场景）
- 每种涉及鼠标位置的事件之后都会调用 `recalculateLogicalMousePosition()`

**阶段 3：分发回调**

- 遍历所有处于非 `INACTIVE` 状态的动作
- 对每个动作，按当前状态查找对应的回调链（`actions_to_func_[action_id][state_index]`）
- 使用 EnTT sigh 的 `collect` 分发：回调返回 `true` 则停止后续分发（占用语义）

这三阶段的顺序是刻意的：先推进确保状态机语义正确，再处理事件写入新状态，最后分发回调——保证回调读到的是**本帧最新**的状态。如果把回调分发放在事件处理之前，回调读到的就是上一帧的状态，会导致响应延迟一帧。

### polling vs callback：两条使用路线

《迷你农场》同时支持两种输入消费方式，分别适合不同的使用场景：

| | polling（查询式） | callback（事件式） |
| --- | --- | --- |
| API | `isActionDown` / `isActionPressed` / `isActionReleased` | `onAction(action_id, state).connect<&Class::method>(instance)` |
| 适合 | 需要连续驱动的逻辑 | 离散触发、需要优先级/占用的交互 |
| 生命周期 | 无需管理，随用随查 | 必须 connect/disconnect |
| 能否占用 | 不能 | 回调返回 `true` 可停止分发 |

**实际例子**：

`PlayerControlSystem` 是两种方式混用的典型——移动用 polling，工具使用和快捷栏切换用 callback：

```cpp
// polling：每帧查询移动方向
if (input_manager_.isActionDown("move_up"_hs))    direction.y -= 1.0f;
if (input_manager_.isActionDown("move_down"_hs))   direction.y += 1.0f;
if (input_manager_.isActionDown("move_left"_hs))   direction.x -= 1.0f;
if (input_manager_.isActionDown("move_right"_hs))  direction.x += 1.0f;

// callback：鼠标点击需要和 UI 做优先级判断
input_manager_.onAction("mouse_left"_hs).connect<&PlayerControlSystem::onMouseLeftClick>(this);
```

`InteractionSystem` 使用 polling 来检测离散交互——用 `isActionPressed("interact"_hs)` 检测"本帧刚按下 F"。这里用 polling 而不是 callback，是因为交互不需要和其他系统做优先级竞争——按 F 时只有交互系统关心这个动作。

**实践建议**：

- **"持续行为"优先 polling**——代码更简单，不需要管 connect/disconnect 生命周期
- **"一次触发/需要优先级"的交互优先 callback**——回调的 bool 返回值是实现"占用"的唯一手段

### 输入占用/转发：为什么回调要返回 bool

在 UI 与世界交互共存的场景里，一个 `mouse_left` 点击可能同时意味着：

- UI：点按钮 / 拖拽物品 / 关闭窗口
- 世界：挥工具 / 种植 / 选择目标

如果不做优先级区分，点 UI 的同时会触发世界逻辑——这在几乎所有游戏中都是 bug。

![输入占用/转发链路](diagrams/L13_input_consumption.png)

《迷你农场》的实现策略：

- `onAction` 的回调签名是 `bool()`，返回 `true` 表示"已消费，停止分发"
- 分发顺序为**后绑定先调用**（EnTT sigh 的 collect 语义）
- 当 `UIManager` 命中一个交互元素（按钮/槽位等）时返回 `true`，后续的游戏订阅者就不会收到这次点击

为什么"后绑定先调用"在项目中刚好管用？看 `GameScene` 的初始化顺序就明白了：

1. **`initSystems()`**：创建 `PlayerControlSystem`，构造函数中 connect `mouse_left`
2. **`initUI()`**：创建 `UIManager`，`registerMouseEvents()` 中 connect `mouse_left`

后 connect 的 `UIManager` 优先被调用。如果它在某个 UI 元素上命中了点击并返回 `true`（消费），`PlayerControlSystem` 就收不到了。反过来，如果 `UIManager` 没有命中任何 UI 元素，它返回 `false`，`PlayerControlSystem` 正常收到点击并执行世界动作。

`UIManager` 具体怎么判断"命中"？在 `onMousePressed` 回调中，它会用当前的 logical 鼠标位置做 hit-test——如果找到了一个 `UIInteractive` 元素（按钮、物品槽等），就记录为 `pressed_element_` 并返回 `true`。在 `onMouseReleased` 回调中，只有当之前有 `pressed_element_` 时才返回 `true`——这保证了"在 UI 上按下再松开"不会漏给世界。

> **注意**：这种"依赖 connect 顺序的隐式优先级"在小项目中可以工作，但如果订阅者数量增长或生命周期变复杂，建议升级为显式 priority（见课后练习 2）。

### 鼠标逻辑坐标：统一 UI 与世界交互的坐标系

一个非常常见的坑是：直接拿 SDL 的鼠标坐标去做 UI hit-test 或 screen→world 映射。在窗口大小等于逻辑分辨率时这恰好能用，但一旦出现 letterbox 或高 DPI，坐标就全漂了。

![鼠标坐标映射流程](diagrams/L13_mouse_coordinate_mapping.png)

在《迷你农场》中你需要区分两类坐标：

| | Mouse Position | Logical Position |
| --- | --- | --- |
| 来源 | SDL 的 window coordinates | InputManager 计算得到 |
| 单位 | 窗口坐标像素 | 逻辑分辨率像素 |
| 用途 | 不应该直接使用 | UI hit-test、`screenToWorld` |

当窗口大小与逻辑分辨率不一致时（尤其是出现 letterbox 黑边），这两套坐标会有显著差异。`InputManager` 每次更新鼠标位置时都会调用 `recalculateLogicalMousePosition()`：

1. 从 `GameState` 读取 `window_size`（SDL 窗口坐标尺寸）和 `logical_size`（逻辑分辨率）
2. 用 `computeLetterboxMetrics()` 计算 viewport 偏移和缩放因子
3. `logical = (mouse - viewport_offset) / scale`
4. clamp 到 `[0, logical_size]`——防止鼠标在 letterbox 黑边区域时坐标超出逻辑范围

为什么必须用 `window_size` 而不是 `pixel_size`？因为 SDL 的鼠标坐标是 window coordinates，而高 DPI 下 window size 和 pixel size 可能不同。例如 Retina 屏上窗口坐标是 800x600 但实际像素是 1600x1200。坐标转换必须在同一个坐标系里做——用 window size 做 letterbox 计算，才能正确映射鼠标的 window coordinates。

`PlayerControlSystem` 中有一个完整的坐标转换链路值得关注：

```
SDL mouse → InputManager.getLogicalMousePosition() → camera.screenToWorld() → 世界坐标
```

`getLogicalMousePosition()` 把鼠标位置映射到逻辑分辨率空间，`screenToWorld()` 再把逻辑坐标转换到世界空间——这两步加起来，就完成了从"玩家点击屏幕位置"到"世界中对应位置"的完整映射。

### ImGui capture：调试 UI 与游戏输入的隔离

《迷你农场》的调试面板使用 ImGui 绘制，ImGui 有自己的输入捕获机制。当用户在调试面板中输入文字或点击滚动时，这些输入不应该同时影响游戏。

`InputManager::processEvent()` 在处理键盘/鼠标事件前会检查 ImGui 的捕获状态：

- `ImGui::GetIO().WantCaptureKeyboard`：ImGui 正在使用键盘（例如在输入框中打字）→ 键盘按下事件不会转化为动作状态
- `ImGui::GetIO().WantCaptureMouse`：ImGui 正在使用鼠标（例如拖动面板/点击按钮）→ 鼠标按下/滚轮事件被阻止

这个检查通过 `#ifdef TF_ENABLE_DEBUG_UI` 保护——Release 版本中不存在 ImGui，这些分支会被编译器完全去除，零开销。

这是一个简单但容易遗漏的工程细节——如果不做隔离，打开调试面板后按方向键会同时移动玩家和操作面板。

## 架构与数据流

### 总览：从 SDL 到 ActionState

![InputManager 数据流总览](diagrams/L13_input_dataflow.png)

数据流的关键路径：

1. **配置加载**：`config/input.json` → `InputManager::loadConfig` → `input_to_actions_` 映射表
2. **每帧更新**：`GameApp::handleEvents` → `InputManager::update`（三段式）
3. **状态消费**：系统通过 polling API 或 callback 读取动作状态
4. **鼠标坐标**：`InputManager` 维护 window 和 logical 两套坐标，供 UI 和相机使用
5. **引擎事件**：窗口退出/大小变化通过 `dispatcher.trigger` 通知其他子系统

`InputManager` 对外隐藏了 SDL 的所有细节——消费者只看到 action name + 状态，不关心底层是键盘、鼠标还是将来的手柄。这和 [资源系统](13-资源系统.md) 讲的 `ResourceManager` 外观模式是同一个设计思路：用一个稳定的接口隔离底层实现的复杂性。

### 输入与场景生命周期：connect / disconnect 的责任归属

输入回调属于"跨帧存活的订阅关系"，所以你必须明确它的生命周期。规则很简单：

- **谁 connect 谁 disconnect**
- **connect 在构造/init，disconnect 在析构/clean**

在项目中你会看到两种模式：

**场景级订阅**（GameScene / PauseMenuScene / SaveSlotSelectScene）：

- 在 `init()` 或构造过程中 connect
- 在析构函数中 disconnect
- 例：`GameScene` 订阅 `inventory/hotbar/pause`，析构时逐一断开

**系统级订阅**（PlayerControlSystem / UIManager）：

- 在构造函数中 connect
- 在析构函数中 disconnect
- 断开时必须指定精确的函数指针和实例

> **一个重要的工程实践**：disconnect 时务必使用 `.disconnect<&Class::method>(this)` 指定精确的委托，而不是无参数的 `.disconnect()` 全部断开。后者会把同一信号上的**所有**订阅者都断开——如果 `PlayerControlSystem` 和 `UIManager` 都订阅了 `mouse_left`，无差别断开会导致另一方也失去响应。

### UIInputBlocker：菜单场景的"透明挡板"

当暂停菜单（`PauseMenuScene`）或存档选择（`SaveSlotSelectScene`）这类 UI 场景被 push 到场景栈时，底层的 `GameScene` 仍然存在且其输入回调仍然活着（回忆 [场景系统](07-场景系统.md)：Scene 栈中被覆盖的场景不会被销毁）。如果不做处理，点击菜单上的按钮可能同时被 `GameScene` 的回调处理。

`UIInputBlocker` 用一种巧妙的方式解决这个问题：

- 它继承自 `UIInteractive`，但 `renderSelf()` 为空（完全透明，不画任何东西）
- 被设为全屏大小（`setAnchor({0,0}, {1,1})`），覆盖整个逻辑分辨率区域
- 当 `UIManager` 做 hit-test 时，blocker 会命中任何位置的点击——由于 `UIManager` 发现命中了一个 UI 元素，它会返回 `true`（消费），阻止事件传播到世界

这就是**复用已有的占用机制**而不是发明新机制——blocker 不需要任何特殊逻辑，它只是一个覆盖全屏的透明 UI 元素，利用 `UIManager` 已有的消费语义来阻断输入。

## 演示：动手验证

### 演示 1：状态机可视化

1. 运行游戏，按 `F5` → `Engine Debug Panels` → 勾选 `Input`
2. 随便按一个键（比如 W），观察面板中对应动作的状态：
   - 按下瞬间：显示 `Pressed`
   - 持续按住：下一帧变成 `Held`
   - 松开瞬间：变成 `Released`
   - 下一帧：回到 `Inactive`
3. 试试面板上的 `Press` / `Hold` / `Release` 按钮——你可以不碰键盘，直接在面板里手动触发动作状态。这在测试"某个动作触发后系统是否正确响应"时非常方便

这个实验建立的直觉是：**状态机是帧级别的**。`PRESSED` 和 `RELEASED` 只存在一帧，`HELD` 会一直保持。

### 演示 2：配置驱动映射

1. 打开 `config/input.json`
2. 把 `"pause"` 的绑定从 `["P", "Escape"]` 改成 `["O", "Escape"]`
3. 重启游戏
4. 按 P 键——暂停菜单不再弹出
5. 按 O 键——暂停菜单正常弹出
6. 打开 `Input` 面板确认：`pause` 动作现在只会被 O 和 Escape 触发

**核心价值**：键位修改完全在配置层完成，没有任何代码变动。这就是"动作映射"带来的工程收益。

### 演示 3：鼠标逻辑坐标

1. 打开 `Input` 调试面板，观察 `Mouse Position` 和 `Logical Position` 两行
2. 在窗口没有 letterbox 时，两组数值应该接近（可能有缩放差异）
3. 拖动窗口改变宽高比（让窗口变得特别宽或特别窄），出现 letterbox 黑边
4. 把鼠标移到黑边区域——注意 `Logical Position` 会 clamp 到逻辑分辨率的边界，不会超出范围
5. 把鼠标移到有效画面区域——`Logical Position` 始终稳定地映射到逻辑分辨率空间

这个实验说明了为什么所有的 UI hit-test 和世界坐标转换都必须使用 logical 坐标——只有它才能在任意窗口尺寸下保持一致。

### 演示 4：输入占用效果

1. 进入游戏场景，打开背包（按 I 或 Tab）
2. 在背包界面上点击鼠标——角色不会挥工具或做其他动作
3. 关闭背包，在空旷地面上点击鼠标——角色正常执行动作
4. 打开暂停菜单（Esc），随意点击——底层世界完全不响应
5. （可选）打开 ImGui 调试面板，在面板中滚动鼠标滚轮——相机缩放不会被触发

第 2 步和第 4 步背后的机制不同：背包 UI 通过 `UIManager` 的回调返回值占用输入；暂停菜单通过 `UIInputBlocker` 全屏覆盖来阻断输入。效果一样，但实现路径不同。

## "踩坑清单"：常见问题与排查

### 问题 1：按键没有反应

最常见的原因是**动作名称拼错或配置中没有定义**。

**排查路径**：
1. 打开 `F5` → `Input` 面板，查看动作列表——你期望的动作是否出现在列表中？
2. 如果不在列表中：检查 `config/input.json` 是否包含这个动作定义
3. 如果在列表中但状态始终为 `Inactive`：检查键名拼写——`SDL_GetScancodeFromName` 对大小写敏感，`"a"` 和 `"A"` 是不同的（正确写法参考 SDL 文档，通常用大写首字母如 `"A"`、`"Left"`、`"Escape"`）
4. 检查日志中是否有 "未知键或按钮名称" 的警告——`InputManager` 会在初始化时报告无法识别的键名

### 问题 2：点击 UI 的同时触发了世界动作

这说明输入占用/消费链路断了。

**排查路径**：
1. 确认 `UIManager` 是否在 `InputManager` 上注册了 `mouse_left` 回调（检查 `registerMouseEvents` 是否被调用）
2. 确认 connect 顺序——`UIManager` 必须在 `PlayerControlSystem` 之后 connect，才能优先接收回调
3. 如果是新增的 UI 场景，检查是否创建了 `UIInputBlocker`——纯 UI 场景（暂停菜单/存档选择）需要 blocker 来阻断底层输入

### 问题 3：鼠标位置偏移（UI 点不准）

大概率是坐标系混用了。

**排查路径**：
1. 确认你使用的是 `getLogicalMousePosition()` 而不是 `getMousePosition()`
2. 打开 `Input` 面板对比两组坐标——如果窗口没有 letterbox，两者应该接近；有 letterbox 时差异明显
3. 如果是 screen→world 转换不准，检查传给 `camera.screenToWorld()` 的是否是 logical 坐标

### 问题 4：长按时动作被反复触发

检查你的代码是否用了 `isActionDown()` 来检测"一次性触发"的动作。`isActionDown` 在 `PRESSED` 和 `HELD` 状态下都返回 `true`——如果你想只在按下瞬间触发一次，应该用 `isActionPressed()`。

| 需求 | 应使用的 API |
| --- | --- |
| 持续移动（按住方向键一直走） | `isActionDown` |
| 按一次 F 触发一次交互 | `isActionPressed` |
| 松开时触发一次（例如蓄力释放） | `isActionReleased` |

### 问题 5：ImGui 面板和游戏输入互相干扰

确认 `TF_ENABLE_DEBUG_UI` 宏是否定义。这个宏控制 ImGui 相关的编译分支——如果 Release 版本意外包含了 ImGui 但没有正确初始化 `ImGuiContext`，`processEvent` 中的 `ImGui::GetCurrentContext()` 检查会返回 nullptr，从而跳过捕获逻辑。正常情况下，Debug 版本启用此宏，Release 版本不启用。

## 课后练习

### 练习 1：为 Input 面板增加"热重载 input.json"按钮

> 目的：把"配置驱动"的输入系统变成完整闭环：改配置 → 运行时重载 → 立即验证。

- **目标**：
  - 在 `Input` 调试面板中加入按钮：`Reload config/input.json`
  - 点击后让 `InputManager` 重新加载映射并立刻生效（失败要有日志/提示）
- **验收标准**（满足 3 项即可）：
  - 成功重载后，动作映射立刻变化（配合 `Input` 面板验证）
  - 失败路径（文件不存在/JSON 无效/键名未知）不会崩溃，并给出明确提示
  - 重载不会导致"动作卡住"（例如某个 action 永远 HELD）
- **提示线索**（模块/文件）：
  - `src/engine/debug/panels/input_debug_panel.*`
  - `src/engine/input/input_manager.*`（`loadConfig` / `initializeMappings`）
  - `config/input.json`
- 提交方式：GitHub PR

### 练习 2：显式化输入优先级（可选）

> 目的：把"依赖 connect 顺序的隐式优先级"升级为"显式 priority/layer"，让 UI 与游戏输入路由更清晰。

- **目标**：
  - 为 `onAction` 增加可选 priority/layer 概念（UI > Game）
  - 确保高优先级订阅者可以占用输入并阻止低优先级订阅者触发
- **验收标准**：
  - 默认行为不变（不传 priority 时保持现状）
  - UI 点击不会触发世界动作（inventory/hotbar/UI 按钮）
  - 能在 `Input` 面板或日志里验证订阅顺序与占用结果
- **提示线索**：
  - `src/engine/input/input_manager.*`（回调分发与停止条件）
  - `src/engine/ui/ui_manager.cpp`（鼠标动作占用）

## 小结 + 下节课预告

这节课的关键要点：

1. **action mapping** 让"按键"变成"语义动作"，改键位不改代码——所有系统只认动作名称，不关心底层按键
2. `PRESSED/HELD/RELEASED` 是**帧语义状态机**，`HELD` 解决了"按住不动时 SDL 不会每帧都产生事件"的现实问题
3. callback 的 `bool` 返回值让 UI 能**占用输入**，避免 UI/世界双触发——connect 顺序决定优先级
4. 鼠标 **logical 坐标**让 UI hit-test 与 world 交互共享稳定坐标系——letterbox/高 DPI 下也不漂

下节课我们会进入**音频系统**：你会看到输入与 UI 交互如何触发音效事件、如何做资源缓存与播放实例管理，以及为什么"可观测的系统"对调音同样重要。
