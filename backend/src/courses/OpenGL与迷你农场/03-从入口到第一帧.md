# 从入口到第一帧：main → GameEntry → GameApp

上节课我们建立了《迷你农场》的宏观架构心智模型：引擎层与游戏层的职责边界、Scene + ECS + 子系统的运行时骨架、以及数据驱动的落地方式。

从这节课开始，我们从"看平面图"走向"走进房间"：**从程序入口 `main()` 出发，追踪控制流直到第一帧画面（TitleScene）呈现在屏幕上**。

这条链路虽然不长，但它决定了你能否快速回答以下这些"真实工程里天天会遇到"的问题：
- 想知道"游戏启动时做了哪些初始化"，你能给出清晰的分层与顺序。
- 你想加"调试直进场景/跳过标题界面/从存档启动"，你知道该改哪里、哪些地方不该耦合。
- 你想查输入/窗口/退出相关 bug，你能沿着事件链路定位到产生点与消费点。

## 本课目标

建立《迷你农场》从 `main()` 到第一帧画面的心智模型，能回答三类问题：

1. **启动阶段**：`main → game::run → GameApp::init` 期间有哪些关键初始化？它们的依赖顺序为何如此？
2. **每帧阶段**：主循环每帧做哪几件事（handleEvents / update / render）？`deltaTime` 从哪来、输入事件如何进入系统？
3. **注入点**：初始场景在哪里决定？为什么这个决策必须由游戏层负责，而不是引擎层硬编码？

---

## 核心概念

### 1. 入口要薄：main 只负责交出控制权

《迷你农场》的 `main()` 只有两行有效代码（见 `src/main.cpp`）：

```cpp
#include "game/game_entry.h"
#include <SDL3/SDL_main.h>
int main(int /* argc */, char* /* argv */[]) {
    return game::run();
}
```

它不做任何"游戏逻辑"，只是把控制权交给游戏层入口 `game::run()`。

**为什么要这么薄？** 三个理由：

1. **入口不会随玩法增长而膨胀**：所有初始化逻辑都在 `GameApp` 和 `game::run()` 内部，main 永远不需要改。
2. **平台适配集中在一处**：`#include <SDL3/SDL_main.h>` 让 SDL 自动处理各平台（Windows/macOS/Linux）的入口约定差异。你不需要在 main 里写 `#ifdef _WIN32`。
3. **方便写测试**：本项目把 engine 和 game 分别编译为静态库，测试程序可以直接链接这些库，无需启动游戏窗口即可测试引擎/游戏逻辑。

> **常见误区**：初学者常把"创建窗口 / 加载资源 / 注册系统"全塞进 main 里。项目小时一切正常，项目大了以后 main 就变成了一个几百行的"万能入口"，每次改逻辑都要翻 main，非常痛苦。

### 2. GameApp：引擎的"可运行壳"

在 `game::run()`（见 `src/game/game_entry.cpp`）中，游戏层做了三件事：

```cpp
int run() {
    initialize_environment();           // 1. 平台环境初始化（如 Windows 控制台 UTF-8）
    spdlog::set_level(spdlog::level::info);

    engine::core::GameApp app;          // 2. 创建引擎应用
    app.registerSceneSetup(setupInitialScene);  // 3. 注册初始场景注入函数
    app.run();
    return 0;
}
```

这里有一个关键设计：**`GameApp` 并不决定"第一个场景是什么"**。它只提供一个回调注册接口 `registerSceneSetup(...)`，由游戏层通过这个接口把初始 Scene 注入进来。

这体现了上节课讲到的引擎层/游戏层边界：
- **`GameApp`（引擎层）**负责：初始化所有子系统、进入主循环、维护 Context、管理退出/窗口事件——也就是"运行框架"。
- **游戏层**负责：选择"第一个场景是什么"（TitleScene / 存档选择 / 直接进入游戏 / 调试场景），并通过事件把 Scene 交给引擎的 `SceneManager`。

一句话：**引擎搭舞台，游戏决定第一幕。**

### 3. 初始化链路：从 Dispatcher 到 SceneManager

当 `GameApp::run()` 被调用时，它首先执行 `init()`（见 `src/engine/core/game_app.cpp`）。初始化分为四个阶段，每个阶段都有严格的依赖顺序：

**阶段一：基础设施**
- **Dispatcher**（事件分发器）——几乎所有后续模块都需要它来收发事件，所以最先创建。
- **Config**（配置管理）——读取 `config/window.json`，为窗口大小/帧率/逻辑分辨率等提供初始参数。

**阶段二：平台与渲染**
- **SDL**——初始化视频/音频子系统、创建窗口。
- **GLRenderer**——创建 OpenGL 上下文，设定逻辑分辨率。
- **Renderer / Camera / TextRenderer**——构建渲染管线的各个环节。

**阶段三：资源、音频与输入**
- **ResourceManager**——加载资源映射表，后续纹理/字体/音频/UI 预设都通过它获取。
- **AudioPlayer**——依赖 ResourceManager 来缓存音频资源。
- **InputManager**——依赖 Dispatcher 和 GameState，负责 SDL 事件轮询与动作状态转换。

**阶段四：胶水层**
- **Context**——把上面所有模块的引用打包成一个"依赖注入容器"，传给 Scene 和系统使用。
- **SceneManager**——依赖 Context，管理场景栈，监听 Push/Pop/Replace 事件。

`init()` 的最后两步值得特别关注：

```cpp
// 注册退出事件和窗口大小变化事件
dispatcher_->sink<utils::QuitEvent>().connect<&GameApp::onQuitEvent>(this);
dispatcher_->sink<utils::WindowResizedEvent>().connect<&GameApp::onWindowResized>(this);

// 调用场景设置函数（创建第一个场景并压入栈）
scene_setup_func_(*context_);

is_running_ = true;
```

注意 `scene_setup_func_` 是游戏层通过 `registerSceneSetup` 注入的那个回调。它会触发 `PushSceneEvent`，但此时主循环还没开始——场景只是被"挂"进了 SceneManager 的 pending 队列，等到第一次 `update()` 时才会真正入栈并初始化。

> **排查技巧**：如果启动后直接黑屏退出，首先检查 `init()` 返回值。每个 `init*()` 都用了 `[[nodiscard]]` 标注，失败会打日志并返回 false，`run()` 会直接 return。

### 4. 一帧的节拍：Time → Input → Update → Render → Dispatch

当 `init()` 成功后，`GameApp::run()` 进入主循环。每一帧发生的事情可以用这个"节拍图"概括：

```text
init()
while running:
  1. deltaTime = Time.update()        // 推进时钟，计算本帧时间步长
  2. Input.handleEvents()             // 轮询 SDL 事件 → 动作状态 + 引擎事件
  3. SceneManager.update(deltaTime)   // 更新栈顶场景 → 处理 pending 场景切换
  4. Renderer.clear()                 // 清屏
  5. SceneManager.render()            // 叠加渲染所有场景
  6. Renderer.present()               // 提交帧缓冲到屏幕
  7. Dispatcher.update()              // 分发本帧 enqueue 的队列事件
close()
```

![每帧节拍数据流图](diagrams/L03_frame_beat.png)

这里有几个值得细想的设计决策：

**为什么 Time 在最前面？** 因为 `deltaTime` 是后续所有"与时间相关"逻辑的输入——动画播放、物理移动、计时器……如果 Time 更新晚了，整帧的时间步长都是错的。

**为什么 Input 在 Update 之前？** Input 阶段会轮询 SDL 事件队列，把 `SDL_EVENT_KEY_DOWN` 等原始事件翻译成 `ActionState`（PRESSED / HELD / RELEASED），并把 `QuitEvent` / `WindowResizedEvent` 等控制流事件即时触发（`trigger`）。只有先完成这一步，后续的 `update` 才能拿到本帧玩家输入的最新状态。

**为什么 Dispatcher.update() 放在 Render 之后？** 这是一个有意的设计选择：用 `enqueue` 方式注册的队列事件（如动画完成、音效播放、时间推进等），会在"本帧画面已呈现"之后才被分发。这样做可以：
1. 避免在 update 过程中递归触发事件导致时序混乱；
2. 把大多数数据类事件自然变成"下一帧的输入"。

这也引出了 `trigger` 和 `enqueue` 的语义区分——**控制流事件通常立即 trigger，数据流事件通常 enqueue 后在帧尾结算**。这个话题会在 后续课程中展开。

### 5. 初始场景为什么能出现在第一帧？

"启动后第一帧就看到 TitleScene"并不是魔法，而是两步协作的结果：

**第一步：游戏层在 setup 阶段触发 PushSceneEvent。**

```cpp
void setupInitialScene(engine::core::Context& context) {
    auto title_scene = std::make_unique<game::scene::TitleScene>("TitleScene", context);
    context.getDispatcher().trigger<engine::utils::PushSceneEvent>(
        engine::utils::PushSceneEvent{std::move(title_scene)});
}
```

这里用了 `trigger`（立即分发），所以 `SceneManager` 的回调 `onPushScene` 会同步执行，把 `TitleScene` 存入 `pending_scene_`。

**第二步：SceneManager 在第一次 update 中处理 pending action。**

```cpp
void SceneManager::update(float delta_time) {
    Scene* current_scene = getCurrentScene();
    if (current_scene) {
        current_scene->update(delta_time);
    }
    processPendingActions();  // ← 在这里，TitleScene 真正入栈并被 init()
}
```

`processPendingActions()` 会调用 `pushScene()`，把 `TitleScene` 压入场景栈并执行其 `init()`。紧接着的 `render()` 阶段就会遍历整个场景栈，调用每个场景的 `render()`——第一帧画面就这样出现了。

**核心规律**：场景切换用事件表达"意图"；实际的入栈/出栈操作在 SceneManager 的 `processPendingActions()` 中统一执行。这种"请求与执行分离"的模式避免了在事件回调中直接修改场景栈可能带来的迭代器失效、递归切换等问题。

> **为什么不在事件回调里直接 push？** 想象一下：A 场景的 update 里触发了 PushSceneEvent，如果 SceneManager 在回调中立刻 push，那么正在遍历场景栈的代码就会发现栈被改了。这类 bug 在小项目中不容易暴露，但在场景复杂度上去之后非常难查。

### 退出链路（从 SDL 到主循环停止）

退出路径是你最该能复盘的一条链路——因为它最常见，也最能训练你的事件链路定位能力：

1. 用户关闭窗口 → SDL 产生 `SDL_EVENT_QUIT`。
2. `InputManager::processEvent` 捕获后调用 `quit()`，内部执行 `dispatcher_->trigger<QuitEvent>()`。
3. `GameApp::onQuitEvent()` 收到事件，将 `is_running_` 设为 `false`。
4. 主循环条件不满足，退出 while，进入 `close()` 做清理。

这条链路的关键点：**产生点与消费点解耦**。`InputManager` 不需要持有 `GameApp` 的引用，也不需要知道"退出"具体意味着什么——它只负责发出 `QuitEvent`，由 `GameApp` 自行决定如何响应。

### 练习 1（入门）：支持"跳过标题界面"启动

**目标**：新增一个启动选项，让开发/调试时可以跳过 `TitleScene`，直接进入 `GameScene`（默认行为保持不变）。

**验收标准**：
- 默认启动仍然进入 `TitleScene`
- 当指定选项（例如 `--skip-title` 或 `--start=game`）时，启动直接进入 `GameScene`
- 选项无效/缺失时有清晰的降级策略（回退到 `TitleScene`）

**提示线索**：
- 入口：`src/main.cpp`、`src/game/game_entry.*`
- 场景注入：`engine::core::GameApp::registerSceneSetup`、`engine::utils::PushSceneEvent / ReplaceSceneEvent`
- 目标场景：`src/game/scene/game_scene.*`、`src/game/scene/title_scene.*`

### 练习 2（进阶）：让 SceneManager 支持"一帧内多个切换请求"

**目标**：当前 `SceneManager` 只记录一个 pending action——如果同一帧内连续触发多个 Push/Pop/Replace，后续请求会被丢弃（你可以在 `onPushScene` 等回调中看到 `spdlog::warn` 日志）。请将其改成队列（FIFO）或同等策略，确保不会静默丢失。

**验收标准**：
- 同一帧内连续触发多个切换请求时，能按顺序全部生效（或给出明确的拒绝策略与日志）
- 增加单元测试覆盖该行为（建议在 `tests/engine/scene/`）
- 不引入新的第三方依赖，不影响现有主线流程

**提示线索**：`src/engine/scene/scene_manager.*`、`src/engine/utils/events.h`

## 小结

你现在应该能在脑内"跑一遍"《迷你农场》的启动流程了：

1. `main()` 把控制权交给 `game::run()`——入口尽可能薄。
2. 游戏层创建 `GameApp`，注入初始场景回调——引擎层不决定"从哪里开始玩"。
3. `GameApp::init()` 按严格的依赖顺序初始化所有子系统，最后调用场景注入回调。
4. 主循环每帧五个节拍：Time → Input → Update → Render → Dispatch。
5. 第一次 `update()` 时，SceneManager 处理 pending action，TitleScene 入栈并初始化；紧随其后的 `render()` 把它画出来——第一帧就此呈现。
