# UI 框架基础：UIManager、元素树与交互状态

在 `输入系统` 这一课，我们把输入系统工程化成了"动作映射 + 状态机 + logical mouse"，让**世界交互**与**UI 交互**能共享同一套稳定输入语义。[音频系统](16-音频系统.md) 我们又把音频系统工程化成"资源映射 + 缓存 + 事件驱动"，并且定义了 `ui_hover / ui_click` 这些**语义化的 UI 音效 key**。

现在，输入有了统一的 logical 坐标，音频有了语义化的播放入口——但 UI 本身还缺一个关键拼图：

> 我们需要一套能把这些基础设施"串"起来的 UI 框架——能稳定接入输入、能稳定做布局、能稳定表达交互状态，而不是到处硬编码"画几张图 + 写几个 if-else"。

## 本节目标与问题定义

本节课用一句话概括：

> TinyFarm 的 UI 以"每个 Scene 一个 `UIManager`"为单位挂载到场景生命周期中；`UIManager` 管理一棵 `UIElement` 树，并把输入（logical mouse）翻译成 `Normal/Hover/Pressed` 状态机与声音反馈。

本节完成后你应该能回答这些问题：
- **挂载点**：为什么 UIManager 放在 Scene 上，而不是当成 ECS 系统？
- **坐标一致性**：为什么 UI 的 hit-test 必须用 logical 坐标？
- **元素树与布局**：UIElement 的 anchor/pivot/padding/margin 到底在解决什么问题？
- **交互状态机**：按钮 hover/press/release 如何用状态表达？什么时候该"吃掉输入"？
- **Behavior 组合**：状态机管"视觉"，但"拖拽/悬浮提示"这类功能响应怎么挂上去？State 与 Behavior 如何分工？
- **模态 UI**：暂停菜单/对话框覆盖时，如何阻止点击穿透到世界？

## 核心概念

### 1. Scene 是 UI 的挂载点：每场景一个 UIManager

在开始讨论 UI 元素之前，我们先要回答一个架构问题：**UI 的生命周期由谁管？**

一种常见做法是把 UI 当成 ECS 系统——给 UI 元素挂组件、用系统更新。但 TinyFarm 没有这么做，原因很直接：UI 的生命周期和场景强绑定，不需要跨场景共享、不需要序列化、也不需要和其他 ECS 组件做查询组合。把 UI 硬塞进 ECS 反而增加了不必要的复杂度。

TinyFarm 的约定很简洁：
- `Scene` 可选持有一个 `std::unique_ptr<engine::ui::UIManager> ui_manager_`
- `Scene::update` 在存在 `ui_manager_` 时调用 `ui_manager_->update()`
- `Scene::render` 在存在 `ui_manager_` 时调用 `ui_manager_->render()`

这带来两个直觉收益：

**第一，UI 生命周期天然跟随场景。** 场景创建时初始化 UI，场景销毁时 UI 自动释放，不需要额外的生命周期管理。比如 `TitleScene::init()` 里直接创建 `UIManager` 并构建按钮树，场景切走后一切自动清理。

**第二，覆盖式 Scene 可以叠加 UI。** 回忆 [场景系统](07-场景系统.md) 的 Scene 栈——暂停菜单作为覆盖 Scene 压入栈顶时，它拥有自己的 `UIManager` 和独立的 UI 树，渲染时叠加在底层场景之上。底层场景的 UI 不需要知道自己被覆盖了。

UIManager 还负责一项可选的"UI 级渲染附加项"：**自定义鼠标指针**。如果 UI image preset 中配置了 `cursor` 预设，UIManager 会在构造时通过 `SDL_HideCursor()` 隐藏系统光标，并在每帧渲染结束时在鼠标 logical 坐标处绘制自定义光标图像——这保证鼠标指针的视觉风格与游戏 UI 一致（未配置则继续使用系统鼠标）。

![Scene 生命周期：update 栈顶 / render 叠加](diagrams/L15_scene_ui_lifecycle.png)

> 关联阅读：`src/engine/scene/scene.*`、`src/engine/scene/scene_manager.cpp`

### 2. UI 的坐标系：全部使用 logical 坐标

UI 框架的第二个基础决策是坐标系统。在 [Renderer 与 GLRenderer](10-Renderer%20与%20GLRenderer.md) 和 [输入系统](15-输入系统.md) 中我们已经知道，《迷你农场》 存在"逻辑分辨率"与"窗口物理像素"之间的映射，窗口缩放或出现 letterbox 时，两者并不一致。

UI 的绘制与命中检测都统一使用 **logical 坐标系**：
- 输入坐标：`InputManager::getLogicalMousePosition()` 返回的是逻辑坐标
- UI 位置与尺寸：`UIElement::position_/size_` 均以 logical 单位表达
- 命中检测：`findInteractiveAt()` 接收 logical 坐标做判断

这能保证在窗口缩放 / letterbox / DPI 改变时：

> 鼠标看到的位置、UI 画出来的位置、hit-test 的位置——三者始终一致。

如果 UI 用了物理像素而输入用了逻辑坐标（或反过来），你会遇到"明明鼠标在按钮上方，但点不中"的幽灵 bug——尤其在非整数缩放比下几乎必现。统一坐标系从根本上消除了这类问题。

> 关联阅读：`docs/input_system.md`（[输入系统](15-输入系统.md)）、`src/engine/ui/ui_manager.cpp`

### 3. UIElement 树：root panel + children，order 决定"上层优先"

有了生命周期和坐标系的基础，接下来看 UI 的核心数据结构——**元素树**。

`UIManager` 在构造时创建一个与逻辑分辨率同大的根节点（root `UIPanel`），所有 UI 元素都是它的子树节点。以 `TitleScene` 为例，它的元素树结构大致如下：

```text
UIPanel (root, 逻辑分辨率大小)
├── UIImage (背景图, order=0)        ← 拉伸铺满
├── UIImage (Logo, order=1)          ← 居中浮动动画
├── UILabel (错误提示, order=2)       ← 条件显示
├── UIStackLayout (按钮组, order=2)   ← 纵向排列
│   ├── UIButton (开始游戏)
│   ├── UIButton (读取存档)
│   └── UIButton (退出)
└── UIButton (菜单按钮, order=3)      ← 右上角
```

UI 树解决的不是"渲染递归"这么简单，它更重要的价值是：

- **相对定位**：子元素的位置相对于父元素的 content bounds（受 padding 影响），而非屏幕绝对坐标。移动父元素时，子元素自动跟随。
- **层级遮挡**：`order_index` 决定渲染顺序与命中优先级。order 值大的**后画**（在视觉上"更靠前"），命中检测时也**优先被检查**。

![UI 元素树示意](diagrams/L15_ui_element_tree.png)

**命中检测的核心思路**是：逆序遍历子节点（order 大的先检查），递归深入先查子树，仅 `UIInteractive` 且 `interactive_ = true` 的元素可被命中返回。这确保了"视觉上最上层的交互元素"总是最先响应点击。

![Hit-test 顺序](diagrams/L15_hit_test_order.png)

> **注意**：普通的 `UIElement`（如 `UIImage`、`UILabel`）不参与命中检测，它们只负责"被看到"。只有继承了 `UIInteractive` 的元素才可能被"点中"。

> 关联阅读：`src/engine/ui/ui_element.*`（`findInteractiveAt` + `order_index`）

### 4. 布局模型：anchor/pivot/padding/margin 的"工程直觉"

元素树确定了层级关系，但每个元素"画在哪里、多大"——这是布局模型要解决的问题。

TinyFarm 的布局**不是** Flex/Constraint 这类复杂系统，而是一套教学向的最小模型，核心由四个属性控制：

| 属性 | 作用 | 影响谁 |
|------|------|--------|
| `anchor_min / anchor_max` | 在父 content bounds 里选一个"参考点"或"参考区间" | 自己的位置（和可能的拉伸） |
| `pivot` | 决定"自身哪个点"对齐到 anchor 位置 | 自己的位置 |
| `padding` | 收缩自己的内容区域 | 子元素的可用区域 |
| `margin` | 在父内容区域里增加额外偏移 | 自己的位置 |

具体的布局计算流程是这样的：

1. 取父元素的 **content bounds**（父 bounds 减去父 padding）
2. 用 `anchor_min/anchor_max`（归一化坐标，0~1）映射到父 content bounds 中的具体位置
3. 如果 `anchor_min == anchor_max`（点锚定），使用元素自身的 `size_`；如果两者不等（区间锚定），元素被拉伸到锚定区间的大小减去 margin
4. 最终位置 = anchor 位置 + position 偏移 + margin 偏移 - pivot * size

对照 `TitleScene` 的实际代码会更直观：

```cpp
// 背景图：anchor 从 (0,0) 到 (1,1) → 拉伸铺满整个屏幕
bg->setAnchor({0.0f, 0.0f}, {1.0f, 1.0f});
bg->setPivot({0.0f, 0.0f});

// Logo：anchor 固定在 (0.5, 0.32) → 水平居中、垂直 32% 处
//       pivot (0.5, 0.5) → 以 Logo 自身中心点对齐到锚点
logo->setAnchor({0.5f, 0.32f}, {0.5f, 0.32f});
logo->setPivot({0.5f, 0.5f});

// 菜单按钮：anchor (1.0, 0.0) → 右上角
//           pivot (1.0, 0.0) → 以自身右上角对齐
//           position (-10, 10) → 向内偏移 10 像素
menu_btn->setAnchor({1.0f, 0.0f}, {1.0f, 0.0f});
menu_btn->setPivot({1.0f, 0.0f});
menu_btn->setPosition({-10.0f, 10.0f});
```

![布局模型示意](diagrams/L15_layout_model.png)

布局计算采用**懒求值**策略：`UIElement` 内部维护一个 `layout_dirty_` 标记，只有在位置/大小/锚点等属性变化时才标记为脏，下次 `update` 或 `render` 时才重新计算。这避免了每帧对整棵树做无意义的全量布局。

> **常见踩坑**：如果你发现添加的 UI 元素"看不见"或者"位置不对"，最常见的原因有两个——（1）忘记设置 anchor 导致元素锚定在父元素的左上角 (0,0) 并被遮挡；（2）把 anchor 和 pivot 搞混，pivot 是"自身的哪个点"，anchor 是"父区域的哪个点"。

> 关联阅读：`src/game/scene/title_scene.cpp`、`src/engine/ui/ui_element.cpp`（`ensureLayout`）

### 5. 交互状态机：UIInteractive + UIState（Normal/Hover/Pressed）

有了元素树和布局，UI 已经能"画出来"了。但一个按钮不只是一张图——鼠标悬浮时要换图、按下时要换图、松开时要触发回调、还要播放音效。这些交互逻辑如何组织？

TinyFarm 的答案是：**用状态机统一描述交互阶段，让"视觉切换/回调/音效"都有明确的触发点。**

可交互元素的基类是 `UIInteractive`（继承自 `UIElement`），它内部持有一个 `std::unique_ptr<UIState> state_`，代表当前的交互状态。状态机只有三个状态：

![交互状态机](diagrams/L15_interaction_state_machine.png)

```text
Normal ──(mouseEnter)──→ Hover ──(mouseExit)──→ Normal
                           │
                     (mousePressed)
                           │
                           ↓
                        Pressed ──(release inside)──→ Hover + clicked()
                                 ──(release outside)──→ Normal
```

每次状态切换时，典型会做三件事：

1. **切视觉**：调用 `applyStateVisual(state_id)` 切换当前显示的图片（例如 normal/hover/pressed 三套皮肤）
2. **播放音效**：`ui_hover` 在 NormalState 收到 `mouseEnter` 时播放，`ui_click` 在进入 PressedState 时播放；也可通过 `setSoundEvent(...)` 覆盖为自定义音效，或调用 `disableSoundEvent(...)` 禁用
3. **触发回调**：`hover_enter()` / `hover_leave()` / `clicked()`（其中 `clicked` 只在 Pressed 状态收到 release inside 时才触发）

一个重要的实现细节：**状态切换是延迟生效的**。当状态需要转换时，新状态先被设置到 `next_state_`，在下一次 `UIInteractive::update()` 中才真正替换 `state_` 并调用新状态的 `enter()`。这避免了在事件处理过程中状态对象被销毁导致的悬垂指针问题。

`UIButton` 是 `UIInteractive` 最典型的子类实现。它在状态机的基础上增加了：
- **预设驱动的皮肤**：通过 `UIButtonSkin` 预设加载 normal/hover/pressed/disabled 四套图片（支持九宫格拉伸），不需要硬编码图片路径
- **文本标签**：支持按状态切换文字颜色/偏移，还支持 ScaleToFit 模式自动缩放文字以适应按钮大小
- **回调函数**：`setOnClick` / `setOnHoverEnter` / `setOnHoverLeave` 挂上 `std::function` 回调

> 关联阅读：`src/engine/ui/ui_interactive.*`、`src/engine/ui/state/ui_*_state.*`、`src/engine/ui/ui_button.*`

### 6. Behavior 组合：给交互元素"挂"功能

上一节的 UIState 解决了"视觉表现"——hover 换图、pressed 换图、播放音效。但 UIInteractive 还有另一个维度的需求：

> 同一个元素可能需要支持 hover 显示提示、拖拽移动、click 回调……这些"功能响应"应该能自由组合，而不是在 `mouseEnter()` 里堆一堆 if-else。

TinyFarm 的做法是在 UIInteractive 上增加了第二套并行机制——**Behavior 组合**。这两套机制各管各的：

| 机制 | 职责 | 典型例子 |
|------|------|----------|
| UIState（状态机） | 视觉表现 + 音效 | Normal/Hover/Pressed 换图、播放 ui_hover/ui_click |
| InteractionBehavior（行为） | 功能响应 | 拖拽移动、hover 显示 tooltip |

![State vs Behavior 双轨机制](diagrams/L15_state_vs_behavior.png)

`InteractionBehavior` 是一个轻量基类，定义了与 UIState 对称的虚方法（`onHoverEnter/Exit`、`onPressed/Released/Click`、`onDragBegin/Update/End`），默认实现全部为空——你只需要覆写关心的方法。

UIInteractive 内部持有一个 `std::vector<std::unique_ptr<InteractionBehavior>>`，每次鼠标事件到达时，**先走状态机（管视觉），再广播给所有 Behavior（管功能）**：

```text
mouseEnter():
  state_->onMouseEnter()         // 视觉：换 hover 图 + 播音效
  for behavior : behaviors_      // 功能：逐个通知
      behavior->onHoverEnter()
```

目前项目提供了两个开箱即用的具体 Behavior：

- **`HoverBehavior`**：通过 `setOnEnter/setOnExit` 挂 `std::function` 回调。典型用途是"鼠标悬浮时显示 tooltip，离开时隐藏"
- **`DragBehavior`**：三阶段回调 `setOnBegin/setOnUpdate/setOnEnd`。典型用途是"拖拽物品槽位"或"拖动面板位置"

一个元素可以同时挂多个 Behavior，互不干扰。例如 InventoryUI 和 HotbarUI 的每个物品槽位同时挂了 `DragBehavior`（拖拽物品）和 `HoverBehavior`（悬浮提示），而 `UIDraggablePanel` 只挂了 `DragBehavior`（拖拽移动面板位置）。

> **设计要点**：State 和 Behavior 是**正交的**——State 管"长什么样"，Behavior 管"干什么事"。一个没有 State 的 UIInteractive（如 UIInputBlocker）不会有视觉反馈但仍能被命中；一个没有 Behavior 的 UIInteractive（如普通按钮）只靠 State + `clicked()` 虚方法就够用。两套机制互不依赖，按需组合。

> 关联阅读：`src/engine/ui/behavior/*`、`src/engine/ui/ui_interactive.*`（`addBehavior`）、`src/engine/ui/ui_draggable_panel.*`

### 7. "吃掉输入"与模态阻断：UIInputBlocker 的用途

到目前为止我们讨论了 UI 如何**响应**输入。但还有一个同样重要的问题：**UI 如何阻止输入继续向下传播？**

想象这个场景：你点击了标题界面的"开始游戏"按钮。如果这个点击事件同时传到了世界交互系统，角色可能会挥一下锄头——这显然不对。

TinyFarm 使用的是 [输入系统](15-输入系统.md) 介绍过的同一套机制：
- `InputManager::onAction(...).connect(...)` 的回调返回 `bool`
- UIManager 注册 `mouse_left` 动作的回调，当 UI 确实处理了这次输入时返回 `true`，阻止后续回调（比如世界交互系统）收到同一事件

但还有一种更极端的情况——**模态 UI**（暂停菜单/对话框）需要让"所有点击都不穿透到底层"，即使点击的位置没有任何可交互元素。

常见做法是加一层全屏 blocker，TinyFarm 用 `UIInputBlocker` 实现：

- `UIInputBlocker` 本质是一个全屏 `UIInteractive`，但**不设置任何 `UIState`**
- 因为没有状态机，它不会切图也不会播放任何音效（`ui_hover`/`ui_click` 都不触发）
- 但因为它仍是 `UIInteractive`（`interactive_ = true`），hit-test 能命中它，UIManager 在 `onMousePressed` 中捕获它并返回 `true`——从而"无声地吃掉"点击

这个设计的精妙之处在于：不需要任何特殊逻辑或额外的标志位，只需要"是交互元素但没有状态机"就自然形成了阻断效果。对照前面讲的 State 和 Behavior 的正交性——UIInputBlocker 就是一个"既没有 State 也没有 Behavior"的 UIInteractive，它的存在价值仅仅是"能被命中"。

> 关联阅读：`src/engine/ui/ui_input_blocker.*`

## 架构与数据流

### 模块图：Input → UI → Render/Audio

理解了各个核心概念后，我们把它们串成一条完整的数据流。从输入到最终的视觉与音频输出，链路如下：

![输入分发链路](diagrams/L15_input_dispatch.png)

UIManager 是这条链路的枢纽——它从 `InputManager` 获取鼠标位置和动作事件，通过 hit-test 找到目标元素，驱动状态机和 Behavior，最终通过 `Renderer` 绘制 UI、通过 `AudioPlayer` 播放反馈音效。

### 时序（示意）：一次点击是如何变成"状态 + 回调"

以下是一次典型的鼠标交互在框架内部的完整流转：

```text
每帧 update:
  UIManager.processMouseHover():
    pos = InputManager.getLogicalMousePosition()
    target = root.findInteractiveAt(pos)       // 从树顶逆序递归
    if target != hovered_element_:
      old_hovered.mouseExit()                  // → state: Hover→Normal
      new_target.mouseEnter()                  // → state: Normal→Hover
      hovered_element_ = new_target

回调 mouse_left PRESSED:
  UIManager.onMousePressed():
    pressed = root.findInteractiveAt(mouse_pos)
    if pressed:
      pressed.mousePressed()                   // → state: Hover→Pressed
      pressed_element_ = pressed
      return true                              // 占用输入，世界不收到

回调 mouse_left RELEASED:
  UIManager.onMouseReleased():
    if pressed_element_:
      target = root.findInteractiveAt(mouse_pos)
      is_inside = (target == pressed_element_)
      pressed_element_.mouseReleased(is_inside) // → Pressed→Hover + clicked()
                                                //   或 Pressed→Normal
      pressed_element_ = nullptr
      return true                               // 占用
    return false                                // 不占用：世界正常收到 release
```

> **关键细节**：只有当 UI 真的捕获了"按下"目标时，才会占用后续的"释放"事件。如果按下时鼠标不在任何 UI 元素上（`pressed_element_` 为空），释放事件会正常传递给世界交互系统——这保证了"点击地面"不会被 UI 错误拦截。

### 基础 UI 元素一览

除了前面详细讨论的 `UIInteractive` 和 `UIButton`，框架还提供了几个基础元素：

| 元素 | 基类 | 职责 |
|------|------|------|
| **`UIPanel`** | UIElement | 容器元素。可选绘制背景色或九宫格皮肤图。UIManager 的根节点就是一个 UIPanel |
| **`UIImage`** | UIElement | 最基础的"画图"元素。给定纹理（或纹理的一个子区域）在 UI 坐标下绘制 |
| **`UILabel`** | UIElement | 文本元素。依赖 `TextRenderer`（[字体与文本渲染](14-字体与文本渲染.md)）计算/渲染文字，支持样式预设与颜色/阴影覆写 |
| **`UIInputBlocker`** | UIInteractive | 全屏透明交互元素。用于模态 UI 阻断（见上文） |

这些元素与 `UIButton` 一起构成了本节课的"UI 工具箱"。下节课 [UI 布局与预设](18-UI%20布局与预设.md) 还会引入布局容器（Stack/Grid）和预设系统，进一步减少手工摆放与硬编码。

## 练习

### 练习 1（推荐）：做一个 UI Debug Panel（提升可观测性）

**目标**：增加一个"面向开发者"的 UI 调试入口，能看到当前 hovered/pressed 元素，并帮助定位 hit-test/布局问题。

**验收标准（基础）**
- `F5 → Engine Debug Panels` 中出现 `UI` 面板（或相近命名）
- 面板能显示：
  - hovered 元素（存在/不存在）
  - pressed 元素（存在/不存在）
  - 当前鼠标 logical 坐标
- 不影响 release/press 逻辑，不产生崩溃（Scene 没有 UIManager 时也安全）

**加分项（可选）**
- Tree view：以树结构展示 root 及子元素（包含 order_index/visible/layout bounds）
- Debug draw：可开关绘制 UI bounds（矩形框），用于直观看命中区域

**提示线索（模块/文件）**
- Debug 面板体系：`src/engine/debug/debug_ui_manager.*`、`src/engine/debug/panels/*`
- UI 查询入口：`engine::ui::UIManager::getRootElement()`、`engine::ui::UIElement::getChildren()`、`getBounds()`

**提交方式**：GitHub PR

### 练习 2（较小）：把"点击音效"改为"点击成立才播放"

**目标**：当前 click 音效在"按下"时触发；把它改成"按下并在同一控件内释放"才播放（避免按下后拖出仍有 click 音效）。

**验收标准**
- 在 TitleScene 上：按下按钮后拖出再松开，不播放 click 音效，也不触发 clicked 回调
- 只有 press + release inside 才会播放 click 音效（并触发 clicked）
- hover 音效不受影响（进入 hover 时仍可播放）

**提示线索（模块/文件）**
- 状态机：`src/engine/ui/state/ui_pressed_state.cpp`
- 音效事件：`src/engine/ui/ui_interactive.*`
- 音频 key：`assets/data/resource_mapping.json`（`ui_click/ui_hover`）

**提交方式**：GitHub PR

## 小结

这节课我们把 UI 的基础工程化要点讲清楚了：

- **挂载点**：Scene 持有 UIManager，UI 生命周期跟随场景自动管理
- **坐标一致性**：UI 全部使用 logical 坐标，与输入系统对齐，消除缩放/letterbox 下的坐标偏差
- **元素树**：root panel + children 的树形结构，order_index 控制渲染与命中优先级
- **布局模型**：anchor/pivot/padding/margin 四个属性解决定位与拉伸，懒求值避免无意义的全量计算
- **交互状态机**：Normal/Hover/Pressed 三状态统一描述交互阶段，状态切换驱动视觉、音效与回调
- **Behavior 组合**：State 管视觉、Behavior 管功能，正交可组合，不需要在交互逻辑里堆 if-else
- **模态阻断**：UIInputBlocker 利用"有交互能力但无状态机"的特性，无声地阻止点击穿透

下节课我们会继续把 UI 往"可复用与可配置"推进：

> 引入更系统化的布局容器（Stack/Grid）、九宫格（NineSlice）与 UI preset（可复用皮肤/样式），让 UI 不再依赖硬编码与手工对齐。
