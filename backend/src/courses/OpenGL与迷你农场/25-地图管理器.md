# 地图管理器：加载/卸载、预加载、快照与离线推进

上节课我们把视角从"单张地图的构建"提升到了**世界图（world graph）**：
- `.world` 文件提供世界布局输入，`WorldState` 把它变成可查询的地图索引（`MapInfo` + 邻接 + 触发器）
- `map_trigger` 通过配对的 `self_id / target_id` + `start_offset` 实现跨地图双向连接
- `MapTransitionSystem` 统一了边缘切图与触发器切图，最终都汇入同一条事务提交路径

但上节课还留了一个伏笔——`MapTransitionSystem` 最终调用的是 `MapManager::loadMap()`，而 `MapManager` 内部到底做了什么，我们只说了一句"加载目标地图"就略过了。

如果你尝试在《迷你农场》里做这些事情，很快就会撞上三类"单地图时代"不存在的工程问题：
- 在 `home_exterior` 耕地/浇水/种植 → 切到 `town` → 再切回来——**种的东西全没了**
- 第一次切到 `town` 时明显**卡了一下**——解析 JSON、加载 tileset、构建实体的成本全堆在那一帧
- 离开 `home_exterior` 好几天再回来——**作物完全没长**，好像时间停止了

这三类问题分别对应三个工程方案：**快照恢复、预加载、离线推进**。它们都在 `MapManager` 里实现。本节课就来彻底拆解这个"地图生命周期编排器"。

## 2) 本节目标与问题定义

本节目标用一句话概括：

> 理解 `MapManager` 如何把"切图"实现为一套可控的地图生命周期事务（unload → load → restore），并通过**预加载**与**快照/离线推进**解决"卡顿/状态丢失/离线变化"三类工程问题。

完成本节后你应该能回答：
1. 为什么"切图 = 事务（transaction）"？事务的阶段划分能帮我们避免哪些 bug？
2. 快照到底存什么、不存什么？为什么"恢复快照"后还要做额外步骤（例如重建空间索引）？
3. 预加载策略是怎么被配置、被消费的？`off/neighbors/all` 分别改变了什么成本曲线？
4. 离线推进由谁触发、对哪些地图生效？怎么避免"重复推进"和"推进漏掉"？

## 3) 核心概念

### 3.1 切图 = 事务：把一次切换拆成明确阶段

先从最核心的概念讲起。把"切图"当成数据库里的一次**事务（transaction）**，你会更容易理解为什么代码要分这么多步骤——事务要么完整执行成功，要么在某个阶段失败后报错退出，不会让系统停留在一个"切了一半"的中间状态。

事务的输入很简单：目标地图 ID + 玩家出生点。事务的输出是：当前地图已完成切换、相机约束已更新、世界状态一致。

下面是 `MapManager::loadMap()` 的**八阶段事务流程**——每一步都有明确的前置条件和产出：

<img src="https://theorhythm.top/gamedev/TF/L23_map_transaction.webp" style='width: 960px;' />

让我们对着代码逐阶段过一遍（`src/game/world/map_manager.cpp`）：

**阶段 1：验证目标**
```cpp
const auto* map_state = world_state_.getMapState(map_id);
if (!map_state) {
    spdlog::error("MapManager: 无法加载地图，未知ID {}", map_id);
    return false;
}
```
如果目标地图在 `WorldState` 中不存在（既不在 `.world` 里，也没被 `ensureExternalMap` 注册过），事务直接失败。这是最早的防护网。

**阶段 2：清理触发器与环境光**
```cpp
mutable_state->triggers.clear();
mutable_state->info.ambient_override.reset();
if (!mutable_state->info.in_world) {
    mutable_state->info.ambient_override = loadAmbientOverride(mutable_state->info.file_path);
}
```
旧触发器信息需要清除——新一轮地图加载时 `EntityBuilder` 会重新同步。对于非 world 地图（例如室内 `home_interior`），还会从地图文件的 properties 中读取环境光覆盖参数。

**阶段 3：卸载当前地图**
```cpp
unloadCurrentMap();
// 内部流程：snapshotMap(current_map_id_) → destroyEntitiesByMap(current_map_id_)
```
**注意顺序**：先做快照，再销毁实体。如果反过来——先销毁再快照——快照就是空的。这个顺序看起来显而易见，但在重构时很容易被打乱，值得用注释强调。

**阶段 4：加载新地图**
```cpp
level_loader_->loadLevel(map_state->info.file_path);
```
创建新的 `LevelLoader` + `EntityBuilder`，解析 `.tmj` 文件，构建 tile layers、对象层实体。`EntityBuilder` 被设置了 `MapId`，所有新建实体都会自动带上这个标记。如果已有玩家实体（`PlayerTag`），`EntityBuilder` 会复用而不是重复创建。

**阶段 5：诊断检查**
```cpp
warnIfMapScopedEntitiesMissingMapId(registry_, map_id);
```
这是一个防御性检查：遍历所有"应该属于地图"的实体类型（TileLayer、AutoTile、MapTrigger、RestArea、Crop、ResourceNode），如果发现有实体缺少 `MapId`，输出警告。缺少 `MapId` 的实体在下次卸载时不会被清理，成为**残留实体**——这是切图 bug 的常见根源。

**阶段 6：配置相机**
```cpp
configureCamera(current_map_pixel_size_);
```
用新地图的像素尺寸重新设置相机的限制边界。这确保相机不会越过地图边缘暴露空白区域。

**阶段 7：恢复状态**
```cpp
restoreSnapshot(map_id);
applyPendingResourceNodes(map_id);
applyOpenedChests(map_id);
```
这三步恢复了地图的"动态历史"——上一次离开时保存的耕地/作物/资源点状态、从存档加载的资源节点信息、以及已打开的宝箱记录。后面我们会详细展开快照恢复的流水线。

**阶段 8：更新世界状态 + 预加载**
```cpp
current_map_id_ = map_id;
world_state_.setCurrentMap(map_id);
// 同步玩家的 MapId
registry_.emplace_or_replace<game::component::MapId>(player, map_id);
// 按策略预加载相关地图
if (loading_settings_.preload_mode == MapPreloadMode::Neighbors) {
    preloadRelatedMaps(map_id);
}
```
最后一步更新"谁是当前地图"的全局状态，并把持久化玩家的 `MapId` 同步到新地图。如果预加载策略是 `neighbors`，此时还会触发相关地图的预加载。

#### MapId：事务的"边界控制符"

在整个事务中反复出现的一个角色是 **`MapId`**（`src/game/component/map_component.h`）：

```cpp
struct MapId {
    entt::id_type id_{entt::null};
};
```

它只是一个组件，挂在实体上表示"这个实体属于哪张地图"。但它的作用贯穿了整个地图生命周期：
- **卸载时**：`destroyEntitiesByMap` 遍历所有 `MapId` 组件，销毁 `id_ == current_map_id` 的实体（玩家除外——它有 `PlayerTag` 保护，是跨地图持久化的）
- **快照时**：`writeDynamicSnapshot` 用 `MapId` 过滤"只序列化属于当前地图的动态实体"
- **恢复后**：`rebuildSpatialIndexForDynamicEntities` 同样用 `MapId` 确保只注册本地图实体

一句话概括：**`MapId` 是地图实体生命周期的边界控制符——没有它，卸载不知道删什么、快照不知道存什么、恢复不知道注册什么。**

### 3.2 快照（Snapshot）：局部持久化的边界与"恢复后的补课"

现在来解决第一个工程问题：**切回旧地图时状态丢失**。

快照不是"把整张地图序列化一份"——那样成本太高，而且大部分地图内容是静态的、可重建的。快照只做**局部持久化**：只存"动态状态"。

在《迷你农场》里，地图内容可以分成两类：

| 类别 | 示例 | 是否需要快照 |
|------|------|-------------|
| **静态/可重建** | tile layers、装饰物、NPC、触发器 | 否——重新 `loadLevel` 就能重建 |
| **动态/需保留** | 耕地、湿润层、作物生长阶段、资源点是否被采集、宝箱是否打开 | 是——这些状态来自玩家操作，不保存就丢了 |

`WorldState::MapState` 为每张地图维护一份 `MapPersistentState`（`src/game/world/world_state.h`）：

```cpp
struct MapPersistentState {
    RegistrySnapshot snapshot{};                          // 动态实体的 ECS 快照
    std::uint32_t last_updated_day{0};                    // 离线推进的基准天数
    std::optional<std::vector<ResourceNodeState>> pending_resource_nodes{};  // 资源点"延迟落地"队列
    std::unordered_set<int> opened_chests{};              // 宝箱打开记录
};
```

#### 写入时机与序列化边界

`MapManager::snapshotMap()` 在每次卸载地图时调用，通过 `writeDynamicSnapshot()`（`src/game/world/map_snapshot_serializer.cpp`）把当前地图的动态实体序列化到 `MapState.persistent.snapshot`。

快照按**组件组**分批序列化——每组都先按 `MapId` 过滤，只收集属于当前地图的实体：

| 组件组 | 收集条件 | 序列化的组件 |
|--------|---------|-------------|
| 耕地（tilled soil） | `AutoTileComponent.rule_id_ == SOIL_TILLED` | MapId + Transform + Sprite + Render + AutoTile |
| 湿润（wet soil） | `AutoTileComponent.rule_id_ == SOIL_WET` | MapId + Transform + Sprite + Render + AutoTile |
| 作物（crops） | 有 `CropComponent` | MapId + Transform + Sprite + Render + Crop |
| 资源点（resources） | 有 `ResourceNodeComponent`（可选，受 flag 控制） | MapId + Transform + Sprite + Render + ResourceNode + Animation + AABBCollider + CircleCollider + SpatialIndexTag |

分组序列化有两个好处：
1. 每组用不同的 view 和 filter，职责清晰
2. 反序列化时也按组恢复，用 `entt::continuous_loader` 逐组加载，并调用 `orphans()` 清理无效引用

#### 恢复流水线：不只是"反序列化"

一个常见误区是："反序列化完 snapshot 就结束了"。实际上恢复是一条**多步流水线**，漏掉任何一步都会导致微妙的 bug。

`MapManager::restoreSnapshot()` 的完整流程：

1. **检查快照是否存在**：`snapshot.valid == false` 说明这张地图从未被快照过（第一次进入），直接跳过
2. **离线追赶**：在恢复之前先调用 `advanceOffline()`——如果玩家离开了好几天，先把快照里的作物按天推进到最新状态
3. **清理基础资源节点**：如果快照包含资源点数据，先把 `loadLevel()` 新建的基础资源节点清除（避免重复）
4. **反序列化快照**：调用 `readDynamicSnapshot()` 把实体恢复到 registry
5. **重建空间索引**：把恢复出来的动态实体重新注册到 `SpatialIndex`

<img src="https://theorhythm.top/gamedev/TF/L23_snapshot_restore.webp" style='width: 960px;' />

**第 5 步为什么必不可少？** 因为空间索引（`StaticTileGrid` / `DynamicGrid`）不是 ECS 的一部分——它是一个独立的数据结构。`readDynamicSnapshot` 只是把组件数据写回 registry，但空间索引对这些新实体一无所知。如果跳过 `rebuildSpatialIndexForDynamicEntities()`：
- 恢复出来的耕地/作物在 `SpatialIndex` 中不存在 → 农场系统查不到它们 → 无法浇水、无法收获
- 恢复出来的资源节点（树/石头）看得见但碰不到 → 玩家可以直接穿过去

这就是"看得见但碰不到"的典型 bug——视觉层（Sprite）恢复了，但交互层（SpatialIndex）没有跟上。

### 3.3 预加载：把卡顿从"关键路径"搬走

第二个工程问题是**切图卡顿**。

切图时的"重工作"主要来自三块：解析 `.tmj/.tsj` JSON 文件、加载 tileset 纹理、构建实体与组件。这些操作全部发生在 `LevelLoader::loadLevel()` 内部，属于同步调用——如果全堆在切图那一帧，玩家就会感受到明显的卡顿。

预加载的思路很朴素：**把这些成本提前做掉**，让切图那一帧只需要从缓存取数据。

本项目把策略做成"可配置的三档"，定义在 `MapLoadingSettings`（`src/game/world/map_loading_settings.h`）：

```cpp
enum class MapPreloadMode : std::uint8_t {
    Off = 0,       // 不预加载
    Neighbors = 1, // 预加载邻接与触发器目标
    All = 2,       // 启动时全量预热
};
```

对应的配置文件是 `assets/data/map_loading_config.json`：
```json
{
    "preload": {
        "mode": "off",
        "comment": "off | neighbors | all"
    },
    "log_timings": true
}
```

三种模式的成本曲线差异：

| 模式 | 启动成本 | 运行期切图成本 | 内存占用 | 适用场景 |
|------|---------|--------------|---------|---------|
| `off` | 最低 | 首次切图最高 | 最低 | 调试/快速迭代 |
| `neighbors` | 中等 | 大幅降低（邻接地图已预热） | 中等 | demo 推荐 |
| `all` | 最高（全部地图预热） | 几乎为零 | 最高 | 地图少、追求流畅 |

#### 消费时机

这些策略由 `GameScene::initMapManager()` 读取，并通过 `MapManager::setLoadingSettings()` 注入。消费时机有两个：

**启动时**（`GameScene::initMapManager()`）：
```cpp
auto settings = MapLoadingSettings::loadFromFile("assets/data/map_loading_config.json");
map_manager_->setLoadingSettings(settings);
if (settings.preload_mode == MapPreloadMode::All) {
    map_manager_->preloadAllMaps();  // 全量预热
}
```

**每次切图后**（`MapManager::loadMap()` 末尾）：
```cpp
if (loading_settings_.preload_mode == MapPreloadMode::Neighbors) {
    preloadRelatedMaps(map_id);
}
```

`preloadRelatedMaps()` 会做两件事：
1. 查 `WorldState::neighborsOf()` 拿四个方向的邻接地图，逐一调用 `preloadMap()`
2. 查 `WorldState::outgoingTriggers()` 拿当前地图的所有触发器目标地图，也预加载

这样，无论玩家是走边缘切图还是走门/传送，目标地图大概率已经在缓存中了。

#### 预加载具体做了什么？

`MapManager::preloadMap()` 创建一个临时的 `LevelLoader`，调用 `preloadLevelData()`——它只解析 JSON 和加载 tileset/纹理到缓存，**不创建实体、不注册空间索引**。这意味着预加载成本主要是 IO 和内存，不会污染当前的 registry。

你可以用 **Debug UI → Map Inspector** 快速确认预加载状态：
- `preload_mode`：当前策略
- `preloaded_maps`：已预热的地图列表
- `current_map_preloaded`：当前地图是否在预热集合中

### 3.4 离线推进：让世界在玩家不在场时也会变化

最后一个工程问题：**玩家离开某地图后，那张地图的世界就"冻结"了**。

比如你在 `home_exterior` 种了作物、浇了水，然后切到 `town` 去逛街。过了三天回来——作物应该长了三天，但如果没有离线推进机制，它们还停留在你离开时的阶段。

离线推进的核心函数是 `simulateOfflineDays()`（`src/game/world/map_snapshot_serializer.cpp`），它的循环逻辑很直白：

```text
for 每一天:
    1. 收集所有"湿润"格子的坐标
    2. 对每株作物：检查是否在湿润格子上 → 推进一天生长
    3. 移除所有湿润层（每天浇水效果只持续一天）
```

这段逻辑不是在正式 registry 上跑的——`advanceOffline()` 先把快照反序列化到一个**临时 registry**，在上面模拟完所有天数后，再把结果写回快照。这样即使模拟出了问题，也不会污染正式的游戏状态。

#### 双触发点：避免"漏推"和"重推"

离线推进有**两个触发点**，它们配合工作才能覆盖所有场景：

**触发点 1：跨天事件（日常推进）**
- `TimeSystem` 在游戏时间跨天时发出 `DayChangedEvent`
- `MapManager::onDayChanged()` 收到事件后，遍历 `WorldState` 中**所有非当前地图**，对每张有快照的地图调用 `advanceOffline()`

```cpp
void MapManager::onDayChanged(const DayChangedEvent& event) {
    for (auto& [map_id, state] : world_state_.mapsMutable()) {
        if (map_id == current_map_id_) continue;  // 跳过当前地图——它由正常系统驱动
        advanceOffline(state, event.day_);
    }
}
```

**触发点 2：地图恢复时（补课追赶）**
- `MapManager::restoreSnapshot()` 在恢复快照之前，先调用 `advanceOffline()` 检查是否需要追赶天数

```cpp
void MapManager::restoreSnapshot(entt::id_type map_id) {
    // ... 省略检查 ...
    advanceOffline(*map_state, current_day);  // 先追赶，再恢复
    readDynamicSnapshot(registry_, map_state->persistent.snapshot);
    rebuildSpatialIndexForDynamicEntities(...);
}
```

**为什么需要两个触发点？**

只靠触发点 1 不够——如果玩家存档后退出游戏、下次读档时跳过了好几天，`DayChangedEvent` 在这段时间内不会被触发。触发点 2 就是为这个场景兜底：玩家回到地图时，`restoreSnapshot` 会拿 `last_updated_day` 和 `current_day` 做比较，把中间遗漏的天数一次性补上。

反过来，只靠触发点 2 也不够——如果玩家一直在同一张地图上待着不走，其他地图不会被 `restoreSnapshot`，但跨天事件还是会推进它们的离线状态。

#### 三道防护：避免重复推进

`advanceOffline()` 内部有三道防护：

```cpp
void MapManager::advanceOffline(MapState& state, std::uint32_t current_day) {
    // 防护 1：无快照则跳过
    if (!state.persistent.snapshot.valid) return;
    // 防护 2：首次快照，初始化基准天数
    if (state.persistent.last_updated_day == 0) {
        state.persistent.last_updated_day = current_day;
        return;
    }
    // 防护 3：已经追赶到最新，不重复推进
    if (current_day <= state.persistent.last_updated_day) return;

    // 实际推进
    entt::registry temp;
    readDynamicSnapshot(temp, state.persistent.snapshot);
    simulateOfflineDays(temp, blueprint_manager_, current_day - state.persistent.last_updated_day);
    writeDynamicSnapshot(temp, state.info.id, state.persistent.snapshot);
    state.persistent.last_updated_day = current_day;
}
```

每次推进成功后更新 `last_updated_day`，这确保了同一天不会被推进两次——即使触发点 1 和触发点 2 在同一帧内都执行了。

## 4) 架构/数据流

### 4.1 模块图：谁提供信息？谁提交事务？谁做体验优化？

把本节涉及的所有模块放在一起看，可以清晰地看到三种角色分工：

- **信息提供者**：`WorldState` 提供地图元数据、邻接关系、触发器列表；`MapLoadingSettings` 提供预加载策略
- **事务提交者**：`MapTransitionSystem` 决定何时切图并提交给 `MapManager`；`TimeSystem` 发出 `DayChangedEvent` 驱动离线推进
- **事务执行者 + 体验优化**：`MapManager` 编排整个地图生命周期，同时负责预加载、快照、离线推进等体验层优化

### 4.2 数据边界：哪些东西跟着地图卸载？哪些东西要跨地图保留？

理解这条边界线对排错至关重要：

| 跟着地图卸载（由 MapId 控制） | 跨地图保留 |
|------|------|
| TileLayer 实体 | 玩家实体（PlayerTag 保护） |
| 装饰物 / NPC / 动物 | WorldState（包括所有地图的 MapState） |
| MapTrigger / RestArea | 快照数据（MapPersistentState） |
| 动态实体（耕地/作物/资源点） | 全局配置（GameTime、ItemCatalog 等 ctx 数据） |

关键区分：**动态实体的运行时表现（ECS 组件）会跟着地图卸载被销毁，但它们的状态已经被快照保存到 `MapPersistentState` 中了**。下次加载时通过恢复流水线"复活"。

## 5) 排错速查

遇到切图相关问题时，按以下清单排查：

| 现象 | 排查方向 |
|------|----------|
| **切图后旧地图状态丢失** | 1) 动态实体是否带 `MapId`？（没有 `MapId` 的实体不会被 `writeDynamicSnapshot` 收集）<br/>2) `snapshotMap` 是否在 `destroyEntitiesByMap` 之前被调用？（检查 `unloadCurrentMap` 内部顺序）<br/>3) `restoreSnapshot` 后 `rebuildSpatialIndexForDynamicEntities` 是否执行？（否则恢复的实体"看得见但碰不到"） |
| **切图卡顿明显** | 1) 检查 `map_loading_config.json` 的 `preload.mode`（`off` 模式不预加载，首次切图必卡）<br/>2) 打开 `log_timings: true`，查看日志中各阶段耗时<br/>3) 在 Map Inspector 确认 `preloaded_maps` 数量和目标地图是否在列表中 |
| **离线推进不生效** | 1) `DayChangedEvent` 是否正常分发？（检查 `TimeSystem` 是否在 `GameScene::update` 中被调用）<br/>2) 目标地图的 `snapshot.valid` 是否为 `true`？（从未被快照过的地图无法推进）<br/>3) `last_updated_day` 是否 < `current_day`？（相等说明已推进到最新） |
| **切图后出现残留实体** | 1) 残留实体是否缺少 `MapId`？（Map Inspector 诊断检查会输出警告）<br/>2) 玩家是否被误删？（确认 `destroyEntitiesByMap` 中的 `PlayerTag` 跳过逻辑正常工作） |
| **宝箱重复开启/奖励重复** | 1) `opened_chests` 集合是否正确记录了 `chest_id`？<br/>2) `applyOpenedChests` 是否在 `restoreSnapshot` 之后执行？（顺序在 `loadMap` 阶段 7 中） |

## 7) 练习

### 练习 1：统一 external map 的 ensure 入口（Redundancy）
- **目标**：减少 `ensureExternalMap` 相关逻辑的分散，让"目标地图不存在就注册"的规则只有一个入口。
- **验收标准**：
  - 新增一个轻量 helper（例如 `WorldState::getOrEnsureMapId(...)`），能够用 name/id 获取 `MapId`，若不存在则注册为 external map
  - `MapTransitionSystem` 与 `MapManager::preloadRelatedMaps` 复用该 helper（行为不变）
  - 代码保持精简：不引入 Strategy/Task Queue 这类提前抽象
- **提示线索**：
  - `src/game/world/world_state.h/.cpp`（external map 的注册与查询）
  - `src/game/system/map_transition_system.cpp`（触发器切图的 ensure 逻辑）
  - `src/game/world/map_manager.cpp`（`preloadRelatedMaps` 中的 ensure 逻辑）

### 练习 2（可选）：扩展 Map Inspector 的"快照可观测性"（Debuggability）
- **目标**：让 Debug UI 能更直接地回答"为什么切回旧地图状态没恢复/离线没生效"。
- **验收标准**：
  - 在 Map Inspector 增加一块 `Snapshot/Persistent` 信息展示：例如 `has_snapshot / opened_chests_count / last_updated_day`
  - （可选）展示"当前 registry 中缺失 `MapId` 的地图对象数量"（用于早期发现残留实体）

  - `src/game/debug/map_inspector_debug_panel.cpp`（ImGui 面板）

  - `src/game/component/map_component.h`（`MapId`）

## 8) 小结

这节课你应该建立了三条很工程化的"经验法则"：

- **把切图当作事务**：`loadMap` 的八个阶段（验证 → 清理 → 卸载 → 加载 → 诊断 → 相机 → 恢复 → 更新）是一条严格有序的管线。理解这条管线，你就能精确定位 bug 出在哪个阶段
- **快照不是万能序列化**：明确"存什么/不存什么"的边界，并且记住恢复只是第一步——空间索引、宝箱状态等"非 ECS 基础设施"需要单独补齐
- **体验优化要可配置、可观测**：预加载的三档策略来自配置文件，离线推进的双触发点确保不遗漏，Debug 面板提供运行时可观测性——这些工程习惯比具体实现更值得迁移

下节课我们会把镜头拉回 `GameScene`：
- 系统的初始化与编排顺序为什么会影响行为正确性——比如 `TimeSystem` 必须在 `CropSystem` 之前更新
- `MapManager` / `WorldState` / `TimeSystem` 这些子系统如何被装配到一个可运行的"游戏循环"里
- 过渡期间（`isTransitionActive`）为什么要冻结世界逻辑，以及 `update()` 中的系统编排顺序隐含了哪些依赖关系
