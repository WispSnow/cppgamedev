# 游戏场景初始化与系统编排：为什么顺序决定一切

在前两节课我们已经把"多地图游戏"这条主线搭起来了：

- **`WorldState`** 负责组织世界图（maps + neighbors + triggers）
- **`MapManager`** 负责把一次切图落实成可控的事务（unload → load → restore）
- **`MapTransitionSystem`** 负责决定"何时切、切到哪、出生点在哪"

但在真正的项目里，光有这些"模块"还不够。你会发现一个更根本的问题悬而未决：

> 这些东西到底由谁来创建？按什么顺序创建？每帧又按什么顺序更新？顺序错了会怎样？

这不是一个"代码能不能编译"的问题——这些模块随便排个顺序也能通过编译。但运行起来就会出现时间不动、交互慢一拍、切图闪烁、UI 首帧空白等一系列"灵异现象"。而且这类 bug 往往不会 crash，只是行为"不太对"，排查起来极其痛苦。

这就是本节课的主题：**`GameScene` 的初始化与系统编排**——把隐式依赖变成显式结构，把"恰好能跑"变成"明确正确"。

## 2) 本节目标与问题定义

本节目标一句话：

> 理解 `GameScene` 作为"组合根（composition root）"如何把 **数据/世界/地图/系统/UI/调试** 装配成可运行的游戏闭环，并用"更新顺序"显式表达系统间依赖。

我们用 4 个问题来驱动理解：

1. 为什么 `GameScene` 不是"写玩法"的地方，却是工程上最关键的文件之一？
2. 启动期装配顺序为什么要分阶段？每个阶段在满足哪些前置条件？
3. `registry.ctx()` 的意义是什么？哪些东西应该进 ctx？为什么"必须先放进去"？
4. 运行期 update 顺序为什么不能乱？"顺序 bug"怎么排查？

## 3) 核心概念

### 3.1 组合根（Composition Root）：把"谁创建谁"集中到一个地方

你可能写过这样的代码：系统 A 在自己的构造函数里创建了系统 B，系统 B 又在 init() 里偷偷拉取了系统 C。到了调试的时候，你想搞清楚"C 到底是谁创建的、什么时候创建的"，得在三个文件之间来回跳。

**组合根**就是为了避免这种局面。它的核心思想很简单：**把所有"创建"和"装配"集中到一个地方做**，这样依赖关系一目了然。

在《迷你农场》里，`GameScene` 就扮演这个角色：

- **它创建并持有关键对象**——`WorldState`、`MapManager`、`SaveService`、28 个系统、全部 UI 控件、调试面板
- **它决定初始化顺序**——先加载数据，再建世界，再装系统，最后挂 UI
- **它决定每帧更新顺序**——先清理、再移动、再更新索引、最后渲染 UI

这种设计的好处是实打实的：

- **依赖关系不会散落在各个系统里**。你不需要猜"TimeSystem 的 GameTime 从哪来"，因为答案就在 `GameScene::init()` 的第二个阶段里
- **顺序 bug 更好定位**。出了问题，你只需要看 `init()` 或 `update()` 里的顺序，而不是在 20 个系统的构造函数里翻找
- **扩展时有明确的"入口"**。新增一个系统？在 `initSystems()` 里加一行创建、在 `update()` 里加一行调用、想好它应该排在谁的前面或后面——就这三步

### 3.2 启动期：把 init() 当作一条流水线

`GameScene::init()` 不是一个"从头写到尾"的大函数。它被拆成了 9 个阶段，每一步都在为后面的步骤提供前置条件：

![init() 阶段化流水线](diagrams/L24_init_pipeline.png)

我们逐个看每个阶段在做什么、为什么要排在这个位置：

**阶段 1：Data + Infra（基础数据与核心设施）**

```cpp
if (!ensureBlueprintManager()) return false;  // 加载蓝图（角色/动物/作物）
if (!ensureItemCatalog()) return false;        // 加载物品目录
if (!createCollisionResolver()) return false;  // 创建碰撞解析器
```

蓝图和物品目录是纯数据，没有依赖任何运行时对象，所以放在最前面。碰撞解析器需要 `registry` 和 `SpatialIndexManager`（来自 Context），也都在这个时间点已就绪。

**阶段 2：ctx + World（注册表上下文 + 世界数据）**

```cpp
if (!initRegistryContext()) return false;  // 把 GameTime 放入 registry.ctx()
if (!initWorldState()) return false;        // 加载 world 文件 + 把 WorldState* 放入 ctx
```

这是关键的"地基"阶段。`GameTime` 和 `WorldState*` 进入 `registry.ctx()` 之后，后续系统才能通过 `registry.ctx().find<GameTime>()` 等方式拿到共享数据。**如果这步跳过或延后，后面的 TimeSystem、MapTransitionSystem 等都会失效。**

**阶段 3：Map Services（工厂与地图管理）**

```cpp
if (!initFactory()) return false;     // 创建 EntityFactory（依赖 BlueprintManager）
if (!initMapManager()) return false;  // 创建 MapManager（依赖 WorldState + EntityFactory）
if (!initSaveService()) return false; // 创建 SaveService（依赖 MapManager + WorldState）
```

注意依赖链：EntityFactory 需要蓝图（阶段 1）→ MapManager 需要工厂和世界（阶段 1+2）→ SaveService 需要前面所有。如果你把 `initFactory()` 放到 `initMapManager()` 后面，MapManager 的构造函数会拿到一个空指针。

**阶段 4：Baseline Map（初始地图）**

```cpp
if (!loadLevel()) return false;       // 加载初始地图
if (!configureCamera()) return false; // 设置相机 zoom
```

到这一步，`MapManager` 已经就绪，可以加载第一张地图了。加载地图会创建实体（包括玩家），这些实体在后续阶段会被系统和 UI 使用。

**阶段 5：Systems（系统装配）**

```cpp
if (!initSystems()) return false;
```

28 个系统在这一步被创建。系统的构造函数会注入 `registry`、`dispatcher`、`InputManager`、`Camera` 等依赖——这些全部来自 `Context`（引擎级）或前面阶段的产出物（数据/世界/工厂）。

值得注意的是：**系统的创建顺序和更新顺序是两回事**。创建顺序只要满足构造函数的参数依赖就行；更新顺序才是真正表达运行时依赖的地方（3.4 节会展开）。

**阶段 6：UI + Debug（界面与调试面板）**

```cpp
if (!initUI()) return false;
#ifdef TF_ENABLE_DEBUG_UI
if (!registerDebugPanels()) return false;
#endif
```

UI 放在系统之后有两个原因：一是 `initUI()` 需要通过 `registry.view<PlayerTag>()` 找到玩家实体（阶段 4 加载地图时创建的），用来给 InventoryUI/HotbarUI 设置目标；二是 UI 需要把 `UIScreenFade` 传给 `MapTransitionSystem`（阶段 5 创建的），让切图时能做淡入淡出。

调试面板同理——它需要拿到 `MapManager`、`WorldState`、`SaveService`、`BlueprintManager` 等对象的引用，所以必须在它们都就绪之后注册。

**阶段 7：Event Listeners（Scene 级事件监听）**

```cpp
dispatcher.sink<game::defs::InventoryChanged>().connect<&GameScene::onInventoryChanged>(this);
dispatcher.sink<game::defs::HotbarChanged>().connect<&GameScene::onHotbarChanged>(this);
dispatcher.sink<game::defs::HotbarSlotChanged>().connect<&GameScene::onHotbarSlotChanged>(this);
```

这些监听器负责把系统事件"转发"给 UI——例如 `HotbarChanged` 事件触发时，`GameScene::onHotbarChanged` 会调用 `hotbar_ui_->setSlotItem()` 来更新快捷栏显示。

为什么放在这里？因为下一步是读档，读档可能触发 `InventoryChanged` 等事件。**如果监听器还没连接，这些事件就会"丢失"，导致 UI 首帧显示空白。**

**阶段 8：Load Save（可选读档）**

```cpp
if (load_slot_) {
    if (!save_service_->loadFromFile(...)) {
        // 读档失败：请求替换为标题场景
        requestReplaceScene(std::make_unique<TitleScene>(...));
        abort_to_title_ = true;
    }
}
```

读档放在监听器之后的原因前面已经解释了。另外还有一个细节：读档失败时，`GameScene` 不会 crash，而是标记 `abort_to_title_` 并请求替换场景。这个设计保证了即使存档损坏，用户也能回到标题画面而不是看到一个黑屏。

**阶段 9：Initial UI Sync（初始 UI 同步）**

```cpp
dispatcher.enqueue<game::defs::InventorySyncRequest>(player);
dispatcher.enqueue<game::defs::HotbarSyncRequest>(player);
```

最后一步：向 dispatcher 发送全量同步请求。注意用的是 `enqueue`（入队）而非 `trigger`（立即触发），所以这些事件会在下一次 `dispatcher.update()` 时才被处理——确保所有系统都已完成初始化。

### 3.3 registry.ctx()：给系统的"共享依赖入口"

在 EnTT 里，`registry.ctx()` 是一个与 registry 绑定的"共享存储区"。它适合放那些**跨系统共享、但不属于某个实体**的数据。

在《迷你农场》中，进入 ctx 的典型对象有：

| 对象 | 类型 | 使用者 |
|------|------|--------|
| `GameTime` | 值类型（直接存储） | TimeSystem、DayNightSystem、TimeOfDayLightSystem |
| `WorldState*` | 指针（间接引用） | MapTransitionSystem、InteractionSystem、ChestSystem |

这里有个工程上值得注意的区别：`GameTime` 是用 `emplace<GameTime>(...)` 直接存在 ctx 里的（值语义），而 `WorldState` 是用 `emplace<WorldState*>(ptr)` 存指针的（因为 `WorldState` 的生命周期由 `GameScene` 管理，ctx 只持有引用）。

ctx 的常见陷阱也很实际：

> **如果 ctx 里的数据没初始化好，系统通常不会崩溃，但会悄悄失效。**

看 `time_system.cpp` 的 update 逻辑就能理解这一点：

```cpp
auto* game_time = registry_.ctx().find<GameTime>();
if (!game_time) {
    spdlog::warn("TimeSystem::update: 注册表上下文中未找到 GameTime");
    return;    // 不崩溃，但时间系统完全失效——时间不动、作物不长、昼夜不变
}
```

如果 `initRegistryContext()` 没有在 `initSystems()` 之前执行，`TimeSystem` 构造时不会报错，但 `update()` 时会每帧打一条 warn 然后直接返回。结果就是：时间停滞、昼夜循环冻结、作物永远不生长——而且没有任何 crash 提示。

所以把 `initRegistryContext()` 放在系统创建之前，不是"习惯性操作"，而是一种**工程化保险**。

### 3.4 运行期：update 顺序就是依赖图

如果说 `init()` 的阶段化解决的是"启动期谁先谁后"，那 `update()` 的顺序解决的就是"每帧内谁先谁后"。

![update 顺序依赖图](diagrams/L24_update_order.png)

我们把 `GameScene::update()` 拆成几个阶段来看：

**Phase 0：清理（Remove）**

```cpp
remove_entity_system_->update(registry_);
```

每帧最先处理标记删除的实体。如果延后到中间，已经被标记删除的实体仍然会参与本帧的移动、碰撞、交互等计算，浪费性能不说，还可能产生"幽灵碰撞"。

**Phase 1：过渡冻结（Transition Freeze）**

```cpp
if (map_transition_system_ && map_transition_system_->isTransitionActive()) {
    map_transition_system_->update();  // 推进过渡状态机（fade out/in）
    light_toggle_system_->update();     // 光源切换不受冻结影响
    Scene::update(delta_time);          // UI 仍然更新（fade 动画需要）
    return;                             // 世界其他系统全部跳过
}
```

切图过渡期间，世界被冻结。这不是"偷懒不更新"——如果过渡期间继续更新移动/AI/交互等系统，玩家可能会在"旧地图已卸载、新地图未加载"的空档里做出操作，导致空间查询崩溃或状态混乱。

注意这里只冻结了"世界逻辑"，UI 和光源切换仍在更新——否则淡出动画本身都不会播放了。

**Phase 2：时间与环境**

```cpp
time_system_->update(delta_time);    // 推进游戏时间、产生时段变更事件
day_night_system_->update();          // 根据最新时间更新光照参数
```

时间必须在行为系统之前更新。如果把时间放到后面，那 NPC 的行为（白天游荡/夜晚睡觉）读到的还是上一帧的时段，会滞后一帧——虽然不严重，但不够"正确"。

**Phase 3：行为与逻辑**

```cpp
player_control_system_->update(delta_time);   // 输入 → 玩家意图
npc_wander_system_->update(delta_time);        // NPC 随机游走
animal_behavior_system_->update(delta_time);   // 动物行为
chest_system_->update(delta_time);             // 宝箱交互
item_use_system_->update(delta_time);          // 物品使用
dialogue_system_->update(delta_time);          // 对话
action_sound_system_->update(delta_time);      // 动作音效
auto_tile_system_->update();                   // 自动瓦片更新
state_system_->update();                       // 状态机更新
```

这些是游戏玩法逻辑，它们会产生移动请求（设置 VelocityComponent）和各种事件。注意它们**不直接修改位置**——位置变更统一由下一步的 MovementSystem 处理。

**Phase 4：移动 + 过渡提交**

```cpp
movement_system_->update(registry_, delta_time);  // 位置更新 + 碰撞解析
map_transition_system_->update();                   // 检查是否触发切图
light_toggle_system_->update();                     // 更新光源状态
```

MovementSystem 根据速度和碰撞解析计算最终位置。紧接着 MapTransitionSystem 检查玩家是否走到了地图边缘或触发器上——如果是，它会提交一次切图请求。

**Phase 5：第二次过渡检查（关键！）**

```cpp
if (map_transition_system_ && map_transition_system_->isTransitionActive()) {
    Scene::update(delta_time);
    return;  // 过渡刚被触发，后续阶段不应继续
}
```

这是一个容易被忽略的设计：**Phase 4 的 `map_transition_system_->update()` 可能刚刚触发了一次过渡**（开始 fade out）。如果不在这里检查并提前返回，后续的 SpatialIndexSystem、PickupSystem 等会在"旧地图实体即将被清除"的状态下继续运行，可能访问到无效数据。

**Phase 6：索引 + 交互 + 相机 + 动画**

```cpp
spatial_index_system_->update(registry_);     // 更新空间索引（依赖最新位置）
pickup_system_->update(delta_time);            // 拾取检测（依赖最新空间索引）
interaction_system_->update();                 // 交互检测（依赖最新空间索引）
camera_follow_system_->update(delta_time);     // 相机跟随（依赖最新位置）
animation_system_->update(delta_time);         // 动画更新
```

这里的依赖链很清晰：

1. **MovementSystem 改变位置** → SpatialIndexSystem 必须在之后，否则空间查询读到的是上一帧位置
2. **SpatialIndexSystem 更新索引** → Pickup/Interaction 必须在之后，否则拾取/交互可能漏判或误判
3. **位置已确定** → CameraFollowSystem 在之后，否则相机会跟随旧位置，画面抖动

**Phase 7：UI**

```cpp
Scene::update(delta_time);  // 基类 update 会调用 UIManager::update
```

UI 放在最后一个更新。这样 UI 读到的是本帧已经结算完毕的世界状态——背包里有什么、玩家在哪里、当前时间是几点——全部都是"最终值"。

### 3.5 render 顺序：同样有依赖

`GameScene::render()` 的顺序比 update 简单，但同样体现依赖：

![render 顺序](diagrams/L24_render_order.png)

```cpp
ysort_system_->update(registry_);                  // 1. Y 排序（决定遮挡关系）
render_system_->update(registry_, renderer, camera); // 2. 场景渲染（SpriteBatch 提交）
light_system_->update(registry_, renderer);          // 3. 光照通道
render_target_system_->update(renderer);             // 4. 后处理（bloom/composite）
#ifdef TF_ENABLE_DEBUG_UI
debug_render_system_->update(registry_, renderer);   // 5. 调试渲染（碰撞框等）
#endif
Scene::render();                                     // 6. UI 叠在最上层
```

核心原则是**先排序、再渲染、后处理在最后、UI 叠在一切之上**。如果把 Y 排序放到渲染之后，你会看到角色和树木的遮挡关系是上一帧的——虽然只差一帧，但在快速移动时会产生明显的"闪烁"。

## 4) 架构总览

### 4.1 模块图：GameScene 把哪些东西装配到一起？

![GameScene 组合根模块图](diagrams/L24_composition_root.png)

这张图展示了 `GameScene` 作为组合根的全貌。左侧是它持有的所有对象（数据/世界/系统/UI/调试），右侧是 `Context` 提供的引擎级依赖（Renderer/Camera/InputManager 等）。所有的"连线"——谁依赖谁、谁创建谁——都在 `GameScene` 内部完成。

### 4.2 典型顺序 bug：用"依赖"解释现象

当你遇到这类问题时，不要急着加 print 或断点。先问自己：**这个症状对应的依赖关系是什么？**

| 症状 | 依赖关系 | 排查方向 |
|------|----------|----------|
| UI 首帧显示空白 | 读档事件 → 事件监听器 | 读档是否在 event listeners 连接之后执行？（阶段 8 vs 阶段 7） |
| 时间不动、昼夜不变 | TimeSystem → ctx(GameTime) | GameTime 是否进了 ctx？TimeSystem 是否在 update 中被调用？ |
| 交互/拾取慢一拍 | SpatialIndex → Movement | SpatialIndexSystem 是否在 MovementSystem 之后更新？ |
| 切图瞬间画面抖动 | 世界冻结 → transition active | update 是否在 transition active 时执行了 early return？ |
| 切图后 crash 或查询异常 | 第二次 early return | transition commit 后是否再次检查了 `isTransitionActive()`？ |
| 新增系统"没有效果" | update 遗漏 | 系统是否在 `initSystems()` 中创建并在 `update()` 中被调用？ |

这些问题的共同特点是：**系统本身的实现是对的，但顺序错了**。组合根模式让你可以在一个文件里排查所有的顺序问题——这就是它最大的工程价值。

## 6) 练习

### 练习 1：external map 列表配置化（Correctness / Architecture）

- **目标**：移除 `initWorldState` 中硬编码的 `ensureExternalMap("home_interior")`，把"哪些室内图需要在启动期注册"变成一个可维护的配置。
- **验收标准**：
  - 新增一个轻量配置（例如 `assets/data/external_maps.json` 或复用某个现有 config 的字段），用列表声明 external maps
  - `GameScene::initWorldState` 读取该列表并逐个 `ensureExternalMap`
  - 行为不变：室内门触发器仍能正常切图；预加载/世界图逻辑不受影响
- **提示线索**：
  - `src/game/scene/game_scene.cpp`（`initWorldState`）——当前的硬编码位置
  - `src/game/world/world_state.h/.cpp`（`ensureExternalMap`）——被调用的接口
  - `assets/maps/farm-rpg.world`（world in-world maps 与 external maps 的边界）
- **提交方式**：GitHub PR（在 PR 描述里写清：配置文件格式 + 自测步骤）

### 练习 2（可选）：给 Debug UI 增加"顺序可观测性"（Docs / Debuggability）

- **目标**：让你在修改 update 顺序或过渡冻结逻辑时，能快速验证自己没有破坏关键阶段。
- **验收标准**：
  - 在 Debug UI 或某个现有面板中展示 `transition_active`（true/false）+（可选）当前 update phase 名称
  - 信息更新频率与显示开销保持轻量（不做 profiler）
- **提示线索**：
  - `src/engine/debug/debug_ui_manager.*`（面板框架）
  - `src/game/debug/*`（可新建一个小面板或扩展现有面板）
  - `src/game/system/map_transition_system.*`（过渡状态的判定方法）

## 7) 小结

这节课你应该带走的核心心智模型是：

- **`GameScene` 是组合根**：它负责装配，不负责玩法细节。所有的"谁创建谁、谁在谁之前"都在这里显式表达
- **init 顺序是"满足前置条件"的流水线**：data → ctx → world → map → systems → UI → listeners → save → sync。每个阶段的位置都有明确的依赖原因
- **update 顺序就是依赖图**：清理 → 过渡冻结 → 时间 → 行为 → 移动 → 过渡提交 → 索引/交互/相机 → UI。特别注意两次过渡检查的设计意图
- **render 顺序**：排序 → 渲染 → 光照 → 后处理 → 调试 → UI
- **排查顺序 bug 的方法**：不要猜，而是画出"症状 → 依赖关系 → 应该在谁之后"的链条

---

下节课我们会把镜头对准**玩家控制与相机**：

- 输入如何变成玩家意图（移动方向、目标选择、工具切换）
- 相机限制与跟随策略如何与地图边界、空间索引协作
- 这些系统为什么对"顺序与依赖"格外敏感——你会发现，本节课建立的心智模型在这里立刻能派上用场
