# 世界状态：WorldState、地图邻接与跨地图触发器

过去几节课，我们完成了从"一张地图文件"到"可渲染、可交互的运行时世界"的完整管线：
- “地图数据管线” 讲了 `.tmj/.tsj` 怎么被解析为瓦片层与对象层
- “关卡载入器与实体建造者” 讲了 `LevelLoader + EntityBuilder` 怎么把对象层分派成各类实体
- “蓝图与实体工厂” 讲了蓝图与实体工厂如何把"角色/动物/作物"变成数据驱动的组件组合

但目前这一切都停留在**单张地图**的范围内。一旦你的游戏世界不止一张地图——比如《迷你农场》里有 `home_exterior`（室外）、`town`（城镇）、`home_interior`（室内）——新的问题就浮现了：

- **地图之间的空间关系**：哪些地图左右相邻？走到边缘该切到哪张？
- **非空间连接**：室内/副本不在 "平面拼图"上，但门和传送点要能把玩家送过去
- **这些信息谁来维护、谁来查询**：不可能让每个系统各自硬编码

本节的核心，就是把视角从"单张地图的构建"提升到**世界图（world graph）**——用 `WorldState` 把所有地图组织成一个可查询的索引，再由 `MapTransitionSystem` 和 `MapManager` 把这些世界级信息落实为运行时的切图行为。

## 2) 本节目标与问题定义

本节要回答三个关键问题：

**1) WorldState 到底是什么？**
它不是"万能全局状态"，它只是一个世界级的索引/目录。它应该存什么、不该存什么？

**2) 两种切图机制如何统一？**
"边缘切图"来自邻接推导，"门/传送触发器切图"来自地图中的 object layer。条件不同、数据来源不同，但最终它们走的是同一条"加载目标地图 + 计算安全落点"的提交路径。

**3) external map 如何接入世界？**
室内地图 `home_interior` 不在 `.world` 文件的平面布局里，但玩家走进一扇门就要能切过去。这类地图怎么被注册、被加载，并参与触发器切换？

**完成本节后，你应该能做到：**
- 读懂 `.world` 文件的最小 schema，理解邻接推导的核心约束（像素对齐 + 边界贴合）
- 在代码层面区分"邻接信息来自哪里、触发器信息来自哪里、谁消费这些信息"
- 遇到切图失败时，有清晰的排错路径：先查 world 对齐 → 再查 trigger 配对 → 再查落点安全

## 3) 核心概念

### 3.1 WorldState：世界级索引，不是"万能全局状态"

名字里带"State"容易让人误以为它是个大杂烩。先明确边界——`WorldState`（`src/game/world/world_state.h`）更像一本**地图索引手册**：

**它描述的是"世界由哪些地图组成、地图之间怎么连通"：**
- 每张地图的元数据：`name / file_path / world_pos_px / size_px / in_world`（→ `MapInfo`）
- 地图之间的邻接关系：N/S/E/W 四个方向（→ `NeighborInfo`）
- 跨地图触发器的注册表：从哪出发、到哪落地（→ `TriggerInfo`）
- 当前地图是谁：`current_map_id`

**它不做的事同样重要——理解边界才能避免"什么都往里塞"的设计退化：**
- 不负责"加载地图文件"——那是 `MapManager` + `LevelLoader` 的职责
- 不负责"每帧判断是否切图"——那是 `MapTransitionSystem` 的职责
- 不负责"管理实体的创建和销毁"——那是 registry + factory 的职责

一句话概括：**WorldState 只提供"可查询的数据结构"，让上层系统（MapTransitionSystem、MapManager）更容易做世界编排。**

![WorldState 结构与查询接口总览](diagrams/L22_world_state_overview.png)

核心查询接口一览：

| 方法 | 返回 | 用途 |
|------|------|------|
| `getMapState(id / name)` | `const MapState*` | 按 ID 或名称查地图的完整状态 |
| `neighborsOf(map_id)` | `NeighborInfo` | 查某地图的 N/S/E/W 邻接 |
| `getNeighbor(map_id, dir)` | `optional<id_type>` | 查某方向是否有邻接（边缘切图的入口） |
| `outgoingTriggers(map_id)` | `span<TriggerInfo>` | 查某地图的所有出发触发器（预加载决策的入口） |
| `ensureExternalMap(name)` | `id_type` | 注册不在 `.world` 里的地图，返回其哈希 ID |

### 3.2 `.world` 文件：邻接推导的输入

邻接关系不是手工配置的——它由 Tiled 的 `.world` 文件推导而来。

`.world` 是一个 JSON 文件，在本项目里只用到 `maps[]` 数组中每个条目的几个字段：
- `fileName`：地图文件名（例如 `home_exterior.tmj`）
- `x / y / width / height`：单位是**像素**（px），表示该地图在世界平面中的位置与尺寸

以 `assets/maps/farm-rpg.world` 为例：
```json
{
  "maps": [
    { "fileName": "home_exterior.tmj", "x": 0,   "y": 0, "width": 560, "height": 400 },
    { "fileName": "town.tmj",          "x": 560, "y": 0, "width": 560, "height": 400 }
  ]
}
```

`WorldState::loadFromWorldFile()` 读取这个文件后，会对每个条目生成 `MapInfo`（`name` 通过去掉扩展名得到，`id` 通过 `entt::hashed_string` 哈希得到），然后调用 `resolveAdjacency()` 推导邻接。

**邻接推导规则**（`WorldState::resolveAdjacency()`）用伪代码概括：
```text
for each map A:
  for each map B (B != A):
    if A.y == B.y:                          // 同 row
      if A.x + A.w == B.x: A.east  = B
      if B.x + B.w == A.x: A.west  = B
    if A.x == B.x:                          // 同 col
      if A.y + A.h == B.y: A.south = B
      if B.y + B.h == A.y: A.north = B
```

拿上面的数据代入：`home_exterior` 的右边界 `x + width = 0 + 560 = 560` 恰好等于 `town` 的左边界 `x = 560`，且两者 `y` 相同 → 推导出 `home_exterior.east = town`，同时 `town.west = home_exterior`。

![邻接推导示意：像素对齐 → 方向推导](diagrams/L22_adjacency_derivation.png)

这里有一个**制作侧必须遵守的强约束**：

> 地图在 `.world` 中的位置与尺寸必须"像素对齐 + 无缝贴合"，否则邻接推导会缺失或错误。

假如 `town` 的 `x` 写成了 561（差 1 像素），`A.x + A.w (560) != B.x (561)`，邻接就推不出来——走到边缘只会被挡回去，而不会切图。代码里还做了**双向校验**：如果 `A.east = B`，但反过来 `B.west != A`，会输出 `spdlog::warn` 提醒你检查布局。

### 3.3 世界图模型：把"邻接"和"触发器"都看作边

理解切图逻辑最好的心智模型，是把整个世界看成一张**图（graph）**：

- **节点（node）**：每张地图
- **边（edge）**：从一张地图通往另一张地图的连接

边有两种来源：
- **邻接边**：由 `.world` 文件的像素布局推导而来（自动、隐式）
- **触发器边**：由 `.tmj` 地图中 object layer 的 `map_trigger` 对象显式定义

一个直观的例子——同一个世界里同时存在两类边：
```text
home_exterior --(east neighbor)--> town          ← 邻接边（来自 .world 推导）
home_exterior --(door trigger)---> home_interior  ← 触发器边（来自 .tmj 中的 map_trigger）
```

邻接边只能连接 `.world` 里的地图（因为只有它们有世界坐标）；触发器边可以连接任意地图——包括不在 `.world` 里的 external map。这就引出了下一个概念。

### 3.4 external map：不在 `.world` 里，也能成为世界的节点

室内地图（如 `home_interior`）或特殊副本（如 `school`）通常不适合放进 `.world` 的平面布局——否则所有地图都得"摊平"到同一张 2D 棋盘上，世界图会越来越难维护。

TinyFarm 用 **external map** 解决这个问题：
- 不在 `.world` 的 `maps[]` 列表里 → 其 `in_world = false`
- 文件路径按约定拼接：`maps_root + name + ".tmj"`（例如 `assets/maps/home_interior.tmj`）
- 没有世界坐标（`world_pos_px` 和 `size_px` 保持默认零值），因此不参与邻接推导

**注册时机**有两种：
1. **启动期显式注册**：`GameScene::initWorldState()` 里手动调用 `world_state_->ensureExternalMap("home_interior")`
2. **运行期按需注册**：`MapTransitionSystem` 或 `MapManager` 在处理触发器时发现目标地图不在 `WorldState` 中，自动调用 `ensureExternalMap`

记住一个关键区分：
> external map 是世界图的"节点"，但不是 world layout 的一部分。它没有世界坐标、没有邻接，只能通过触发器被连入世界图。

### 3.5 触发器属性 schema：配对机制与落点偏移

触发器切图的核心在于**配对**——两张地图各放一个 `map_trigger` 对象，用 `self_id / target_id` 互相引用，形成一条双向通道。

**Tiled 侧的 Custom Properties**（常量定义在 `src/game/loader/tiled_conventions.h`）：

| Property | 类型 | 含义 |
|----------|------|------|
| `self_id` | int | 当前触发器的 ID（在本地图内唯一） |
| `target_id` | int | 目标地图中对接触发器的 `self_id` |
| `target_map` | string | 目标地图名称（无扩展名，如 `home_interior`） |
| `start_offset` | string | 玩家出现在目标触发器的哪个方向（`left / right / top / bottom`） |

**配对关系示意**——以"室外的门"和"室内的入口"为例：
```text
home_exterior 门触发器:          home_interior 入口触发器:
  self_id    = 1                   self_id    = 2
  target_id  = 2                   target_id  = 1
  target_map = home_interior       target_map = home_exterior
  start_offset = bottom            start_offset = top
```

当玩家走进 `home_exterior` 的门（踩到 self_id=1 的触发区域）→ `MapTransitionSystem` 读取 `target_map=home_interior` 和 `target_id=2` → 加载 `home_interior` → 在新地图中找 `self_id=2` 的触发器 → 用它的 `rect + start_offset` 计算玩家落点。

![触发器配对与落点偏移示意](diagrams/L22_trigger_pairing.png)

**`start_offset` 决定了玩家出现在目标触发器矩形的哪一侧**（枚举定义在 `src/game/component/map_component.h` 的 `StartOffset`）：

| 值 | 落点位置 |
|----|---------|
| `Left` | 触发器矩形左侧外，垂直居中 |
| `Right` | 触发器矩形右侧外，垂直居中 |
| `Top` | 触发器矩形上方外，水平居中 |
| `Bottom` | 触发器矩形下方外，水平居中 |
| `None` | 触发器矩形中心 |

偏移距离由 `MapTransitionSystem` 的 `edge_offset_`（默认 8px）控制。这个偏移很重要——它确保玩家出生后不会立刻再次踩到触发区域，避免"刚进去就被弹回来"的乒乓效应。

**运行时的组件表达**——`EntityBuilder::buildMapTrigger()` 会把 Tiled 的 properties 解析成 `MapTrigger` 组件：

```cpp
struct MapTrigger {
    Rect rect_;                   // 触发区域（世界坐标）
    entt::id_type map_id_;        // 归属地图
    int self_id_;                 // 本触发器 ID
    int target_id_;               // 对接触发器 ID
    entt::id_type target_map_;    // 目标地图（hashed）
    std::string target_map_name_; // 目标地图名称
    StartOffset start_offset_;    // 落点偏移方向
};
```

**同步到 WorldState**——除了创建 ECS 组件，`buildMapTrigger()` 还会把 `TriggerInfo`（一个轻量镜像结构）同步到 `WorldState::MapState::triggers`。这样做的目的是让 `MapManager` 在做预加载决策时，不需要遍历 registry 里的所有实体，而是直接查 `WorldState::outgoingTriggers()` 就能知道"当前地图有哪些触发器指向哪些目标地图"。

### 3.6 两种切图：不同的触发条件，同一条提交路径

理解了数据从哪里来之后，我们来看 `MapTransitionSystem`（`src/game/system/map_transition_system.h`）如何在运行时做切图决策。

**边缘切图（edge transition）**：
1. 每帧检查玩家的 **collider bounds**（AABB 或 Circle 的包围盒）是否超出当前地图边界
2. 确定越界方向 → 调用 `WorldState::getNeighbor(current_map, dir)` 查邻接
3. 有邻接 → 计算目标地图的出生点：保持非越界轴坐标，越界轴推入 `edge_offset_` px
4. 没有邻接 → 把玩家的 collider bounds 夹回地图范围内（即"被边界挡住"）

**触发器切图（trigger transition）**：
1. 每帧遍历当前地图的所有 `MapTrigger` 组件，检查玩家位置是否在某个触发器的 `rect` 内（`Rect::contains(pos)`）
2. 匹配到触发器 → 查找目标地图（必要时调用 `ensureExternalMap` 注册 external map）
3. 加载目标地图后，在新地图的触发器中找 `self_id == trigger.target_id_` 的对接触发器
4. 用对接触发器的 `rect + start_offset` 计算落点

**两者的共同点**——无论哪种切图，最终都会汇入同一条提交路径：

> 加载目标地图 → `findSafeSpawnPosition()`（用碰撞检测确保落点没被阻挡） → 更新玩家位置 → 对齐相机

当场景配置了 `UIScreenFade` 时，切图还会走淡入淡出过渡：`FadingOut → commitPendingTransition → FadingIn`。过渡期间 `isTransitionActive()` 返回 `true`，其他系统可以据此冻结世界逻辑，避免切图过程中出现异常行为。

### 4.2 时序（心智版）：一次切图发生了什么

把"切图"当作一次**事务（transaction）**会更容易理解——要么完整执行（地图加载 + 玩家传送 + 相机对齐），要么回退（目标地图不存在/加载失败则取消）。

```text
MapTransitionSystem::update()
  ├─ edge: collider bounds 越界 → getNeighbor → computeEdgeSpawnPos
  └─ trigger: Rect::contains(pos) → target_map → paired trigger → computeOffsetPosition

beginTransition(pending)
  └─ fade out → commitPendingTransition() → fade in → finishTransition()

commitPendingTransition()
  ├─ MapManager::loadMap(target_map_id)
  │   ├─ unloadCurrentMap()  (快照 + 销毁旧地图实体)
  │   ├─ LevelLoader::loadLevel()  (重建实体 + MapTrigger)
  │   └─ setCurrentMap() + configureCamera()
  ├─ 计算 spawn_pos (edge 路径取 edge_spawn_pos / trigger 路径查对接触发器)
  ├─ findSafeSpawnPosition()  (碰撞检测，螺旋搜索附近安全格)
  └─ 更新 player.position + camera
```

注意 `findSafeSpawnPosition()` 的策略：先检查目标位置是否可通行，如果被阻挡，则以 16px 为步长、在 3 格半径内做螺旋搜索，找到第一个安全位置。如果搜索失败，会发出 `spdlog::warn` 并强制使用目标位置——这时玩家可能会卡在碰撞体里，但至少不会被吞掉。

## 5) 排错速查

切图失败是多地图游戏中最常见的问题之一。按以下顺序排查，通常能快速定位原因：

| 步骤 | 检查什么 | 怎么看 |
|------|---------|--------|
| 1. World 对齐 | `.world` 里两张地图的边界是否严格贴合？ | 打开 `farm-rpg.world`，验证 `x + width` 或 `y + height` 是否精确等于邻接地图的 `x` 或 `y`。差 1 像素就会导致邻接推导失败 |
| 2. Trigger 配对 | `self_id / target_id` 是否配对正确？`target_map` 名称拼写？`start_offset` 是否合法？ | 在 Tiled 中打开 object layer，检查触发器的 Custom Properties。常见错误：两端的 `self_id/target_id` 写反了、`target_map` 多了 `.tmj` 扩展名 |
| 3. External map 注册 | 目标地图是 external map 时，是否已注册？ | 查 `GameScene::initWorldState()` 或确认运行时 `ensureExternalMap` 被调用（看 spdlog 日志中是否有 `注册外部地图` 消息） |
| 4. 对接点存在 | 目标地图中是否存在 `self_id == 源触发器.target_id` 的对接触发器？ | 在目标 `.tmj` 中找 `map_trigger` 对象，核对其 `self_id` 值。如果对接触发器不存在，`commitPendingTransition` 会退回到 `fallback_spawn_pos` |
| 5. 落点安全 | 玩家出生点是否被碰撞体挡住？ | 看日志中是否有 `目标出生点阻塞，寻找附近安全位置` 或 `未能在附近找到安全位置` 消息；检查目标触发器周围是否有 SOLID 瓦片 |
| 6. Debug UI | 切图后 `current_map_id / name / in_world` 是否符合预期？ | 打开 Debug UI → Map Inspector 面板，特别关注 `in_world` 字段——external map 应该显示 `false` |

## 7) 课后作业

### 作业 1：触发器判定从"点 inside"升级为"collider overlap"（Correctness）
- **现状**：`handleTriggerTransition()` 用 `Rect::contains(pos)` 做点判定——只看玩家 transform 的原点是否在触发器 rect 内。
- **问题**：玩家的原点通常在脚底中心，而触发器区域可能比较小。玩家的身体（collider）已经明显覆盖触发区域了，但原点还没进去，视觉上会感觉"明明碰到了却没反应"。
- **目标**：改为用玩家 collider 的 bounds 与 trigger rect 做 overlap 判定。
- **验收标准**：
  - 玩家 collider bounds 与 trigger rect 有重叠时即可触发（不要求原点进入）
  - 仅修改触发判定逻辑，不改变 trigger schema（Tiled 侧的 properties 不变）
- **提示线索**：
  - `src/game/system/map_transition_system.cpp` — `handleTriggerTransition()` 中的 `rect.contains(pos)` 判定
  - `src/engine/component/collider_component.h` — `AABBCollider` / `CircleCollider` 的 `offset_` 和 `size_` / `radius_` 字段
  - 可参考同文件中 `handleEdgeTransition()` 如何从 collider 提取 `bounds_min / bounds_max`

### 作业 2（可选）：触发器空间索引（Performance）
- **现状**：每帧线性遍历 registry 中全部 `MapTrigger` 组件做判定。当地图里有大量触发器时，这是 O(n) 的开销。
- **目标**：把触发器注册进空间索引，改为"查玩家所在 tile 附近的触发器"。
- **验收标准**：
  - 功能行为不变（触发条件与落点计算结果一致）
  - 能在 Debug 日志或面板中观察到"查询范围"显著缩小
- **提示线索**：
  - `src/engine/spatial/spatial_index_manager.*` — 静态网格的查询能力
  - `src/game/loader/entity_builder.cpp` — 可参考 `buildRestArea()` 中 `registerRectToStaticGrid` 的注册方式
  - `src/game/system/map_transition_system.cpp` — 将遍历 `view<MapTrigger>` 替换为空间查询

## 8) 小结

这节课的要点：

- **`.world` 文件**提供世界布局输入，`WorldState` 把它变成可查询的世界图（`MapInfo` + 邻接 + 触发器）
- **`map_trigger`** 通过配对的 `self_id / target_id` + `start_offset` 实现跨地图双向连接，external map 通过 `ensureExternalMap` 按需注册
- **`MapTransitionSystem`** 统一了两类切图（边缘 / 触发器），最终都汇入"加载目标地图 + 安全落点 + 更新玩家与相机"的事务提交路径

下节课我们会把镜头拉近到 `MapManager` 内部：
- 地图卸载时的**快照（snapshot）**——为什么要在卸载前保存动态实体状态，以及如何恢复
- **预加载策略**如何利用 WorldState 提供的"邻接 + 触发器目标图"来决定提前加载哪些地图
- **离线推进**——玩家不在场时，其他地图的世界变化（比如作物生长）如何被补偿
- 这些都依赖于本节建立的"世界级信息"——没有 WorldState，MapManager 就是一个只知道"加载文件"的工具，无法做任何智能化的优化
