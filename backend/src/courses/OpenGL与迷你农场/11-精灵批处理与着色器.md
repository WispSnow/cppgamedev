# 精灵批处理与着色器：批处理、纹理/UV 与像素风渲染要点

上节课我们理清了渲染系统的两层架构：`Renderer`（外观层）负责提供简单的绘图接口，`GLRenderer`（OpenGL 后端）负责多 pass 管线和视口适配。核心结论是——**先在固定的逻辑分辨率 FBO 里画世界，再把结果合成到窗口 viewport**，坐标系与输入都对齐到 logical。

但它回避了两个"再往下一层"的问题：

1. 当一帧要画几百个精灵时，GPU 那边到底发生了什么？为什么"画得多"不一定慢，而"提交得多"反而会卡？
2. 像素风游戏里，那些常见的"边缘抖动、画面发糊"是怎么来的？逻辑分辨率只是答案的一部分，还需要什么？

这节课我们就来解决这两个问题。

## 本节目标与问题定义

先建立一个实用直觉——2D 渲染的成本可以粗略拆成两部分：

| 成本类型 | 消耗 | 受什么影响 |
| --- | --- | --- |
| **CPU 提交成本** | 每次 `glDraw*` 调用、纹理绑定、uniform 更新都有固定开销 | draw call 数量 |
| **GPU 像素成本** | 屏幕上要处理多少像素、跑多少后处理/光照 pass | 分辨率与 pass 数 |

对于《迷你农场》这种 2D 像素风游戏来说，GPU 像素成本通常不是瓶颈——真正容易踩到的是 **CPU 提交成本**。如果每个精灵都单独发一条绘制命令，几百个精灵就是几百次 draw call，帧时间很快就会被 CPU 侧的驱动开销吃掉。

本节课聚焦在四个环环相扣的主题：

1. **SpriteBatch（批处理）**：如何把几百次绘制命令压缩到少数几次
2. **Shader**：批处理命令到了 GPU 之后，vertex/fragment shader 具体做了什么
3. **UV 与图集**：`src_rect`（像素矩形）怎么变成 shader 能用的 UV 坐标，以及为什么"图集"能进一步减少 draw call
4. **像素风画面稳定性**：NEAREST 采样、Pixel Snap 与逻辑分辨率如何协同避免抖动与糊边

这四个主题之所以放在同一节课，是因为它们构成一条完整的数据链路：上层系统提交精灵 → SpriteBatch 收集并生成绘制命令 → Shader 在 GPU 上执行顶点变换与纹理采样 → 采样参数（NEAREST/Pixel Snap）决定最终画面是否"像素完美"。

> 建议先把两份项目级速查文档过一遍（会在本节反复引用）：
> - `docs/rendering.md`（第 7 节 SpriteBatch/UV/Pixel Snap 速查）
> - `docs/resolution_and_viewport.md`（逻辑分辨率与坐标系）

## 核心概念

### Draw Call：你真正要减少的是什么？

一个非常实用的直觉：

> 2D 渲染慢，很多时候不是"画太多像素"，而是"提交太多次绘制命令"。

在 OpenGL 里，一次 `glDrawElements` 就是一条 draw call。但 draw call 本身并不贵——贵的是它**伴随的状态切换**：

- **绑定纹理**（`glBindTexture`）：告诉 GPU "接下来的三角形用这张图"
- **更新 uniform**（例如 `uViewProj`、颜色、开关）：把 CPU 侧数据传给 shader
- **切换混合模式/帧缓冲**等渲染状态

每一次状态切换都涉及 CPU 与驱动的交互。单独一次几乎感觉不到，但如果一帧有 500 个精灵、每个精灵都单独绑定纹理再 draw 一次——500 次状态切换叠加起来，就能明显拖慢帧时间。

所以我们真正要减少的不只是"draw call 数"，而是 **draw call 及其伴随的状态切换总次数**。

### SpriteBatch：批处理能做什么，不能做什么？

思路很直觉——既然"每个精灵单独提交"太贵，那我们就**先在 CPU 侧把一帧的精灵攒起来，最后一次性提交给 GPU**。这就是 SpriteBatch 的核心职责。

《迷你农场》的 SpriteBatch（`src/engine/render/opengl/sprite_batch.*`）分两步工作：

**第一步：入队（queue）**

每当上层系统要画一个精灵，SpriteBatch 就在 CPU 侧的缓冲区里追加一组数据：
- **4 个顶点**（Vertex）：每个顶点包含位置（`pos_`）、纹理坐标（`uv_`）、颜色（`color_`），构成一个矩形 quad
- **6 个索引**：把 4 个顶点拆成 2 个三角形（GPU 只能画三角形）

同时，SpriteBatch 维护一个 **命令列表**（`commands_`）。入队时它会检查：如果这个精灵的纹理和上一个命令用的纹理相同，就直接把上一条命令的 `index_count` 加 6（合并）；否则新建一条命令。

**第二步：提交（flush）**

一帧结束时，SpriteBatch 把攒好的顶点和索引**一次性上传到 GPU**（通过 `glBufferSubData`），然后遍历命令列表——每条命令绑定一次纹理、调用一次 `glDrawElements`。

用思路版伪代码表达：

```text
queueSprite(texture, dest_rect, uv_rect, color):
  append 4 vertices + 6 indices to CPU buffer
  if last command uses same texture:
    last_command.index_count += 6        // 合并！不产生新 draw call
  else:
    push new command(texture, index_offset, index_count=6)

flush():
  upload all vertices/indices to GPU (one glBufferSubData)
  for each command (in order):
    glBindTexture(command.texture)       // 纹理切换
    glDrawElements(command.index_offset, command.index_count)  // draw call
```

你会发现：**draw call 数 = 命令数 ≈ 纹理切换段数**。如果连续 100 个精灵都来自同一张纹理，它们只产生 1 条命令、1 次 draw call。

**关键边界（一定要记住）：**

> SpriteBatch **不能**为了减少 draw call 而随意重排精灵顺序。

为什么？因为精灵的提交顺序就是渲染顺序——先提交的画在下面，后提交的画在上面。如果为了让"同一纹理的精灵连续"而重新排列它们，遮挡关系就会乱掉（人物跑到建筑后面去了）。

所以 SpriteBatch 只能做"**局部合并**"：连续使用同一纹理的精灵合成一条命令。它无法做全局按纹理分桶排序——那是图集（atlas）要解决的问题，我们稍后会讲。

### Shader：Sprite Shader 在做什么？

SpriteBatch 把顶点数据交给了 GPU，GPU 怎么知道该拿这些数据画出什么？答案是 **shader**。

你可以把 shader 理解成"运行在 GPU 上的小函数"，分两阶段执行：

1. **Vertex Shader**（`assets/shaders/quad.vert`）：对每个顶点执行一次。它的工作是把顶点坐标从世界/屏幕空间变换到裁剪空间（NDC），同时把 UV 和颜色传递给下一阶段。

2. **Fragment Shader**（`assets/shaders/texture.frag`）：对最终画面上的每个像素执行一次。它根据插值后的 UV 坐标去纹理上采样颜色，再和顶点色相乘，输出最终的像素颜色。

《迷你农场》的 sprite shader 接口很简洁：

| 角色 | 名称 | 说明 |
| --- | --- | --- |
| 顶点输入 | `aPos` (vec2) | 精灵顶点在世界/屏幕空间的位置 |
| 顶点输入 | `aUV` (vec2) | 该顶点对应的纹理坐标 |
| 顶点输入 | `aColor` (vec4) | 顶点颜色（用于着色/透明度） |
| Uniform | `uViewProj` (mat4) | 相机的视图-投影矩阵 |
| Uniform | `uTex` (sampler2D) | 当前绑定的纹理 |
| Uniform | `uUseTexture` (int) | 是否采样纹理（0=纯色，1=纹理） |
| 输出 | `FragColor` (vec4) | 最终像素颜色 = 纹理色 × 顶点色 |

注意 `uUseTexture` 这个开关：当它为 0 时，shader 不采样纹理，直接用顶点色输出——这用于绘制纯色矩形（比如碰撞盒的调试线框）。当它为 1 时，`FragColor = texture(uTex, vUV) * vColor`——纹理色和顶点色相乘，这就是 2D 游戏里"着色/Tint"效果的原理。

<img src="https://theorhythm.top/gamedev/TF/L09_shader_interface.webp" style='width: 960px;' />

**Shader 与 SpriteBatch 的配合关系：**

SpriteBatch 在 `flush()` 时，会先激活 shader program，设置好 `uViewProj` 和 `uTex` 等 uniform，然后逐条执行命令。每条命令对应一次 `glBindTexture` + `glDrawElements`，GPU 就用当前绑定的纹理和 shader 来处理该命令覆盖的那批顶点。

shader 程序本身由 `ShaderProgram`（`src/engine/render/opengl/shader_program.*`）封装编译/链接逻辑，`ShaderLibrary`（`src/engine/render/opengl/shader_library.*`）负责缓存与复用——你不需要每帧重新编译 shader，而且还支持开发期热重载（练习 1 会用到）。

### `src_rect(像素) → uv(0..1)`：图集裁剪的核心

现在你知道 shader 会用 UV 坐标去纹理上采样。但在游戏的资源层，我们习惯用**像素矩形**（`src_rect`）来表达"这个精灵在大纹理里的哪块区域"——比如"从 (32, 64) 开始，宽 16 高 16 像素"。

这两种表达方式之间需要一步转换。原理很简单：**把像素坐标除以纹理的宽高，就得到了 0..1 范围的 UV 坐标。**

```text
u0 = x / texWidth       v0 = y / texHeight
u1 = (x + w) / texWidth v1 = (y + h) / texHeight
```

在代码里，这个转换由 `Renderer::getSrcRectUV()` 完成（`src/engine/render/renderer.cpp`）：

```cpp
// 简化示意
glm::vec4 getSrcRectUV(const GL_Texture& texture, const Rect& src_rect) {
    return {
        src_rect.pos.x / texture.width,                      // u_min
        src_rect.pos.y / texture.height,                     // v_min
        (src_rect.pos.x + src_rect.size.x) / texture.width,  // u_max
        (src_rect.pos.y + src_rect.size.y) / texture.height   // v_max
    };
}
```

理解了这一步，**图集（atlas）的收益就很清晰了**：

> 一张图集把多个精灵拼在同一张 OpenGL 纹理上。不同精灵只是 `uv_rect` 不同，但它们共用同一个 `texture`。
>
> 对 SpriteBatch 来说，连续绘制同一图集里的精灵，纹理不切换，命令就能合并——draw call 自然就少了。

举个例子：假设农场里有 50 棵不同状态的作物，它们的精灵全部来自同一张作物图集。如果这 50 棵作物恰好是连续提交的，SpriteBatch 就只需要 **1 条命令**，而不是 50 条。

反过来，如果这 50 棵作物的精灵分散在 5 张不同的纹理上，即使 SpriteBatch 再怎么优化，也不可能把它们合并到一次 draw call 里。所以**资源组织方式（是否使用图集）直接影响批处理效率**。

> 选读线索：文字渲染同样是这套路——`FontManager` 把字形渲染到一张 glyph atlas 上，`TextRenderer` 通过 UV 裁剪取出每个字符。原理和精灵图集完全一致。

### 像素风画面稳定性：NEAREST + Pixel Snap + 逻辑分辨率

性能问题解决了，接下来看画面质量。像素风游戏有一个特殊的"画面标准"：**每个像素应该是一个边界清晰、大小一致的色块**。一旦出现像素边缘发糊、大小不均匀、或者相机移动时闪烁/抖动，玩家马上就会感觉"不对劲"。

这类画面瑕疵几乎都来自同一个根源：**子像素采样**——也就是说，采样点落在了两个纹素（texel）的交界处，硬件不知道该用哪个像素的颜色。

《迷你农场》用三个手段协同解决这个问题：

**1. 纹理默认 NEAREST 采样（`TextureManager`）**

`TextureManager` 在加载纹理时，默认设置 `GL_NEAREST`：

```cpp
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_S, GL_CLAMP_TO_EDGE);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_T, GL_CLAMP_TO_EDGE);
```

- `GL_NEAREST`：采样时直接取最近的那个纹素，不做任何混合。这保证了每个像素都是"硬边界"，不会出现相邻像素颜色混在一起的"糊边"。
- `GL_CLAMP_TO_EDGE`：当 UV 落在纹理边界外时，重复边缘像素而不是环绕。这避免了图集中相邻精灵颜色"渗"进来。

如果你把采样模式换成 `GL_LINEAR`（线性插值），像素风画面会立刻变糊——因为线性采样会把相邻纹素的颜色按距离加权混合。这对照片级图形是好事，但对像素风是灾难。

**2. Pixel Snap：相机像素对齐（`GLRenderer`）**

即使用了 NEAREST 采样，如果相机位置不是整数像素，精灵的屏幕坐标也会落在半像素上——这时采样点可能在相邻两帧间跳来跳去，表现为"闪烁/抖动"。

Pixel Snap 的做法是：**在构建相机矩阵时，把相机平移量对齐到最近的像素边界**。这样屏幕上每个纹素都恰好对应一个逻辑像素，不会出现"跨越两个像素"的情况。

在调试面板里（`F5` → `Engine Debug Panels` → `OpenGL Renderer`），你可以用 `Pixel Snap` 复选框切换这个开关，**慢慢移动相机对比开/关的效果**——开着时画面稳如磐石，关掉后仔细看边缘就能看到抖动。

**3. 逻辑分辨率（[Renderer 与 GLRenderer](10-Renderer%20与%20GLRenderer.md)）**

上节课讲的逻辑分辨率也是"像素稳定性"链条的一环：在低分辨率的逻辑空间里渲染，然后整体放大到窗口——放大倍数如果是整数（比如 ×2、×3），每个逻辑像素恰好映射到 2×2 或 3×3 个屏幕像素，大小完全均匀。

**三者缺一不可：**

| 只做了… | 会发生什么 |
| --- | --- |
| 只用 NEAREST，没有 Pixel Snap | 相机移动时边缘仍会抖动 |
| 只用 Pixel Snap，没有 NEAREST | 纹理边缘会糊/渗色 |
| 有采样和对齐，但没有逻辑分辨率 | 非整数缩放导致像素大小不均匀 |

这三个是"协同关系"：只做其中一项，通常不够稳定。

## 架构与数据流

### 从系统到 GPU：SpriteBatch 在哪里？

把前面讲的概念放回架构里，数据链路是这样的：

```
RenderSystem/TextRenderer/UI
        ↓ drawSprite / drawTexture
    Renderer（外观层）
        ↓ getSrcRectUV: src_rect → UV
    GLRenderer（后端）
        ↓ 分发到对应 pass
    ScenePass / UIPass / EmissivePass
        ↓ 每个 pass 持有一个 SpriteBatch
    SpriteBatch
        ↓ flush: glBindTexture + glDrawElements
    GPU（quad.vert → texture.frag）
```

<img src="https://theorhythm.top/gamedev/TF/L09_spritebatch_architecture.webp" style='width: 960px;' />

几个要点：

- **每个 Pass 有自己的 SpriteBatch**。ScenePass 在逻辑分辨率的 FBO 上渲染世界精灵；UIPass 在窗口 viewport 上渲染 UI 元素；EmissivePass 处理自发光精灵。它们各自独立收集、独立 flush。
- **UV 转换发生在 Renderer 层**（`getSrcRectUV()`），而不是在 SpriteBatch 里。SpriteBatch 收到的已经是归一化的 UV 坐标。
- **Pixel Snap 在 GLRenderer 层**，通过调整相机矩阵实现，对所有 pass 统一生效。

对应的源码线索：

| 职责 | 文件 |
| --- | --- |
| ScenePass（世界渲染） | `src/engine/render/opengl/scene_pass.*` |
| UIPass（UI 渲染） | `src/engine/render/opengl/ui_pass.*` |
| EmissivePass（自发光） | `src/engine/render/opengl/emissive_pass.*` |
| SpriteBatch 批处理核心 | `src/engine/render/opengl/sprite_batch.*` |
| Sprite Shader | `assets/shaders/quad.vert` + `assets/shaders/texture.frag` |

### 怎么"看见批处理"？用 Pass Stats 建立直觉

这节课强烈建议你把调试面板当作"性能直觉训练器"。

**操作路径：**`F5` → `Engine Debug Panels` → `OpenGL Renderer` → `Pass Stats`

面板里有几个关键数字：

| 指标 | 含义 | 关注什么 |
| --- | --- | --- |
| `Sprites` | 本帧提交的精灵数（quad 数） | 场景复杂度 |
| `Vertices` | ≈ `Sprites × 4` | 数据量 |
| `Indices` | ≈ `Sprites × 6` | 数据量 |
| `Draw Calls` | 该 pass 实际执行的 `glDrawElements` 次数 | **核心指标** |

**怎么判断 batching 是否健康？**

- `Sprites` 很大、`Draw Calls` 很小 → 大量精灵被合并到少数几条命令里，batching 效率很高
- `Draw Calls` 接近 `Sprites` → 几乎每个精灵都触发了一次纹理切换，说明资源组织可能需要调整（考虑使用图集或调整渲染排序）

**动手试试：** 在游戏中走到不同区域，观察 `Scene` pass 的 `Sprites` 和 `Draw Calls` 变化。你会发现，在使用大量同图集素材的区域（比如农田），`Draw Calls` 远小于 `Sprites`；而在混合使用不同纹理的区域，`Draw Calls` 会上升。

## 练习

### 练习 1：实现 Shader 热重载入口

> 目的：把 shader/library/pass 的 reload 能力串成"能用的开发体验"，并巩固你对 shader 生命周期的理解。

- 目标：
  - 在 `OpenGL Renderer` 调试面板中加入按钮（例如 `Reload Sprite Shaders`）。
  - 点击后重载渲染用 shader（覆盖 `ScenePass/UIPass` 使用的 sprite program，以及 `EmissivePass` 使用的 emissive program）。
- 验收标准（满足 3 项即可）：
  - 点击按钮不会崩溃；成功时新的 shader 立即生效
  - 失败时输出清晰错误信息（日志或面板提示），并保持旧 shader 继续工作
  - 不引入新的第三方依赖，不破坏现有测试
- 提示线索（模块/文件）：

## 小结 + 下节课预告

回顾一下本节课的核心链路：

1. **SpriteBatch** 在 CPU 侧把一帧的精灵攒成顶点/索引缓冲，按"连续纹理段"生成命令，一次性提交给 GPU——draw call 数 ≈ 纹理切换段数，而不是精灵数。但它不能为了合并而破坏渲染顺序。
2. **Shader** 是 GPU 上真正执行渲染的函数：vertex shader 做坐标变换，fragment shader 做纹理采样。《迷你农场》的 sprite shader 接口只有 `aPos/aUV/aColor` + `uViewProj/uTex/uUseTexture`，非常精简。
3. **UV 与图集** 是连接"资源描述"和"GPU 采样"的桥梁。`src_rect` 除以纹理尺寸得到 UV；图集把多个精灵放在同一张纹理上，从源头减少纹理切换。
4. **像素风画面稳定性** 依赖三者协同：`GL_NEAREST` 保证硬边界不糊、`GL_CLAMP_TO_EDGE` 防止边缘渗色、Pixel Snap 保证相机对齐、逻辑分辨率保证缩放均匀。缺一项就可能出现抖动或瑕疵。

下节课（光照与后处理）我们进入"画面效果的管线化"——Lighting/Emissive/Bloom/Composite 这些后处理 pass 是如何串成多通道流水线的，以及这些效果的开关在架构里应该放在哪里。
