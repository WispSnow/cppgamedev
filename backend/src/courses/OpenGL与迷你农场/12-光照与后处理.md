# 光照与后处理：Lighting/Emissive/Bloom/Composite 的流水线

上两节课我们把 2D 渲染从"能画出来"推进到了"画得高效、画得稳定"：

1. **逻辑分辨率 + letterbox viewport**（[Renderer 与 GLRenderer](10-Renderer%20与%20GLRenderer.md)）：先在固定 logical size 的 FBO 里画世界，再把结果等比合成到窗口 viewport。坐标系只有三套：世界空间（随相机）、逻辑空间（离屏 FBO）、窗口像素空间（最终显示）。
2. **SpriteBatch + Pass Stats**（[精灵批处理与着色器](11-精灵批处理与着色器.md)）：批处理把几百个精灵压缩到少数几次 draw call，成本瓶颈在"CPU 提交"而非"GPU 像素"。调试面板里的 Pass Stats 是你的"性能直觉训练器"。

但到目前为止，我们的画面还是"平的"——没有光影变化，没有发光物体的柔和光晕，白天和黑夜看起来一模一样。

这节课我们把视角往上抬一层：**当"场景渲染"不再是唯一的输出，我们需要把 Lighting / Emissive / Bloom / Composite 串成一个可维护、可调参、可观测的流水线。**

## 本节目标与问题定义

核心问题可以用一句话概括：

> 在不破坏现有 2D 渲染闭环（RenderSystem + SpriteBatch）的前提下，引入"多 pass 离屏渲染 + 合成"的后端管线，让游戏拥有可控的光照与后处理效果，并能通过调试面板验证效果与成本。

在《迷你农场》里，我们希望看到这些变化：
- 画面有**环境光（Ambient）** + **方向光（Directional）**，随昼夜自然过渡
- 场景里有**点光（Point）** 和 **聚光（Spot）**——路灯、光圈、火把
- 有些物体是**自发光（Emissive）**——夜晚窗户的暖光、魔法物件的辉光
- 自发光能触发 **Bloom（泛光）**——模糊扩散形成柔和光晕
- 最终结果通过 **Composite** 合成，仍保持 [Renderer 与 GLRenderer](10-Renderer%20与%20GLRenderer.md) 的 viewport/letterbox 规则

同时，这套东西还要满足工程化约束：
- 上层系统只调用 `Renderer` 的高层 API，**不需要知道 OpenGL / FBO / shader**
- 每个 pass 的"输入 / 输出 / 坐标空间 / 混合方式"**清晰可说**
- 调试面板能快速验证：哪个开关影响画面？哪个 pass 产生了成本？

## 核心概念

### 多 pass：把渲染当作"生产者 → 消费者"

上节课我们只关心一个 ScenePass——SpriteBatch 把精灵画到 FBO，然后合成到窗口。现在多了光照和后处理，画面不再是"一步出图"，而是**多步接力**。

最好的心智模型不是"这帧画了什么"，而是"**这帧生产了哪些纹理**"：

| Pass | 产出 | 用一句话描述 |
| --- | --- | --- |
| **ScenePass** | `scene_color_tex` | 世界里所有精灵的基础画面（"没有光照的白天"） |
| **LightingPass** | `light_color_tex` | 所有光源贡献的累加结果（"光照遮罩"） |
| **EmissivePass** | `emissive_color_tex` | 自发光物体的颜色和强度（"哪里在发光"） |
| **BloomPass** | `bloom_tex` | 对发光纹理做模糊后的光晕（"光晕有多散"） |
| **CompositePass** | 最终 backbuffer | 把上面四张纹理 + 环境光合在一起（"最终画面"） |

把它画成一张数据流图：

<img src="https://theorhythm.top/gamedev/TF/L10_pipeline_dataflow.webp" style='width: 960px;' />

这张图里最关键的"工程化点"是：

> **逻辑坐标空间（Logical）** 是离屏渲染的统一尺寸；
> **窗口像素空间（Window Pixels）** 只在最后合成 / 绘制 UI / ImGui 时使用。

前四个 pass 都在逻辑分辨率的 FBO 里渲染——这意味着它们的分辨率不随窗口大小变化，保证了画面一致性。CompositePass 才把结果"投射"到窗口的 letterbox viewport 里。

### Pass 的职责：清晰分工比"省一步"更重要

很多同学会问：能不能把 Lighting / Emissive / Bloom 全塞进一个 shader？

理论上可以，但工程上不推荐。拆 pass 的收益通常是：
- **逻辑更清楚**：每个 pass 只回答一个问题（画场景 / 累加光照 / 生成发光遮罩 / 做后处理 / 做最终合成）
- **易调试**：你能单独看某一张中间纹理（本项目直接在 DebugPanel 的 Pass Preview 里预览）
- **易扩展**：后续加雾效、颜色分级、遮罩等，往往就是加一个 pass

《迷你农场》的分层很清晰：
- `Renderer`：**外观层（Facade）**，上层系统只依赖它
- `GLRenderer`：**后端编排（Pipeline Orchestration）**，在 `present()` 里按顺序串起所有 pass
- `ScenePass / LightingPass / EmissivePass / BloomPass / CompositePass / UIPass`：**各司其职**

这和 [精灵批处理与着色器](11-精灵批处理与着色器.md) 讲的"每个 Pass 持有自己的 SpriteBatch"是一脉相承的——只不过 LightingPass 和 BloomPass 不用 SpriteBatch，而是各自有自己的 shader 和绘制逻辑。

### 混合（Blending）：为什么 Lighting 和 Emissive 常用"加法"

理解了多 pass 之后，一个自然的问题是：**这些纹理最后怎么"合"在一起？**

2D 光照最常见的思路是：**把光当作一张"亮度 / 颜色遮罩"**，然后在合成时把它乘回场景。

在《迷你农场》的管线里：
- **LightingPass**：每个光源画一个 quad，贡献用**加法混合**（`GL_ONE + GL_ONE`）累加到同一张纹理上。直觉是——两盏灯照在同一个点，亮度就是两盏灯的贡献之和。
- **EmissivePass**：自发光物体也是**加法混合**（`GL_SRC_ALPHA + GL_ONE`），效果类似——多个发光体重叠时，亮度叠加。
- **CompositePass**：消费所有纹理，按公式合成最终画面。

CompositePass 的核心公式（`assets/shaders/composite.frag`）：

```glsl
vec3 light = clamp(light_tex + uAmbient, 0.0, 1.0);
final_color = scene * light + emissive + bloom * uBloomStrength;
```

几个值得停下来看清楚的点：

- **`uAmbient`（环境光颜色）在这里才加入**——它不是 LightingPass 产出的一部分，而是 CompositePass 的独立 uniform。这让你可以在不重新渲染光照的前提下，单独调环境光亮度。
- **`clamp` 防止光照过曝**——light + ambient > 1 时截断到 1。如果没有这步，阳光下叠加路灯会出现"刺白"。
- **`uBloomStrength` 控制泛光叠加比例**——拉到 0 就等于关掉 Bloom 的视觉贡献，但 Bloom 管线仍在运行（除非你同时关掉 Bloom 开关）。
- **`scene * light`**——乘法意味着"没有光的地方是黑的"。光照遮罩为 0 的区域，不管场景画了什么都不可见。这就是为什么环境光（ambient）很重要——它保证即使没有任何光源，画面也不会全黑。

> **常见困惑**：为什么 emissive 是"加法"而不是"乘法"？因为自发光物体的特点是——**即使完全没有外部光照，它自己也能发光**。所以 emissive 独立于 `scene * light`，直接叠加到最终画面上。

还有一个容易忽略的工程细节：CompositePass 在初始化时会创建 1×1 的**默认纹理**——白色纹理作为 `light_tex` 的默认值（"全亮"），黑色纹理作为 `emissive_tex` 和 `bloom_tex` 的默认值（"不发光"）。这样即使上层没有提交任何光源或发光物体，shader 也不会因为纹理为空而崩溃或出现黑屏。

### 坐标空间：世界是 world，离屏是 logical，合成是 viewport

这节课最容易混淆的不是"有没有光"，而是"**这个 pass 在什么坐标系里画 quad**"。

把每个 pass 的坐标空间写成一张表：

<img src="https://theorhythm.top/gamedev/TF/L10_coordinate_spaces.webp" style='width: 960px;' />

其中最值得点名的细节是**方向光的特殊处理**：

- **点光 / 聚光** 是"世界里的一个范围"——光源有位置、有半径，quad 的顶点在**世界空间**构建，通过相机的 `view-projection` 矩阵投影到屏幕上。当相机移动时，光自然跟着世界移动。
- **方向光** 更像"从某个方向照过来的一层渐变"——它不属于世界中的某个点，而是影响整个画面。如果你也用世界空间 quad，那相机移动时渐变方向会跟着偏移，"太阳"看起来就像黏在地面上而不是挂在天上。

所以方向光在实现上使用了一个巧妙的做法：**临时切换到屏幕空间正交投影**，画一个覆盖整个 viewport 的全屏 quad。渲染完方向光之后，再恢复相机的 view-projection 矩阵继续处理点光和聚光。你可以在 `LightingPass::flush()` 中看到这个"投影切换"的代码。

> **常见陷阱**：如果你忘记在方向光渲染后恢复相机矩阵，后续的点光 / 聚光会全部画在屏幕空间而不是世界空间——表现是"灯光不随相机移动"。

### Bloom：为什么要降采样？为什么要 ping-pong？

Bloom 的直觉是：

> 把"亮的区域"做模糊，然后再叠回去，让亮的东西产生柔和光晕。

但如果你直接在全分辨率做大半径高斯模糊，会非常贵——13-tap 的模糊核在 1280×720 的纹理上跑一遍就是近百万次采样。

常见的工程解是**降采样金字塔**：
1. **降采样（downsample）**：生成多级更小的纹理（1/2、1/4、1/8、1/16）
2. **在小纹理上做模糊**：分辨率低了，采样次数自然少了，但视觉上模糊范围却更大（因为每个纹素覆盖了更大的画面面积）
3. **逐级上采样并叠加（upsample + accumulate）**：从最小级开始，逐级放大并加法叠回上一级，形成层次感的光晕

而 **ping-pong** 的意义是：高斯模糊可以分解为"水平模糊 + 垂直模糊"两步（可分离性），但每一步都需要"读 A 写 B"——你不能同时读写同一张纹理。所以需要两组 FBO（ping 和 pong），在它们之间来回切换：

```text
for each level:
  blurHorizontal(src → ping)    // 读源纹理/上一级，写 ping
  blurVertical(ping → pong)     // 读 ping，写 pong

upsampleAndAccumulate:           // 从最小级 pong 逐级向上叠加
  for i = LEVELS-1 downto 1:
    additive_blit(pong[i] → pong[i-1])

bloom_tex = pong[0]
```

《迷你农场》使用 4 级降采样（`BLOOM_LEVELS = 4`），所以 Bloom 的总 draw call 约为 8（每级 2 次模糊）+ 3（上采样叠加）= 11 次。

Bloom 的层级示意：

<img src="https://theorhythm.top/gamedev/TF/L10_bloom_pyramid.webp" style='width: 960px;' />

**工程补充**：《迷你农场》在**没有任何发光提交时会跳过整个 Bloom 管线**——避免每帧白白做降采样与模糊。你可以在 Pass Stats 里验证：无发光物体时 Bloom 的 draw call 应该为 0。

**另一个值得注意的细节**：EmissivePass 的 FBO 使用 **RGBA16F**（16 位浮点），而不是普通的 RGBA8。这是因为自发光的强度值可以超过 1.0（比如一个 intensity = 3.0 的光源），如果用 8 位整数存储就会被截断到 1.0，后续 Bloom 就提取不到"特别亮"的区域了。而 LightingPass 用的是 **RGB8**——光照累加不需要 alpha 通道，也不需要超过 1.0 的范围（clamp 在合成公式里完成）。

本课你不需要背具体公式，记住三个关键词就够了：**downsample / ping-pong / sigma（模糊半径）**。

## 架构与数据流

### 从 ECS 到 GPU：灯光数据如何一路"流"到 shader

《迷你农场》的光照不是在渲染层"凭空出现"的，它来自 ECS——灯光和发光都是**挂在实体上的组件**。

数据流分三段：

**第一段：ECS 组件持有灯光数据**

| 组件 | 存储什么 | 典型用途 |
| --- | --- | --- |
| `PointLightComponent` | 半径、偏移、颜色、强度 | 路灯、火把、营火 |
| `SpotLightComponent` | 半径、方向、内/外锥角、颜色、强度 | 探照灯、手电筒 |
| `EmissiveRectComponent` | 矩形尺寸、强度、颜色 | 发光窗户、光板 |
| `EmissiveSpriteComponent` | 引用实体的 Sprite + Transform、强度、颜色 | 魔法物品、发光标记 |

全局光照（环境光 + 方向光）则存储在 `registry.ctx<GlobalLightingState>()` 中——这是一个共享上下文对象，不挂在任何实体上，任何系统都可以读写。`GlobalLightingState` 包含一个 `ambient` 颜色和一个以哈希 ID 为键的方向光字典（太阳和月亮各有一个条目）。

**第二段：系统收集数据并提交给 Renderer**

`LightSystem`（引擎层）在每帧的**渲染阶段**被调用，它做三件事：
1. 从 `GlobalLightingState` 读取环境光，调用 `renderer.setAmbient()`
2. 遍历所有启用的方向光，调用 `renderer.addDirectionalLight()`
3. 遍历所有带灯光组件的实体（排除 `InvisibleTag` 和 `LightDisabledTag`），逐个调用 `renderer.addPointLight()` / `addSpotLight()` / `addEmissiveRect()` / `addEmissiveSprite()`

这里有一个细节值得注意：**Renderer 在提交光源时会做视锥剔除（culling）**——如果一个点光的范围完全在相机视野之外，就直接跳过，不发送给 GPU。这对大地图上有大量光源的场景很重要。

**第三段：GLRenderer 把数据分发给对应的 Pass**

`GLRenderer` 内部维护了 `LightingPass`（点光/聚光/方向光的 command 列表）和 `EmissivePass`（通过 SpriteBatch 收集发光 sprite/rect）。当 `present()` 被调用时，各 pass 按顺序 flush 自己的命令。

模块流向图：

<img src="https://theorhythm.top/gamedev/TF/L10_ecs_to_gpu.webp" style='width: 960px;' />

你会发现：**上层系统只关心"我要一个点光 / 我要一个发光精灵"，不关心"它最终通过哪个 shader 写入哪张纹理"。** 这就是 Renderer 外观层的价值——它在 [Renderer 与 GLRenderer](10-Renderer%20与%20GLRenderer.md) 里管理的是"画精灵"的接口，这节课扩展到了"提交灯光"的接口，但上层系统的使用方式完全一致。

### 昼夜系统：时间如何驱动光照变化

灯光数据不只是"静态挂在实体上"——《迷你农场》有一个完整的昼夜驱动链路，让光照随游戏时间自然变化。

**DayNightSystem**（游戏层）在每帧的**更新阶段**执行：
1. 从 `GameTime` 读取当前小时（带分钟小数，如 14.5 = 下午两点半，保证过渡平滑而非整点跳变）
2. 根据 `light_config.json` 中的日出（5:00–7:00）/ 日落（17:00–19:00）过渡时间段，用 `smoothstep` 计算太阳和月亮的淡入淡出系数
3. 从配置的环境光关键帧中插值出当前的环境光颜色——凌晨偏暗蓝 `(0.08, 0.08, 0.12)`、正午偏亮灰、傍晚偏暖橙
4. 计算太阳方向——基于归一化时间的三角函数：6 点在东方、12 点在正上方、18 点在西方
5. 把所有结果写入 `registry.ctx<GlobalLightingState>()`

所有的光照参数——日出日落时间、太阳颜色、月亮颜色（冷蓝色 `(0.65, 0.7, 0.9)`，强度 0.2）、环境光关键帧——全部来自 `assets/data/light_config.json`。改配置就能改效果，不用碰代码。

**TimeOfDayLightSystem**（游戏层）则处理"哪些灯光只在特定时段生效"：
- 带 `NightOnlyTag` 的实体（如路灯、窗户灯）只在"黑暗时段"（默认 18:00–6:00）启用
- 带 `DayOnlyTag` 的实体只在白天启用
- 实现方式很直接：根据 `GameTime.isDarkForEmissives()` 的结果，给实体添加或移除 `LightDisabledTag`
- 如果一个实体同时带了 `NightOnlyTag` 和 `DayOnlyTag`（逻辑冲突），系统会直接禁用它——这是一种防御性处理

> 注意 `InvisibleTag` 和 `LightDisabledTag` 的区别：`InvisibleTag` 让实体的**精灵和灯光都不渲染**（实体完全消失）；`LightDisabledTag` 只关闭灯光，**精灵仍然可见**——路灯的灯柱白天依然要看到，只是不发光而已。

这个设计有一个很好的测试性：`TimeOfDayLightSystem` 是纯逻辑系统——它只操作 Tag 组件，不涉及任何渲染 API。你可以在 `tests/game/time_of_day_light_system_test.cpp` 里看到这种"测试组件变化而不是测试画面"的思路。

### 一帧里发生了什么？（简化时序）

把更新阶段和渲染阶段串起来看，你会更容易理解"为什么先 RenderSystem 再 LightSystem"：

<img src="https://theorhythm.top/gamedev/TF/L10_frame_sequence.webp" style='width: 960px;' />

注意：这不是"严格代码调用栈"，而是帮助你建立心智模型：
**更新阶段产生数据（时间 → 光照参数），渲染阶段先提交精灵再提交灯光，后端在 present 时统一执行多 pass 管线。**

关键的顺序依赖：
- `TimeSystem` 必须在 `DayNightSystem` 之前——否则光照参数基于过期的时间
- `RenderSystem` 必须在 `LightSystem` 之前——ScenePass 的精灵要先收集好，LightingPass 才能正确渲染遮罩
- `present()` 在所有提交之后——这时所有 command / batch 都已经准备好，一次性执行管线

### 调试验证：把 DebugPanel 当作"效果 ↔ 成本"的仪表盘

这节课强烈建议你边读代码边开面板验证。

**操作路径：** `F5` → `Engine Debug Panels` → `OpenGL Renderer`

面板里几块区域各自解决不同问题：

| 区域 | 能做什么 | 解决什么问题 |
| --- | --- | --- |
| **Lighting** | 开关点光 / 聚光 / 方向光 / 发光 | 验证"某类光源有没有接上"，快速隔离问题 |
| **Ambient** | 调环境光颜色 | 验证合成公式，模拟不同时段的光照感受 |
| **Bloom** | 调 Strength / Sigma，开关 Bloom | 验证"泛光强度 vs 模糊范围 vs 性能开销"的关系 |
| **Pass Stats** | 看每个 pass 的 draw call / 顶点数 / 精灵数 | 建立"效果 ↔ 成本"的直觉 |
| **Pass Preview** | 直接预览 4 张中间纹理 | 确认"每个 pass 产出是什么"，定位渲染异常 |

**动手试试——三个实用的观察练习：**

1. **开关隔离**：把 Point Lights / Spot Lights / Directional Lights / Emissive 逐个关闭，观察画面变化和 Pass Stats 的 draw call 变化。你会发现方向光通常是"全屏一次绘制"，draw call 稳定在 1–2；而点光 / 聚光随实体数量变化。

2. **调参对比**：把 `Bloom Strength` 从 0 拉到 3.0，观察泛光从"几乎没有"到"过曝发白"的过渡。再把 `Blur Sigma` 从 2.0 拉到 10.0，看光晕从"紧凑"变成"弥漫整个画面"。回到 Pass Stats 确认：Bloom 的 draw call 数不随参数变化（它只取决于降采样级数），但极大的 sigma 在视觉上更"贵"——因为模糊核覆盖了更多纹素。

3. **昼夜驱动**：在 `Game Debug Panels` → `Game Time` 里手动拖动时间，观察：太阳方向光的渐变如何随时间偏移、环境光颜色如何从暖橙过渡到冷蓝、路灯的点光在 18:00 后亮起（`NightOnlyTag` 生效）。在 Pass Preview 里看 Light 纹理的变化——白天几乎全亮，夜晚只有光源覆盖区域是亮的。

## 小结

你现在应该能用几句话描述《迷你农场》的"光照与后处理流水线"：

1. **多 pass 的本质是多张纹理的生产与消费**：Scene / Light / Emissive / Bloom 是中间结果，Composite 把它们合成到最终画面。合成公式是 `scene * clamp(light + ambient) + emissive + bloom * strength`。
2. **数据从 ECS 流向 GPU**：灯光组件 → LightSystem 收集 → Renderer 外观层 → GLRenderer 分发给各 Pass → shader 执行。昼夜系统通过 `GlobalLightingState` 驱动环境光和方向光的变化，`NightOnlyTag / DayOnlyTag` 控制灯光的时段可见性。
3. **坐标空间是关键边界**：world（随相机）vs logical（离屏统一）vs viewport / window pixels（最终显示与 UI）。方向光用屏幕空间渲染，点光 / 聚光用世界空间渲染——这个区别容易被忽略。
4. **工程化的胜利来自可观测性**：面板能让你把"效果变化"和"成本变化"对应起来，而不是凭感觉调参。Bloom 在无发光提交时自动跳过，这种"按需执行"的思路值得在自己的项目中复用。
