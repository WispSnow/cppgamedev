# 2D 渲染最小闭环：Transform + Sprite + Render 排序

上节课我们把 TinyFarm 的 ECS 约定讲清了：**一个 Scene 一个 registry**，System 围绕 registry 读写组件与 Tag；Scene 栈遵循 **update(仅栈顶) / render(整个栈)** 的规则。

从这节课开始，我们把"ECS 的数据与系统"落到一个更直观的闭环上：**渲染**。你会看到：实体上的 `Transform/Sprite/Render` 三份数据，是如何被渲染系统取出、排序、提交，最终变成屏幕上的像素。

## 本节目标与问题定义

2D 渲染的难点通常不在于"能不能画出一个 Sprite"，而在于把它工程化成一套稳定约定：

- 一帧渲染从哪里开始、到哪里结束？（入口与边界）
- "要画什么/画到哪/按什么顺序画"分别由哪些数据与系统负责？
- 遮挡关系（YSort）在项目里是怎么实现的？有哪些常见坑？
- "隐藏"和"剔除"都是看不见，它们在工程上到底有什么区别？

本节目标是建立 TinyFarm 的 2D 渲染"最小闭环"心智模型：从 `GameApp::render()` 到 `Renderer::drawSprite()`，把链路串起来，并能在代码里快速定位对应模块。

## 核心概念

建议你把 `docs/rendering.md` 当作本节的"项目级约定说明书"。下面我们用更直观的方式把关键点串起来。

### 渲染最小闭环：Transform + Sprite + Render

在 TinyFarm 里，Sprite 渲染的最小数据组合是三份组件：

- `engine::component::TransformComponent`：**位姿数据**（`position_/scale_/rotation_`，旋转为弧度制）
- `engine::component::SpriteComponent`：**精灵数据**（纹理引用/源矩形/大小/翻转/`pivot_` 锚点）
- `engine::component::RenderComponent`：**渲染排序与调色**（`layer_/depth_/color_`，默认 `layer_ = MAIN_LAYER = 10`）

只要一个实体同时拥有这三份组件，它就会被 `RenderSystem` 取出并提交绘制。

![组件三件套与 pivot 约定](diagrams/L07_component_trio.png)

你也可以用下面这张表快速记忆各组件的职责与常见坑：

| 组件 | 负责什么 | 常见坑/提醒 |
| --- | --- | --- |
| `TransformComponent` | 画到哪（位置/缩放/旋转） | `rotation_` 是弧度制 |
| `SpriteComponent` | 画什么（纹理/裁剪/大小/锚点） | `pivot_` 建议 0..1，决定锚点落在精灵的哪里 |
| `RenderComponent` | 怎么排序/怎么调色 | `(layer_, depth_)` 越小越先画；`depth_` 常用于 ysort |

**pivot 与 position 的关系是本节最重要的约定：**

> `Transform.position_` 表示"锚点在世界中的位置"，锚点由 `Sprite.pivot_` 定义（建议范围 0..1；`(0,0)`=左上，`(0.5,0.5)`=中心，`(0.5,1.0)`=底部中心）。

在 `RenderSystem` 内部，最终的绘制位置按以下公式计算：
```
size     = sprite.size_ * transform.scale_
position = transform.position_ - sprite.pivot_ * size
```
即：**先由 `transform.position_` 确定锚点的世界坐标，再用 `pivot_` 反推精灵左上角的绘制坐标**。这条约定直接影响遮挡（YSort）是否自然（见下文 YSort 部分）。

### 排序 key：layer + depth（越小越先画）

TinyFarm 用 `(layer_, depth_)` 作为渲染排序 key，`RenderComponent::operator<` 定义了比较规则：先比 `layer_`，相同则比 `depth_`，**越小越先绘制**（即靠底层）。

- `layer_`：跨"大层级"的顺序（例如：地面/作物/角色/覆盖层）
- `depth_`：同一层内的顺序（例如：角色之间的前后遮挡）

你可以把它理解成两层排序：先按 `layer_` 分组，组内再按 `depth_` 排序。

![layer/depth 排序示意](diagrams/L07_layer_depth_sort.png)

项目里为 gameplay 动态对象提供了命名层级（`src/game/defs/render_layers.h`），具体定义如下：

| 命名常量 | 数值（相对 MAIN_LAYER=10） | 适用对象 |
| --- | --- | --- |
| `ACTOR` | 10 | 角色/成熟作物等主要动态实体 |
| `CROP_SEED` | 9 | 种子阶段作物（角色下方，避免遮挡脚底） |
| `SOIL_WET` | 8 | 湿润耕地（存档恢复时使用） |
| `SOIL` | 7 | 普通耕地（存档恢复时使用） |

> Tiled 加载的 tile layer 使用从 0 开始递增的 layer index，这些命名常量用于 gameplay 动态对象，通常应高于 Tiled 图层的 index 值。

> **用"名字"表达层级意图**，比在代码里直接写 `10 - N` 更稳、更可读。

### YSort：用 y 坐标驱动 depth（遮挡在前）

在 2D 俯视/斜俯视游戏里，我们希望"更靠下（y 更大）的对象看起来更在前面，遮挡更靠上的对象"。

TinyFarm 的最小实现就一行：
```
// YSortSystem::update
render.depth_ = transform.position_.y
```
当世界坐标 y 越大表示越靠下时：y 越大 → `depth_` 越大 → 越晚绘制 → 视觉上更"在前面"遮挡其他对象。

![YSort 规则与 pivot 常见坑](diagrams/L07_ysort_pivot.png)

**常见坑：YSort 的"排序点"是 `Transform.position_`，不是精灵底边。**

如果 `pivot_` 设在中心（`(0.5, 0.5)`），高个子精灵的"排序点"在精灵中心，很容易出现"头在前、脚在后"的不自然遮挡。

经验做法：
- 让 `Transform.position_` 代表"脚底/接地位置"
- 让 `Sprite.pivot_` 接近底部，例如 `(0.5, 1.0)`

这样两者自洽：排序点（position）在脚底，绘制坐标也从脚底往上偏移，遮挡看起来就自然了。

还有一个隐患值得注意：**当前 `YSortSystem` 会覆盖所有同时拥有 `RenderComponent + TransformComponent` 的实体的 `depth_`**——包括那些你本来想手动控制 depth 的对象。本节练习会引导你用 `YSortTag` 解决这个问题。

### 隐藏 vs 剔除：InvisibleTag vs Viewport Clipping

"看不见就不画"在工程上其实分两层，理解它们的区别很关键：

- **隐藏（逻辑层）**：`engine::component::InvisibleTag`
  带这个 Tag 的实体不会进入 `RenderSystem` 的 view（`RenderSystem` 和 `LightSystem` 都用 `entt::exclude<InvisibleTag>` 过滤）。适用场景：临时隐藏目标光标、昼夜条件切换光源显隐、调试开关等"玩法/逻辑决策"。

- **剔除（渲染层）**：Viewport Clipping
  实体仍然进入渲染流程，但在 `Renderer::drawSprite()` 提交绘制前会做视口裁剪：如果精灵完全在视野外，就不提交绘制命令，减少 draw calls。

**两者的核心差异：**
- `InvisibleTag` 是"我不想画这个东西"（玩法意图）
- Viewport Clipping 是"你画了也看不到"（渲染优化）

两者可以同时存在、互不干扰。

## 架构与数据流

### 从入口到 `drawSprite()`：一条链路串到底

本节只需要记住这条最短闭环调用链：

```
GameApp::render()
  └─ clearScreen()
  └─ SceneManager::render()          # 从栈底到栈顶叠加渲染所有 Scene
      └─ GameScene::render()
          └─ YSortSystem::update()   # 写 RenderComponent.depth_ = position.y
          └─ RenderSystem::update()  # 排序 + 遍历 + drawSprite
          └─ LightSystem::update()   # 光照提交
          └─ Scene::render()         # UI 渲染
  └─ present()
```

![渲染调用链数据流](diagrams/L07_render_data_flow.png)

注意 `SceneManager::render()` 是从栈底到栈顶叠加渲染——这正是"暂停菜单/弹窗覆盖在游戏画面之上"的工程基础（在[场景系统](07-场景系统.md)中有详细说明）。

### RenderSystem 的"只看思路版"伪代码

`RenderSystem` 做的事情可以用几行伪代码概括：

```text
# 1. 对所有 RenderComponent 排序（按 layer/depth）
registry.sort<RenderComponent>()

# 2. 开始一帧渲染（计算 view rect、矩阵等）
renderer.beginFrame(camera)

# 3. 遍历并绘制（关键：用 view.use<RenderComponent>() 强制按排序迭代）
view = registry.view<Render, Transform, Sprite>(exclude<InvisibleTag>)
view.use<RenderComponent>()

for each entity in view:
    size     = sprite.size_ * transform.scale_
    position = transform.position_ - sprite.pivot_ * size  # pivot 反推左上角
    drawSprite(sprite, position, size, color, rotation...)
        # Renderer 内部：如果 dst_rect 完全在视野外 → 跳过（Viewport Clipping）
```

> **EnTT 的关键陷阱**：`registry.view` 默认会选择"最小的 storage"迭代，而不是按你排好序的 `RenderComponent` storage。如果省略 `view.use<RenderComponent>()`，排序就等于白做了！本项目有专门的测试约束这一点（`tests/engine/system/render_system_view_use_test.cpp`）。

### 调试线索：用面板把"渲染提交成本"看出来

> 渲染不是"画在屏幕上"这么抽象，而是"向底层提交绘制命令"。

TinyFarm 提供了调试面板帮你建立这种直觉：

1. 运行游戏后按 `F5`，打开 `Engine Debug Panels`
2. 勾选 `OpenGL Renderer` 面板
   - **切换 `Viewport Clipping`**：观察 draw calls 如何随开关变化
   - **查看 `View Rect (world)`**：确认当前相机裁剪范围是否合理
   - **查看 `Pass Stats`**：观察 `ScenePass` 的 draw calls/vertices 随场景复杂度的变化

这是建立"渲染=提交绘制命令"直觉最直接的方式，不需要读 shader 细节。

## 练习

### 练习 1：为 YSort 增加显式标记（`YSortTag`）

> 目的：让"自动 ysort"与"手动 depth"可以共存，避免 `YSortSystem` 强行覆盖所有对象的 `depth_`。

**目标：**
- 新增一个 Tag（例如 `engine::component::YSortTag`），只有带该 Tag 的实体才会被 `YSortSystem` 写入 `RenderComponent.depth_`。

**验收标准（满足 3 项即可）：**
- 默认行为不变：游戏里角色与场景物体的遮挡关系仍然正确（需要的实体被正确加上 Tag）
- 可以让某些对象"例外"：不加 Tag 的对象不会被 ysort 覆盖，可以保留手动 depth
- 通过构建与测试：不引入新依赖，不破坏现有测试

**提示线索（模块/文件）：**
- `src/engine/component/tags.h`（添加 Tag 的位置参考）
- `src/engine/system/ysort_system.h/.cpp`（只处理带 Tag 的实体）
- `src/game/factory/entity_factory.*` / `src/game/loader/entity_builder.*`（哪些实体需要 ysort，通常在创建时打 Tag）

**提交方式：** GitHub PR

## 小结与预告

你现在应该能用 4 句话描述 TinyFarm 的 2D 渲染最小闭环：

1. **数据在 ECS**：`Transform/Sprite/Render` 三份组件定义"画什么/画到哪/怎么排序"；`position_` 是锚点位置，`pivot_` 决定锚点在精灵上的位置，两者配合决定绘制坐标。
2. **System 组织渲染**：`YSortSystem` 写 `depth_`，`RenderSystem` 排序并遍历实体（必须 `view.use<RenderComponent>()` 才能让排序生效），逐个 `drawSprite`。
3. **Renderer/GLRenderer 负责怎么画**：纹理获取、视口剔除、提交到不同 pass，可在调试面板里看到 draw calls/vertices。
4. **隐藏 ≠ 剔除**：`InvisibleTag` 是逻辑层过滤（玩法意图）；Viewport Clipping 是渲染层视口裁剪（渲染优化）。

下节课（Renderer 与 GLRenderer）我们会更深入地拆开 `Renderer` 与 `GLRenderer`：它们如何分层封装、如何计算视图投影与"逻辑分辨率"，以及为什么这些约定能让渲染管线保持可扩展。
