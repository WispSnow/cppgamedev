# 场景系统：Scene 栈、生命周期与切换策略

上节课我们深入了事件系统的核心机制——`trigger`（立即分发）与 `enqueue`（帧尾结算），并建立了"控制流事件 vs 数据流事件"的分类思维。

在那节课的案例二中，我们看到了一个有趣的模式：`SceneManager` 收到 `PushSceneEvent` 时并没有立刻切换场景，而是**先记录意图、后在安全点落地**。当时只是一笔带过，说这是"延后处理（Deferred Execution）"的典型应用。

现在，我们要正式展开这个话题。

> **为什么游戏不像网页那样随时跳转？**
> - 你在标题界面点了"开始游戏"，接下来发生了什么？旧画面怎么消失？新场景的资源什么时候加载？
> - 你在游戏中按了 `Esc`，画面变暗，弹出暂停菜单——但牛羊不再走动，作物不再生长。这是如何做到的？
> - 如果你在 UI 回调里直接删掉当前场景，会发生什么？（这就像在走路时突然抽掉脚下的地砖。）
>
> 这些问题的答案，都藏在《迷你农场》的**场景系统（Scene System）**中。

## 本课目标

学完本节后，你将能做到：

1. **用一句话描述 Scene 栈的核心约定**：栈顶负责更新、整栈叠加渲染——并理解这对"暂停菜单 / 模态弹窗 / 覆盖 UI"的意义。
2. **理解场景生命周期与切换策略**：`init/update/render/clean` 各自的职责，以及为什么场景切换请求要"先表达意图、后在安全点落地"（pending actions）。
3. **在代码里定位一条完整的场景切换链路**：谁发起 `Push/Pop/Replace`，谁消费并改栈，改栈发生在一帧的哪个时机。

## 1. 核心心智模型：Scene 栈

《迷你农场》的场景系统不使用复杂的状态机图，而是采用一个直观的**栈（Stack）结构**。

### 1.1 Update Top, Render All

这是本节课最重要的约定，请务必记住：

> **SceneManager 维护一个场景栈：Update 只更新栈顶，Render 从底到顶叠加渲染。**

![Scene Stack 规则](diagrams/L05_scene_stack_rule.png)

**为什么要这样设计？** 这种设计是为了完美支持 RPG / 模拟类游戏的"覆盖式 UI"需求：

1. **覆盖显示（Render All）**：当你打开"暂停菜单"时，它被压入栈顶。此时栈底的"游戏场景"依然在渲染，所以玩家能透过半透明背景看到游戏画面，体验连续流畅。
2. **逻辑冻结（Update Top）**：只有栈顶的"暂停菜单"在接收 `update()`，底层的"游戏场景"停止更新。这意味着你不需要在 `GameScene` 里写满 `if (!is_paused) { update_cows(); }` ——系统架构天然保证了冻结。

打开 `src/engine/scene/scene_manager.cpp`，让我们看看这两条规则在代码中长什么样：

```cpp
void SceneManager::update(float delta_time) {
    // 约定 1：只更新栈顶——覆盖式 Scene（如 PauseMenu）可以冻结底层逻辑
    Scene* current_scene = getCurrentScene();
    if (current_scene) {
        current_scene->update(delta_time);
    }
    // 所有逻辑跑完后，才处理切换（稍后详解）
    processPendingActions();
}

void SceneManager::render() {
    // 约定 2：叠加渲染整个栈——PauseMenu 覆盖在 GameScene 画面之上
    for (const auto& scene : scene_stack_) {
        if (scene) {
            scene->render();
        }
    }
}
```

代码非常简洁，但效果强大：暂停菜单不需要任何特殊标志位或条件判断，纯粹靠栈结构的物理法则。

### 1.2 切换策略：Push、Pop 还是 Replace？

既然是栈，就有进出操作。《迷你农场》区分了三种操作语义：

| 操作 | 典型用途 | 视觉效果 | 逻辑影响 |
| :--- | :--- | :--- | :--- |
| **Replace** | 场景大切换（Title → Game） | 旧场景消失，新场景出现 | 整栈清空，新场景初始化 |
| **Push** | 打开子菜单 / 弹窗（Game → PauseMenu） | 新场景覆盖在旧场景上，旧场景可见 | 旧场景**挂起**（不再 update），新场景运行 |
| **Pop** | 关闭子菜单 / 返回（PauseMenu → Game） | 顶层场景消失，露出下层场景 | 顶层场景销毁，下层场景**恢复**运行 |

![切换策略选择准则](diagrams/L05_switch_strategy_table.png)

**决策口诀**：
- **Replace**：用来"换主流程"——不再需要旧场景。
- **Push / Pop**：用来"加 / 关一层覆盖"——旧场景还在栈里等你回来。

## 2. 安全机制：Pending Actions

理解了栈结构后，下一个挑战是**切换时机**。

### 2.1 危险的"立即切换"

假设你在 `GameScene::update()` 的某个逻辑（比如 UI 按钮点击）里直接调用了 `scene_manager.pop()`：

```cpp
// ⚠️ 错误示范！
void GameScene::onExitClicked() {
    sceneManager.pop(); // 危险！当前场景立即被析构！
    // ...函数返回后，SceneManager 试图继续执行 update...
    // ...访问了野指针。BOOM！
}
```

这就好比你在开车时试图给汽车换轮胎——车还在跑，轮胎就被拆了。

### 2.2 解决方案：先表达意图，后安全落地

《迷你农场》采用了**Pending Actions（待处理动作）**模式。类比一下：你把信扔进邮筒（表达意图），邮递员每天傍晚统一收信处理（安全落地）。

![Pending Actions 数据流](diagrams/L05_pending_actions_flow.png)

**第一步——表达意图**：在 UI 回调或逻辑中，调用 `requestPushScene()` / `requestPopScene()` / `requestReplaceScene()`。这些方法内部会触发对应的事件：

```cpp
// src/engine/scene/scene.cpp
void Scene::requestPushScene(std::unique_ptr<Scene>&& scene) {
    context_.getDispatcher().trigger<PushSceneEvent>(
        PushSceneEvent{std::move(scene)});
}
```

**第二步——SceneManager 记录意图**：事件被立刻送达（`trigger`），但 SceneManager 只是存到"待办箱"里，不立刻改栈：

```cpp
// src/engine/scene/scene_manager.cpp
void SceneManager::onPushScene(PushSceneEvent& event) {
    if (pending_action_ != PendingAction::None) {
        spdlog::warn("SceneManager: 已有待处理动作，忽略 PushSceneEvent。");
        return;
    }
    pending_action_ = PendingAction::Push;
    pending_scene_ = std::move(event.scene);
}
```

**第三步——安全落地**：在 `update()` 的**最后一行**，SceneManager 检查"待办箱"，执行真正的栈操作：

```cpp
void SceneManager::update(float delta_time) {
    if (getCurrentScene()) {
        getCurrentScene()->update(delta_time);
    }
    // 所有逻辑跑完后，才处理切换 —— 这是"安全点"
    processPendingActions();
}
```

这个机制带来了一个极佳的副作用：**时序的可预测性**。无论你在帧的哪个角落发起切换，新场景的 `init()` 永远在当前场景的 `update()` 彻底结束后发生，新场景的第一次 `update()` 永远在下一帧开始。

> **回忆 [事件系统](06-事件系统.md)**：我们在事件系统那节课提到，`trigger` 保证了"消息立刻送达"，但**收到消息后怎么处理是接收方的自由**。SceneManager 正是这个原则的最佳示范——用 `trigger` 确保意图不丢失，用 pending action 确保时序安全。

### 2.3 同一帧多次切换怎么办？

如果同一帧里先请求了 `Push(A)` 又请求了 `Replace(B)`，会发生什么？

看 `onPushScene` 的第一行——`if (pending_action_ != PendingAction::None)` ——**第二个请求会被丢弃并打印 Warning**。这个设计保持了确定性：一帧最多执行一次场景切换。

## 3. Scene 基类与生命周期

在追踪完整切换链路之前，我们先来认识"场景"本身的接口。

### 3.1 生命周期四步：init → update → render → clean

打开 `src/engine/scene/scene.h`，Scene 基类定义了四个虚函数：

```cpp
class Scene {
public:
    [[nodiscard]] virtual bool init();      // 初始化：加载资源、创建实体、注册事件
    virtual void update(float delta_time);  // 每帧更新逻辑
    virtual void render();                  // 每帧渲染画面
    virtual void clean();                   // 清理：释放资源、断开事件监听

protected:
    engine::core::Context& context_;        // 引擎上下文（共享资源入口）
    entt::registry registry_;               // 独立的 ECS 注册表
    std::unique_ptr<UIManager> ui_manager_; // 可选的 UI 管理器
    bool is_initialized_ = false;           // 初始化标志
};
```

注意几个设计要点：

- **`init()` 返回 `bool`**：如果初始化失败返回 `false`，SceneManager 会中止入栈并触发退出事件，防止在不完整的状态下运行。
- **每个 Scene 持有独立的 `registry_`**：GameScene 的实体（玩家、NPC、作物）与 TitleScene 的实体互不干扰——场景即边界。这个话题会在 [ECS 在本项目中的落地](08-ECS%20在本项目中的落地.md)（ECS）中展开。
- **`ui_manager_` 是可选的**：不是所有场景都需要 UI，派生类按需创建。

### 3.2 构造函数 vs init()：为什么要分开？

这是一个常见的疑问：既然都要初始化，为什么不在构造函数里做完？

```cpp
// 构造函数：只做最轻量的成员变量赋值
Scene::Scene(std::string_view name, engine::core::Context& context)
    : scene_name_(name), context_(context) {
}

// init()：做"重"操作——加载资源、创建实体、注册事件
bool Scene::init() {
    is_initialized_ = true;
    return true;
}
```

原因有二：
1. **场景可能被创建了但还没入栈**（处于 pending 状态）。如果构造函数就加载大量资源，万一最终不入栈，就白费了。
2. **`init()` 可以返回失败状态**，而构造函数不能优雅地报告失败（需要抛异常或用 two-phase init 模式）。

### 3.3 clean()：断开一切连接

`clean()` 是生命周期的终点。看看基类的实现：

```cpp
// src/engine/scene/scene.cpp
void Scene::clean() {
    if (!is_initialized_) return;
    context_.getSpatialIndexManager().resetIfUsingRegistry(&registry_);
    registry_ = entt::registry{};  // 重建 registry，彻底释放所有实体和组件
    is_initialized_ = false;
}
```

派生场景会在 `clean()` 中做额外清理。比如 `PauseMenuScene` 需要恢复之前的游戏状态：

```cpp
// src/game/scene/pause_menu_scene.cpp
void PauseMenuScene::clean() {
    context_.getGameState().setState(previous_state_); // 恢复 Playing 状态
    Scene::clean();
}
```

> **重要提醒**：如果你在 `init()` 里注册了事件监听器（`dispatcher.sink<Event>().connect(...)`），一定要在 `clean()` 或析构函数里 `disconnect`。否则场景被销毁后，事件系统还持有指向已释放内存的回调指针——典型的 Use-After-Free 崩溃。

## 4. 代码实战：追踪切换链路

理论讲完了，让我们去代码里看几条真实的切换链路。

### 4.1 起点：游戏层注入初始场景

游戏启动时，谁负责把第一个场景放进栈？

打开 `src/game/game_entry.cpp`：

```cpp
void setupInitialScene(engine::core::Context& context) {
    auto title_scene = std::make_unique<game::scene::TitleScene>("TitleScene", context);
    context.getDispatcher().trigger<PushSceneEvent>(
        PushSceneEvent{std::move(title_scene)});
}
```

注意这里用的是 `trigger<PushSceneEvent>` 而不是直接操作 SceneManager——即使是"第一个场景"，也走事件通道，保持了统一的切换路径。

`GameApp` 在初始化末尾调用这个回调函数，TitleScene 被 push 入栈，这就是为什么游戏一启动就看到标题界面。

### 4.2 Replace：从标题进入游戏

打开 `src/game/scene/title_scene.cpp`，找到 Start 按钮的回调：

```cpp
void TitleScene::onStartClicked() {
    auto next = std::make_unique<game::scene::GameScene>(
        "GameScene", context_, title_game_time_);
    requestReplaceScene(std::move(next));
}
```

用 **Replace** 而不是 Push——因为进入游戏后，标题界面就不再需要了。`replaceScene()` 内部会**清空整个栈**再推入新场景，保证内存中不会残留旧场景。

而同一个文件中，Load 按钮的处理方式截然不同：

```cpp
void TitleScene::onLoadClicked() {
    auto on_select = [this](int slot) {
        auto next = std::make_unique<game::scene::GameScene>(
            "GameScene", context_, nullptr, slot);
        requestReplaceScene(std::move(next));
    };
    auto menu = std::make_unique<SaveSlotSelectScene>(
        "SaveSlotSelect", context_, std::move(on_select));
    requestPushScene(std::move(menu)); // Push，不是 Replace！
}
```

Load 用的是 **Push**——因为存档选择界面是覆盖在标题之上的弹窗，玩家按 Back 可以回到标题。

### 4.3 Push + Pop：暂停菜单的覆盖与返回

打开 `src/game/scene/game_scene.cpp`，找到暂停触发的逻辑：

```cpp
bool GameScene::onPauseToggle() {
    if (context_.getGameState().isPaused()) {
        return false;  // 已经暂停了，不重复处理
    }
    // ...
    auto* game_time = registry_.ctx().find<game::data::GameTime>();
    auto menu = std::make_unique<PauseMenuScene>(
        "PauseMenu", context_, save_service_.get(), game_time);
    requestPushScene(std::move(menu));
    return true;
}
```

此时发生了什么？

1. `GameScene` 发出 `PushSceneEvent`（通过 `requestPushScene`）。
2. SceneManager 记录 pending push。
3. 本帧 `update()` 结束后，SceneManager 执行 push：调用 `PauseMenuScene::init()`，将其压入栈顶。
4. **下一帧开始**：栈变成了 `[GameScene, PauseMenuScene]`。SceneManager 只 update 栈顶（PauseMenuScene），GameScene 的逻辑被冻结——牛羊不再走动，作物不再生长。
5. 但在 render 阶段，GameScene **仍然被渲染**（因为 Render All），PauseMenuScene 画在上面。

![暂停菜单覆盖时序](diagrams/L05_pause_overlay_sequence.png)

再看 `PauseMenuScene` 的 `init` 和 `clean`——它巧妙地利用 `GameState` 来传达暂停状态：

```cpp
// src/game/scene/pause_menu_scene.cpp
bool PauseMenuScene::init() {
    previous_state_ = context_.getGameState().getCurrentState(); // 保存当前状态
    context_.getGameState().setState(engine::core::State::Paused); // 设为暂停
    // ...创建 UI...
    return true;
}

void PauseMenuScene::clean() {
    context_.getGameState().setState(previous_state_); // 恢复之前的状态
    Scene::clean();
}
```

当玩家点 Resume 时：

```cpp
void PauseMenuScene::onResumeClicked() {
    requestPopScene();  // Pop 自身，回到 GameScene
}
```

Pop 之后，PauseMenuScene 的 `clean()` 被调用，`GameState` 恢复为 `Playing`，GameScene 重新开始收到 `update()` 调用——世界恢复运转。

### 4.4 嵌套栈：PauseMenu → SaveSlotSelect

场景栈可以嵌套多层。在暂停菜单中点击 Save：

```cpp
// src/game/scene/pause_menu_scene.cpp
void PauseMenuScene::onSaveClicked() {
    auto on_select = [this](int slot) {
        // ...存档逻辑...
        requestPopScene(); // 关闭 SaveSlotSelectScene
    };
    auto select = std::make_unique<SaveSlotSelectScene>(
        "SaveSlotSelect", context_, std::move(on_select),
        SaveSlotSelectScene::Mode::Save);
    requestPushScene(std::move(select)); // 再压一层！
}
```

此时栈变成了 `[GameScene, PauseMenuScene, SaveSlotSelectScene]`——三层场景叠加渲染：最底下是游戏画面，中间是变暗的暂停菜单，最上面是存档选择界面。只有 SaveSlotSelectScene 在接收 update。

当玩家选完存档后 Pop，回到 PauseMenuScene；再点 Resume 后 Pop，回到 GameScene。每一步都符合栈的 LIFO（后进先出）语义。

### 4.5 Replace 跨状态：从暂停直接回标题

从暂停菜单点击 Title 按钮：

```cpp
void PauseMenuScene::onBackToTitleClicked() {
    requestReplaceScene(
        std::make_unique<TitleScene>("TitleScene", context_));
}
```

这里用 **Replace**，它会清空整个栈（包括底下的 GameScene 和当前的 PauseMenuScene），然后推入新的 TitleScene。这是一个"大跳转"——游戏状态被彻底丢弃，回到起点。

## 5. 常见错误

1. **忘记在 `clean()` 里断开事件监听器**
   - 如果你在 `init()` 里 `dispatcher.sink<Event>().connect(...)`，一定要在 `clean()` 或析构函数里 `disconnect`。
   - *后果*：场景 Pop 销毁后，事件系统还持有指向已释放内存的回调——典型的 Use-After-Free 崩溃。

2. **在构造函数里做重操作**
   - 加载资源、创建实体这些事应该放在 `init()` 里，不要放在构造函数中。
   - *原因*：pending 状态的场景可能最终不入栈；而且 `init()` 可以返回失败让 SceneManager 优雅处理。

3. **直接操作 SceneManager 的栈**
   - 永远通过 `requestPushScene()` / `requestPopScene()` / `requestReplaceScene()` 表达意图，不要绕过事件直接调用内部方法。
   - *原因*：直接操作可能在不安全的时机修改栈，导致野指针或不可预期的行为。

4. **Pop 到空栈**
   - 如果栈被 Pop 空了，SceneManager 会自动触发 `QuitEvent` 退出游戏。这在大多数情况下是你想要的行为——但要小心不要意外多 Pop。

## 小结

场景系统是《迷你农场》"时空骨架"的重要一环：

- **空间维度**：Scene 栈实现了界面的层级管理——**Update Top** 冻结底层逻辑，**Render All** 叠加显示所有层。
- **时间维度**：Pending Actions 保证了生命周期的安全流转——意图与落地分离，一切切换都发生在可控的"安全点"。
- **生命周期**：`init → update → render → clean` 四步走，构造轻量、初始化可失败、清理必断连。

有了这个骨架，下节课（ECS 应用）我们将往场景里填充血肉——**ECS（Entity Component System）**。我们将探讨为什么每个 Scene 都有自己独立的 `Registry`，以及如何把游戏里的花草牛羊变成一个个数据驱动的实体。
