# 事件系统：EnTT Dispatcher 的使用方式与边界

上节课我们建立了 Debug UI 的完整心智模型——热键链路、面板分类与生命周期、输入隔离机制。在那节课的最后，我们认识了一个特殊的调试面板 **Dispatcher Trace**，它能实时追踪事件分发的时序：哪些事件是 Immediate（同步分发），哪些是 Queued（帧尾结算）。

当时你可能还没完全理解这两个词的含义。从这节课开始，它们将成为你每天打交道的核心概念。

> **"事件"这个词听起来很美好：解耦、灵活。但在实际工程中，它往往是新手最大的 Bug 制造机：**
> - "我明明发出去了，为什么没反应？"（时序问题）
> - "为什么这个变量在下一帧才变？"（机制理解偏差）
> - "到底该直接调函数，还是发事件？"（架构决策困难）
>
> 这节课不讲复杂的观察者模式理论，只解决一个核心问题：**在《迷你农场》里，事件到底什么时候生效？**

## 本课目标

学完本节后，你将能做到：

1. **准确描述 `trigger/enqueue/update` 的语义差异**，并按"控制流事件 / 数据流事件"选择合适的分发方式。
2. **在工程里定位事件链路**：谁生产事件、谁消费事件、事件在哪一帧被处理（立即 / 帧尾）。
3. **理解事件的分层边界**：引擎事件（`engine::utils::*`）vs 游戏事件（`game::defs::*`），以及"事件 vs 直接调用"的取舍原则。

## 1. 核心心智模型：分发时机

《迷你农场》使用 `entt::dispatcher` 作为事件总线。在写任何代码前，你必须把这张图刻在脑子里：

![事件分发时机流程图](diagrams/L04_event_timing_flowchart.png)

### 1.1 三种核心操作

**`trigger<T>(...)`——立即生效**

语义：现在、立刻、马上执行。当前的函数调用栈会暂停，直接去执行所有监听者的回调。监听者处理完了，才会返回这一行继续往下走。

本质上，它就是一次**"群发的直接函数调用"**。

**`enqueue<T>(...)`——稍后生效**

语义：把消息塞进信箱，回头再看。事件被放入一个队列，**监听者此刻完全不知情**。

生效时间：直到有人显式调用了 `dispatcher.update()`。

**`dispatcher.update()`——清空信箱**

语义：处理所有积压的信件。

位置：这一点至关重要——**《迷你农场》把它放在了 `render()` 之后**。

### 1.2 关键结论：帧尾结算

让我们看一眼 `src/engine/core/game_app.cpp` 的 `run()` 函数：

```cpp
// 简化后的帧节拍
while (is_running_) {
    time_->update();                    // 时间推进
    handleEvents();                     // SDL 事件 → 引擎事件（可能 trigger）
    update(delta_time);                 // 场景/系统更新（可能 enqueue）
    render();                           // 渲染画面

    // 【关键】结算点在这里！
    dispatcher_->update();              // 分发所有 enqueue 的事件
}
```

**这意味着：如果你在 `update()` 里 `enqueue` 了一个事件，它在"本帧画面画完之后"才会被处理。** 换句话说，对于游戏逻辑而言，**本帧 enqueue 的事件，是给下一帧用的输入**。

> **为什么把结算放在 `render()` 后面而不是 `update()` 后面？** 因为这样可以保证：整个 `update` 阶段，所有系统都在同一个"数据快照"上运行，不会有人因为中途收到事件而看到不一致的状态。渲染完成后再结算，时序最清晰。

## 2. 工程约定：Trigger 还是 Enqueue？

《迷你农场》对事件的分发策略有明确的工程约定（详见 `docs/events.md`）。我们把它提炼为两个分类：

![事件分类与分发策略选择](diagrams/L04_event_policy_table.png)

### 2.1 控制流事件 → 用 `trigger`

当你需要**立刻改变程序控制流**时，必须用 `trigger`：

- **退出游戏**（`QuitEvent`）：如果不用 trigger，程序可能多跑一帧逻辑再退出，产生奇怪的副作用。
- **窗口大小变化**（`WindowResizedEvent`）：渲染器必须立刻知道新尺寸并重建视口，否则这一帧画出来的东西就是歪的。
- **场景切换请求**（`PushSceneEvent`/`PopSceneEvent`/`ReplaceSceneEvent`）：切换意图需要立刻被 `SceneManager` 记录下来。

> **注意一个微妙之处**：即使使用 `trigger`，监听者也可以选择**"延迟落地"**。比如 `SceneManager` 收到 `PushSceneEvent` 时不会立刻切换场景栈，而是先记录为 pending action，等 `update()` 末尾再统一执行。`trigger` 保证了"消息立刻送达"，但**收到消息后怎么处理是接收方的自由**。

### 2.2 数据流事件 → 用 `enqueue`

**绝大多数游戏逻辑事件**应该用 `enqueue`：

- **日常反馈**：播放音效（`PlaySoundEvent`）、播放动画（`PlayAnimationEvent`）、对话展示（`DialogueShowEvent`）
- **状态变更通知**：物品栏变化（`InventoryChanged`）、时间推进（`DayChangedEvent`、`HourChangedEvent`）
- **交互请求**：使用工具（`UseToolEvent`）、物品操作（`AddItemRequest`）

用 `enqueue` 有三个好处：

1. **防止递归爆炸**：如果在 A 的回调里 trigger B，B 又 trigger A……用 `trigger` 会导致栈溢出。用 `enqueue` 则安全得多——它们只是在队列里排队，不会形成调用链。
2. **批量处理更稳定**：比如"天亮了"（`DayChangedEvent`）可能触发几百个作物生长。如果在 `update` 中间直接 trigger，可能造成明显的帧顿挫；放在帧尾统一结算更可控。
3. **时序更可预测**：所有 `enqueue` 事件在同一个结算点被处理，不会出现"A 系统看到了事件但 B 系统还没看到"的不一致。

### 2.3 速查：如何判断用哪种？

问自己两个问题：

1. **"如果这个事件晚一帧处理，会出 Bug 吗？"** —— 如果会，用 `trigger`。
2. **"这个事件可能在回调中触发新事件吗？"** —— 如果可能，用 `enqueue` 更安全。

大多数情况下，答案都是 `enqueue`。只有少数"不等不行"的场合才需要 `trigger`。

## 3. 事件的分层边界

打开 `src/engine/utils/events.h` 和 `src/game/defs/events.h`，你会发现事件定义被分成了两层：

### 3.1 引擎事件（`engine::utils::*`）

这些事件与具体游戏玩法无关，属于引擎基础设施：

```cpp
// 控制流事件
struct QuitEvent {};
struct PushSceneEvent { std::unique_ptr<Scene> scene; };
struct PopSceneEvent {};
struct WindowResizedEvent { int width; int height; bool pixel_size; };

// 数据流事件
struct PlayAnimationEvent { entt::entity entity_; entt::id_type animation_id_; bool loop_; };
struct AnimationFinishedEvent { entt::entity entity_; entt::id_type animation_id_; };
struct PlaySoundEvent { entt::entity entity_; entt::id_type sound_id_; };
struct DayChangedEvent { std::uint32_t day_; };
struct HourChangedEvent { std::uint32_t day_; float hour_; };
```

注意事件定义的注释里已经标注了推荐的分发方式（`trigger` 还是 `enqueue`），这不是随便写的——它就是项目的分发策略约定。

### 3.2 游戏事件（`game::defs::*`）

这些事件只在《迷你农场》的玩法逻辑中使用：

```cpp
struct UseToolEvent { Tool tool_; glm::vec2 world_pos_; };
struct AddItemRequest { entt::entity target; entt::id_type item_id; int count; };
struct InventoryChanged { entt::entity target; std::vector<InventorySlotUpdate> slots; };
struct InteractRequest { entt::entity player; entt::entity target; };
struct DialogueShowEvent { entt::entity target; std::string speaker; std::string text; };
```

### 3.3 命名习惯与语义暗示

仔细观察事件的命名，你会发现一些规律：

| 命名后缀 | 语义 | 举例 |
|---------|------|------|
| `*Event` | 已发生的事实通知 | `QuitEvent`、`AnimationFinishedEvent`、`DayChangedEvent` |
| `*Request` | 请求某个操作执行 | `AddItemRequest`、`InteractRequest`、`AdvanceTimeRequest` |
| `*Changed` | 状态变更通知 | `InventoryChanged`、`HotbarChanged` |

这种命名不是强制的语法规则，但它能帮助你一眼判断事件的"意图方向"。

### 3.4 事件 vs 直接调用：什么时候不该用事件？

事件带来解耦，但也带来间接性。并不是所有通信都应该用事件。判断标准是：

**用事件的场景**：
- 生产者不需要知道消费者是谁（一对多、多对多）
- 发送方和接收方处于不同模块（跨层通信）
- 可能有多个接收方需要响应同一个动作

**直接调用的场景**：
- 调用方和被调用方在同一个系统/模块内部（内聚性高）
- 需要同步获取返回值
- 只有唯一的接收方，且这种关系不太可能变化

举个例子：`AudioSystem::onPlaySoundEvent()` 内部调用 `audio_player.playSound()` 是直接调用，因为 `AudioSystem` 和 `AudioPlayer` 是同一模块内的紧密协作。但"系统 A 想播放音效"这个意图通过 `PlaySoundEvent` 事件传递给 `AudioSystem`——因为 A 不需要知道音效的具体播放方式。

## 4. 代码实战：追踪事件链路

理论讲完了，让我们去代码里看几个真实的链路，验证上面的结论。

### 4.1 案例一：退出的同步链路（trigger）

打开 `src/engine/input/input_manager.cpp`：

```cpp
void InputManager::processEvent(const SDL_Event& event) {
    // ...
    case SDL_EVENT_QUIT:
        quit();
        break;
}

void InputManager::quit() {
    // 控制流事件：必须马上停止，不能等下一帧
    dispatcher_->trigger<engine::utils::QuitEvent>();
}
```

再看 `src/engine/core/game_app.cpp`：

```cpp
// 初始化时订阅
dispatcher_->sink<utils::QuitEvent>().connect<&GameApp::onQuitEvent>(this);

// 回调
void GameApp::onQuitEvent() {
    is_running_ = false;   // 立即收到通知
}
```

因为是 `trigger`，`is_running_` 会**立刻**变为 `false`。当 `handleEvents()` 返回后，主循环的 `while (is_running_)` 判断立刻失败，程序优雅退出。

如果这里用了 `enqueue`，退出事件要等到 `dispatcher_->update()` 才被处理——但 `update()` 在循环末尾，意味着程序还会多跑一轮完整的 `update + render`，可能执行不必要的逻辑。

### 4.2 案例二：场景切换的"安全落地"（trigger + 延迟执行）

打开 `src/engine/scene/scene.cpp`，这里是事件的**生产方**：

```cpp
void Scene::requestPushScene(std::unique_ptr<Scene>&& scene) {
    context_.getDispatcher().trigger<engine::utils::PushSceneEvent>(
        engine::utils::PushSceneEvent{std::move(scene)});
}
```

再打开 `src/engine/scene/scene_manager.cpp`，这里是事件的**消费方**：

```cpp
void SceneManager::onPushScene(engine::utils::PushSceneEvent& event) {
    if (pending_action_ != PendingAction::None) {
        spdlog::warn("SceneManager: 已有待处理动作，忽略 PushSceneEvent。");
        return;
    }
    // 收到事件时，只是记了个小本本
    pending_action_ = PendingAction::Push;
    pending_scene_ = std::move(event.scene);
}

void SceneManager::update(float delta_time) {
    if (current_scene) current_scene->update(delta_time);
    // 只有当当前场景跑完逻辑后，才安全地切换
    processPendingActions();
}
```

虽然用了 `trigger`（消息立刻送达），但 `SceneManager` 并没有立刻切换场景，而是**延后处理**。

**为什么这样设计？** 设想一下，如果在 `onPushScene` 里直接切换：旧场景正在 `update` 中间发出了切换请求 → 旧场景的 `current_scene` 指针立刻被销毁 → 函数返回后继续执行旧场景剩下的代码…… **Crash！**

这就是**延后处理（Deferred Execution）**的价值。虽然这里没用 `dispatcher` 的队列机制，但思想完全一致：**收到请求后先记录，在安全点统一执行**。

### 4.3 案例三：动画完成的异步链路（enqueue）

打开 `src/engine/system/animation_system.cpp`：

```cpp
// 动画播放完毕且不循环
if (anim_component.current_frame_index_ >= current_animation.frames_.size()) {
    if (current_animation.loop_) {
        anim_component.current_frame_index_ = 0;
    } else {
        anim_component.current_frame_index_ = current_animation.frames_.size() - 1;
        // 发送动画播放完成事件——注意是 enqueue
        dispatcher_.enqueue(engine::utils::AnimationFinishedEvent{
            entity, anim_component.current_animation_id_});
    }
}
```

再看 `src/game/system/state_system.cpp`，它消费这个事件：

```cpp
void StateSystem::onAnimationFinishedEvent(const engine::utils::AnimationFinishedEvent& event) {
    // 解锁动作——玩家可以再次操作
    registry_.remove<game::component::ActionLockedTag>(event.entity_);
    // 回到待机状态
    if (auto state = registry_.try_get<game::component::StateComponent>(event.entity_); state) {
        state->action_ = game::component::Action::Idle;
        registry_.emplace_or_replace<game::component::StateDirtyTag>(event.entity_);
    }
}
```

这里用 `enqueue` 而非 `trigger` 是合理的：

1. `AnimationSystem::update()` 正在遍历所有动画实体。如果在遍历过程中 `trigger` 了一个事件，`StateSystem` 的回调可能修改 `registry`（添加/删除 Tag），**破坏正在进行的遍历**。
2. 动画完成不需要"立刻生效"——晚一帧解锁动作，玩家完全感知不到。

### 4.4 案例四：时间事件的批量结算（enqueue）

打开 `src/game/system/time_system.cpp`：

```cpp
void TimeSystem::update(float delta_time) {
    // ...时间推进计算...
    while (game_time->minute_ >= 60.0f) {
        game_time->minute_ -= 60.0f;
        game_time->hour_ += 1.0f;
        // 每过一小时，enqueue 一个事件
        dispatcher_.enqueue<engine::utils::HourChangedEvent>(game_time->day_, game_time->hour_);

        if (game_time->hour_ >= 24.0f) {
            game_time->hour_ -= 24.0f;
            game_time->day_++;
            // 跨天事件
            dispatcher_.enqueue<engine::utils::DayChangedEvent>(game_time->day_);
        }
    }
}
```

`CropSystem` 监听 `DayChangedEvent`，推进所有作物的生长状态：

```cpp
// crop_system.cpp 构造函数中：
dispatcher_.sink<engine::utils::DayChangedEvent>().connect<&CropSystem::onDayChanged>(this);
```

如果游戏中有"快进时间"的功能（比如睡觉跳过 8 小时），`TimeSystem::advanceTimeHours()` 会在一帧内 enqueue 多个 `HourChangedEvent` 和可能的 `DayChangedEvent`。这些事件全部在帧尾统一结算，比在循环中间逐个 trigger 要稳定得多。

## 5. 事件订阅与生命周期管理

事件系统还有一个容易忽略的工程问题：**谁订阅、何时订阅、何时取消订阅**。

### 5.1 订阅模式

在《迷你农场》中，订阅通常发生在**构造函数或初始化阶段**：

```cpp
// AnimationSystem 构造函数
AnimationSystem::AnimationSystem(entt::registry& registry, entt::dispatcher& dispatcher)
    : registry_(registry), dispatcher_(dispatcher) {
    dispatcher_.sink<engine::utils::PlayAnimationEvent>()
        .connect<&AnimationSystem::onPlayAnimationEvent>(this);
}
```

### 5.2 取消订阅：防止悬垂回调

**最常见的 Bug 之一**：对象已经析构了，但 dispatcher 里还留着指向它的回调。下次事件触发时——**Crash！**

《迷你农场》的约定是在析构函数中统一断开：

```cpp
AnimationSystem::~AnimationSystem() {
    dispatcher_.disconnect(this);  // 断开当前对象绑定的所有回调
}
```

`disconnect(this)` 会一次性断开所有以 `this` 为实例绑定的回调，不需要逐个事件去 disconnect。这是 EnTT 提供的便捷方法，推荐使用。

### 5.3 共享 Dispatcher 的方式：通过 Context

所有系统和场景通过 `Context` 访问同一个 `dispatcher`：

```cpp
// context.h
entt::dispatcher& getDispatcher() const { return dispatcher_; }
```

`Context` 在 `GameApp::init()` 中创建，持有对 dispatcher 的引用。场景和系统通过 `Context` 获取 dispatcher，不需要自己创建，也不需要全局变量。这保证了整个应用使用**同一个事件总线**。

## 6. 调试利器：用 Dispatcher Trace 验证

还记得上节课介绍的 Dispatcher Trace 面板吗？现在是用它的时候了。

运行游戏，按 `F5` 打开 Engine 面板，勾选 `Core: Dispatcher Trace`。你会看到两类分发记录：

1. **Immediate**：对应 `trigger`。事件在被调用时就已经分发。
2. **Queued**：对应 `enqueue`。事件在 `dispatcher.update()` 期间才被分发。

![Dispatcher Trace 检查清单](diagrams/L04_tracing_checklist.png)

**实战调试技巧**：如果你发现自己发出的事件一直显示 Queued，但逻辑却依赖它立刻生效——这就是 Bug 的根源。把 `enqueue` 改成 `trigger`（或者调整你的逻辑让它不依赖立刻生效）就能解决。

**作业 1（思考与验证）：同帧冲突问题**

在 `SceneManager` 的代码里，现在的逻辑是：

```cpp
if (pending_action_ != PendingAction::None) {

```
这意味着如果同一帧里先请求了 `Push`，又请求了 `Pop`，第二个请求会被**直接丢弃**。

- **任务**：构造一个测试用例，在同一帧内连续发送两个场景切换事件，观察日志输出。

- **目标**：任何系统只需要 `enqueue<PlaySoundEvent>(...)` 就能播放音效，而不需要包含 `AudioSystem` 或 `AudioPlayer` 的头文件。
- **验证**：在 Dispatcher Trace 面板中确认你的事件出现在 Queued 列表中。

## 小结

事件系统不是魔法，它只是两种函数调用的变体：

- **`trigger`** = 群发的同步函数调用（立刻执行，适合控制流）
- **`enqueue`** = 排队等候的函数调用（帧尾结算，适合数据流）

掌握了 `dispatcher.update()` 在帧尾这一事实，你就掌握了《迷你农场》事件流动的脉搏。
