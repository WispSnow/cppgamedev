# 玩家控制与相机：输入驱动、目标选择与跟随策略

上节课我们拆解了 `GameScene` 的初始化与系统编排，得出了一条关键结论：

> 系统的创建顺序和更新顺序决定了游戏的正确性——顺序错了，bug 会以最隐蔽的方式出现。

但"顺序正确"只是底盘。你打开游戏时，最先感知到的不是内部架构有多优雅，而是两件非常直觉的事：

- **玩家是否"好控制"**：按 WASD 角色立刻动、松手立刻停、切工具有即时反馈、点击目标框"所见即所得"。
- **镜头是否"好用"**：跟随平滑不抖动、缩放可控、相机永远不会跑出地图露出黑边。

这两件事背后，对应两个核心系统：

- **`PlayerControlSystem`**——把键盘/鼠标的原始输入转化为"玩家意图"（移动/朝向/目标格/动作请求）。
- **`CameraFollowSystem`**——让相机成为一个"可控的观察者"（跟随/缩放/重置 + 边界约束）。

这节课我们就来拆解这两个系统的设计思路和关键实现细节。

## 2. 本节目标与问题定义

**一句话目标：**

> 把 [输入系统](15-输入系统.md) 建立的输入系统（Action mapping）真正"落地"到玩法层——用 ECS 的组件和事件表达"玩家意图"，并让相机成为可控的观察者，为后续的交互（[交互与对话](28-交互与对话.md)）、物品栏（[物品栏与快捷栏](29-物品栏与快捷栏.md)）和农场玩法（[物品使用与农场循环](30-物品使用与农场循环.md)）提供统一入口。

我们用 4 个问题来驱动理解：

1. **为什么 `InputManager` 只做"动作状态"，而不直接在里面写"移动/砍树/种地"？** ——职责边界问题。
2. **连续输入（移动）和离散输入（点击/切换快捷栏）在工程上应该怎么组织？** ——两种消费模式问题。
3. **鼠标指向世界里的哪个 tile？为什么会出现"鼠标与目标框对不齐"的坑？** ——坐标系转换问题。
4. **相机跟随/缩放应该由谁负责 clamp？为什么"边界约束"应该下沉到 `Camera`？** ——职责归属问题。

带着这四个问题，我们逐一展开。

## 3. 核心概念

### 3.1 Action（动作名）是"输入语义"，SDL 事件是"输入细节"

打开 `config/input.json`，你会看到本课关心的几组动作名：

- **移动**：`move_up` / `move_down` / `move_left` / `move_right`
- **快捷栏**：`hotbar_1` ~ `hotbar_10`
- **相机**：`camera_reset_zoom`

还有两个隐含的动作——`mouse_left` 和 `mouse_right`。它们不需要在配置里显式声明，`InputManager` 会在启动时自动注入默认映射，供 UI 和点击逻辑使用。

这里的核心设计思想在 [输入系统](15-输入系统.md) 已经讲过，但值得再强调一遍：

- **动作名是稳定的"语义层 API"**——`"move_up"` 永远表示"玩家想向上走"。
- **SDL 事件（W 键 / 上箭头 / 手柄摇杆）只是可替换的"实现细节"**。

这能让你做到：改按键不改玩法代码；同一套玩法逻辑可以同时支持键盘、手柄和自定义键位。

### 3.2 输入 → 意图 → 效果：用 ECS 把职责拆开

这是本节最核心的架构决策。

`PlayerControlSystem` **不直接做"种地/浇水/收获"**，它只负责把输入翻译成 ECS 世界里的意图——写组件、打标签、发事件。具体来说：

| 意图 | 写入的组件/标签 | 谁来消费 |
|------|----------------|---------|
| 移动方向 + 速度 | `VelocityComponent` | `MovementSystem`（做碰撞解析并落地到 `TransformComponent`） |
| 动画状态（Walk/Idle/Hoe…） | `StateComponent` + `StateDirtyTag` | `AnimationSystem`（切换对应动画） |
| 当前持有的工具/种子 | `ActorComponent.tool_` / `.hold_seed_` | 控制系统自身 + 快捷栏 UI |
| 当前目标格 | `TargetComponent`（世界坐标 + 颜色） | `RenderTargetSystem`（画目标框）、动画事件系统（命中位置） |
| 动作锁定 | `ActionLockTag` | 控制系统自身（锁住期间不移动/不刷新目标） |

"效果落地"由后续系统完成——比如动画关键帧触发 `UseToolEvent` / `UseSeedEvent`，再由 `FarmSystem` / `CropSystem` 等具体玩法系统消费。这条完整的链路我们留到 [物品使用与农场循环](30-物品使用与农场循环.md) 详解，本节只关注到"控制系统发出意图"为止。

**为什么要这样拆？** 因为如果 `PlayerControlSystem` 直接调用"种地"逻辑，它就会和农场系统、作物系统、动画系统全部耦合在一起。而现在，控制系统只需要关心"玩家想做什么"，至于"做了之后世界怎么变"是别人的事。这种拆分让每个系统都可以独立测试、独立修改。

#### 连续输入 vs 离散输入：两种消费模式

`PlayerControlSystem` 用两种方式从 `InputManager` 获取输入：

| 模式 | 典型场景 | API | 调用时机 |
|------|----------|-----|----------|
| **轮询（polling）** | 移动（WASD） | `isActionDown("move_up"_hs)` | `update()` 每帧检查 |
| **回调（callback）** | 鼠标点击 / 快捷栏切换 | `onAction("mouse_left"_hs).connect<&callback>()` | 状态变化瞬间触发 |

为什么这么分？

- **移动**是"持续意图"——只要按住就要生效，松手就归零。每帧轮询正好匹配这种语义：按住 → `isActionDown()` 返回 `true` → 设置速度；松开 → 返回 `false` → 速度归零。
- **点击/切换**是"离散事件"——只关心"按下的那一帧"。如果放在 `update()` 里用 `isActionPressed()` 来检查，逻辑上可行但会让代码变成一大堆 `if` 分支。注册回调让代码更清晰：每个离散动作一个处理函数，职责一目了然。

这也呼应了"输入系统"中 `InputManager` 同时提供 `isActionDown()` 与 `onAction()` 两套 API 的设计意图。

#### 快捷栏选择：事件驱动的工具/种子切换

按数字键 `1~0` 切换快捷栏时，发生了一条事件链：

![快捷栏事件链](diagrams/L25_hotbar_event_chain.png)

玩家按下 `hotbar_3` → `PlayerControlSystem` 调用 `switchToHotbarSlot(2)` 切换到第 3 个槽位 → 根据槽位里的物品，dispatch `SwitchToolEvent` 或 `SwitchSeedEvent` → 多个订阅者各自响应（控制系统更新 `ActorComponent`、快捷栏 UI 更新高亮、其他关心"当前选择"的系统同步状态）。

**为什么要绕一圈发事件，而不直接写 `ActorComponent`？**

因为"当前选了什么"不只有 `PlayerControlSystem` 关心——快捷栏 UI 需要更新高亮，物品提示需要知道当前工具，甚至音效系统可能需要根据工具类型切换手持音效。事件是广播机制，一次 dispatch，所有订阅者各自响应，避免控制系统逐个通知每个依赖方。

值得一提的是，`PlayerControlSystem` 用了一个巧妙的 C++ 技巧来注册 10 个快捷栏回调：

```cpp
// 编译期生成 10 个动作 ID
static constexpr std::array<entt::id_type, 10> HOTBAR_ACTION_IDS = {
    entt::hashed_string{"hotbar_1"}.value(),
    // ... hotbar_2 ~ hotbar_10
};

// 用 index_sequence 展开，为每个槽位生成独立的回调函数
template <std::size_t... Is>
void connectHotbarSlots(std::index_sequence<Is...>) {
    (input_manager_.onAction(HOTBAR_ACTION_IDS[Is])
        .connect<&PlayerControlSystem::onHotbarSlot<static_cast<int>(Is)>>(this), ...);
}
```

这样只需一行调用 `connectHotbarSlots(std::make_index_sequence<10>{})` 就完成了全部注册——不需要手写 10 遍，也不需要运行时循环，每个回调都是独立的编译期函数指针。

### 3.3 坐标系转换链路：window → logical → world → tile

鼠标指向 tile 的链路是 [玩家控制与相机](27-玩家控制与相机.md) 最容易踩坑的部分。我们先看全貌：

![坐标系转换链路](diagrams/L25_coord_chain.png)

拆成三段理解：

**第一段：window → logical（`InputManager` 负责）**

SDL 给你的鼠标坐标是 window 坐标（物理像素），但《迷你农场》使用信箱渲染（letterbox），实际画面可能不占满整个窗口。`InputManager` 会把 window 坐标换算成"逻辑坐标"——即画面内容区域的坐标，已经处理好了高 DPI 和信箱偏移。

**第二段：logical → world（`Camera` 负责）**

逻辑坐标是"屏幕空间"的，而我们需要知道鼠标指向"世界"的哪个位置。`Camera::screenToWorld()` 做这件事：

```cpp
glm::vec2 screenToWorld(const glm::vec2& screen_pos) const {
    const glm::vec2 centered = screen_pos - logical_size_ * 0.5f;  // 以屏幕中心为原点
    return centered / zoom_ + position_;  // 除以缩放、加上相机位置
}
```

注意这个计算受 `position_`（相机位置）和 `zoom_`（缩放级别）两个因素影响。所以即使鼠标没动，只要相机移动或缩放变化，`screenToWorld` 的结果也会变——这就是为什么目标格需要每帧更新。

**第三段：world → tile（`SpatialIndexManager` 负责）**

世界坐标是连续的浮点数，但工具/种子的作用目标是离散的 tile。`SpatialIndexManager` 提供两个关键 API：

- `getTileCoordAtWorldPos(world_pos)` → 返回整数 tile 坐标 `glm::ivec2`
- `getRectAtWorldPos(world_pos)` → 返回 tile 的矩形区域（位置 + 尺寸）

`PlayerControlSystem` 用前者做范围判断，用后者算出目标格的中心位置——这保证了目标框总是**对齐到 tile 网格**，不会出现"偏半格"的问题。

**常见坑：为什么鼠标和目标框"对不齐"？**

如果你自己实现类似功能时遇到目标框偏移，排查路径通常是这条链路的某一段出了问题：

1. letterbox 偏移没算对 → logical 坐标就是错的
2. `screenToWorld` 用了过期的相机状态（更新顺序问题）→ world 坐标偏了
3. tile 大小与空间索引不一致 → tile 网格对不上

### 3.4 目标选择（Targeting）= 范围门控 + 可视化反馈

在《迷你农场》里，"目标格"不是全地图都能选。`PlayerControlSystem` 在每帧更新时做了三个判断：

**第一步：是否需要显示目标？**

只有当玩家手持工具或种子时，才需要显示目标格。如果空手，直接给目标实体加上 `InvisibleTag`，隐藏目标框。

**第二步：范围门控。**

计算鼠标所在 tile 与玩家所在 tile 的距离：

```cpp
auto player_tile = spatial_index_manager_.getTileCoordAtWorldPos(player_pos);
auto mouse_tile  = spatial_index_manager_.getTileCoordAtWorldPos(mouse_world_pos);
int dx = mouse_tile.x - player_tile.x;
int dy = mouse_tile.y - player_tile.y;

if (std::abs(dx) > TOOL_TARGET_TILE_RANGE || std::abs(dy) > TOOL_TARGET_TILE_RANGE)
    return std::nullopt;  // 超出范围，不显示
```

`TOOL_TARGET_TILE_RANGE` 默认为 2，即以玩家为中心的 5x5 邻域。超出范围就返回"无目标"，`PlayerControlSystem` 会把目标框隐藏。

**第三步：对齐到 tile 中心。**

在范围内时，用 `getRectAtWorldPos()` 拿到 tile 的矩形，然后取中心点作为 `TargetComponent` 的 `position_`。这保证目标框精确对齐到 tile 网格。

这个设计既是**玩法规则**（你不能隔着半张地图用锄头），也是**用户体验**——目标框的显示/隐藏让玩家一眼就知道"当前能操作哪里、不能操作哪里"。

### 3.5 动作锁（ActionLock）+ 动画事件：让命中位置稳定可复现

想象这个场景：玩家点击了一个 tile 使用锄头，`StateComponent` 切换到 `Action::Hoe`，挥锄动画开始播放。动画持续若干帧，在某一帧的关键帧触发 `UseToolEvent`——这一帧才是"真正命中"的时刻。

问题来了：如果在动画播放期间，玩家的移动和鼠标仍在实时刷新目标位置，那么关键帧触发时命中的 tile 可能已经不是点击时看到的那个了。**"看到的"和"命中的"不一致——这是 bug。**

解决策略是**动作锁**，分三步：

1. **点击瞬间**：确定目标 tile，写入 `TargetComponent`，给玩家加上 `ActionLockTag`。
2. **锁定期间**：`PlayerControlSystem` 检测到 `ActionLockTag` 存在，**跳过移动和目标刷新**——速度设为零，目标位置冻结。
3. **动画关键帧触发**：动画事件系统在 `"tool_hit"` / `"seed_plant"` 帧 enqueue 对应事件（`UseToolEvent` / `UseSeedEvent`），具体玩法系统消费事件后移除 `ActionLockTag`，玩家恢复自由。

![动作锁 + 动画事件时间线](diagrams/L25_action_lock_timeline.png)

这个设计保证了"看到的目标框"和"真正命中的 tile"在整个动作期间保持一致。

还有一个细节：点击触发动作时，`PlayerControlSystem` 会根据目标位置计算朝向并写入 `StateComponent.direction_`。这样玩家的 sprite 会面向点击的方向播放动作动画，视觉上更自然。

**工具 vs 种子的优先级**：当玩家同时持有工具和种子时（逻辑上不应该发生，但快捷栏切换的边界情况可能出现），种子的优先级高于工具——因为"种地"是一个更精确的意图（需要消耗种子库存），应该优先响应。

## 4. 相机跟随与缩放

### 4.1 `CameraFollowSystem`：平滑跟随的工程实现

`CameraFollowSystem` 的职责很聚焦：让相机跟着玩家走，同时响应滚轮缩放和中键重置。

**跟随逻辑**的核心是**指数衰减插值**：

```cpp
const float lerp_factor = 1.0f - std::exp(-follow_speed_ * delta_time);
auto new_pos = glm::mix(camera_pos, player_pos, lerp_factor);
camera_.setPosition(new_pos);
```

为什么用 `1 - exp(-speed * dt)` 而不是简单的 `speed * dt`？

- **帧率无关**：线性插值 `speed * dt` 在高帧率和低帧率下的视觉效果不同；指数衰减在数学上是帧率无关的。
- **自然减速**：相机离目标越远追得越快、越近追得越慢，到了 `stop_distance_threshold_`（默认 2 像素）以内就停下。这避免了最后几个像素的"抖动"。
- **可调参数**：`follow_speed_`（默认 5.0）越大追得越紧，越小越"悠闲"。

**缩放逻辑**同样简洁：

```cpp
float wheel_y = input_manager_.getMouseWheelDelta().y;
camera_.zoom(wheel_y * CAMERA_ZOOM_STEP_PER_WHEEL_TICK);  // 每滚一格 ±0.15
```

中键按下时重置缩放到默认值（2.0x）：

```cpp
if (input_manager_.isActionPressed("camera_reset_zoom"_hs)) {
    camera_.setZoom(DEFAULT_CAMERA_ZOOM);
}
```

### 4.2 为什么"边界约束"下沉到 `Camera` 而不是 `CameraFollowSystem`？

`Camera::setPosition()` 内部会自动调用 `clampPosition()`，如果设置了 `limit_bounds_`，相机位置会被约束在地图边界内。

为什么不让 `CameraFollowSystem` 来做 clamp？

- **`Camera` 可能被多个系统修改**：不只跟随系统，未来可能有镜头抖动、过场动画平移、调试模式手动控制等。如果 clamp 放在跟随系统里，其他修改相机的代码就绕过了边界约束。
- **单一职责**：clamp 是"相机的物理约束"，不是"跟随策略的一部分"。下沉到 `Camera` 后，不管谁修改了相机位置，clamp 都会自动生效。

`clampPosition()` 的实现考虑了缩放级别：

```cpp
glm::vec2 view_size = logical_size_ / zoom_;         // 当前视口的世界大小
glm::vec2 half_size = view_size * 0.5f;
glm::vec2 min_pos   = bounds.pos + half_size;         // 相机最小位置
glm::vec2 max_pos   = bounds.pos + bounds.size - half_size; // 相机最大位置
position_ = glm::clamp(position_, min_pos, max_pos);
```

注意：当视口比地图还大时（比如极度缩小），`max_pos < min_pos`，此时直接把相机居中到地图中心，避免出现"相机在两个边界之间来回弹跳"的问题。

### 4.3 缩放 clamp

`Camera` 的 `setZoom()` 和 `zoom()` 都会把值约束到 `[min_zoom_, max_zoom_]` 范围内：

```cpp
void Camera::setZoom(float z) {
    zoom_ = glm::clamp(z, min_zoom_, max_zoom_);
    clampPosition();  // 缩放变化后位置可能越界，重新 clamp
}
```

注意 `setZoom()` 后面还跟了一次 `clampPosition()`——因为缩放改变了视口大小，原本在边界内的相机位置可能因为视口变大而"越界"了。

## 5. 架构与数据流

### 5.1 模块图：从输入到目标选择与相机跟随

![输入→意图→效果 模块图](diagrams/L25_input_intent_effect.png)

> 注意图中的虚线自环：`PlayerControlSystem` 在切换快捷栏时 dispatch `SwitchToolEvent` / `SwitchSeedEvent`，同时自己也是这些事件的订阅者（更新 `ActorComponent`）。这使得 UI 等其他系统也能同步响应，而不需要控制系统挨个通知。

从这张图可以看出，`PlayerControlSystem` 是一个"中枢"——它读取 `InputManager` 和 `Camera` 的状态，写入多个组件，通过事件与其他系统间接通信。但它**不读取也不写入**任何具体玩法的结果（比如耕地状态、作物数据）。这条边界是刻意维护的。

### 5.2 顺序敏感点：update 顺序再一次至关重要

回顾 [游戏场景初始化与系统编排](26-游戏场景初始化与系统编排.md) 的核心结论，再看本节涉及的系统：

**`PlayerControlSystem` 依赖：**
- 本帧的输入状态（`InputManager` 已经 `update()` 过）
- 本帧的相机状态（用于 `screenToWorld`）

**`CameraFollowSystem` 依赖：**
- 玩家的最新位置（`MovementSystem` 已经把 `VelocityComponent` 落地到 `TransformComponent`）

所以正确的 update 顺序是：

```
InputManager.update()        // 1. 采集输入
    ↓
PlayerControlSystem.update() // 2. 输入→意图
    ↓
MovementSystem.update()      // 3. 速度→位移（含碰撞解析）
    ↓
CameraFollowSystem.update()  // 4. 相机跟随（基于最新位置）
```

如果把相机跟随放在移动系统之前，相机就会跟着"上一帧的位置"走——在高速移动或低帧率时会出现明显的"拖尾感"。

当你未来想加"镜头抖动""缩放到鼠标""多目标平均跟随"等功能时，第一步不是写代码，而是先问自己：

> 这个功能依赖什么状态？它应该被放在 update 的哪个阶段？

3. **`src/game/system/camera_follow_system.*`** + **`src/engine/render/camera.*`**：跟随（指数衰减插值）、缩放（滚轮/重置）、边界 clamp。
4. **`src/engine/input/input_manager.*`**：动作状态机（`PRESSED/HELD/RELEASED`）与逻辑鼠标坐标。如果 [输入系统](15-输入系统.md) 的内容还记得，可以快速跳过。
5. **`src/engine/spatial/spatial_index_manager.*`**：`getTileCoordAtWorldPos` 与 `getRectAtWorldPos`——目标格落地的关键桥梁。
6. **`src/game/system/animation_event_system.cpp`**：动画关键帧到玩法事件的桥——`"tool_hit"` → `UseToolEvent`，`"seed_plant"` → `UseSeedEvent`。本课只理解链路存在即可，[物品使用与农场循环](30-物品使用与农场循环.md) 详解落地效果。

## 7. 练习

### 练习 1：目标格"按需更新"

- **目标**：当鼠标指向的 tile 没有变化时，不重复计算/写入 `TargetComponent`。行为保持不变，但减少不必要的写入。
- **验收标准**：
  - 鼠标不动时目标框稳定；鼠标跨 tile 时目标框正确跳格
  - 玩家移动 / 相机移动导致鼠标 world 位置变化时，目标框仍能正确更新
  - 不引入新的复杂抽象；保持改动小而可读
- **提示线索**：
  - `src/game/system/player_control_system.cpp`（`resolveTargetPosition` 与 `syncTargetComponent`）
  - 可以缓存上一帧的 tile 坐标，只在 tile 坐标变化时才更新 `TargetComponent`
  - 注意边界情况：相机缩放变化也会导致同一屏幕位置对应不同的 world 坐标
- **提交方式**：GitHub PR

### 练习 2（可选）：增加"玩家控制"调试面板

- **目标**：加一个轻量 Debug 面板（或扩展现有面板），实时显示：logical mouse / world mouse / mouse tile / player tile / in-range / 当前工具 / 种子。
- **验收标准**：
  - 面板展示的信息足够定位"鼠标与目标格不对齐""范围门控不生效"等问题
  - 不做 profiler，不引入新依赖，渲染开销保持轻量
- **提示线索**：
  - `docs/player_control.md`（你要展示哪些字段）
  - `src/game/debug/*`（新建或扩展一个 panel）
  - `src/engine/debug/debug_ui_manager.*`（面板注册入口）

## 8. 小结

这节课的要点：

1. **输入系统的正确落地位置**：`InputManager` 提供动作状态（语义层），`PlayerControlSystem` 把动作翻译成 ECS 意图（组件 + 事件）。"意图"与"效果"分离，是保持系统解耦的关键。
2. **目标选择的本质**：一条坐标系转换链路（window → logical → world → tile）+ 范围门控（`TOOL_TARGET_TILE_RANGE`）+ 可视化反馈（`TargetComponent` + `InvisibleTag`）。坐标转换是最常踩坑的环节，排查时沿着链路逐段验证。
3. **相机的工程化要点**：平滑跟随（指数衰减插值）+ 缩放（滚轮/重置）+ 边界约束（`Camera` 统一 clamp）。约束下沉到 `Camera` 而不是跟随系统，是为了让所有修改相机的代码都受到保护。
