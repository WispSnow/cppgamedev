# 游戏架构设计：分层、ECS 与数据驱动

上节课我们把项目成功构建并运行起来：configure/build/run 三阶段、依赖管理策略、运行时资源与工作目录的关系。

从这节课开始，我们进入真正的架构主线：**在不阅读实现代码的前提下，建立《迷你农场》的宏观心智模型**。你可以把这个模型理解为一张"建筑平面图"——有了它，你就不需要走遍每间房才能知道厨房在哪。具体来说，它能帮助你：
- 快速回答"这个功能应该在哪个模块"
- 理解模块间的依赖方向与职责边界
- 知道后续每一讲要拆解什么问题

## 本课目标

建立《迷你农场》的架构心智模型，能回答三个问题：
1. 这个仓库按什么逻辑分层组织？各层的职责边界是什么？
2. 运行时有哪些"关键骨架"（Scene、ECS、子系统）？它们如何协作？
3. "数据驱动"在《迷你农场》中是怎么落地的？为什么要这样设计？

## 核心概念

### 1. 为什么需要架构设计？

在小项目里，你可以把所有逻辑堆在一个文件里，项目照样跑得很好。但随着代码量增长到几千甚至几万行，问题会迅速浮现：
- **牵一发动全身**：改一处 bug，莫名其妙引爆另一处功能
- **新人无从下手**：面对几十个源文件，不知道从哪看起
- **复用困难**：想把渲染逻辑搬到另一个项目，发现它和物品栏、存档系统纠缠不清

**架构设计的目标**就是提前解决这些问题：通过清晰的分层与模块边界，让代码**可理解、可维护、可扩展**。

> **类比**：架构设计就像城市规划——住宅区、商业区、工业区各有边界。你不需要了解每栋建筑的内部结构，只凭分区就能快速定位"去哪里买菜"。

### 2. 分层：Engine（可复用）vs Game（具体玩法）

《迷你农场》采用**引擎/游戏分层**的经典模式：

```
src/
├── engine/     # 引擎层：与具体游戏无关的通用能力
│   ├── core/       # GameApp、Context、Time、Config
│   ├── scene/      # Scene 栈、场景生命周期
│   ├── component/  # 引擎通用组件（Transform、Sprite、Collider 等）
│   ├── system/     # 引擎通用系统（Animation、Movement、Render 等）
│   ├── render/     # 渲染器、SpriteBatch、Shader、后处理管线
│   ├── resource/   # 资源管理、纹理/字体/音频缓存
│   ├── input/      # 输入系统、动作映射
│   ├── audio/      # 音频播放器
│   ├── ui/         # UI 框架（布局、交互、预设）
│   ├── spatial/    # 空间索引（碰撞检测、实体查询）
│   └── loader/     # 关卡加载器（Tiled 地图解析）
│
└── game/       # 游戏层：TinyFarm 特定的玩法逻辑
    ├── scene/      # 具体场景（Title、Game、Pause 等）
    ├── system/     # 玩法系统（种植、时间、交互、NPC 等）
    ├── component/  # 游戏特定组件（Crop、Inventory、NPC 等）
    ├── world/      # 世界状态、地图管理
    ├── factory/    # 蓝图管理、实体工厂
    ├── data/       # 游戏数据（GameTime、ItemCatalog）
    ├── save/       # 存档系统
    └── ui/         # 游戏 UI（背包、快捷栏、时钟等）
```

**设计原则**：
- **引擎层不依赖游戏层**：引擎可以被复用到其他游戏项目
- **游戏层依赖引擎层**：调用引擎提供的能力来实现玩法
- **边界清晰**：通过事件、接口解耦，而不是直接引用

你可以把它理解为：**engine 提供工具箱与运行框架，game 负责把工具箱组合成玩法闭环**。

> **常见疑问**：这两层在编译产物上也是分开的吗？是的——引擎层和游戏层分别编译为独立的静态库（`engine_lib` 和 `game_lib`），最终由 `main.cpp` 链接在一起。这种物理隔离进一步保证了依赖方向不会"反转"。

### 3. 运行时骨架：Scene + ECS + 子系统

光有分层还不够——程序运行起来后，各模块如何协作？《迷你农场》的运行时结构可以概括为三个核心部分。

#### Scene（场景栈）

每个 Scene 代表一个完整的游戏状态。《迷你农场》中有这些典型场景：
- **TitleScene**：标题画面
- **SaveSlotSelectScene**：存档选择
- **GameScene**：主游戏
- **PauseMenuScene**：暂停菜单

Scene 以**栈**的形式组织，支持三种操作：
- **Push**：压入新场景（如在游戏中打开暂停菜单）
- **Pop**：弹出当前场景（如关闭暂停菜单，回到游戏）
- **Replace**：清空栈并切换到新场景（如从标题画面进入游戏）

栈结构带来一个关键约定：**更新时只更新栈顶，渲染时从底向上叠加**。这意味着当暂停菜单覆盖在游戏画面上时，底层的游戏逻辑会被"冻结"，但画面仍然可见——暂停菜单半透明地叠在游戏画面之上。

![场景栈操作示意图](diagrams/L02_scene_stack.png)

#### ECS（实体-组件-系统）

ECS 是《迷你农场》组织游戏对象的核心模式，它把传统 OOP 中"一个类既有数据又有行为"的模式拆成三个正交的维度：

- **Entity（实体）**：只是一个 ID（`uint32_t`），本身没有任何数据或行为
- **Component（组件）**：纯数据结构，挂载在 Entity 上（如位置、精灵、速度）
- **System（系统）**：纯逻辑，遍历拥有特定组件组合的所有实体并处理它们

![ECS 概念关系图](diagrams/L02_ecs_concept.png)

**为什么不用传统的继承体系？** 想象一下经典的 OOP 设计：`GameObject → Character → Player`。现在要加一个"可被拾取的、会发光的、有动画的掉落物"——你很快就会陷入多重继承的泥潭。而在 ECS 中，掉落物只是一个 Entity，挂上 `TransformComponent` + `SpriteComponent` + `AnimationComponent` + `PickupComponent` 就行了，完全通过**组合**而非继承来定义行为。

《迷你农场》使用 **EnTT** 作为 ECS 框架。一个重要的设计决策是：**每个 Scene 持有自己独立的 `entt::registry`**。这意味着不同场景的实体和组件天然隔离——暂停菜单的 UI 实体不会和游戏世界的角色实体混在一起。

#### 子系统（Subsystem）与 Context

除了 ECS 的 System，还有一类"全局子系统"贯穿整个应用生命周期，不隶属于任何单个 Scene：
- **渲染子系统**：Renderer、Camera、SpriteBatch
- **资源子系统**：ResourceManager（纹理/字体/音频缓存的统一入口）
- **输入子系统**：InputManager（动作映射与状态查询）
- **音频子系统**：AudioPlayer

这些子系统通过 **Context** 统一管理。Context 本质上是一个**依赖注入容器**：在 `GameApp` 启动时创建所有子系统实例，然后通过 Context 聚合它们的引用，再把 Context 注入到每个 Scene 的构造函数中。这样，Scene 和 System 就能方便地获取所需服务，而不需要遍寻全局变量：

```cpp
// GameScene::render() 中的典型用法
void GameScene::render() {
    auto& renderer = context_.getRenderer();   // 从 Context 获取渲染器
    auto& camera = context_.getCamera();       // 从 Context 获取相机

    // 将子系统引用传给 ECS System
    render_system_->update(registry_, renderer, camera);
}
```

注意这里的模式：Scene 从 Context 取出子系统引用，再传递给具体的 System。System 本身不持有 Context 引用，只接收它真正需要的依赖——这让 System 的职责更明确，也更容易测试。

![Context 与子系统关系图](diagrams/L02_context_subsystems.png)

> **ECS System vs 全局子系统**：这两者容易混淆。简单区分——ECS System 处理的是"实体数据"（每帧遍历带有特定组件的实体），全局子系统提供的是"基础设施服务"（渲染、输入、音频等能力）。ECS System 依赖全局子系统来完成工作。

### 4. 数据驱动：把"内容"从"代码"里挪出来

《迷你农场》的"内容"大量来自数据文件而不是硬编码：

| 数据类型 | 文件位置 | 作用 |
|----------|----------|------|
| 蓝图 | `assets/data/actor_blueprint.json` 等 | 定义实体的组件组合（角色、动物等） |
| 物品 | `assets/data/item_config.json` | 物品属性（工具、种子、作物等） |
| 作物 | `assets/data/crop_config.json` | 作物生长阶段与产出 |
| 地图 | `assets/maps/*.tmj` | Tiled 导出的关卡数据 |
| 配置 | `config/*.json` | 窗口、渲染、输入等运行时配置 |
| 资源映射 | `assets/data/resource_mapping.json` | UI 预设、音效等资源路径映射 |

**数据驱动的好处**：
- **加内容不改代码**：新增一种作物只需在 `crop_config.json` 里加一条记录，不需要写新的 C++ 类
- **可配置可调试**：数值平衡不需要重新编译，改完 JSON 重启即可生效
- **关注点分离**：策划/美术改数据，程序员改逻辑，各自独立工作

![数据驱动示意图](diagrams/L02_data_driven.png)

> **常见陷阱**：数据驱动不等于"什么都塞进 JSON"。核心的系统逻辑（如碰撞检测算法、渲染管线流程）仍然应该写在代码里。数据驱动适合的是**内容和配置**——那些经常变化、不影响程序结构的部分。

### 宏观骨架图

有了前面的铺垫，我们可以把整个架构串联起来。下图展示了《迷你农场》从入口到运行时的完整架构：

![宏观架构图](diagrams/L02_architecture_overview.png)

### 理解这张图的三个要点

1. **启动入口很薄**：`main` 只是"把应用启动起来"，真正的"游戏进入逻辑"在 `GameEntry`
2. **场景承载状态**：不同 Scene 组织不同的 UI/系统/实体集合，通过 SceneManager 管理生命周期
3. **系统驱动运行**：每帧由 System 处理输入、更新世界、渲染画面；世界的"内容"来自数据层

### 依赖原则

图中的箭头表示"依赖"——游戏层依赖引擎层，引擎层依赖平台层。**反过来不行**。

这在代码级别意味着：
- 引擎层的代码不能 `#include` 游戏层的头文件
- 如果引擎需要知道游戏层的信息，通过**事件**或**接口**实现（这个话题我们会在 [事件系统](06-事件系统.md) 详细展开）

## 小结

回到开头的三个问题，现在你应该能清晰地回答：

1. **仓库如何分层？** `engine` 提供与游戏无关的通用能力（渲染、输入、资源、UI 等），`game` 基于引擎实现《迷你农场》的具体玩法。两层分别编译为独立的静态库，依赖方向单向：game → engine。
2. **运行时有哪些骨架？** Scene 栈管理游戏状态的切换与叠加；ECS 通过"实体 = ID + 组件组合，系统遍历处理"的模式组织游戏对象；全局子系统（渲染、输入、音频等）通过 Context 注入到 Scene 中，供 System 按需使用。
3. **数据驱动如何落地？** 蓝图、物品、作物、地图等内容全部由 JSON/TMJ 文件定义，代码只负责"读取并解释数据"。加内容不改代码，改数值不需要重编译。

这个心智模型会贯穿整个课程。后续每一讲拆解具体模块时，你都可以回来看这张"地图"定位自己在哪。
