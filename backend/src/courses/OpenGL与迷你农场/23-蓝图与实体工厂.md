# 蓝图与实体工厂：把"角色/动物/作物"变成可配置数据

上节课我们拆开了构建阶段的内部分工：`LevelLoader` 负责遍历 Tiled 数据并分派，`BasicEntityBuilder` 负责通用组件构建，`game::EntityBuilder` 通过 type dispatch 把不同对象送到各自的构建分支。

在上节课的最后，你应该注意到了一个关键细节——当 `EntityBuilder::build()` 遇到 `type="actor"` 或 `type="animal"` 时，它并没有自己组装组件，而是直接把工作交给了 `EntityFactory`：

```cpp
// src/game/loader/entity_builder.cpp
void EntityBuilder::buildActor(entt::id_type name_id) {
    auto position = glm::vec2(object_json_->value("x", 0.0f),
                              object_json_->value("y", 0.0f));
    // ...
    entity_id_ = entity_factory_.createActor(name_id, position);
}
```

为什么 builder 不直接 `emplace` 组件？因为"复杂实体"需要的组件太多了——一个角色至少需要 Transform、Sprite、Animation、Collider、Audio、Velocity、State、Render、Name 等十来个组件。如果这些拼装逻辑散布在 builder 和各个系统里，你很快就会得到：

- **组件组合重复**：actor 和 animal 都需要 Transform/Sprite/Animation/Collider/Audio/...，到处写一遍
- **内容扩展成本高**：加一个新 NPC 就要改代码，而不是改数据
- **排错困难**：蓝图 key、动画 id、音效 key——出问题时不知道断在哪一环

本节课要解决的正是这个问题：如何把"复杂实体的装配"抽成一条 **数据驱动的、可扩展、可排错** 的工程路径。

## 本节目标与问题定义

用一句话定义本节目标：

> 理解《迷你农场》如何用 `BlueprintManager + EntityFactory` 把 JSON 蓝图变成运行时 ECS 组件组合（角色/动物/作物），从而实现"加新内容主要改数据而不是改核心逻辑"，并掌握扩展与排错的定位路径。

这句话可以拆成三个具体问题：

1. **数据怎么表达内容差异？**
同样是"actor/animal/crop"，哪些差异应该写在 JSON 数据里（sprite/animations/sounds/行为参数/生长阶段），哪些差异必须留在代码里（装配规则/组件组合/系统语义）？

2. **装配点应该放在哪里？**
为什么需要 `EntityFactory` 作为"复杂实体的唯一装配点"，而不是在 loader/system 里到处拼组件？

3. **扩展与排错怎么做？**
我新加一个 NPC 或动物，为什么不出现？我填了一个 sound key，为什么没声音？蓝图 key 拼错了怎么定位？

完成本节后，你至少能做到：
- 读懂三份蓝图文件（actor/animal/crop）的最小 schema 与命名约定，并能自己加新条目
- 读懂从"蓝图 key"到"实体组件组合"的完整主链路
- 能用 Blueprint Inspector 快速定位"蓝图是否加载 / key 是否匹配 / 资源引用是否缺失"

## 核心概念

### 3.1 蓝图（Blueprint）是一张"组件配方"

在很多引擎中，"蓝图"意味着可视化脚本或继承树。在《迷你农场》里，蓝图的定义要简单得多——它就是一张 **组件配方（component recipe）**：

- **配方的原料**：JSON 文件中的纯数据（精灵路径、动画帧、音效 key、行为参数……）
- **配方的产物**：一组 ECS 组件，挂载在同一个实体上
- **配方的解释器**：`BlueprintManager`——把 JSON 解析成 C++ 的 typed structs
- **配方的执行器**：`EntityFactory`——把 typed structs 装配进 `entt::registry`

这条分工链定义了三层明确的边界：

| 层次 | 负责 | 不负责 |
|------|------|--------|
| **JSON 数据** | 表达"内容差异"——sprite / animations / sounds / 参数 | 不表达装配规则、组件组合 |
| **BlueprintManager** | 解析 JSON → typed structs；提供查询接口 | 不创建实体、不触碰 registry |
| **EntityFactory** | 查询蓝图 → 装配组件组合 → 注册进 registry | 不解析 JSON、不关心数据从哪来 |
| **System** | 消费组件（动画、音频、作物生长……） | 不反过来去"解析蓝图文件" |

这种分工是刻意的。它意味着——当你想加一个新 NPC 时，你修改的是 **JSON 数据**，而不是 `EntityFactory` 或系统的代码。只有当你需要新字段（比如给动物增加一个"进食偏好"参数）时，才需要沿着 `blueprint.h → blueprint_manager.cpp → entity_factory.cpp` 三个文件往下走。

![EntityFactory：组件配方](diagrams/L21_component_recipe.png)

### 3.2 "启动期加载"与"运行期生成"：两条路径，同一套蓝图

蓝图数据在项目中会在两个阶段被使用，但不管在哪个阶段，实体的创建都走同一条路——通过 `EntityFactory`。

**阶段一：启动期（Boot）——把 JSON 加载进内存**

`GameScene::init()` 的最开头就会调用 `ensureBlueprintManager()`，把三份蓝图文件一次性加载进 `BlueprintManager`：

```cpp
// src/game/scene/game_scene.cpp
bool GameScene::ensureBlueprintManager() {
    blueprint_manager_ = std::make_shared<game::factory::BlueprintManager>();
    blueprint_manager_->loadActorBlueprints("assets/data/actor_blueprint.json");
    blueprint_manager_->loadAnimalBlueprints("assets/data/animal_blueprint.json");
    blueprint_manager_->loadCropBlueprints("assets/data/crop_config.json");
    // ...
}
```

紧接着，`initFactory()` 会创建 `EntityFactory`，并把 `BlueprintManager` 注入给它：

```cpp
bool GameScene::initFactory() {
    entity_factory_ = std::make_unique<game::factory::EntityFactory>(
        registry_, *blueprint_manager_, &spatial_index_manager, &auto_tile_library);
}
```

从这一刻开始，**蓝图表就是只读的、常驻内存的查询源**；工厂随时可以根据蓝图 key 创建实体。

**阶段二：运行期（Runtime）——在需要的时候创建实体**

运行期有两类典型的调用入口：

| 调用场景 | 入口 | 工厂方法 |
|---------|------|---------|
| 地图加载期 | `EntityBuilder::buildActor()` | `entity_factory_.createActor(name_id, position)` |
| 地图加载期 | `EntityBuilder::buildAnimal()` | `entity_factory_.createAnimal(name_id, position)` |
| 玩法运行期 | `FarmSystem::plantSeed()` | `entity_factory_.createCrop(crop_type_id, position, day)` |

关键的一致性保证是：

> 无论实体是在地图加载时生成，还是在玩家种植时生成，**装配逻辑都在 `EntityFactory` 里**——同一条蓝图，同一套组件组合，同一个装配点。

这不是巧合，而是设计选择。如果 `FarmSystem` 自己拼组件，它和工厂之间就会出现"看起来差不多但默认值不同"的分裂，最终让排错变得困难。

### 3.3 约定比字段更重要：key 命名与 id 规则

数据驱动系统最怕的不是算法错误，而是"我以为写对了，其实写错了 key"。本节你需要记住三条最关键的约定（完整细节见 `docs/blueprints.md`）：

**约定 1：Blueprint key 来自地图 object 的 `name`（或系统传入的 type/id）**

例如：
- Tiled 的 object layer 里有一个点对象，`type="actor"` 且 `name="friend"` → 运行时会用 `"friend"` 作为 key 查询 actor blueprint
- `FarmSystem` 种植时传入 `crop_type_id` → 用它查询 crop blueprint

Blueprint key 的匹配是 **hash-based** 的（通过 `entt::hashed_string`），大小写敏感。写错一个字母，查询就会失败——你不会得到编译错误，只会在运行时看到 `"未找到角色蓝图"` 的日志。

**约定 2：动画 id 的展开规则——`<anim>_<dir>`，left/right 自动镜像**

这是最容易出错的约定之一。以 `actor_blueprint.json` 中的 `idle` 动画为例：

```json
"idle": {
    "path": "assets/.../Idle.png",
    "direction": ["down", "up", "right"],
    "frames": [0, 1, 2, 3],
    ...
}
```

`BlueprintManager::parseAnimationsMap()` 会把这个配置展开成四个动画 id：

```text
idle_down   ← direction[0]，对应第 1 行
idle_up     ← direction[1]，对应第 2 行
idle_right  ← direction[2]，对应第 3 行
idle_left   ← 自动镜像 idle_right（翻转 flip_horizontal）
```

![动画 ID 展开规则](diagrams/L21_animation_id_expansion.png)

注意关键的一点：`EntityFactory::createMobBase()` 会用 `"idle_down"` 作为默认动画：

```cpp
addAnimationComponent(entity, animations, "idle_down"_hs);
```

这意味着——**你的蓝图至少要能生成 `idle_down` 这个动画 id**。如果 `direction` 数组里既没有 `"down"`，也没有配置无方向的 `idle` 动画，工厂在创建实体时不会报错，但实体刚创建出来就找不到默认动画。

> **常见陷阱**：你在 `direction` 里只写了 `["left", "up"]`，会生成 `idle_left`、`idle_up`、`idle_right`（镜像），但不会有 `idle_down`——默认动画缺失。

**约定 3：音效 key 必须在 `resource_mapping.json` 里有映射**

蓝图里的 `"sound": "cow_moo"` 只是一个语义 key，不是文件路径。它需要通过 `assets/data/resource_mapping.json` 映射到真实的音频文件路径，才能被音频系统播放（[资源系统](13-资源系统.md)/L14 的连接点）。如果映射缺失，音效不会报错——只是静默不播放。

## 架构与数据流

### 4.1 本节主链路：从 JSON 到实体

从宏观上看，"蓝图驱动的实体创建"是一条三段式链路：

```text
加载（Load）         →    装配（Assemble）      →    消费（Consume）
JSON files              EntityFactory               Systems
  ↓                        ↓                          ↓
BlueprintManager        registry.emplace(...)       CropSystem
(parse → typed structs)  (组件组合)                 ActionSoundSystem
                                                    AnimationSystem ...
```

![从 JSON 到实体：加载 → 装配 → 消费](diagrams/L21_module_overview.png)

你可以把这张图当成"扩展路径地图"：

| 你想做什么 | 改哪里 |
|-----------|-------|
| 加新内容（新 NPC / 新动物 / 新作物） | `assets/data/*.json` + 地图 object（纯数据，不改代码） |
| 加新字段（新参数，例如"攻击力"） | `blueprint.h`（struct 定义）→ `blueprint_manager.cpp`（解析）→ `entity_factory.cpp`（装配） |
| 排错（为什么不生效） | 从 `GameScene` 的加载入口 → Blueprint Inspector → 调用点逐级定位 |

### 4.2 `createMobBase`：DRY 的核心——actor 和 animal 共享的装配基底

打开 `entity_factory.cpp`，你会发现 `createActor` 和 `createAnimal` 的第一步都是调用同一个私有方法 `createMobBase`。这是因为角色和动物共享大量基础组件：

```text
createMobBase(name_id, display_name, speed, sprite, sounds, animations, position):
  entity = registry.create()
  addTransformComponent(entity, position)       // 位置
  addSpriteComponent(entity, sprite)            // 精灵
  addAnimationComponent(entity, animations,     // 动画（默认 idle_down）
                        "idle_down"_hs)
  addAudioComponent(entity, sounds)             // 音频
  registry.emplace<ActorComponent>(entity, speed, Tool::None)
  registry.emplace<CircleCollider>(entity, ...)  // 碰撞
  registry.emplace<VelocityComponent>(entity)    // 速度
  registry.emplace<RenderComponent>(entity)      // 渲染
  registry.emplace<NameComponent>(entity, ...)   // 名字
  registry.emplace<StateComponent>(entity)       // 状态
  registry.emplace<SpatialIndexTag>(entity)      // 空间索引
```

然后 `createActor` 和 `createAnimal` 在这个基底上各自**补差异**：

**`createActor` 的差异路径：**
- 如果是 `"player"` → 加 `PlayerTag`、初始化物品栏（`InventoryComponent`）和快捷栏（`HotbarComponent`），并填入起始工具
- 如果不是 player → 加 `NPCTag`，根据蓝图配置添加 `WanderComponent`（游走行为）和 `DialogueComponent`（对话触发）

**`createAnimal` 的差异路径：**
- 加 `NPCTag` + `AnimalTag`
- 如果蓝图有音效配置 → 加 `ActionSoundComponent`（动作音效）
- 加 `WanderComponent`（动物都会游走）
- 加 `SleepRoutine`（夜间睡眠行为，默认 true）
- 加 `AnimalBehaviorState`（进食行为定时器）
- 如果蓝图有对话 → 加 `DialogueComponent`

这种"基底 + 差异补齐"的模式就是工厂模式在 ECS 项目中的典型落地。它让组件装配集中在一处，避免了在 loader、system、builder 之间到处拼组件。

### 4.3 为什么 `EntityFactory` 是"唯一装配点"

本项目坚持一个工程规则：

> **复杂实体（多个组件组合）由工厂统一装配。**

这有三个好处：

1. **DRY**：`createMobBase` 把 actor/animal 共有的十几个组件收敛到一处，上层方法只补差异。
2. **一致性**：装配顺序与默认值统一——例如默认动画 `idle_down`、Collider 偏移、`MapId` 附着。无论是地图加载时创建的动物，还是未来可能通过事件生成的动物，组件组合都一致。
3. **可演进**：未来给所有角色/动物加组件（比如"脚步音效"、"受击闪烁"），只需要改 `createMobBase` 一处，所有复杂实体自动获得新能力。

反过来，如果在 loader / system 到处装配：
- 你会得到一堆"看起来差不多但细节不一致"的拼装代码
- 某天你发现"NPC A 有碰撞，NPC B 却没有"——原因是两段代码各自加了不同的组件，但没人发现差异

### 4.4 蓝图的解析细节：从 JSON 到 typed structs

`BlueprintManager` 内部通过一组 `parse*` 辅助函数完成 JSON 到 C++ 结构体的转换。理解这些函数有助于你在扩展蓝图字段时知道"在哪里加代码"：

| 辅助函数 | 职责 | 产物 |
|---------|------|------|
| `parseSprite(json)` | 解析 `path/src_size/position/dst_size/pivot` | `SpriteBlueprint` |
| `parseOneAnimation(json)` | 解析单个动画的帧信息和事件 | `AnimationBlueprint` |
| `parseAnimationsMap(json)` | 遍历所有动画条目，处理 direction 展开与 left/right 镜像 | `map<id, AnimationBlueprint>` |
| `parseSound(json)` | 解析触发器名 → sound key / 概率 / 冷却 | `SoundBlueprint` |
| `parseMobBlueprintCommon(json)` | 聚合调用上面四个函数，提取共有字段 | `MobBlueprintCommon`（内部结构） |

Actor 和 Animal 的 JSON 结构高度相似（都有 sprite/animations/sounds/speed/wander_radius 等），所以 `BlueprintManager` 用 `parseMobBlueprintCommon` 提取共有部分，然后 `loadActorBlueprints` 和 `loadAnimalBlueprints` 各自补差异字段。

Crop 的结构不同于 actor/animal——它不需要动画和音效，而是用 `stages` 数组描述生长阶段。每个阶段包含一个 `GrowthStage` 枚举、天数要求和贴图配置。`parseCropStages` 会按顺序解析这些阶段，第一个阶段通常应该是 `seed`。

### 4.5 为什么需要 Blueprint Inspector：数据驱动必须可观测

数据驱动系统最常见的问题不是"算法错"，而是"数据没生效"。具体来说，排错时你需要回答三类问题：

| 症状 | 可能原因 | 在 Blueprint Inspector 里看什么 |
|------|---------|-------------------------------|
| NPC/动物没出现 | blueprint key 不匹配（地图 name 拼写 ≠ JSON key） | counts：确认对应类别蓝图数量；lookup：按 key 查询 |
| 有实体但没声音 | sound key 没在 resource_mapping.json 中映射 | missing references：检查未映射的 sound id |
| 有实体但站着不动/白屏 | 缺少 `idle_down` 动画 | lookup → 展开动画列表，确认 `idle_down` 存在 |
| 贴图显示为空白 | sprite path 路径不存在 | missing references：检查缺失的贴图路径 |

打开方式：`F5 → Game Debug Panels → Blueprint Inspector`

Inspector 提供三个核心功能：
- **counts**：一眼确认"蓝图有没有加载成功"（actor / animal / crop 各多少条）
- **lookup**：按 key 查询某个蓝图的完整字段（最常用的排错入口）
- **missing references**：列出缺失的贴图路径和未映射的 sound id

这就是"内容制作/配置"阶段最实用的一类工具：**不是为了 debug 代码，而是为了 debug 数据**。

## 实例解析：三份蓝图文件的结构

为了让"蓝图是配方"这个概念更具体，我们来看看三份蓝图文件各自表达了什么。

### 5.1 `actor_blueprint.json`——角色蓝图

打开这个文件，你会看到顶层是一个 JSON 对象，每个 key 就是一个 blueprint key：

```json
{
    "player": {
        "name": "player",
        "sprite": { "path": "assets/.../Idle.png", "src_size": {...}, "pivot": {...} },
        "animations": {
            "idle":     { "direction": ["down", "up", "right"], "frames": [0,1,2,3], ... },
            "walk":     { "direction": ["down", "up", "right"], "frames": [0,1,2,3,4,5], ... },
            "hoe":      { "direction": ["down", "up", "right"], "events": {"tool_hit": 5}, ... },
            ...
        },
        "speed": 100.0
    },
    "friend": {
        "name": "Lyria",
        "dialogue_id": "friend_intro",
        "wander_radius": 48.0,
        "interact_distance": 64.0,
        ...
    }
}
```

几个要点：
- `"player"` 和 `"friend"` 是 blueprint key，分别对应地图 object 的 `name="player"` 和 `name="friend"`
- 玩家有大量工具动画（hoe/watering/sickle/axe/pickaxe），NPC 只有 idle 和 walk——差异全在数据里
- NPC 多了 `dialogue_id` 和 `wander_radius`，这些字段会被工厂用来决定是否添加 `DialogueComponent` 和 `WanderComponent`
- 动画的 `events` 字段（如 `"tool_hit": 5`）表示在第 5 帧触发一个事件——这是动画系统与工具使用系统的解耦点（[物品使用与农场循环](30-物品使用与农场循环.md) 会展开）

### 5.2 `animal_blueprint.json`——动物蓝图

动物蓝图和角色蓝图结构类似，但多了几个动物特有的字段：

```json
{
    "sheep": {
        "name": "sheep",
        "wander_radius": 32.0,
        "sleep_at_night": true,
        "sounds": {
            "idle": { "sound": "sheep_baa", "probability": 0.35, "cooldown": 7.0 }
        },
        "animations": {
            "idle":  { "direction": ["left", "down", "up"], ... },
            "walk":  { "direction": ["left", "down", "up"], ... },
            "sleep": { "direction": ["left", "down"], ... },
            "eat":   { "direction": ["left", "down"], ... }
        },
        "speed": 10.0
    },
    "cow": { ... }
}
```

几个值得关注的差异：
- **`sleep_at_night`**：控制动物是否在夜间进入睡眠状态（映射到 `SleepRoutine` 组件）
- **`sounds.idle`**：表示在 idle 状态时有 35% 概率播放 `sheep_baa` 音效，冷却 7 秒。这里的 `"sheep_baa"` 是语义 key，最终要通过 `resource_mapping.json` 找到真实文件路径
- **动画多了 `sleep` 和 `eat`**：动物有独立的睡眠和进食行为动画，由 `AnimalBehaviorSystem` 消费
- **`direction` 从 `["left", "down", "up"]` 开始**：注意！这里的 direction 第一个是 `"left"` 而非 `"right"`，镜像规则会自动补上 `right`。但更重要的是——这里没有明确写 `"down"` 在 idle 动画中对应哪一行，你需要理解 `parseAnimationsMap` 的行偏移逻辑

### 5.3 `crop_config.json`——作物蓝图

作物蓝图的结构与前两者不同——它用 `stages` 数组描述生长过程：

```json
{
    "crops": [
        {
            "type": "strawberry",
            "stages": [
                { "stage": "seed",    "days_required": 1, "sprite": { "path": "...Spring Crops.png", "position": {"x": 0, "y": 16}, ... } },
                { "stage": "sprout",  "days_required": 2, "sprite": { ... } },
                { "stage": "growing", "days_required": 2, "sprite": { ... } },
                { "stage": "mature",  "days_required": 0, "sprite": { ... } }
            ],
            "harvest_item_id": "strawberry_item"
        },
        { "type": "potato", ... }
    ]
}
```

几个要点：
- 顶层是 `"crops"` 数组（不是像 actor/animal 那样用 key → object 的结构），`type` 字段就是 blueprint key
- 每个 `stage` 包含生长阶段枚举（seed/sprout/growing/mature）、天数要求和对应的贴图
- `days_required: 0` 表示这是终态（mature），不会再往下推进
- `harvest_item_id` 指向物品系统中的 item id——收获时由 `CropSystem` 查询并分发
- `EntityFactory::createCrop` 会用第一个阶段（seed）的贴图创建实体，后续由 `CropSystem` 在每天时间推进时切换贴图

## 练习

### 练习 1（推荐）：加一个"纯数据驱动"的 NPC 或动物

**目标**：不改任何核心逻辑，仅通过蓝图数据与地图 object 配置，让游戏里出现一个新 NPC/动物（可复用已有贴图资源）。

这个练习的意义在于——亲手走一遍"数据驱动"的完整路径，建立"改数据 → 看效果 → 用 Inspector 排错"的肌肉记忆。

- 验收标准：
  - 在 `assets/data/actor_blueprint.json` 或 `assets/data/animal_blueprint.json` 新增一个条目（key 自定）
  - 在地图 `.tmj` 的 object layer 新增一个 point object：
    - `type="actor"` 或 `type="animal"`
    - `name="<你的 blueprint key>"`
  - 运行游戏能看到实体出现（并具备至少 idle 动画）
  - 打开 Debug UI → `Blueprint Inspector`：
    - counts 包含你新增的条目
    - lookup 能查到该 key
    - `Missing References` 中不应出现你新增条目引用的贴图路径（或你能解释并修复）
- 提示线索（模块/文件）：
  - 数据：`assets/data/actor_blueprint.json`、`assets/data/animal_blueprint.json`
  - 地图对象：`assets/maps/*.tmj`（用 Tiled 编辑更直观）
  - 调用点：`src/game/loader/entity_builder.cpp`（看 `object.name → blueprint key`）
  - 排错：`src/game/debug/blueprint_inspector_debug_panel.cpp`、`docs/blueprints.md`
- 提交方式：GitHub PR（一个作业一个 PR；描述"新增了什么蓝图/在哪张地图加了 object/如何验证"）

### 练习 2（可选挑战）：给 Blueprint Inspector 增加"约定校验"报告

**目标**：把"约定"变成可检查项（而不是靠记忆），提升数据驱动系统的可维护性。

建议挑一个最常见的约定来做（任选其一）：
- A) 检查每个 actor/animal 是否都能生成 `idle_down`（否则默认动画可能无法播放）
- B) 检查动画 `direction` 中是否包含重复 token（例如重复写了两次 `down`）
- C) 检查 sounds 配置里是否存在空 sound key

- 验收标准：
  - 在 `Blueprint Inspector` 增加一个 section（例如 `Validation`）
  - 至少输出：
    - `errors_count`
    - （可选）列出前 N 条错误（包含 blueprint key 与错误原因）
  - 保持实现轻量：不要把 `BlueprintManager` 膨胀成复杂校验器（校验可以放 Debug 面板侧）
  - `ctest --test-dir build --output-on-failure` 通过（允许你补 1 个小单测）
- 提示线索（模块/文件）：
  - `src/game/debug/blueprint_inspector_debug_panel.*`
  - `src/game/factory/blueprint_manager.h`（读取蓝图表）
  - `docs/blueprints.md`（约定列表）

## 小结

本节可的要点：

- **蓝图是配方**：JSON 文件只表达"内容差异"；`BlueprintManager` 把 JSON 解析成 typed structs（可查询的蓝图表）；`EntityFactory` 把蓝图装配成 ECS 实体的组件组合。三者分工明确，互不越界。
- **工厂是唯一装配点**：复杂实体的组件拼装集中在 `EntityFactory`，不散落在 loader 或 system 中。`createMobBase` 收敛共性组件，`createActor`/`createAnimal`/`createCrop` 各自补差异——DRY、一致、可演进。
- **扩展靠约定，排错靠 Inspector**：blueprint key、动画 id 的展开规则、音效 key 的映射——这些约定决定了"数据是否生效"。Blueprint Inspector 把这些约定变得可观测、可检查，让数据驱动不再是黑盒。

下节课我们会把视角从"单张地图生成实体"提升到"世界级空间编排"：

> 当角色/动物/作物都能通过数据生成后，你还需要把多张地图组织成一个可导航的世界：
> `WorldState` 如何表达"当前在哪张地图/地图之间如何邻接/跨地图触发器怎么连线"，以及 `MapTransitionSystem` 如何驱动地图切换。
