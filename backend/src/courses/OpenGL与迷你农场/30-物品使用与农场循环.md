# 物品使用与农场循环：工具、耕地、作物、生长与掉落

上节课 我们用"单一数据源 + 事件驱动同步"把库存系统做成了一个稳定闭环：

- **Inventory 是唯一数据源**（Single Source of Truth）——物品内容只在 `InventoryComponent` 里
- **Hotbar 是书签**——只保存"引用到哪个 inventory slot"，不复制物品数据
- **UI 只发 Request，系统改组件并发 Changed**——这条规矩保证了数据永远一致

但 [物品栏与快捷栏](29-物品栏与快捷栏.md) 的闭环是"封闭"的——物品在库存里进进出出，却从未真正影响到世界。这节课要做的就是**把库存接回世界**：让玩家可以拿起锄头翻地、撒下种子种田、收获果实放回背包，形成一个完整的农场玩法循环。

> **选择工具/种子 → 点击目标格 → 播放动作 → 在动画关键帧结算 → 改变世界状态 → 回到库存 → UI 更新**

本节最重要的一个直觉是：

> **点击并不会立刻改变世界。** 点击只是"启动动作"，真正的玩法结算发生在**动画关键帧事件**里。

为什么要这样绕一圈？因为这条规则同时解决了三个问题：

- **手感稳定**：锄头落地的瞬间才翻出耕地，而不是点击的瞬间就变——视觉与结算同步
- **职责清晰**：输入系统不需要知道"锄地要做什么"，玩法系统也不需要关心"玩家是怎么触发的"
- **扩展安全**：以后加 NPC 自动劳动、网络同步、或者可取消的蓄力动作，都不需要改动结算逻辑

## 2. 本节目标与问题定义

本节目标一句话：

> 以"锄地→浇水→种植→生长→收获→掉落/拾取"为主线，用事件把输入/动画/UI 与玩法结算解耦，并用"可查询的世界状态"把多个系统组织成一个可维护的闭环。

把这个目标拆成 3 个核心问题。

### 2.1 "我想做什么"与"什么时候生效"如何分离？

玩家按下鼠标的那一刻，意图就已经确定了——"我要在这格锄地"。但生效时机不应该由输入决定，而应该由**动画进度**决定。

这自然地把链路切成两段：

1. **输入段**：`PlayerControlSystem` 决定动作 + 锁定目标（`ActionLockedTag` + `TargetComponent`）
2. **结算段**：动画播到关键帧 → `AnimationEvent` → 转换为 `UseToolEvent` / `UseSeedEvent` → `FarmSystem` 结算

### 2.2 世界状态怎么表达，才能让多个系统靠"查询"协作？

农场玩法里最常见的判断是：

- 这格是不是耕地？（决定能不能浇水、能不能种）
- 这格是不是湿润的？（决定生长速度）
- 这里有没有作物？什么阶段？（决定能不能收获）
- 这里有没有掉落物？（决定能不能拾取）

如果把这些状态藏在某个系统的私有变量里，其他系统每次需要判断都得"问人"。本项目的做法是：**用实体表达世界状态，并注册到空间索引**。这样任何系统只要查询空间索引，就能得到答案——不需要互相持有引用。

### 2.3 "消耗与产出"如何可靠地回到库存？

农场循环必须能落回 [物品栏与快捷栏](29-物品栏与快捷栏.md) 的库存体系：

- 种植成功扣种子 → `RemoveItemRequest`
- 收获获得产物 → `AddItemRequest`
- 拾取掉落物 → `AddItemRequest`

全部通过 `InventorySystem` 统一结算，再由 `InventoryChanged` 驱动 UI 同步。可以把库存系统想象成游戏经济的"唯一写入口"——所有数量变化都必须经过这道门。

## 3. 核心概念

### 3.1 两段式链路：输入启动动作，关键帧触发结算

用一段伪时间线来理解整条链路：

```text
T0  玩家点击鼠标左键
T0  PlayerControlSystem:
      → 计算目标格，写入 TargetComponent
      → 给玩家添加 ActionLockedTag（锁定移动和后续点击）
      → 设置 StateComponent.action_（如 Action::Hoe）
      → 触发动画状态变更（StateDirtyTag）

T1  AnimationSystem: 动画播放到关键帧
      → enqueue AnimationEvent（event_name = "tool_hit" / "seed_plant"）

T1  AnimationEventSystem: 消费 AnimationEvent
      → tool_hit → enqueue UseToolEvent（工具类型 + 目标世界坐标）
      → seed_plant → enqueue UseSeedEvent（种子类型 + 目标坐标 + 来源实体 + 槽位索引）

T1  FarmSystem: 消费 UseToolEvent / UseSeedEvent
      → 修改世界（创建耕地/湿润/作物实体、移除资源点、生成掉落）
      → trigger AddItemRequest / RemoveItemRequest（库存结算）
      → enqueue PlaySoundEvent（反馈音效）
```

<img src="https://theorhythm.top/gamedev/TF/L28_two_phase_pipeline.webp" style='width: 960px;' />

注意这里有一个微妙但重要的区别：**玩法结算用 `trigger`（同步），反馈用 `enqueue`（延迟到下一帧）**。

- `trigger`：`RemoveItemRequest`、`AddItemRequest` 等影响数据一致性的事件用同步分发，确保"种子扣了 → 作物种了"在同一帧内原子完成
- `enqueue`：`PlaySoundEvent`、`AddAutoTileEntityEvent` 等反馈类事件用延迟分发，不影响主链路逻辑

> **常见陷阱**：如果你把库存扣减改成 `enqueue`，那么在同一帧内连点两次可能会"扣两次种子但种一棵作物"——因为第一次扣减还没生效，第二次检查时种子数量还是旧的。`ActionLockedTag` 在输入层防了一次，`trigger` 在结算层又防了一次，形成双重保护。

**关键帧事件从哪来？**

关键帧事件是在动画数据中配置的。当 `AnimationSystem` 播放动画并到达标记了事件的帧时，它会 `enqueue` 一个 `AnimationEvent`，其中 `event_name_id_` 字段标识事件类型（如 `"tool_hit"`、`"seed_plant"`、`"harvest"`）。`AnimationEventSystem` 订阅这些事件并做翻译：

```cpp
// animation_event_system.cpp
void AnimationEventSystem::onAnimationEvent(const engine::utils::AnimationEvent& event) {
    switch (event.event_name_id_) {
        case "tool_hit"_hs:
            handleToolHitEvent(event);   // → UseToolEvent
            break;
        case "seed_plant"_hs:
            handleSeedPlantEvent(event); // → UseSeedEvent
            break;
        case "harvest"_hs:
            handleHarvestEvent(event);   // → UseToolEvent(Sickle)
            break;
    }
}
```

值得注意的是，**收获（harvest）也走工具链路**——`handleHarvestEvent` 会转换成 `UseToolEvent(Tool::Sickle, ...)`，然后由 `FarmSystem::onUseToolEvent` 中的 `Sickle` 分支处理。这种复用减少了重复代码：收获逻辑只需要在一个地方写。

### 3.2 世界状态用"实体 + 空间层"表达

本节涉及的几类世界状态：

| 状态 | 表达方式 | 空间层 | 备注 |
| --- | --- | --- | --- |
| 耕地（tilled） | AutoTile entity（`soil_tilled`） | `SOIL` | 可被查询"这格能不能浇水/种植" |
| 湿润（wet） | AutoTile entity（`soil_wet`） | `WET` | 叠加在耕地上；每天清理，第二天需要重新浇 |
| 作物（crop） | 独立实体 + `CropComponent` | `CROP` | 带有生长阶段、倒计时、种植日等完整状态 |
| 资源点（树/石） | `ResourceNodeComponent` | `ROCK` / `MAIN` | 带有耐久度（`hits_to_break_`）和掉落配置 |
| 掉落物（pickup） | `PickupComponent` + `ScatterMotionComponent` | （动态碰撞） | 散射运动 + 拾取延迟；最终转为 `AddItemRequest` |

<img src="https://theorhythm.top/gamedev/TF/L28_world_state_layers.webp" style='width: 960px;' />

这套设计的关键约定是**空间层 ID**，定义在 `spatial_layers.h` 中：

```cpp
namespace game::defs::spatial_layer {
    inline constexpr entt::id_type SOIL = "soil"_hs;  // 耕地
    inline constexpr entt::id_type WET  = "wet"_hs;   // 湿润
    inline constexpr entt::id_type CROP = "crop"_hs;   // 作物
    inline constexpr entt::id_type ROCK = "rock"_hs;   // 石头
    inline constexpr entt::id_type MAIN = "main"_hs;   // 主层（地面瓦片等）
}
```

有了这套约定，系统之间就不需要互相持有引用了。举个例子，`FarmSystem` 想知道"这格能不能种植"，只需要两个查询：

```cpp
// farm_system.cpp — plantSeed
if (spatial_index_.getTileEntityAtWorldPos(world_pos, spatial_layer::CROP) != entt::null) {
    return false;  // 已有作物，不能种
}
entt::entity soil_or_wet = findSoilOrWetAt(spatial_index_, world_pos);
if (soil_or_wet == entt::null) {
    return false;  // 没有耕地，不能种
}
```

不需要 `#include "crop_system.h"`，不需要调用别的系统的方法——空间索引就是系统间协作的"共享语言"。

> **为什么耕地和湿润是 AutoTile 实体？** 因为它们需要根据相邻格的状态自动选择贴图边缘（如耕地的边角过渡）。AutoTile 系统在前面的课程已经讲过，这里只是复用它来表达地表状态。

### 3.3 库存是唯一数据源：所有消耗/产出都走 Request

从农场玩法的角度看，库存有两类交互：

1. **消耗（consume）**：种植扣种子、使用消耗品
2. **产出（grant）**：收获产物、资源掉落拾取

但无论哪一种，最终都应该走同一条"经济写入口"：

```text
Farm/Crop/Pickup/...  →  AddItemRequest / RemoveItemRequest
                          → InventorySystem（结算）
                            → InventoryChanged → UI 更新
```

这条规则能避免两类常见 bug：

- **"世界给了奖励，但 UI 没显示"**——绕开了 `InventorySystem` 的 `InventoryChanged` 事件，UI 就不知道数据变了
- **"UI 显示变了，但实际物品没变"**——UI 直接改了显示数据而没走 Request，组件里的数量还是旧的

> **一条有用的调试规则**：如果你发现物品数量不对，先在 `InventorySystem::onAddItem` / `onRemoveItem` 上加断点——所有合法的数量变化都应该经过这里。如果断点没命中，说明有人绕开了这条路。

### 3.4 日结算：DayChangedEvent 驱动作物生长与湿润清理

农场循环里有一条"慢节奏"的主线：**按天推进**。`TimeSystem` 在每个新的一天产生 `DayChangedEvent`，`CropSystem` 订阅后做两件事：

1. **推进所有作物生长**：遍历所有 `CropComponent` 实体，减少 `stage_countdown_`
   - 如果该格有 WET 层实体（昨天浇过水），倒计时 **−2**
   - 如果没浇水，倒计时 **−1**
   - 倒计时归零后推进到下一阶段：更新 `current_stage_`、切换贴图、调整渲染层
   - 到达最后一个阶段后标记为 `Mature`，等待镰刀收获

2. **清理所有湿润层**：遍历所有 `AutoTileComponent`，找到 `rule_id_ == SOIL_WET` 的实体并标记删除——这让"浇水"变成每天需要重复做的事

<img src="https://theorhythm.top/gamedev/TF/L28_day_settlement.webp" style='width: 960px;' />

来看一下 `CropSystem` 的核心逻辑：

```cpp
// crop_system.cpp
void CropSystem::updateCropGrowth(entt::entity crop_entity) {
    auto& crop = registry_.get<CropComponent>(crop_entity);
    if (crop.current_stage_ == GrowthStage::Mature) return;  // 已成熟，不再更新

    const auto& transform = registry_.get<TransformComponent>(crop_entity);
    bool watered = isWatered(transform.position_);  // 查询 WET 层

    crop.stage_countdown_ -= watered ? 2 : 1;       // 浇水加速

    if (crop.stage_countdown_ <= 0) {
        advanceToNextStage(crop_entity, crop);       // 推进阶段 + 更新贴图
    }
}
```

> **本节不深入讲时间系统本身**——我们只把 `DayChangedEvent` 当成一个"外部信号"。时间模型的完整设计（昼夜周期、时段划分、快进机制）会在 [游戏时间与昼夜](31-游戏时间与昼夜.md) 展开。

### 3.5 物品使用：UI 触发的经济链路（ItemUseSystem）

除了"工具/种子 → 改变世界"这条主链路，还有一条**纯经济链路**：在 UI 中直接使用物品。

例如，`item_config.json` 里的草莓配置了 `on_use`：

```json
{
    "id": "strawberry_item",
    "on_use": {
        "consume": 1,
        "effects": [{ "type": "add_item", "id": "strawberry_seed", "count": 3 }]
    }
}
```

意思是"消耗 1 个草莓，获得 3 颗草莓种子"。这给了玩家一条"自给自足"的种子来源。

整条链路是：

```text
UI（背包/快捷栏右键） → UseItemRequest → ItemUseSystem
  → 模拟（simulate） → 通过？
    → 是：RemoveItemRequest + AddItemRequest → InventorySystem → UI 更新
    → 否：弹出"背包空间不足"提示，不做任何修改
```

`ItemUseSystem` 的关键设计是**先模拟、再执行**（simulate-then-execute）：

1. 拷贝一份库存槽位的快照（`std::vector<ItemStack> simulated = inv.slots_`）
2. 在快照上模拟消耗和产出——消耗方先在源槽位扣减，产出方优先回填源槽位，再尝试合并、最后填空槽
3. 如果产出放不下（快照模拟失败），直接弹出"背包空间不足"提示，**不做任何修改**
4. 模拟通过后，才执行真正的 `RemoveItemRequest` + `AddItemRequest`

<img src="https://theorhythm.top/gamedev/TF/L28_item_use_simulate.webp" style='width: 960px;' />

这种模式保证了操作的**原子性**：要么全成功，要么什么都不发生。你不会遇到"扣了草莓但种子没地方放"的半完成状态。

注意这条链路**不经过 `ActionLockedTag` 和动画**——它是瞬时的 UI 操作，不需要播放动作。同时，产出会**优先回填原槽位**（`preferred_slot_index`），这样"消耗 1 个草莓获得 3 颗种子"后种子会尽量出现在草莓原来所在的位置，符合玩家的直觉。

### 4.2 四条你会反复用到的"主路径"

#### 路径 A：工具链（Hoe / WateringCan / Sickle / Axe / Pickaxe）

1. hotbar 选择到工具 → `applySelectionForActiveSlot` 触发 `SwitchToolEvent` → `ActorComponent.tool_` 被设置
2. 左键点击 → 添加 `ActionLockedTag` + 设置 `StateComponent.action_`（如 `Action::Hoe`）→ 开始播放对应动画
3. `tool_hit` 关键帧到达 → `AnimationEventSystem` 读取 `StateComponent.action_` 翻译为对应的 `Tool` 类型 → `enqueue UseToolEvent`
4. `FarmSystem::onUseToolEvent` 根据工具类型分派：
   - **Hoe（锄头）**：`addTilledEntity` — 检查可耕性 + 创建 `soil_tilled` AutoTile 实体 + 注册到 SOIL 层 + 播放音效
   - **WateringCan（浇水壶）**：`addWetEntity` — 检查是否已有耕地 + 创建 `soil_wet` AutoTile 实体 + 注册到 WET 层
   - **Sickle（镰刀）**：`harvestCrop` — 查询 CROP 层是否有成熟作物 + **检查背包是否有空间** + 收获物进背包 + 移除作物和湿润层
   - **Axe（斧头）**/ **Pickaxe（镐）**：`hitTree` / `hitRock` — 命中资源点 + 累加命中计数 + 达到耐久后生成掉落

收获流程有一个**容量校验**值得注意：

```cpp
// farm_system.cpp — harvestCrop
const auto& inventory = registry_.get<InventoryComponent>(player);
if (!inventoryCanAdd(inventory, harvest_item_id, 1, stack_limit)) {
    // 弹出"背包空间不足"提示，作物保持不变
    helpers::emitDialogueBubbleShow(dispatcher_, ...);
    return false;
}
// 校验通过后才实际发放并移除作物
dispatcher_.trigger(AddItemRequest{player, harvest_item_id, 1});
```

也就是说，如果背包满了，收割动作会执行（动画播放），但作物不会消失——玩家需要腾出空间后再来收。

#### 路径 B：种子链（Plant）

1. hotbar 选择到种子 → `SwitchSeedEvent` → `ActorComponent` 记录持有种子的类型、物品 ID、和物品栏槽位索引
2. 左键点击 → 添加 `ActionLockedTag` + 设置 `Action::Planting` → 开始种植动画
3. `seed_plant` 关键帧到达 → `AnimationEventSystem` 读取 `ActorComponent` 的种子信息，并**校验槽位中的种子是否还在**（防止动画播放过程中种子被消耗掉了），然后 `enqueue UseSeedEvent`
4. `FarmSystem::onUseSeedEvent`：
   - 验证来源实体有效且有 `InventoryComponent`
   - 验证指定槽位的物品仍然是对应种子
   - 调用 `plantSeed`：检查该格没有作物 + 有耕地/湿润层 → 创建作物实体
   - 种植成功后 `trigger RemoveItemRequest` 扣减对应槽位的 1 颗种子

**为什么种子事件需要携带槽位索引？** 因为玩家可能有多个种子在不同槽位。如果只传种子类型而不传槽位，`RemoveItemRequest` 就不知道该从哪个槽位扣——可能扣错位置，导致快捷栏的引用失效。

#### 路径 C：日结算链（Growth）

1. `TimeSystem` 产生 `DayChangedEvent`（带有当前天数）
2. `CropSystem::onDayChanged` 遍历所有 `CropComponent` 实体：
   - 查询该作物位置是否有 WET 层实体 → 决定倒计时减 2（浇过水）还是减 1（没浇水）
   - 倒计时归零后推进到下一阶段：查找蓝图中的下一个 `CropStageBlueprint`，更新 `current_stage_` 和 `stage_countdown_`，切换贴图，设置渲染层为 `ACTOR` 层（让成长中的作物能与角色正确做 Y 排序）
   - 最后一个阶段标记为 `Mature`，等待镰刀收获
3. 同一回调中清理所有 `soil_wet` 自动图块实体（让"浇水"变成每天需要重复做的事）

> **设计取舍**：浇水的效果是"当天结算时 −2，未浇水 −1"，而不是"浇水后立刻生长"。这意味着浇水的效果在下一天结算时才体现。这符合农场游戏的日结算节奏，也简化了实时状态同步的复杂度。

#### 路径 D：物品使用链（ItemUse）

1. UI（背包/快捷栏）右键触发 `UseItemRequest`（携带目标实体、槽位索引、数量）
2. `ItemUseSystem` 查询 `item_config.json` 中的 `on_use` 配置
3. 先在快照上模拟消耗 + 产出（simulate），确认空间足够
4. 通过后执行 `RemoveItemRequest`（扣消耗品）+ `AddItemRequest`（给产出）；产出优先回填原槽位
5. 弹出"获得 Xxx x3"之类的提示气泡

#### 路径 E：资源掉落与拾取（Resource → Pickup → Inventory）

资源点（树木/石头）与普通工具操作有一个关键不同——它们**需要多次命中才会被摧毁**：

```cpp
// farm_system.cpp — hitResourceNode
node->hit_count_++;
if (node->hit_count_ < node->hits_to_break_) {
    return true;  // 还没破碎，播放命中动画和音效
}
// 耐久归零：生成掉落 → 清理碰撞/空间索引 → 标记实体删除
dropResource(*node, world_pos);
cleanup(target, world_pos);
registry_.emplace<NeedRemoveTag>(target);
```

`dropResource` 根据 `ResourceNodeComponent` 的掉落配置（`drop_item_id_`、`drop_min_`/`drop_max_`）生成随机数量的 `Pickup` 实体。每个 Pickup 带有 `ScatterMotionComponent`——从原点散射到随机偏移位置，带有抛物线弧度，形成"物品飞散"的视觉效果。

掉落实体落地后，`PickupSystem` 接管：每帧检测玩家碰撞体与掉落物碰撞体的重叠，拾取延迟结束后 `trigger AddItemRequest`，物品进入背包，掉落实体被移除。

```text
ResourceNode(多次命中) → dropResource → Pickup 实体(散射动画 + 拾取延迟)
  → PickupSystem(碰撞检测) → trigger AddItemRequest → InventorySystem → UI 更新
```

### 4.3 演示与调试：如何"可靠地快进到下一天"

为了演示作物生长，你需要触发 `DayChangedEvent`：

- **推荐做法 1**：调 `GameTimeDebugPanel` 的 `time_scale_`（加快时间流速，让时间自然跑到下一天）
- **推荐做法 2**：使用面板的"快进 1 天 / 1 小时"按钮（走 `AdvanceTimeRequest`）

**不推荐的做法**：直接手动修改 `GameTime.day_` 但不触发事件——这会导致"看起来天数变了，但作物不长"的困惑，因为 `CropSystem` 是通过 `DayChangedEvent` 驱动的，不是轮询 `GameTime.day_` 的变化。

## 6. 课后练习

### 练习 1：把"收获直接进背包"改成"收获掉落 pickup，再拾取进背包"

**目标**
让作物收获产物不再直接 `AddItemRequest` 给玩家，而是生成一个（或多个）`Pickup` 实体；玩家走过去拾取后再进入背包。

**验收标准**
- 收获成熟作物后，地上出现掉落物（有散射/延迟更好，但不是必须）
- 玩家走近后掉落物消失，背包数量增加
- 全程保持 [物品栏与快捷栏](29-物品栏与快捷栏.md) 的不变量：最终入包仍然走 `AddItemRequest → InventorySystem`

**提示线索**
- `src/game/system/farm_system.cpp` 的 `harvestCrop` 方法——这是你要改的地方
- `src/game/factory/entity_factory.h/.cpp` 的 `createResourcePickup`——已经有现成的 pickup 创建接口
- `src/game/system/pickup_system.cpp`——不需要改，它已经能处理任何 `PickupComponent` 实体
- 可以参考 `dropResource` 方法的实现，它就是为资源点做掉落的

### 练习 2：让工具使用链路支持"非玩家来源"（为 NPC/动物预留）

**目标**
扩展事件契约，让 `UseToolEvent` 携带 source entity；并让 `FarmSystem` 以"事件来源"为准结算（而不是假定只有玩家能用工具）。

**验收标准**
- 玩家使用工具不受影响（行为保持一致）
- 通过一个最小例子证明"非玩家实体也能触发 UseToolEvent 并结算"（可用测试或临时 debug spawn）
- 保持代码精简，不引入新框架

**提示线索**
- `src/game/defs/events.h` — `UseToolEvent` 目前只有 `tool_` 和 `world_pos_`，需要加 `source` 字段
- `src/game/system/animation_event_system.cpp` — `handleToolHitEvent` 需要把 `event.entity_` 传入 `UseToolEvent.source`
- `src/game/system/farm_system.cpp` — `harvestCrop` 目前用 `helpers::getPlayerEntity` 硬编码获取玩家，需要改为从事件的 `source` 读取
- 可以对照 `UseSeedEvent` 的设计——它已经有 `source` 字段了

## 7. 小结

本节课的要点：

1. **结算发生在动画关键帧**：输入只负责启动动作与锁定目标，关键帧事件才是"玩法生效"的统一落点。玩法结算用 `trigger`（同步），反馈用 `enqueue`（延迟）——这个区分保证了数据一致性。
2. **世界状态用实体表达**：耕地/湿润/作物/资源点/掉落都在世界里"可查询"，系统之间靠空间层 ID 和空间索引协作，不需要互相持有引用。
3. **库存是唯一数据源**：消耗/产出最终都走 `AddItemRequest` / `RemoveItemRequest`，由 `InventorySystem` 统一结算并驱动 UI。这条规则让所有数量变化都有一个可审计的"唯一入口"。
4. **物品使用先模拟后执行**：`ItemUseSystem` 用快照做 dry-run，确保操作原子性——要么全成功，要么什么都不发生，不会出现"扣了材料但产物没地方放"的半完成状态。

下节课我们会把"时间系统"作为主角：

- `TimeSystem` 如何把连续时间切分成可复用的离散事件（小时/天/时段）
- 昼夜系统如何消费这些事件来驱动环境光照变化
- "休息/睡觉"如何成为时间快进的触发器，并与作物生长形成另一个玩法闭环
