# 关卡载入器与实体建造者：通用构建 + 游戏扩展

上节课我们把"地图数据管线"从头到尾走了一遍：`.tmj/.tsj` 三类文件、三类图层、`gid` 索引链、properties 四级作用域，以及最终的两个运行时落点——**ECS 实体**与 **SpatialIndex 静态语义**。

那节课的视角是"管线全景"：你知道了数据从哪来、经过哪些模块、最终落到哪里。但如果你真的想往项目里**加东西**，很快会撞到更具体的问题：

- 我在 Tiled 的 object layer 里加了一个 `type="quest_giver"` 的点对象，为什么运行时什么都没生成？——因为你还没告诉构建器"遇到这个 type 该做什么"。
- 地图切换触发器（`map_trigger`）除了变成实体，还需要被 `MapManager` 跨地图查询（用于预加载邻居），信息应该写到哪里？——答案是 `WorldState`，但这件事谁来做？
- 我想让"通用组件构建"和"游戏语义扩展"分开：哪些代码放引擎层、哪些放游戏层，边界怎么守住？

这三个问题的共同点是：**它们都发生在管线的"构建阶段（build stage）"**。[地图数据管线](21-地图数据管线.md) 讲清了管线从头到尾怎么走，[关卡载入器与实体建造者](22-关卡载入器与实体建造者.md) 要做的是把镜头拉近到这个阶段——拆开 `LevelLoader` 和 `EntityBuilder` 的内部分工，搞清楚"谁负责循环、谁负责生成、谁负责补齐游戏语义"。

## 本节目标与问题定义

用一句话定义本节目标：

> 理解《迷你农场》如何用 `LevelLoader + BasicEntityBuilder / EntityBuilder` 把 Tiled 的 tile/object 描述构建成运行时 ECS 实体，并掌握"新增 object type / 新增 tile 语义时该改哪里"的扩展路径（保持 engine/game 分层不被污染）。

你完成本节后，至少能回答三类工程问题：

1. **分工问题**：`LevelLoader` vs `BasicEntityBuilder` vs `game::EntityBuilder` 各自负责什么？为什么要这么分？
2. **扩展点问题**：我想加新 object type / 新对象属性 / 新 tile 语义，应该从哪些文件入手？
3. **横切需求问题**：为什么每个实体都需要 `MapId`？为什么 trigger 要写入 `WorldState`？为什么 player 在切图时要"复用而非重建"？

## 核心概念

### 3.1 "编排器 vs 构建器"：谁负责循环，谁负责生成

加载一张地图，本质上要做两件事：**遍历数据**和**生成实体**。如果把这两件事混在一起写，代码很快就变成"解析逻辑和游戏逻辑纠缠在一起"的大泥球。所以《迷你农场》把加载过程拆成了两类角色：

- **编排器（Orchestrator）**——`engine::loader::LevelLoader`：负责"读 JSON → 遍历 layers → 把数据准备好 → 调用扩展点"。它知道 Tiled 的格式规则，但**不知道任何游戏语义**（什么是 actor、什么是 trigger，它都不管）。
- **构建器（Builder）**——`engine::loader::BasicEntityBuilder`（通用层）+ `game::loader::EntityBuilder`（游戏扩展层）：负责"拿到输入 → 创建实体 → 挂载组件"。它不关心数据从哪来（是 tile layer 还是 object layer），只关心**怎么把输入变成运行时实体**。

你可以用一个直觉来理解这种分工：

> **流水线 + 插槽**：流水线（LevelLoader）决定"每一步要处理什么类型的数据"；插槽（EntityBuilder）决定"这份数据应该生成什么实体和组件"。

这种拆分的直接收益是——当你想加新 object type 时，**只需要在游戏层 builder 里加一个分支**，不需要改动 LevelLoader 的解析逻辑。引擎层稳定不动，游戏层自由扩展。

### 3.2 构建器的三种 `configure` 形态：为什么不只有一个

回想 [地图数据管线](21-地图数据管线.md) 讲过的三类图层：tile layer 提供"密度最高、每格一个 gid"的数据；object layer 提供"离散对象，各自有坐标、type、properties"的数据；image layer 只挂一张大图。

这三类数据的输入形态差异很大。`BasicEntityBuilder` 通过三个 `configure(...)` 重载，把这些差异**收敛到同一条 `configure → build → getEntityID` 主线**上：

| `configure` 重载 | 输入来源 | 典型场景 |
|---|---|---|
| `configure(object_json)` | object layer：自绘形状（无 gid） | 点对象（actor/animal 出生点）、矩形区域（map_trigger / rest / light-emissive） |
| `configure(object_json, tile_info)` | object layer：图片对象（有 gid） | 引用 tileset tile 的 object，同时带自身 transform 与 tile 的 sprite/collider/animation |
| `configure(index, tile_info)` | tile layer：data 数组中的瓦片 | 瓦片层中 gid != 0 的每个格子，由 index 计算世界坐标 |

三个重载的区别在于"输入里有什么"：

- **只有 object JSON**：对象在 Tiled 里不引用任何 tile（纯坐标 + properties），比如一个点对象标记出生点位。
- **object JSON + tile info**：对象既有自己的坐标/properties，又引用了 tileset 中的一个 tile（带纹理、碰撞、动画等信息）。
- **index + tile info**：来自 tile layer 的瓦片，没有 object JSON，位置由 index 按行列计算得出（`x = (index % width) * tile_w`，`y = (index / width) * tile_h`）。

这样设计的收益是：`LevelLoader` 在循环中只需关心"我拿到的数据是哪种形态 → 调对应的 `configure`"，而所有组件组装逻辑全部内聚在 builder 里。**调用者不需要知道 builder 内部怎么组装组件，builder 也不需要知道调用者在遍历哪种 layer。**

### 3.3 注入点：`MapManager::loadMap` 把游戏扩展注入到引擎通用流水线

引擎层的 `LevelLoader` 不应该知道"actor / animal / map_trigger / light"这些游戏语义——否则每个新项目都要改引擎层，就谈不上"通用"了。

所以"游戏扩展"不是写死在引擎里的，而是通过**注入**完成的。注入点就在 `MapManager::loadMap`：

```text
MapManager::loadMap(map_id):
  unloadCurrentMap()                              // 1. 先卸载旧地图
  loader = make_unique<LevelLoader>(scene)        // 2. 创建引擎层编排器
  builder = make_unique<game::EntityBuilder>(     // 3. 创建游戏层构建器
      loader, context, registry, factory)
  builder.setMapId(map_id)                        // 4. 注入地图归属 ID
  builder.setReusePlayerIfExists(has_player)      // 5. 告诉 builder：player 已存在就复用
  loader.setEntityBuilder(move(builder))          // 6. 注入到引擎层编排器
  loader.loadLevel(map_path)                      // 7. 引擎层开始解析 + 分派
```

注意第 6 步：`setEntityBuilder` 接受的是 `BasicEntityBuilder` 的基类指针。LevelLoader 全程只通过基类接口调用 `configure / build / decorateExternalEntity`，完全不知道自己拿到的其实是一个游戏层的扩展 builder。这是一个经典的**依赖反转（Dependency Inversion）**——引擎层定义接口，游戏层提供实现。

这样做的三个收益：
- **引擎层保持通用**：只负责解析与调度，不知道 MapId / player / trigger 等游戏概念
- **扩展点集中可控**：游戏层只需要实现自己的 builder，所有游戏语义都在一个地方
- **配置一次性注入**：MapId、player 复用策略等游戏侧配置在注入时设好，builder 内部按需使用，不需要运行时反复查询

### 3.4 横切语义：三个"不显眼但不能少"的游戏层需求

在 [地图数据管线](21-地图数据管线.md) 里，我们主要关注的是"怎么把 Tiled 数据变成 ECS 实体"。但到了游戏层，光有实体还不够——有几个需求会**横切所有实体类型**，而不是只属于某个特定的 object type。《迷你农场》在构建阶段需要补齐三个这样的横切语义。

#### (1) MapId：让"地图生命周期"可控

地图切换不是"只加载新地图"这么简单，还意味着**当前地图的所有实体应该被统一销毁或快照**。如果有实体没被标记"属于哪张地图"，切图时就不知道该销毁谁、该保留谁——轻则残留实体（上一张地图的 NPC 还站在新地图上），重则快照污染（保存/恢复的状态混入了不属于本地图的实体）。

为此，《迷你农场》给"地图归属"引入了一个最小组件：`game::component::MapId`，只有一个字段——当前地图的 ID。

**它的关键不在于结构有多复杂，而在于覆盖面必须完整。** 这意味着 MapId 要通过两条路径注入：

- **路径 A：builder 创建的实体** → `attachMapId()`：在 `EntityBuilder::build()` 的末尾统一调用，无论走了哪个 type dispatch 分支（actor / trigger / light / 通用），最后都会带上 MapId。
- **路径 B：LevelLoader 自己创建的实体** → `decorateExternalEntity()`：tile layer 的"容器实体"和 image layer 的"背景精灵"是 LevelLoader 直接创建的（没走 builder 的 build 流程），所以需要通过这个回调让游戏层补齐 MapId。

<img src="https://theorhythm.top/gamedev/TF/L20_mapid_coverage.webp" style='width: 960px;' />

> **常见陷阱**：如果你在 `EntityBuilder` 里加了一个新的构建分支，但忘了确保 `attachMapId()` 会被调用，这些实体在切图时就不会被清理。排查方法：用 `Map Inspector` 检查"没有 MapId 的实体"（参见练习 2）。

#### (2) triggers 写入 WorldState：为跨地图编排铺路

`map_trigger` 在运行时有双重身份：
- **作为实体**：它是一个带碰撞区域的 ECS 实体，玩家踩上去就触发地图切换。这由 `MapTrigger` 组件 + 交互系统负责。
- **作为元数据**：它包含"从哪张地图的哪个出口通往哪张地图的哪个入口"的链接信息。这部分信息需要被 `MapManager` 在**不加载目标地图**的前提下查询到——比如"当前地图通往哪些地图？需要预加载谁？"

为了满足第二个需求，`EntityBuilder::buildMapTrigger()` 在创建 `MapTrigger` 组件的同时，会把 trigger 信息同步写入 `WorldState::MapState::triggers`：

```text
buildMapTrigger():
  // 1. 创建实体 + MapTrigger 组件（运行时碰撞检测用）
  entity = registry.create()
  registry.emplace<MapTrigger>(entity, ...)

  // 2. 同步到 WorldState（跨地图查询用）
  world_state.getMapState(map_id).triggers.push_back(trigger_info)
```

<img src="https://theorhythm.top/gamedev/TF/L20_trigger_worldstate.webp" style='width: 960px;' />

这种"实体 + 元数据双写"的模式看起来有点冗余，但它解决了一个根本问题：**运行时系统查 ECS 组件就够了（[交互与对话](28-交互与对话.md)），而世界级编排需要在实体不存在时也能查到链接关系（[世界状态](24-世界状态.md)/[地图管理器](25-地图管理器.md)）。** 两个写入点服务于不同粒度的消费者。

#### (3) player 复用：切图不重建，持久化状态不丢失

每张地图在 Tiled 里都有一个 `type="actor", name="player"` 的出生点。如果每次切图都按出生点重新创建玩家实体，那玩家身上的所有运行时状态（物品栏、快捷栏、动画状态……）都会丢失。

《迷你农场》的解决方案很简洁：

- `MapManager::loadMap` 在注入 builder 之前，检查 registry 里是否已经存在带 `PlayerTag` 的实体。如果存在，就设置 `builder.setReusePlayerIfExists(true)`。
- `EntityBuilder::buildActor()` 在遇到 `name == "player"` 时，如果 `reuse_player_if_exists_` 为 true，就**直接复用已有实体**，只更新它的位置到新地图的出生点，然后立即返回——不创建新实体、不重建组件。

这样，玩家的所有持久化状态（组件数据）在切图过程中完整保留，只有位置发生了变化。

### 3.5 把"加载"做成可观测系统：Map Inspector 的定位价值

当你在 Tiled 里改了配置、运行游戏却"没效果"时，最低效的做法是凭直觉猜。更好的做法是**先用 Map Inspector 缩小问题范围**。

打开方式：`F5 → Game Debug Panels → Map Inspector`

它能帮你快速区分三类问题的根源：

| 症状 | 可能原因 | Map Inspector 里看什么 |
|------|----------|----------------------|
| 新加的 object 没效果 | type 拼写不匹配约定 | Unknown Tokens → 检查 Unknown Object Types 列表 |
| 某层瓦片不显示 | layer 的 `visible` 被设为 false | 对象计数 → 看该 layer 是否被跳过 |
| 碰撞没生效 | tile flag 拼写错误 | Unknown Tokens → 检查 Unknown Tile Flags |
| 触发器不工作 | 缺少必需 properties（如 `target_map`） | 日志 warning → 检查缺失字段报告 |

> **排错习惯**：在构建阶段出的问题，80% 可以通过 Map Inspector 定位。先看面板、再看代码，远比直接 debug 加载流程高效。

### 4.2 层分派：LevelLoader 如何根据 layer 类型选择路径

`LevelLoader::loadLevel()` 在解析完 tileset 后，遍历 `.tmj` 的 `layers[]` 数组，根据每个 layer 的 `type` 字段分派到三条处理路径。每条路径有不同的 builder 调用方式：

<img src="https://theorhythm.top/gamedev/TF/L20_layer_dispatch.webp" style='width: 960px;' />

**object layer 路径**（LevelLoader 视角）：
```text
for object in object_layer:
  if object has gid:                                    // 图片对象：引用了 tileset 里的某个 tile
    tile_info = getTileInfoByGid(gid)
    builder.configure(object_json, tile_info).build()   // → configure 重载 2
  else:                                                 // 自绘形状：纯坐标 + properties
    builder.configure(object_json).build()              // → configure 重载 1
```

**tile layer 路径**（LevelLoader 视角）：
```text
container = registry.create()                           // 创建 layer 容器实体
for index, gid in tile_layer.data:
  if gid == 0: continue                                 // 空格跳过
  tile_info = getTileInfoByGid(gid)
  builder.configure(index, tile_info).build()           // → configure 重载 3
  tiles.push_back(builder.getEntityID())
  spatialIndex.setTileType(coord, tile_info.type)       // 写入空间索引
registry.emplace<TileLayerComponent>(container, tiles)  // 容器持有所有瓦片实体
builder.decorateExternalEntity(container)               // ← 补齐 MapId（路径 B）
```

**image layer 路径**（LevelLoader 视角）：
```text
entity = registry.create()                              // LevelLoader 直接创建
registry.emplace<Transform>(entity, ...)
registry.emplace<Sprite>(entity, ...)
registry.emplace<Parallax>(entity, ...)                 // 如果有视差配置
builder.decorateExternalEntity(entity)                  // ← 补齐 MapId（路径 B）
```

注意：image layer 的实体是 LevelLoader **直接创建**的，没有经过 builder 的 `configure → build` 流程。这就是为什么需要 `decorateExternalEntity` 回调——否则这些实体就不会带 MapId。

### 4.3 `EntityBuilder::build()` 的内部分派

当 `LevelLoader` 调用 `builder.build()` 时，游戏层的 `EntityBuilder::build()` 会根据输入数据的特征做 type dispatch：

```text
build():
  if 自绘形状（有 object_json，无 tile_info）:
    // --- 按 type + 形状做 dispatch ---
    if point && type == "actor":         buildActor(name)         // → EntityFactory
    elif point && type == "animal":      buildAnimal(name)        // → EntityFactory
    elif type == "map_trigger":          buildMapTrigger()        // → 创建实体 + 写 WorldState
    elif type == "rest":                 buildRestArea()          // → 创建休息区实体
    elif type == "light":                buildLight(name)         // → point / spot / emissive
    else:                                BasicEntityBuilder::build()  // 回退到通用构建
  else:
    // --- 有 tile_info 的对象或瓦片 ---
    BasicEntityBuilder::build()                                   // 通用组件构建
    if tile_info:  buildFarmTag()                                 // 检测 chest/crop/tree/rock

  // --- 横切补齐（无论走了哪个分支）---
  attachMapId()                                                   // 路径 A：带上 MapId
```

关键设计点：
- **`attachMapId()` 在所有分支之后统一调用**——无论走了 actor / trigger / light 还是通用分支，最终都会带上 MapId。这保证了覆盖面的完整性。
- **trigger 写入 WorldState 发生在 builder 内部**（`buildMapTrigger` 里），而不是由 LevelLoader 调用。LevelLoader 全程只做 `configure → build`，对游戏语义**完全无感知**。
- **复杂实体（actor / animal）交给 `EntityFactory`**——builder 自己不组装这些复杂实体，而是委托给工厂。工厂的内部（蓝图、资源映射）留到 [蓝图与实体工厂](23-蓝图与实体工厂.md) 展开。

## 课后练习

### 练习 1（推荐）：做一个 game 层 `ObjectPropertiesReader`，统一 object properties 的读取与报错

**背景**：目前 `EntityBuilder` 的各个构建分支（`buildMapTrigger` / `buildPointLight` / `buildSpotLight` / `buildEmissiveRect` 等）各自手写 JSON 属性读取逻辑。当 object type 越来越多时，三类问题会成倍放大：字段名拼写漂移、默认值不一致、报错信息格式不统一。

**目标**：为游戏层提供一套小而稳定的 properties 读取器，避免上述问题；并用它改造至少 2 个构建分支（推荐 `map_trigger` + `light`）。

- 验收标准：
  - 新增一个 `ObjectPropertiesReader`（或同等功能的工具类），支持：
    - `getString / getInt / getFloat / getBool`
    - `getEnum(token→enum)`（例如 `start_offset`）
    - 对"缺失字段 / 类型不符 / 取值非法"输出统一错误格式（包含 `map_id` 或 map name、object id、type/name/point）
  - 至少改造 2 个分支，使主逻辑更聚焦于"创建组件"，而不是"到处找 JSON 字段"
  - （可选加分）把错误信息也同步到 diagnostics，让 `Map Inspector` 能聚合展示"缺失字段报告"
  - `ctest --test-dir build --output-on-failure` 通过（允许你新增 1–2 个单测）
- 提示线索（模块/文件）：

## 小结

本节课的要点：

- **分工**：`LevelLoader`（编排器）管 JSON 解析与 layer 分派，`BasicEntityBuilder`（通用构建器）管通用 ECS 组件，`game::EntityBuilder`（游戏扩展构建器）管 type dispatch 与横切语义落点。三者通过依赖反转解耦，引擎层定义接口、游戏层提供实现。
- **扩展**：加新 object type 时，在游戏层 builder 加分支；加新 tile 语义时，回到 tileset properties 与引擎层的语义落点。每次扩展后，用 Map Inspector 验证加载结果——把"加载"当成可观测系统，而不是黑盒。
- **横切**：MapId 保证地图生命周期可控（覆盖面要完整），trigger 双写保证世界级编排可行（实体 + 元数据各服务不同消费者），player 复用保证切图不丢状态。
