# 测试用例入门（GoogleTest）

上节课我们跑通了《迷你农场》从 `main()` 到第一帧画面的完整链路，建立了"启动 → 主循环 → 场景注入"的心智模型。在上节课的练习 2 中，你可能注意到了这样一句话："增加单元测试覆盖该行为"。

如果你对此无从下手，这节课就是为你准备的。

## 为什么要在这里插一节测试课？

在以后的课程中，你会越来越频繁地遇到这样的作业要求：

> "请补一个单元测试覆盖这个行为。"

你明明理解了架构设计，却可能因为"不知道怎么跑测试"或"不确定测什么"而卡在最后一步。本节课用《迷你农场》仓库里的真实例子，带你走通"构建 → 运行 → 编写"的全过程。不讲 TDD 理论，只讲实操。

## 本课目标

学完本节后，你将能回答三个核心问题：

1. **在哪跑？** 知道《迷你农场》的测试代码在哪，以及如何用 `ctest` 跑全量或过滤到单个测试。
2. **怎么写？** 掌握最小 `TEST(...)` 的写法，知道何时该用 `EXPECT_*`、何时该用 `ASSERT_*`。
3. **测什么？** 理解在游戏开发中，哪些东西值得测（纯逻辑、数据状态），哪些不该碰（渲染像素）。

## 1. 核心概念：游戏开发中的单元测试

### 1.1 我们到底在测什么？

新手最常见的误区是想"测试所有东西"，包括画面是不是画对了。但在游戏工程里，我们遵循一个朴素原则：**高性价比优先**。

![测试金字塔](diagrams/L03A_test_pyramid.png)

从金字塔的底部往上看：

- **单元测试（底层，数量多、速度快）**：测纯逻辑与边界条件——时间计算、背包容量判断、状态机转换。输入输出清晰，不依赖显卡或窗口，毫秒级完成。
- **集成/行为测试（中层）**：测系统行为（ECS/System）——构造一个最小的 `registry`，放入特定的 Entity 和 Component，运行 System 的 `update`，然后验证数据变化或发出的事件。
- **端到端/视觉测试（顶层，成本高、易碎）**：测"画面对不对"。这类测试极其脆弱（跨平台驱动差异、字体渲染差异都会导致失败），维护成本远大于收益。

**本课的重点在底层和中层。** 在《迷你农场》里，你不会看到任何"断言这个像素点是红色"的测试。

> **黄金法则**：如果某段逻辑修改后让你**很害怕回归**（怕改坏旧功能），且它**可以不启动游戏窗口就验证**，那它就是单元测试的最佳候选。

### 1.2 AAA 模式：让测试像说明书一样清晰

写测试时，请遵循经典的 **AAA (Arrange-Act-Assert)** 结构：

![AAA 模式示意图](diagrams/L03A_aaa_pattern.png)

```text
Arrange (准备)：构造最小的输入数据、上下文环境
Act     (执行)：调用被测逻辑（通常只调用一次核心函数）
Assert  (验证)：检查结果是否符合预期
```

这不仅是为了规范格式，更是让你的测试代码成为"可执行的文档"——任何人读一个 AAA 结构的测试，都能在 10 秒内理解被测行为。

### 1.3 最小测试用例骨架

```cpp
#include <gtest/gtest.h>

TEST(SuiteName, BehaviorName) {
    // 1. Arrange — 准备输入
    int a = 10;
    int b = 20;

    // 2. Act — 执行被测逻辑
    int result = a + b;

    // 3. Assert — 验证结果
    EXPECT_EQ(result, 30);
}
```

**命名习惯**：
- `SuiteName`（套件名）：对应被测的类或系统，如 `TimeTest`、`RemoveEntitySystemTest`。
- `BehaviorName`（行为名）：描述你在测什么具体行为，如 `NegativeTimeScaleClampsToZero`（负时间缩放应被截断为零）。

好的命名让你不用打开测试文件就知道测了什么。当 CI 报红时，光看测试名就能大致定位问题方向。

### 1.4 `EXPECT` vs `ASSERT`：继续执行 vs 立即终止

GoogleTest 提供了两套断言宏，区别在于失败后的行为：

![EXPECT 与 ASSERT 对比](diagrams/L03A_expect_vs_assert.png)

- **`EXPECT_*`（推荐默认使用）**：失败后**继续执行**后续代码。
  - *典型场景*：验证数值、状态。即使第一项错了，你还想看后面的检查点，以便一次性收集更多调试信息。

- **`ASSERT_*`（致命断言）**：失败后**立即终止**当前测试函数。
  - *典型场景*：前置条件检查。例如"文件加载必须成功"、"指针必须非空"。如果这步失败了，后续代码一定会 crash，继续执行毫无意义。

**经验法则**：先想"如果这步失败了，后面的代码还能安全运行吗？" 不能→用 `ASSERT_*`；能→用 `EXPECT_*`。

## 2. 架构与数据流：测试是如何跑起来的？

### 2.1 CMake 接入流程

在《迷你农场》中，测试并不是什么魔法，它们只是普通的 C++ 可执行文件，由 CMake 管理构建和发现。

![CMake 测试构建与运行流程](diagrams/L03A_test_cmake_flow.png)

这条链路有三个关键环节：

1. **根 `CMakeLists.txt`**：定义了 `BUILD_TESTING` 开关（默认 ON）。打开时，执行 `enable_testing()` 并加入 `add_subdirectory(tests)`。你可以在命令行用 `-DBUILD_TESTING=OFF` 关掉它，也可以直接修改 `CMakeLists.txt` 中 `option(BUILD_TESTING ...)` 的默认值——如果你平时不需要编译测试，改文件更省事。
2. **`tests/CMakeLists.txt`**：定义了 `engine_tests` 和 `game_tests` 两个可执行目标，并使用 `gtest_discover_tests()` 将它们注册给 CTest。
3. **`cmake/Dependencies.cmake`**：通过 `find_or_fetch_dependency` 宏引入 GoogleTest——优先查找本地已安装版本，找不到则自动从 GitHub 拉取 `v1.17.0`。

> 如果你 `cmake configure` 阶段报 GTest 相关错误，第一步就是检查 `Dependencies.cmake` 中的拉取逻辑和网络状况。

### 2.2 "会跑"指南：从构建到运行

**Step 1：生成与构建**

```bash
# 生成项目（BUILD_TESTING 默认为 ON，无需额外参数）
cmake -S . -B build

# 构建测试目标
cmake --build build --target engine_tests game_tests
```

> 如果你之前改过 `BUILD_TESTING` 的默认值，也可以在命令行显式指定：`cmake -S . -B build -DBUILD_TESTING=ON`。
> 使用 Visual Studio 或 Xcode 等多配置生成器时，记得加上 `--config Debug`。

**Step 2：运行测试**

**方式 A：使用 CTest（推荐，输出整洁）**

```bash
# 运行所有测试，失败时输出详细日志
ctest --test-dir build --output-on-failure
```

**方式 B：直接运行二进制（适合调试单个测试）**

```bash
# 直接调用生成的可执行文件
./build/tests/engine_tests
```

**Step 3：过滤测试（只跑你关心的）**

当你正在开发 `Time` 模块时，不需要每次都跑全量测试：

```bash
# CTest 方式（-R 支持正则）
ctest --test-dir build -R TimeTest --output-on-failure

# 二进制方式（--gtest_filter）
./build/tests/engine_tests --gtest_filter=TimeTest.*
```

这两种方式的效果一样——都只运行名字匹配 `TimeTest` 的测试。区别是 CTest 方式的输出更整洁（汇总通过/失败数量），而直接运行二进制在调试器（如 CLion/VS）中更方便设断点。

## 3. 实战演练：从真实代码学测试写法

空讲语法没有意义。下面我们通过《迷你农场》仓库中的三个真实测试，分别展示三种典型场景的写法。

### 3.1 纯逻辑测试：`time_test.cpp`

> 参考文件：`tests/engine/core/time_test.cpp`

这是最简单的测试类型——不依赖任何框架组件，只测试一个类的输入输出。

```cpp
TEST(TimeTest, NegativeTimeScaleClampsToZero) {
    // Arrange
    engine::core::Time time;

    // Act — 设置一个非法的负值
    time.setTimeScale(-3.0F);

    // Assert — 应被截断为 0
    EXPECT_FLOAT_EQ(time.getTimeScale(), 0.0F);
}
```

注意这里用的是 `EXPECT_FLOAT_EQ` 而非 `EXPECT_EQ`——浮点数比较需要考虑精度误差，GoogleTest 提供了专门的浮点断言。

**这个测试好在哪？** 它测的是边界条件（负值输入），这正是 bug 最容易藏身的地方。"正常路径"通常不出错，"边界路径"才是回归测试的重点。

### 3.2 ECS/System 测试：`remove_entity_system_test.cpp`

> 参考文件：`tests/engine/system/remove_entity_system_test.cpp`

当你要测一个 ECS System 时，核心思路是：**构造一个最小世界（registry），放入刚好够用的 Entity 和 Component，运行 System，然后检查数据变化。**

```cpp
TEST(RemoveEntitySystemTest, RemovesAllTaggedEntitiesInSingleUpdate) {
    // Arrange — 构造"最小世界"
    entt::registry registry;
    const entt::entity keep = registry.create();  // 不打标签，应保留
    const entt::entity a    = registry.create();
    const entt::entity b    = registry.create();
    registry.emplace<engine::component::NeedRemoveTag>(a);  // 打上"待删除"标签
    registry.emplace<engine::component::NeedRemoveTag>(b);

    // Act — 运行系统
    RemoveEntitySystem system;
    system.update(registry);

    // Assert — 只有 keep 存活
    EXPECT_TRUE(registry.valid(keep));
    EXPECT_FALSE(registry.valid(a));
    EXPECT_FALSE(registry.valid(b));
}
```

**关键模式**：你不需要启动游戏窗口、不需要初始化渲染器——`entt::registry` 是一个纯数据容器，直接 `create()` 就能构造测试用的"世界"。这就是 ECS 架构的可测试性优势。

### 3.3 事件驱动测试：`action_sound_system_test.cpp`

> 参考文件：`tests/game/action_sound_system_test.cpp`

事件系统的测试稍微复杂一些，因为你需要"接住"系统发出的事件来验证行为。

![事件测试模式](diagrams/L03A_event_test_pattern.png)

核心步骤：

```cpp
// 1. Arrange — 准备捕获器
struct CapturedSounds {
    std::vector<entt::id_type> triggers{};
    void onSound(const engine::utils::PlaySoundEvent& evt) {
        triggers.push_back(evt.sound_id_);
    }
};

entt::registry registry;
entt::dispatcher dispatcher;
ActionSoundSystem system(registry, dispatcher);

CapturedSounds captured{};
dispatcher.sink<engine::utils::PlaySoundEvent>()
          .connect<&CapturedSounds::onSound>(&captured);

// ... (省略 Entity/Component 构造) ...

// 2. Act
system.update(0.0f);    // 系统产生逻辑，enqueue 事件
dispatcher.update();     // 【关键】让事件真正分发给监听器

// 3. Assert
ASSERT_EQ(captured.triggers.size(), 1u);
EXPECT_EQ(captured.triggers[0], "idle"_hs);
```

**注意这里用了 `ASSERT_EQ` 而非 `EXPECT_EQ`**：如果捕获到的事件数量不对，后续按索引访问 `captured.triggers[0]` 会越界崩溃，所以必须用致命断言提前拦截。这就是 1.4 节讲的"失败后还能安全运行吗"的判断。

## 4. 实战技巧：避开常见坑

### 4.1 测事件系统：记得 `dispatcher.update()`

这是新手踩坑频率最高的问题：

> "明明 `enqueue` 了事件，为什么监听器没收到？"

**原因**：《迷你农场》的 `dispatcher` 使用延迟分发（Queued Dispatch）——`enqueue` 只是把事件放入队列，必须显式调用 `dispatcher.update()` 才会真正触发回调。

```cpp
// ❌ 错误写法：忘了 dispatcher.update()
system.update(0.0f);
EXPECT_EQ(captured.triggers.size(), 1u);  // 永远是 0！

// ✅ 正确写法：显式分发
system.update(0.0f);
dispatcher.update();  // 不要忘了这行
EXPECT_EQ(captured.triggers.size(), 1u);
```

### 4.2 文件路径：别写死绝对路径

如果你在测试里写 `Load("C:/MyProject/assets/...")`，你的同事（和 CI 服务器）会恨死你。

**解法**：测试工程通过 CMake 注入了 `PROJECT_SOURCE_DIR` 宏，用它拼出跨平台可用的路径。

```cpp
// ✅ 参考：tests/game/blueprint_manager_smoke_test.cpp
const std::string path =
    std::string(PROJECT_SOURCE_DIR) + "/assets/data/actor_blueprint.json";
ASSERT_TRUE(manager.loadActorBlueprints(path));
```

### 4.3 临时文件：别污染项目目录

测试如果需要写文件（比如测试"保存到磁盘"的功能），千万别写在项目源码目录里——否则 `git status` 会多出一堆脏文件。

**解法**：使用 `std::filesystem::temp_directory_path()` 获取系统临时目录，测试结束后清理。

```cpp
// 参考：tests/game/blueprint_manager_smoke_test.cpp
const auto tick = std::chrono::steady_clock::now().time_since_epoch().count();
const std::filesystem::path tmp =
    std::filesystem::temp_directory_path() /
    ("tinyfarm_test_" + std::to_string(tick) + ".json");

// ... 在 tmp 路径写入/读取 ...

std::filesystem::remove(tmp);  // 测试结束后清理
```

## 小结

你现在已经掌握了在《迷你农场》中编写和运行测试的"最小闭环"：

1. **构建**：`cmake -DBUILD_TESTING=ON` 打开开关，构建 `engine_tests` / `game_tests`。
2. **运行**：`ctest --test-dir build --output-on-failure` 跑全量，`-R` 或 `--gtest_filter` 做过滤。
3. **编写**：AAA 结构打底，`EXPECT_*` 做常规断言，`ASSERT_*` 守前置条件。
4. **选择测什么**：优先测纯逻辑和边界条件；ECS/事件系统用"最小世界 + 捕获器"模式；不测渲染像素。

下节课（Debug UI 与可观测性基础）将建立另一种"观察程序内部状态"的手段——调试面板。测试帮你验证"逻辑对不对"，调试面板帮你观察"运行时状态是什么"。两者互补，是后续课程中你最常用的两把工具。
