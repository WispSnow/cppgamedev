# 物品栏与快捷栏：UI 同步、拖拽映射与状态一致性

上节课我们建立了一条关键原则：**玩法系统只发事件，UI 只订阅事件**。交互系统通过空间查询找到可交互对象，发出 `InteractRequest`；对话气泡通过 `DialogueShowEvent` 被动刷新——世界与 UI 之间的桥梁始终是事件，而非直接调用。

这节课，我们把同样的原则应用到一个看似更"日常"却更容易出 bug 的系统：**物品栏（Inventory）与快捷栏（Hotbar）**。

为什么它值得单独拿一整节课来讲？

- **它是下一课（物品使用与农场循环）的前置**——工具/种子的选择、消耗与奖励，都建立在一个可靠的库存系统之上。如果这一层不稳，后面所有玩法循环都会"漏水"。
- **它是 UI 同步的典型雷区**——你很容易写出"能跑，但拖拽几次就不同步"的代码。问题往往不出在简单场景，而是在合并堆叠、翻页、快捷键切换这些组合操作中暴露。

本节的演示非常直观——你可以在 demo 中直接操作验证：
- `I` 打开物品栏，`Tab` 切换快捷栏显示
- 拾取物品进入库存，自动尝试绑定到快捷栏空位
- inventory↔inventory 交换/合并堆叠；inventory→hotbar 绑定；hotbar↔hotbar 交换绑定；拖到空白处解绑
- 数字键切换快捷栏槽位，高亮与"当前可用工具/种子"始终一致

## 本节目标与问题定义

本节的核心目标一句话：
> 用"**单一数据源 + 事件驱动同步**"的结构，把 Inventory/Hotbar 这类状态密集型 UI 做成一个稳定、可扩展的闭环。

展开来看，我们要解决三个问题。

### 问题一：数据应该存在哪里？

这是最容易犯错的地方。一个常见的做法是：
- Inventory 有一份 `ItemStack`
- Hotbar 也存一份 `ItemStack`（或 `item_id/count`）
- UI 再缓存一份显示状态

三份数据，三个"真相"。一开始很好写——每个模块各管各的。但一旦需求变多（移动、合并、消耗、拾取、翻页），你就会发现**每个操作都需要三份同步代码**，而且顺序稍有差错，UI 就会显示旧数据，或者快捷键指向了已经被消耗的物品。

本项目的选择很简单：**Inventory 是唯一数据源（Single Source of Truth）**。Hotbar 不保存物品内容，只保存"引用到哪个 inventory slot"——就像书签指向书页，而非复印一页书。

### 问题二：UI 怎样同步状态？

库存是一个"高频变化"的数据源（拖拽、拾取、消耗随时发生），因此我们需要两种同步策略：
- **full sync（全量推送）**：把所有槽位的状态一次性推给 UI——简单可靠，适合状态边界（打开 UI、初始化、读档）
- **diff update（增量推送）**：只推送变更的槽位——高效轻量，适合高频操作（拖拽、拾取、消耗）

两者组合使用：在每次"状态可能不确定"的时刻用 full sync 兜底，日常操作用 diff 保持高效。

### 问题三：拖拽映射如何保持一致？

拖拽和绑定会逼你回答这些设计问题：
- inventory↔inventory 交换时，Hotbar 的引用要不要跟着物品走？
- 同一个 inventory slot 能不能同时绑定到两个 hotbar slot？
- 合并堆叠后，如果 source 被清空，它的快捷键应该怎么处理？

这些问题本质上是在定义**不变量（invariant）**——系统需要自动维护的规则。如果你不把它们写清楚，bug 就会藏在"不常测到的组合"里，直到玩家操作时才暴露。

## 核心概念

### 单一数据源：Hotbar 是"书签"，不是第二份数据

先看两个组件的结构：

- `InventoryComponent`（`inventory_component.h`）保存真正的物品堆：`ItemStack{item_id_, count_}`。两页背包，每页 5×4=20 个槽位，共 40 个槽位。
- `HotbarComponent`（`hotbar_component.h`）的每个槽位只保存一个 `inventory_slot_index_`（`int`，-1 表示空）。10 个固定槽位。

注意 `HotbarSlot` 结构体里没有 `item_id`，也没有 `count`——**快捷栏显示的物品，永远是从 inventory 里"查出来"的**。

一个简单的心智模型：
```text
Inventory = 数据表（source of truth）
Hotbar    = 一组"书签"（bookmark），指向数据表中的某一行
UI        = 只读视图（view），通过事件刷新
```

<img src="https://theorhythm.top/gamedev/TF/L27_data_model.webp" style='width: 960px;' />

这个设计的好处在于：无论你做多少种操作（添加、移动、合并、消耗），只要修改 `InventoryComponent`，所有依赖它的地方（Hotbar 显示、UI 渲染、工具选择）都能通过同一条路径得到更新。

### 事件契约：UI 发 Request，System 发 Changed

这是 [事件系统](06-事件系统.md) 讲过的 Request/Changed 分层模式在库存系统中的具体落地。我们把 UI 与 System 的交互约束为两类事件（`events.h`）：

**请求事件（UI/Scene → System）——"我想做什么"：**
- `InventoryMoveRequest{from_slot, to_slot, allow_merge}`：拖拽移动/交换/合并
- `HotbarBindRequest{hotbar_index, inventory_slot}`：把 inventory slot 绑定到 hotbar
- `HotbarUnbindRequest{hotbar_index}`：解绑
- `HotbarActivateRequest{hotbar_index}`：激活某个槽位（切换选中）
- `InventorySyncRequest / HotbarSyncRequest`：要求系统推送一次 full sync
- `InventorySetActivePageRequest{active_page}`：翻页
- `UseItemRequest{inventory_slot_index, count, show_prompt}`：使用物品

**变更广播（System → UI）——"状态已经变了"：**
- `InventoryChanged{slots, full_sync, active_page}`：库存变化（可以是 diff 或 full）
- `HotbarChanged{slots, full_sync, active_slot}`：快捷栏变化
- `HotbarSlotChanged{slot_index}`：高亮变化（选中的槽位切换了）

最核心的规则只有一句话：
> **UI 不直接改组件；System 不直接改 UI。双方只通过事件契约对齐。**

这条规则的好处是：UI 只需要知道"发什么请求"和"收到什么变更"，不需要知道系统内部如何处理请求；系统也不需要知道 UI 是什么样子。两边可以独立开发和测试。

### full sync 与 diff：两种同步策略

具体到代码中：

- `InventoryUI` 内部维护一个 `slot_items_` 缓存（覆盖所有页的全部槽位）。收到 `InventoryChanged(full_sync=false)` 时，只更新缓存中对应 index 的条目，然后重绘当前页；收到 `full_sync=true` 时，则重建整个缓存。
- `HotbarUI` 通过 `HotbarChanged` 事件得到每个槽位"已展开"的 `item_id/count`——UI 不用自己去读 `InventoryComponent`。

这种结构让 UI 保持"很笨但很稳定"的角色：
```text
UI = cache + render（只管存和画）
System = mutate + emit（只管改和发）
```

### 级联刷新：从 InventoryChanged 到 HotbarChanged

这是本节最容易忽略但最关键的机制。

假设一个场景：玩家拾取了 5 个木材，木材被添加到 inventory 的第 3 个槽位（slot 2），而 hotbar 的第 1 个槽位（index 0）恰好引用了 inventory slot 2。这时候 hotbar 的显示也必须更新——但 `InventorySystem` 只关心库存变更，它不该知道 hotbar 的存在。

解决方案是**级联刷新（cascade refresh）**：

1. `InventorySystem` 修改 `InventoryComponent` 后，发出 `InventoryChanged(diff)`。
2. `HotbarSystem` 订阅了 `InventoryChanged`。在 `onInventoryChanged` 中，它遍历所有 hotbar slot，检查每个 slot 引用的 `inventory_slot_index_` 是否出现在变更列表中。
3. 对于受影响的 slot，`HotbarSystem` 读取最新的 `ItemStack`，把 `item_id/count` 展开到 `HotbarSlotUpdate` 中，然后发出一条 `HotbarChanged(diff)`。

<img src="https://theorhythm.top/gamedev/TF/L27_cascade_refresh.webp" style='width: 960px;' />

这条链路是"单一数据源"在运行时真正生效的桥梁——你只改 `InventoryComponent`，`HotbarUI` 就能自动跟上，不需要任何模块手动"通知" hotbar。

### 两种 UI 更新路径：直接订阅 vs GameScene 适配器

仔细观察数据流图，你会发现两个 UI 的更新方式不同：
- `InventoryChanged` **直接**到达 `InventoryUI`
- `HotbarChanged` 先到 `GameScene`，再由 GameScene 更新 `HotbarUI`

为什么不统一？因为两个 UI 的复杂度和依赖不同。

**InventoryUI 直接订阅 `InventoryChanged`。** 它内部管理分页缓存（`slot_items_` 覆盖所有页面），diff/full sync 的判断逻辑都是 UI 内部的事情，不需要外部介入。

**HotbarUI 由 GameScene 充当"薄适配器（thin adapter）"。** HotbarUI 只有 10 个固定槽位，逻辑简单，但它需要显示物品图标（`Image`），而图标的查找需要 `ItemCatalog`。HotbarUI 不持有 `ItemCatalog` 引用——让每个 UI 组件都知道数据查找的细节，会增加不必要的耦合。所以由 GameScene 在中间做一层翻译：

```cpp
// game_scene.cpp — onHotbarChanged
for (const auto& slot : evt.slots) {
    hotbar_ui_->setSlotInventoryIndex(slot.hotbar_index, slot.inventory_slot_index);
    if (slot.item_id != entt::null && slot.count > 0) {
        const auto icon = item_catalog_->getItemIcon(slot.item_id);
        hotbar_ui_->setSlotItem(slot.hotbar_index, {slot.item_id, slot.count, icon});
    } else {
        hotbar_ui_->clearSlot(slot.hotbar_index);
    }
}
```

`ItemCatalog::getItemIcon` 内部合并了"查物品 → 取 icon_id → 获取图片"三步查找，避免在多个调用处重复这套模式。

这个设计的好处是：HotbarUI 只关心"设置槽位内容"，不需要知道 icon 从哪来、catalog 如何工作。GameScene 承担的只是一层很薄的数据翻译，不包含业务逻辑。

<img src="https://theorhythm.top/gamedev/TF/L27_ui_update_paths.webp" style='width: 960px;' />

### 不变量（Invariant）：让系统替你守规则

我们显式定义了 4 条不变量（完整版见 `docs/inventory_hotbar.md`）：
1. **Inventory 是唯一数据源**：所有 `ItemStack` 只存在于 `InventoryComponent`
2. **Hotbar 只存引用**：`inventory_slot_index_`，不保存 `ItemStack`
3. **单向数据流**：UI 发 Request / System 发 Changed
4. **一对一绑定**：一个 inventory slot 最多绑定到一个 hotbar slot

第 4 条由 `HotbarSystem::onBind` 保证：当某个 inventory slot 已经绑定到别的 hotbar slot 时，新的 bind 会先把旧位置解绑，再在新位置建立绑定——保证同一物品不会同时出现在两个快捷键上。

写拖拽逻辑时，你可以用一个检查表问自己：
- 我是不是把 `item_id/count` 存了两份？（违反不变量 1、2）
- 我是不是在 UI 里直接改了 `InventoryComponent` / `HotbarComponent`？（违反不变量 3）
- 我是不是让一个 inventory slot 同时出现在两个 hotbar slot？（违反不变量 4）

如果任何一项为"是"，说明设计出了偏差，需要退回来重新审视数据流。

### 代码组织：跨模块的共享辅助

本节涉及的模块之间有些操作模式是重复的，代码通过提取共享辅助函数来消除重复：

- **`inventory_helpers.h`**：`tryMerge` / `tryFillEmpty` / `stackLimitOrDefault` 是"向槽位塞物品"的基础操作，被 `InventorySystem`（添加/移动物品时的合并逻辑）和 `ItemUseSystem`（使用物品后产出结果时的预检模拟）共同使用。
- **`ui_drag_drop_helpers.h`**：`beginDragPreview` / `endDragPreview` / `findTarget` 封装了拖拽预览的生命周期管理和跨 UI 的目标查找，被 `InventoryUI` 和 `HotbarUI` 共享。

这是一个实用的工程原则：当两个模块独立编写但都需要同一段逻辑时，提取到一个共享 header 中比"复制粘贴后各自维护"更安全——修改一处即可同步生效，也不会出现"两份代码逐渐 diverge"的问题。

<img src="https://theorhythm.top/gamedev/TF/L27_event_data_flow.webp" style='width: 960px;' />

注意图中两个关键细节：
- `HotbarSystem` 同时**监听** `InventoryChanged` 和**发出** `HotbarChanged`——这就是级联刷新机制的体现。
- `HotbarChanged → GameScene → HotbarUI` 表示 GameScene 充当适配器；而 `InventoryChanged → InventoryUI` 是直接订阅。两条路径的选择取决于 UI 的依赖复杂度。

### 四条常用路径

下面我们跟踪四条最具代表性的操作路径，帮你建立"输入 → 请求 → 系统处理 → 变更广播 → UI 更新"的完整心智模型。

#### 路径 A：打开物品栏（full sync）

这是最简单但最重要的路径——它是系统自检的"安全阀"。

1. 玩家按下 `I`，GameScene 收到 `inventory` toggle
2. GameScene 设置 InventoryUI 可见，然后 enqueue `InventorySyncRequest` 与 `HotbarSyncRequest`
3. `InventorySystem::onSync` 把所有槽位打包成 `InventoryChanged(full_sync=true)` 发出
4. `HotbarSystem::onSync` 先归一化无效映射（越界的 `inventory_slot_index_` 清为 -1），再发出 `HotbarChanged(full_sync=true)`
5. InventoryUI 清空旧缓存并重建；GameScene 收到 HotbarChanged 后清空 HotbarUI 并重新设置所有槽位

同样的 full sync 逻辑在**初始化**和**读档**后也会执行一次，确保 UI 与组件状态从第一帧就对齐。

#### 路径 B：拾取物品（diff + 自动绑定）

拾取流程展示了"级联刷新 + 自动绑定"如何协作。

1. 拾取系统（或其他系统）发出 `AddItemRequest{target, item_id, count}`
2. `InventorySystem::onAddItem` 在 `InventoryComponent` 中找到合适的槽位（先尝试合并到已有堆叠，再尝试填入空槽），修改数据后发出 `InventoryChanged(diff)`
3. 如果该物品还没有出现在 hotbar 上，系统会尝试找一个空的 hotbar 槽位，发出 `HotbarBindRequest`——**自动绑定**
4. `HotbarSystem` 处理 bind 并发出 `HotbarChanged(diff)`

关键点：**自动绑定不会复制物品**，它只是在 hotbar 中新建一个"书签"指向该库存槽位。物品仍然只有一份，存在 `InventoryComponent` 中。

#### 路径 C：inventory↔inventory 拖拽（三种分支 + 映射维护）

这是本节最复杂的路径。拖拽触发 `InventoryMoveRequest`，`InventorySystem::onMoveItem` 根据 source 和 target 的状态做出不同处理。**每种处理对 hotbar 映射的影响不同**，这正是"一致性"问题的核心。

**分支 1：swap（交换）**——source 和 target 都有物品且是不同物品
- 交换两个槽位的 `ItemStack`
- 同步交换 hotbar 中引用这两个 slot 的 `inventory_slot_index_`（通过 `swapHotbarInventorySlotMappings`）
- 效果：物品交换了位置，快捷键跟随物品——玩家的"锄头在 1 号键"不会因为整理背包而丢失

**分支 2：move（移动到空槽）**——target 为空
- 把 source 的 `ItemStack` 移到 target，source 清空
- 如果 hotbar 有 slot 引用了 source，把引用改为指向 target
- 效果：物品换了位置，快捷键跟着走

**分支 3：merge（合并堆叠）**——source 和 target 是同一物品，且 `allow_merge=true`
- 把 source 的数量合入 target（不超过 `stack_limit`）
- 如果 source 被完全合入（数量归零），需要处理 hotbar 映射

merge 是最复杂的分支，因为它会让一个槽位"消失"。本项目定义了一条明确的规则——

**Rule A**：当 source 与 target **都**被 hotbar 引用时，**保留 target 的引用，清空 source 的引用**。

为什么不能交换？因为 source 已经变空了——如果把 target 的快捷键换到空槽位上，玩家的快捷键就会指向一个空的 `ItemStack`，功能凭空消失。保留 target 的引用，至少保证了合并后那堆物品仍然在某个快捷键上。

如果只有 source 有引用，则把引用转移到 target（物品没消失，只是换了位置）。如果只有 target 有引用，无需额外操作。

<img src="https://theorhythm.top/gamedev/TF/L27_merge_branches.webp" style='width: 960px;' />

#### 路径 D：右键使用物品（UseItemRequest）

物品栏 UI 支持右键使用物品（例如把小麦加工为面粉）：
1. `InventoryUI` 发出 `UseItemRequest{target, inventory_slot_index, count, show_prompt=true}`
2. `ItemUseSystem` 接收请求，先用 `simulateAdd` 预检背包容量（复用 `inventory_helpers.h` 中的 `tryMerge`/`tryFillEmpty`），确认产出物能放得下后，消耗源物品并产出结果
3. 产出通过 `AddItemRequest` 回到 `InventorySystem`，走正常的 diff 更新链路

注意 `show_prompt` 参数的用途：物品栏右键使用时为 `true`，会弹出"获得 XX"气泡提示；快捷栏右键使用时为 `false`（快捷栏的使用体验更偏向"快速操作"，不需要额外提示）。物品使用的完整机制会在 [物品使用与农场循环](30-物品使用与农场循环.md) 详细展开，这里只需要理解它如何与库存系统的 diff 链路对接。

## 常见坑与排错建议

### 1) UI 不更新 / 显示旧数据

**首先检查 full sync 入口**：打开 UI 时是否 enqueue 了 `InventorySyncRequest` / `HotbarSyncRequest`？如果这一步漏了，UI 可能一直显示初始化时的空状态。

**然后检查事件订阅**：InventoryUI 是否订阅了 `InventoryChanged`？如果 InventoryUI 更新了但 HotbarUI 没有，检查级联链路——`HotbarSystem` 是否订阅了 `InventoryChanged`？

### 2) Hotbar 显示了物品，但按键切换后工具/种子不生效

问题通常在 `PlayerControlSystem`。当 `HotbarChanged` 事件影响了当前激活的 slot 时，`PlayerControlSystem::onHotbarChanged` 需要重新调用 `applySelectionForActiveSlot()` 来刷新"当前选中的工具/种子"。如果这个回调被遗漏，你会看到 hotbar 图标正确但实际使用的还是旧选择。

### 3) 拖拽合并后某个快捷键消失或"跳槽"

这是 merge 场景的典型边界问题。检查 `InventorySystem::onMoveItem` 中 merge 分支的 hotbar 映射处理是否遵循了 Rule A。最常见的错误是在 source 已清空后仍然尝试 swap 映射，导致快捷键指向空槽。

### 4) HotbarSync 后某个槽位消失

`HotbarSystem::onSync` 会"归一化"无效映射：如果某个 hotbar slot 的 `inventory_slot_index_` 越界（例如 ≥ `InventoryComponent::TOTAL_SLOTS`），会被清为 -1。这是防御性设计——避免 hotbar 长期持有"悬空引用"。如果你在 sync 后发现槽位莫名消失，先检查对应的 `inventory_slot_index_` 是否指向了一个有效范围内的槽位。

5. **系统如何处理**：`inventory_system.cpp`（move/swap/merge + hotbar 映射维护）+ `hotbar_system.cpp`（bind/unbind/级联刷新）
6. **共享辅助**：`inventory_helpers.h`（`tryMerge` / `tryFillEmpty`）+ `ui_drag_drop_helpers.h`（拖拽预览与目标查找）
7. **装配与适配**：`game_scene.cpp`（sync 请求、事件监听、HotbarUI 适配器）
8. **选择与生效**：`player_control_system.cpp`（数字键切换 → `HotbarSlotChanged`；`HotbarChanged` → 刷新当前工具/种子选择）

## 课后练习

### 练习 1：拆分堆叠（Split Stack）
- **目标**：在物品栏中把一个堆叠拆成两堆（例如从 10 个拆 3 个到目标槽位）。
- **验收标准**：
  - 能在 UI 上触发拆分（例如：按住 modifier 再拖拽 / 或右键弹出简单输入框，形式不限）
  - 拆分过程不破坏本节不变量：Inventory 是唯一数据源；Hotbar 仍然只存引用；UI 不直接改组件
  - 拆分后两个槽位数量正确：源槽位减少，目标槽位增加（或创建新堆叠）
- **提示线索**：
  - 事件契约：`events.h`（你可能需要新增 `InventorySplitRequest`）
  - 系统落地：`inventory_system.cpp`
  - UI 交互：`inventory_ui.cpp`

### 练习 2：把 InventoryUI 的 diff 更新做成"真正的增量刷新"
- **目标**：当收到 `InventoryChanged(diff)` 时，只更新当前页中受影响的槽位，而不是整页重绘。
- **验收标准**：
  - full sync 时仍能正确刷新整页（或重建缓存）
  - diff 时只更新"在当前页"的槽位；不在当前页的更新只更新缓存，不触发重绘
  - 不改变现有系统/事件行为（只优化 UI 侧）
- **提示线索**：
  - `inventory_ui.cpp`：`slot_items_` 本地缓存与 `renderPage` 的关系
  - `events.h`：`InventoryChanged.slots` 提供了受影响槽位的 index 列表

## 小结

本节课的要点：

1. **Single Source of Truth**——Inventory 存数据，Hotbar 存引用。不要让物品信息出现第二份拷贝。
2. **级联刷新**——`InventoryChanged → HotbarSystem → HotbarChanged`，让引用模型在运行时自动生效。你只需要改 `InventoryComponent`，下游的 Hotbar 显示和工具选择会自动跟上。
3. **Event-driven UI**——UI 发请求，系统发变更，靠事件契约同步。GameScene 在需要时充当薄适配器，但不包含业务逻辑。
4. **Invariants**——拖拽、合并、绑定的规则（尤其是 merge 的 Rule A 和一对一绑定）需要被明确定义并由系统自动维护。如果你发现某个操作"有时候不一致"，先回到不变量检查表，看看哪条被破坏了。

下节课，我们会把这个库存闭环接到真正的玩法循环上：
- 工具/种子如何作用于世界——耕地、浇水、种植、收获
- 物品使用（`UseItemRequest`）如何驱动消耗与产出，结果再次回到 inventory
- 音效、动画事件与提示气泡如何增强玩家反馈，同时保持架构解耦
