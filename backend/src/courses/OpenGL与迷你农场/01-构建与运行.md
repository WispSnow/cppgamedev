## 核心概念

### 1. 三阶段：从“蓝图”到“成品”

要理解构建，首先要区分这三个独立但紧密衔接的阶段：

- **Configure (配置)**：这是“筹备”阶段。CMake 会读取 `CMakeLists.txt`，检测你的编译器，定位（或下载）依赖库，并最终生成一套适合你系统的“施工蓝图”（如 Makefile 或 Visual Studio 工程文件）。
- **Build (编译)**：这是“施工”阶段。编译器根据蓝图，将 C++ 源码编译成目标文件，并最终“焊接”（链接）成可执行程序。
- **Run (运行)**：这是"交付"阶段。程序脱离编译环境，需要在正确的"土壤"（资源文件、动态库）中才能启动。

> **最佳实践**：TinyFarm 强制建议使用 **"out-of-source build"**。我们将所有生成物统一放在 `build/` 目录下，这样无论怎么折腾，都不会污染源代码。

### 2. 模块化构建：让 CMake 清晰简洁

TinyFarm 的构建系统没有把成百上千行配置塞进一个文件，而是采用了**模块化设计**。主 `CMakeLists.txt` 就像一个指挥官，只负责串联各专项模块：

```text
CMakeLists.txt          ← 统筹全局：定义目标、串联模块
└── cmake/
    ├── CompilerSettings.cmake   ← 编译器配置（C++20 开启、平台兼容）
    ├── Dependencies.cmake       ← 依赖管理中心（最核心的模块）
    ├── BuildHelpers.cmake       ← 自动化助手（负责资源复制、DLL 处理）
    └── ... (其他专项配置)
```

**为什么这种设计很重要？**
如果我们要更换一个音频库，只需要在 `Dependencies.cmake` 里修改策略，而不需要改动引擎逻辑代码。这种“关注点分离”的思想，从构建系统就开始了。

![CMake 模块结构](diagrams/L01_commands.png)

### 3. 依赖三级跳：系统 → 源码 → 自动下载

TinyFarm 的依赖管理遵循一套**“三级回退策略”**，这在 `cmake/Dependencies.cmake` 中通过 `find_or_fetch_dependency` 宏实现：

1. **第一优先级**：先看你系统里有没有装好现成的库（`find_package`）。
2. **第二优先级**：如果没有，看本地 `external/` 目录下有没有对应的源码。
3. **第三优先级**：如果还没有，利用 CMake 的 `FetchContent` 模块去远程仓库在线拉取并现场编译。

**这解释了两个常见现象：**
- **初次配置很慢**：因为它在忙着“跨越太平洋”下载依赖，并根据你的系统进行首次编译。
- **配置失败**：通常是网络问题或缺失基础系统库。此时，手动下载源码放到 `external/` 目录是最高效的补救手段。

![依赖解析策略](diagrams/L01_deps.png)

### 4. "能编译"不代表"能运行"：运行时资源的自动复制

TinyFarm 在代码里加载资源时，用的是**相对路径**：
- `config/window.json` —— "去我旁边的 config 文件夹里找配置文件"。
- `assets/textures/...` —— "去我旁边的 assets 文件夹里找贴图"。

源码仓库里的 `assets/` 和 `config/` 放在项目根目录，而编译产物在 `build/` 目录深处。如果不做任何处理，可执行文件旁边就没有这些资源，程序自然无法启动。

**我们的对策——自动化复制**：在构建过程中，CMake 会自动把 `assets/` 和 `config/` 完整复制到可执行文件所在的目录（由 `BuildHelpers.cmake` 负责）。构建完成后，你可以直接运行程序，无需任何额外配置。

## 排查指南：哪里报错点哪里

当你遇到问题时，请按这个逻辑链条排查：

1. **Configure 阶段报错**：通常是**依赖**没对。检查网络或安装缺失的系统库。
2. **Build 阶段报错**：通常是**环境/代码**没对。检查 C++20 支持是否开启，编译器版本是否达标。
3. **运行崩溃/黑屏**：通常是**资源**没对。检查输出目录下是否有 `assets` 和 `config` 文件夹。

## 课后练习

> 练习为可选内容，建议通过提交 PR 的方式完成。

### 练习：实现资源的“增量复制”

**背景**：目前 `assets/` 每次构建都会全量复制，当素材变多时会很慢。而 `config/` 已经通过 `CopyConfig.cmake` 实现了基于 MD5 的增量更新。

**目标**：修改 `cmake/scripts/CopyAssets.cmake` 或相关逻辑，让 `assets/` 也支持增量复制（仅在文件内容变化时才重新拷贝）。

**验收标准**：
- 资源未变动时，重新构建时不会复制素材。
- 资源变动后，运行程序能立刻看到更新。

## 小结

回到开头的三个问题，现在你应该能清晰地回答：

1. **三阶段各自在忙什么？** Configure 画蓝图（检测环境、定位依赖、生成构建文件），Build 照图施工（编译、链接），Run 交付使用（在正确的资源环境中启动程序）。
2. **初次配置为什么慢？** 因为"三级回退策略"可能需要在线拉取并编译依赖。如果网络不畅，把源码手动放到 `external/` 目录即可绕过下载。
3. **能编译为什么跑不起来？** 因为程序用相对路径加载资源，而 `BuildHelpers.cmake` 负责在构建时自动把 `assets/` 和 `config/` 复制到可执行文件旁边。如果运行崩溃，第一时间检查这两个文件夹是否到位。
