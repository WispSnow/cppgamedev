# 资源系统：ResourceManager 外观模式与资源映射

前三节课我们把"渲染"这条链路从能画到画得好全部走通了：逻辑分辨率 + 视口适配、SpriteBatch 批处理、多 pass 离屏渲染与后处理合成。到这里，你已经能在屏幕上看到光影效果了。

但如果你现在回头看代码，会发现一件事——上面这些模块都在"消费"资源（纹理、音效、字体），却从来没有深入讲过**谁负责管理这些资源、它们怎么被加载、又怎么被缓存和释放**。

想象一个真实的开发场景：
- Title 界面需要一张背景图和一首背景音乐
- 进入游戏后需要加载角色图集、作物图集、地图瓦片、各种音效
- UI 按钮需要 normal/hover/pressed 三态贴图加音效
- 换一首标题音乐，你希望改一行配置就好，不想碰代码

如果这些加载逻辑散落在各个模块里——Scene 里写了 `loadTexture()`，UI 里又写了一次，System 里再来一次——你很快就会遇到：**模块间依赖混乱**（UI 为什么要知道 OpenGL？）、**重复加载**（同一张图被加载了三次）、**路径硬编码**（换资源就要改一堆 `.cpp`）。

所以这节课的核心不是"怎么加载一张 png"，而是讲**工程化的资源系统**：它如何让上层只依赖稳定 API、如何用数据把"语义 key"映射到真实路径、以及如何用调试面板验证资源加载与内存预算。

## 本节目标与问题定义

核心问题可以用一句话概括：

> 在《迷你农场》里建立一个可维护、可观测的资源入口：用 `ResourceManager` 作为 Facade，统一纹理/音频/字体/UI 预设的加载与缓存，并通过 `resource_mapping.json` 支持"语义 key → 路径"的替换能力。

本节完成后你应该能回答这三个问题：

1. **职责边界**：哪些模块可以直接接触 OpenGL / miniaudio / FreeType，哪些模块只能通过 `ResourceManager`？
2. **ID 策略**：什么时候用 `key-id`（语义 key + 映射预加载），什么时候用 `path-hash`（路径即 ID）？怎么选？
3. **可观测性**：资源没加载 / 重复加载 / 占用异常时，应该先看哪里？

## 核心概念

### Facade：统一入口，让依赖方向可控

假设没有 `ResourceManager`，TitleScene 要播放音乐、显示背景，代码大概长这样（伪代码）：

```cpp
// TitleScene 直接依赖了三个底层模块
#include "texture_manager.h"   // OpenGL 相关
#include "audio_manager.h"     // miniaudio 相关
#include "font_manager.h"      // FreeType 相关

void TitleScene::init() {
    auto* tex = texture_manager.loadTexture(...);
    auto  bgm = audio_manager.loadMusic(...);
    auto* font = font_manager.loadFont(...);
}
```

问题很明显：TitleScene 需要知道三个管理器的存在，而这三个管理器各自依赖不同的底层库。一旦你想改底层实现（比如把 miniaudio 换成 FMOD），所有直接依赖 `AudioManager` 的地方都要改。

《迷你农场》的做法是经典的 **Facade（外观模式）**：

- `ResourceManager` 作为**唯一入口**，对外提供稳定 API（`loadTexture` / `getSound` / `getFont` / `getUIPresetManager` + 调试接口）
- 内部持有并管理五个子管理器的生命周期：

| 子管理器 | 职责 | 底层依赖 |
| --- | --- | --- |
| `TextureManager` | 纹理加载、OpenGL 上传、缓存 | OpenGL (GLAD) + stb_image |
| `AudioManager` | 音效/音乐解码、PCM 缓存 | miniaudio + stb_vorbis |
| `FontManager` | 字体加载、字形光栅化与图集缓存 | FreeType + HarfBuzz |
| `UIPresetManager` | UI 按钮皮肤/图片预设的 JSON 解析与查询 | nlohmann-json |
| `AutoTileLibrary` | 自动瓦片规则表（与地图更相关，[地图数据管线](21-地图数据管线.md) 讲） | — |

上层（Scene / UI / System）**只通过 `ResourceManager` 拿资源，永远不碰子管理器**。

这解决了两个工程痛点：

1. **依赖收敛**：上层模块只依赖 `ResourceManager` 一个头文件，而不是分别依赖 OpenGL、miniaudio、FreeType 等底层库。依赖关系从"网状"变成了"星型"。
2. **可替换**：将来你想给 `TextureManager` 加异步加载或 LRU 淘汰，只要 `ResourceManager` 的接口不变，上层完全不用改。

下图展示了这个 Facade 结构——启动阶段如何从 JSON 预加载资源、运行时上层系统如何通过统一入口访问子管理器、以及调试面板如何观察缓存状态：

<img src="https://theorhythm.top/gamedev/TF/L11_facade_module.webp" style='width: 960px;' />

> **记住这条原则：上层不应该知道 TextureManager / AudioManager 的存在，更不应该直接接触底层库。**

### ResourceManager 的创建与初始化

`ResourceManager` 的创建发生在 `GameApp::initResourceManager()` 中，是整个应用的早期初始化步骤之一：

```cpp
// src/engine/core/game_app.cpp
bool GameApp::initResourceManager() {
    resource_manager_ = ResourceManager::create(dispatcher_.get());
    if (!resource_manager_) {
        spdlog::error("初始化资源管理器失败。");
        return false;
    }
    resource_manager_->loadResources("assets/data/resource_mapping.json");
    return true;
}
```

注意这里的顺序：先 `create()`（创建所有子管理器），再 `loadResources()`（从映射文件预加载资源）。`create()` 使用工厂方法而非构造函数，是因为 `FontManager::create()` 可能失败（FreeType 初始化失败），而构造函数无法优雅地报告失败。

### `resource_mapping.json`：用数据把"语义 key"绑定到真实路径

`assets/data/resource_mapping.json` 是资源系统的**核心数据文件**。它的作用是：

> 把代码里稳定的语义 key（例如 `"title-bg-music"`）映射到真实文件路径（例如 `assets/audio/02_spring_fairy_tale.ogg`）。

看一下实际内容（精简版）：

```json
{
  "ui_button_presets": "assets/data/ui_button_presets.json",
  "ui_image_presets": "assets/data/ui_image_presets.json",
  "sound": {
    "ui_click": "assets/audio/Fantasy_UI (10).wav",
    "ui_hover": "assets/audio/Fantasy_UI (1).wav",
    "watering": "assets/audio/water_splash.wav",
    "harvest": "assets/audio/plant_harvest.wav"
  },
  "music": {
    "title-bg-music": "assets/audio/02_spring_fairy_tale.ogg",
    "scene-bg-music": "assets/audio/01_spring_journey.ogg"
  },
  "texture": {
    "title-bg": "assets/textures/UI/farm-rpg-bg.png",
    "title-logo": "assets/textures/UI/farm-rpg-logo.png"
  }
}
```

这带来的好处非常直接：

- **替换资源不改代码**：想换标题音乐？把 `"title-bg-music"` 指向另一个 `.ogg` 文件就行。
- **资源 key 作为契约**：TitleScene / UI / 系统只需要知道 key，不需要知道路径。代码里写 `"title-bg-music"`，美术资源换了十遍，代码一行不用动。
- **集中管理**：所有"启动阶段应该预加载的资源"都列在一个文件里，一目了然。

`loadResources()` 内部的逻辑也很直白——遍历 JSON 的每个 section（`sound` / `music` / `texture` / `font`），对每一条 `key → path` 调用对应的 `loadXxx(id, path)`。此外还处理了 `ui_button_presets` 和 `ui_image_presets` 字段，加载 UI 预设数据。

### 两种资源 ID 策略：key-id vs path-hash

在实际项目中，你会发现资源的标识方式不止一种。《迷你农场》里有两种策略，选择哪种取决于使用场景：

<img src="https://theorhythm.top/gamedev/TF/L11_id_strategy_comparison.webp" style='width: 960px;' />

#### 策略 A：key-id（语义 key）

你会在 `TitleScene` 看到这类用法：

```cpp
// src/game/scene/title_scene.cpp
constexpr entt::hashed_string TITLE_BG_ID{"title-bg"};
constexpr entt::hashed_string TITLE_LOGO_ID{"title-logo"};

// 使用时只传 ID，不带路径
auto src_size = context_.getResourceManager().getTextureSize(TITLE_BG_ID);
```

音乐 ID 则集中定义在 `audio_ids.h` 中：

```cpp
// src/game/defs/audio_ids.h
constexpr entt::hashed_string TITLE_BG_MUSIC_ID{"title-bg-music"};
constexpr entt::hashed_string SCENE_BG_MUSIC_ID{"scene-bg-music"};
```

key-id 的特点：

- 代码表达"**这是什么**"（标题背景、标题音乐），而不是"在哪里"（文件路径）
- **依赖预加载**：key 本身不包含路径信息，运行时无法从 key 推导出路径。所以 key-id **必须**在启动阶段通过 `resource_mapping.json` 预加载到缓存中
- **适用场景**：Title / UI / 固定资源——数量有限、需要可替换的资源

#### 策略 B：path-hash（路径即 ID）

在蓝图系统（`BlueprintManager`）中你会看到另一种风格：

```cpp
// src/game/factory/blueprint_manager.cpp
auto path_str = json.value("path", "");
auto path_id = entt::hashed_string(path_str.c_str());  // 路径本身的哈希就是 ID
```

path-hash 的特点：

- 调用点**同时携带 ID 和路径**，因此可以"按需加载"——缓存未命中时，用 `data()` 里保存的路径去加载
- 缺点是：**改路径就会改 ID**，同一个资源换了路径后会被当成新资源
- **适用场景**：蓝图 / 数据驱动生成的大量资源——不想把几十上百条目都塞进映射文件

**选型建议一句话**：数量少且需要可替换 → key-id + mapping；数量多且由数据驱动 → path-hash。

### 子管理器的缓存策略

虽然上层不直接使用子管理器，但理解它们的缓存方式能帮助你排查问题和建立"资源不是免费的"直觉。

**TextureManager**

- 缓存结构：`unordered_map<entt::id_type, TextureResource>`
- 每条缓存记录了 OpenGL 纹理句柄（`GL_Texture`）、来源路径、估算内存（`width * height * 4` 字节）
- 用 `unique_ptr` + 自定义删除器管理 GPU 资源（析构时调用 `glDeleteTextures`）
- **重复加载保护**：如果 ID 已在缓存中，直接返回已有纹理，不会重新上传

**AudioManager**

- 音效（`sounds_`）和音乐（`music_`）**分开缓存**：两个独立的 `unordered_map`
- 缓存的是解码后的 PCM 浮点采样数据（`AudioBuffer`），用 `shared_ptr` 管理
- 为什么用 `shared_ptr`？因为音频需要持续播放，播放期间缓存不能被释放。`AudioPlayer` 拿到的是 `shared_ptr<const AudioBuffer>`（只读句柄），即使缓存被清空，正在播放的数据仍然安全
- 内存估算：`sample_count * sizeof(float)` 字节

**FontManager**（本课只需了解入口，细节在 [字体与文本渲染](14-字体与文本渲染.md) 讲）

- 缓存键是 `(id, pixel_size)` 的组合——同一个字体文件在不同字号下是**不同的缓存条目**
- 底层维护的是字形图集（glyph atlas），内存开销主要在 atlas 纹理上

### UI 预设：把"UI 资源"从代码中剥离

`UIPresetManager` 是资源系统中一个独特的子模块——它管理的不是原始资源（图片/音频），而是**结构化的 UI 样式数据**。

看一个按钮预设的例子（`ui_button_presets.json` 中的 `"primary"` 条目）：

```json
{
  "primary": {
    "images": {
      "normal":  { "path": "assets/farm-rpg/UI/button.png", "source": [0, 16, 48, 16] },
      "hover":   { "path": "assets/farm-rpg/UI/button.png", "source": [0, 16, 48, 16] },
      "pressed": { "path": "assets/farm-rpg/UI/button.png", "source": [0, 32, 48, 16] }
    },
    "nine_slice": { "left": 3.0, "top": 5.0, "right": 3.0, "bottom": 5.0 },
    "label": {
      "text": "按钮",
      "font_path": "assets/fonts/VonwaonBitmap-16px.ttf",
      "font_size": 16,
      "color": [1.0, 1.0, 1.0, 1.0]
    },
    "sounds": {
      "hover": "assets/audio/UI_button11.wav",
      "click": "assets/audio/UI_button08.wav"
    }
  }
}
```

一个预设里包含了按钮所需的**全部视觉和交互信息**：三态贴图（normal/hover/pressed）+ 九宫格拉伸参数 + 文字样式 + 音效路径。

使用时，代码只需要一个预设 ID：

```cpp
// src/game/scene/title_scene.cpp
auto start_button = UIButton::create(context_, "secondary", position, size, callback);
```

`"secondary"` 就是预设 ID。`UIButton::create()` 内部会通过 `UIPresetManager` 查找这个 ID 对应的皮肤数据，然后自动配置好图片、九宫格、音效等。你不需要在代码里写任何路径或颜色值。

类似地，`ui_image_presets.json` 定义了常用 UI 图片预设（如 `"cursor"`、`"inventory_panel"`），在代码中通过 ID 获取 `Image` 结构体。

这套机制的价值在于：**改按钮样式只改 JSON，不改代码。** 甚至可以为不同的游戏风格维护多套预设文件。

### 调试面板：你的资源仪表盘

`Resource` 调试面板（`ResMgrDebugPanel`）是验证资源系统状态的第一入口。你可以在运行时通过 `F5` → `Engine Debug Panels` → `Resource` 打开它。

面板展示了五类缓存的详细信息：

| 分类 | 展示内容 |
| --- | --- |
| Textures | 每张纹理的 ID、OpenGL 句柄、尺寸、来源路径、估算内存 |
| Fonts | 每个字体条目的 ID、字号、字形数量、行高参数、atlas 页数/内存 |
| Sounds | 每条音效的 ID、来源路径、声道数/采样率/时长、估算内存 |
| Music | 每条音乐的 ID、来源路径、声道数/采样率/时长、估算内存 |
| Auto Tiles | 自动瓦片规则条目（[地图数据管线](21-地图数据管线.md) 再讲） |

**两个典型的使用场景：**

1. **验证预加载**：在 TitleScene 打开面板，检查 `title-bg` / `title-bg-music` 等 key 是否已出现在缓存中。如果没有，说明 `resource_mapping.json` 配置有问题。

2. **观察场景切换的资源变化**：在 TitleScene 记下缓存条目数，然后进入 GameScene，再看面板——你会看到纹理/音效条目明显增加（角色图集、作物图集、地图瓦片等被加载了）。这能帮你建立"场景切换会触发资源加载"的直觉。

## "踩坑清单"：常见问题与排查

### 问题 1：为什么我只传了一个 ID，却加载失败？

这是最常见的误解，根源在于 `entt::hashed_string` 的双重身份：

- `value()`：返回哈希值（`entt::id_type`），用作缓存的 key
- `data()`：返回原始字符串，在 path-hash 语义下被当作文件路径使用

本项目中，`getTexture(entt::hashed_string)` / `getSound(entt::hashed_string)` 这类接口，在缓存未命中时会尝试把 `data()` 当作路径去加载。

因此当你传入语义 key（例如 `"title-bg"`）时：
- **已预加载** → `value()` 命中缓存 → 正常返回
- **未预加载** → 尝试把 `"title-bg"` 当路径读文件 → 文件不存在 → 失败

**排查路径**：
1. 打开 `F5` → `Engine Debug Panels` → `Resource`，看缓存里有没有这条资源
2. 看日志中是否出现"加载失败"相关信息
3. 回到 `assets/data/resource_mapping.json` 检查 key 是否存在、路径是否正确

### 问题 2：为什么同一张图占了两份内存？

如果你用两个不同的 key（或一个 key + 一个路径）加载同一个文件，`TextureManager` 会认为它们是不同的资源（因为 `entt::id_type` 不同），从而上传两次。

解决办法：统一使用一个 ID 来引用同一个资源。如果多个地方需要同一张图，要么都用同一个 key-id，要么都用同一个路径的 path-hash。

### 问题 3：预设按钮创建返回 nullptr

`UIButton::create(context, "preset_id", ...)` 返回 nullptr 通常是因为 `UIPresetManager` 里找不到这个预设 ID。检查：
1. `resource_mapping.json` 中 `"ui_button_presets"` 是否指向了正确的 JSON 文件
2. 该 JSON 文件中是否有你使用的 key
3. JSON 格式是否合法（一个多余的逗号就能导致整个文件解析失败）

## 演示：动手验证

### 演示 1：Resource 面板观察

1. 运行游戏，进入 Title 界面
2. 按 `F5` → 找到 `Engine Debug Panels` → 勾选 `Resource`
3. 观察 Textures 分类：你应该能看到 `title-bg` 和 `title-logo` 两条纹理
4. 观察 Music 分类：你应该能看到 `title-bg-music`
5. 点击 Start 进入 GameScene，再看面板——纹理和音效条目大量增加

### 演示 2：不改代码替换资源

1. 打开 `assets/data/resource_mapping.json`
2. 把 `"title-bg-music"` 的路径从 `02_spring_fairy_tale.ogg` 改成 `01_spring_journey.ogg`
3. 重新运行游戏——标题音乐变了，代码一行没动

这就是"语义 key + 映射文件"的核心价值：**资源路径是数据，不是代码。**

### 演示 3：UI 预设即数据

1. 打开 `assets/data/ui_button_presets.json`
2. 找到 `"primary"` 预设，观察它的 `images` / `nine_slice` / `label` / `sounds` 字段
3. 打开 `assets/data/ui_image_presets.json`
4. 找到 `"cursor"` 预设，看看鼠标光标的图片是如何被数据化描述的

在代码中使用这些预设时，只需要一个字符串 ID（如 `"primary"`、`"cursor"`），所有视觉和交互细节都来自 JSON。

### 练习 1：为 Resource 面板添加"热重载数据"按钮

> 目的：把资源系统从"能加载"提升到"开发体验可用"，并巩固你对 mapping / presets 生命周期的理解。

- **目标**：在 `Resource` 调试面板中加入两个按钮：
  - `Reload resource_mapping.json`：重新读取映射文件并加载新资源
  - `Reload UI presets`：重新加载 UI 按钮/图片预设
- **验收标准**（满足 3 项即可）：
  - 按钮点击不会崩溃；成功时日志/面板有明确提示
  - 错误路径（文件不存在/JSON 无效）能被捕获并提示，不影响已有缓存的正常使用
  - UI presets 重新加载后，至少能在 Title/UI 中看到变化（例如按钮样式/hover/click 音效）
- **提示线索**：
  - `src/engine/debug/panels/res_mgr_debug_panel.*`
  - `src/engine/resource/resource_manager.*`：关注 `loadResources()` / `loadUIButtonPresets()` / `loadUIImagePresets()`
  - `assets/data/resource_mapping.json`、`assets/data/ui_button_presets.json`、`assets/data/ui_image_presets.json`

### 练习 2：为 TextureManager 增加可选纹理参数（可选，进阶）

> 目的：理解"缓存不是免费的"，并为后续更复杂的渲染/UI 做铺垫（过滤方式、sRGB 等）。

- **目标**：允许在 mapping 或数据里声明纹理参数（例如 NEAREST/LINEAR 过滤方式、是否 sRGB）
- **验收标准**：
  - 默认行为不变；新增字段可选且有回退策略
  - 不破坏现有资源加载与渲染结果
- **提示线索**：
  - `src/engine/resource/texture_manager.*`（纹理上传与参数设置）
  - `assets/data/resource_mapping.json`（扩展 schema 的入口）

## 小结

这节课的关键要点：

1. **`ResourceManager` 是 Facade**：上层只依赖它，不直接依赖底层库。依赖方向从"网状"变"星型"。
2. **`resource_mapping.json` 让语义 key 可替换**：改数据，不改代码。key-id 适合固定资源，path-hash 适合数据驱动的大量资源。
3. **`Resource` 面板是你的仪表盘**：用它验证"是否加载 / 是否重复 / 占用多少"，建立"缓存不是免费的"直觉。

下节课（字体与文本渲染）我们会把资源系统里最"看不见但很关键"的部分补齐：字体与文本渲染。

从 `FontManager` 到 glyph atlas 再到 `TextRenderer`，你会看到：
- "一行文字"背后其实是一套完整的资源缓存系统（字体文件 + 字形光栅化 + 图集纹理）
- 为什么文本渲染同样需要预算与可观测性（atlas 内存、glyph 命中率）
- 世界文本和 UI 文本在渲染路径上有什么差异
