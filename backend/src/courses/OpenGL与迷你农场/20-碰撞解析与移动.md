# 碰撞解析与移动：从目标位移到可行位移

上节课我们搭建了空间查询的基础设施——`StaticTileGrid` 回答"这块瓦片是什么"，`DynamicEntityGrid` 回答"附近有哪些碰撞体"，`SpatialIndexManager` 把两者统一到一套查询 API 里，解决的是"怎么查"的问题。

但"查得到"和"用得对"是两回事。只要你开始真正写移动逻辑——哪怕只是让角色朝墙走一步——就会发现一个绕不开的核心问题：

> 我们每帧能算出一个 **目标位置（`target_pos`）**，但游戏体验需要的是一个 **可行位置（`resolved_pos`）**。两者经常不相等。

本节就是把这件事工程化落地。在 TinyFarm 里，移动不是简单的"把 position 改成 target"，而是一条完整的解析管线：

> `Velocity → target_pos → CollisionResolver → resolved_pos`

---

## 本节目标

用一句话定义：

> 理解 TinyFarm 如何把"移动系统产出的目标位置（`target_pos`）"通过 `CollisionResolver` 解析为"可行位置（`resolved_pos`）"，并让静态瓦片（SOLID/薄墙）与动态实体碰撞器共同生效。

学完本节，你应该能回答三个问题：
1. 移动系统的"三段式"管线是什么？每一段由哪个模块负责？
2. SOLID 和薄墙（`BLOCK_*`）在检测方式上有什么本质区别？
3. AABB 和 Circle 碰撞器如何共享同一套解析逻辑？

---

## 1. 为什么不能只做"终点重叠判定"？

最直觉的碰撞实现是：算出 `target_pos`，检查终点是否和墙/实体重叠——不重叠就走过去，重叠就不动。

这个做法在实践中会产生三类典型问题：

**穿墙（tunneling）**：当速度大或 `dt` 抖动时，`target_pos` 可能直接跨过一道薄墙或窄障碍。终点不重叠，但运动路径穿过了墙——判定通过，玩家却穿墙了。

**卡边**：只要终点触发碰撞就整轴不动，玩家会在离墙还有一段距离时就停住，手感非常"硬"。

**无法滑动（no slide）**：斜向移动撞墙时，如果"一票否决"整个移动，玩家会同时丢掉 X 和 Y 两个方向的速度，无法贴着墙壁滑动——这在几乎所有 2D 游戏里都是不可接受的手感。

所以，碰撞解析的核心不是一个简单的 `if/else`，而是一套**可解释、可调试、可扩展**的策略组合。这正是 `CollisionResolver` 的设计目标。

---

## 2. 核心概念

本节需要建立四个心智模型。

### 2.1 移动三段式：target_pos 只是"意图"，resolved_pos 才是"结果"

TinyFarm 的运动链路在 ECS 里分为三层：

| 层次 | 职责 | 负责模块 |
|------|------|----------|
| **意图层** | 玩家控制 / AI 写入移动速度 | `PlayerControlSystem` / `NPCWanderSystem` 等 → `VelocityComponent.velocity_` |
| **积分层** | 用 `current_pos + v * dt` 算出目标位置 | `MovementSystem` |
| **解析层** | 把 `target_pos` 解析成不穿墙、不重叠的可行位置 | `CollisionResolver::resolveMovement()` → `TransformComponent.position_` |

用伪代码表示这条管线：

```text
target_pos   = current_pos + velocity * dt
resolved_pos = CollisionResolver.resolveMovement(entity, current_pos, target_pos)
transform.position = resolved_pos
mark TransformDirtyTag          // 通知空间索引同步
```

**这条管线的关键设计决策**：`CollisionResolver` 是纯函数式的——它不直接修改 ECS 中的任何数据，只接收输入、返回结果。这意味着你可以在不同上下文中复用它（比如 AI 路径验证），也可以在不改变架构的前提下替换解析策略。

### 2.2 静态阻挡语义：SOLID vs 薄墙（BLOCK_*）

TinyFarm 的静态阻挡来自 tile 的 `TileType` 位标志（定义在 `tilelayer_component.h`）。这是一个**位掩码枚举**，低 4 位编码物理阻挡方向，高位编码逻辑属性：

```text
bit 0-3:  BLOCK_N(1) | BLOCK_S(2) | BLOCK_W(4) | BLOCK_E(8)
bit 4-8:  HAZARD(16) | WATER(32) | INTERACT(64) | ARABLE(128) | OCCUPIED(256)
组合:     SOLID = BLOCK_N | BLOCK_S | BLOCK_W | BLOCK_E = 15
```

位掩码的好处是组合灵活：
- `hasTileFlag(type, BLOCK_N)` —— 检测是否阻挡从北方进入（任一位匹配即可）
- `hasAllTileFlags(type, SOLID)` —— 检测是否完全实心（四个方向全部阻挡）
- 自由组合新语义，例如 `ARABLE | OCCUPIED` 表示"已被占用的可耕地"

由此产生两种本质不同的阻挡语义：

**SOLID（实心墙体）**：四个方向标志全部置位。概念上，这个 tile 是"填满的"——不允许碰撞器的任何部分进入该区域。适合用**区域重叠判定**：检查碰撞器的包围矩形是否与 SOLID tile 重叠。

**薄墙 / 方向阻挡（`BLOCK_N/S/W/E`）**：只有部分方向标志置位。概念上，这像一道栅栏或门口——tile 本身不是实心的，但**从特定方向跨越 tile 边界**会被阻挡。适合用 **sweep 扫掠**：检查运动路径是否跨越了被阻挡的边界线。

> **一句话区分**：SOLID 关注的是"你在不在墙里"，薄墙关注的是"你有没有跨过那条线"。

<img src="https://theorhythm.top/gamedev/TF/L18_tile_type_and_thin_wall.webp" style='width: 960px;' />

值得注意的是，薄墙的阻挡检测是**双向的**：tile A 的 `BLOCK_E` 和相邻 tile B 的 `BLOCK_W` 都能阻挡从 A 到 B 的穿越。代码中 `isThinWallBlockedBetween()` 会同时检查两侧，确保无论在哪侧设置标志，阻挡都能生效。

### 2.3 轴分解：为什么先解 X 再解 Y 会自然产生"滑动"

把一次 2D 位移 `delta = (dx, dy)` 拆成两次独立的 1D 位移：
1. 先尝试沿 X 移动 `dx`（Y 保持不变）
2. 再尝试沿 Y 移动 `dy`（X 使用第一步的结果）

这样做的好处立竿见影：如果 X 方向被墙挡住了但 Y 方向畅通，玩家仍然能沿 Y 轴前进。**反映到游戏体验上，就是"贴墙滑动"**——玩家斜向推墙时不会卡住不动，而是沿着墙面滑行。

这也是 TinyFarm 的 `CollisionResolver::resolveMovement()` 采用的核心策略。

<img src="https://theorhythm.top/gamedev/TF/L18_axis_decomposition.webp" style='width: 960px;' />

> **为什么不是"先 Y 后 X"？** 在 TinyFarm 的当前实现中固定为先 X 后 Y。对于大多数 2D 游戏场景，轴的优先级对手感影响很小。如果你的项目需要更精细的控制（比如根据移动方向动态选择优先轴），可以在 `resolveMovementForShape()` 中调整顺序。

### 2.4 动态阻挡：broadphase 候选 → narrowphase 相交

动态实体（NPC、动物、树木等）的碰撞不能每次遍历全场景，所以 TinyFarm 延续 [空间索引](19-空间索引.md) 的两阶段方案：

- **broadphase**：`DynamicEntityGrid` 根据空间分区给出候选集合（candidates）——只包含可能重叠的实体
- **narrowphase**：用真实碰撞形状（AABB 或 Circle）做精确相交判定，排除误报

在碰撞解析中，这条链路的用途非常明确：当你沿某个轴尝试移动到候选位置时，只要**与任意动态碰撞器发生重叠**，就认为这个轴"被阻挡"，保持原位。

这是一个刻意的简化：**重叠即阻挡**，不做物理推挤（MTV/推开），不计算反弹或摩擦。对于农场经营类游戏，这个策略已经足够——角色碰到障碍物就停下，不需要弹飞或滑开。

## 3. 架构与数据流

理解了核心概念后，我们从代码层面看这些概念是如何落地的。

### 3.1 系统执行顺序

在 `GameScene::update()` 中，与移动/碰撞相关的系统按以下顺序更新（省略无关系统）：

```text
PlayerControlSystem / NPCWanderSystem / ...  → 写 VelocityComponent
StateSystem                                  → 状态决策
MovementSystem                               → velocity → target → resolved → position
SpatialIndexSystem                           → 用 TransformDirtyTag 同步动态网格
PickupSystem / InteractionSystem / ...       → 消费最新位置做查询
CameraFollowSystem                           → 跟随最新位置
```

这里有一个**不可违反的约束**：`SpatialIndexSystem` 必须在 `MovementSystem` 之后运行。原因很直接：MovementSystem 改变了实体位置并打上 `TransformDirtyTag`，SpatialIndexSystem 根据这个 tag 刷新动态网格——只有按这个顺序，后续的 PickupSystem、InteractionSystem 等系统查询到的才是本帧最新的实体位置。

### 3.3 MovementSystem：从 velocity 到 resolved_pos

`MovementSystem::update()` 遍历所有拥有 `VelocityComponent + TransformComponent` 的实体，核心逻辑分四步：

```text
for each entity with (Velocity, Transform):
    v = velocity.velocity_
    if |v| ≈ 0: continue              // 极小速度视为静止，避免浮点噪声

    target_pos = transform.position_ + v * dt

    if has_collider:
        resolved_pos = collision_resolver->resolveMovement(entity, current_pos, target_pos)
    else:
        resolved_pos = target_pos       // 无碰撞器 → 自由移动

    if position actually changed:       // epsilon 比较，避免浮点抖动
        transform.position_ = resolved_pos
        mark TransformDirtyTag          // 通知 SpatialIndexSystem 同步
```

<img src="https://theorhythm.top/gamedev/TF/L18_movement_system_flow.webp" style='width: 960px;' />

这里有两个值得注意的设计细节：

**`CollisionResolver` 是可选的**：如果构造 `MovementSystem` 时不传入 resolver（传 `nullptr`），所有实体直接使用 `target_pos`，不做任何碰撞解析。这意味着你可以在不需要碰撞的场景（如标题画面的视差背景）中复用同一个移动系统。

**帧内动态网格同步**（`sync_dynamic_grid_during_movement`）：当多个实体在同一帧移动时，会出现一个微妙的时序问题——实体 A 移动后，实体 B 的碰撞查询可能还在用上一帧的网格数据，导致 B "看不到" A 的新位置。开启此选项后，MovementSystem 会在移动每个实体前后调用 `syncDynamicCollider()` 做就地同步。代价是更多的网格更新操作，但对于本项目的实体规模完全可以接受。

### 3.4 CollisionResolver：轴分解解析策略

`CollisionResolver` 是一个无状态的工具类（`collision_resolver.h`），提供两个核心 API：
- **`resolveMovement(entity, current_pos, target_pos)`**：把目标位移解析成可行位移——本节主线
- **`canMoveTo(entity, target_pos)`**：只判定"能不能到达目标位置"——被 NPC 漫游、地图切换等系统使用

#### 解一条轴的完整流程

以沿 X 轴移动为例，`resolveMovementForShape()` 内部对每条轴执行以下步骤：

```text
start_rect  = boundsAt(resolved_pos)           // 当前碰撞器包围矩形
target_rect = start_rect shifted by dx         // 沿 X 平移后的包围矩形
direction   = dx > 0 ? East : West

// Step 1: 薄墙 sweep —— 裁剪到"贴边但不跨边界"的位置
sweep = SpatialIndexManager.resolveStaticSweep(start_rect, target_rect, direction)
candidate_pos.x = sweep.rect.pos.x + half_extent.x - collider.offset_.x

// Step 2: SOLID 判定 —— 裁剪后的位置是否落入实心墙体
if StaticTileGrid.hasSolidInRect(boundsAt(candidate_pos)):
    block this axis → 保持原位

// Step 3: 动态 overlap —— 候选集 → 精确相交判定
if anyDynamicOverlap(candidate_pos, self):
    block this axis → 保持原位

// Step 4: 所有检查通过 → 提交本轴移动
resolved_pos.x = candidate_pos.x
```

**三步检查的顺序是刻意的**：

1. **薄墙 sweep 在最前**——它处理的是"路径上的边界"，会把 candidate 裁剪到第一个被阻挡的 tile 边界前（留一个极小的 epsilon 间隙）。如果不先做 sweep，高速移动可能直接跨过薄墙。
2. **SOLID 判定在中间**——sweep 之后的位置仍可能落在 SOLID tile 里（比如在拐角处），需要再做一次区域判定。
3. **动态 overlap 在最后**——基于已经过静态裁剪的安全位置做精确判定，避免"先查动态碰撞、再被静态 sweep 裁回来"的无效计算。

#### AABB 与 Circle 碰撞器的统一

在代码中，AABB 和 Circle 两条解析路径被统一到模板函数 `resolveMovementForShape<ColliderT>()` 中。差异通过函数重载注入，而非 `if/else` 分支：

| 差异点 | AABB | Circle |
|--------|------|--------|
| `boundsRectAt(pos, collider)` | `pos + offset - size * 0.5` | `center - vec2(radius), vec2(radius * 2)` |
| `half_extent` | `size * 0.5f` | `vec2(radius)` |
| `anyDynamicOverlap()` | 矩形查询 + `intersectsRectQuery` | 圆形查询 + `intersectsCircleQuery` |

这是一个典型的"函数重载 + 模板"实现静态多态的模式：编译期根据碰撞器类型选择正确的重载，运行时零开销。

<img src="https://theorhythm.top/gamedev/TF/L18_template_unification.webp" style='width: 960px;' />

> **注意**：Circle 碰撞器在**静态碰撞**（SOLID 判定和薄墙 sweep）时使用的是其包围矩形，而非圆形本身。这意味着在 tile 拐角处，圆形碰撞器的表现会略"胖"于理论值。课后练习 1 就是针对这个近似做精确化改进。

### 3.5 resolveStaticSweep：sweep 方向的统一分派

`SpatialIndexManager::resolveStaticSweep()` 是静态 sweep 的统一入口。它根据移动方向决定调用哪个底层 sweep 函数：

```text
is_vertical  = (direction == North || direction == South)
positive_dir = (direction == South || direction == East)

if is_vertical:
    sweepVertical(start_rect, target_rect, positive_dir)
else:
    sweepHorizontal(start_rect, target_rect, positive_dir)
```

底层的 `sweepVertical` / `sweepHorizontal`（定义在 `StaticTileGrid` 中）沿移动方向**逐 tile 边界扫描**：

1. 计算碰撞器的前沿边（leading edge）在起点和终点之间跨越了哪些 tile 边界
2. 对每条边界，检查相邻两行/两列的 tile 是否有对应方向的阻挡标志（例如 `BLOCK_S` 或 `BLOCK_N`）
3. 遇到第一个被阻挡的边界就停下——返回"刚好贴在边界前"的矩形位置（带 epsilon 缩减）
4. 如果没有命中任何边界，返回原始 target 位置（不裁剪）

返回值是 `SweepResult`，包含裁剪后的矩形位置和命中信息（`hit_solid` / `hit_thin_wall` / 边界坐标），这些调试信息可以在 Spatial Index 调试面板中可视化查看。

### 3.6 碰撞形状抽象（collider_shape.h）

`collider_shape.h` 是一个纯函数工具头（header-only），把"碰撞器组件 → 几何形状 → 相交判定"封装成无状态的 inline 函数。它在 [空间索引](19-空间索引.md) 中已经出现过，本节中承担了更多职责：

| 函数 | 用途 |
|------|------|
| `boundsRectAt(pos, AABBCollider/CircleCollider)` | 根据实体位置和碰撞器参数计算包围矩形 |
| `circleCenterAt(pos, CircleCollider)` | 计算圆心世界坐标 |
| `buildColliderShape(registry, entity)` | 从 ECS 读取 Transform+Collider，构造统一的 `ColliderShape` |
| `intersectsRectQuery(rect, shape)` | 矩形 vs ColliderShape 相交判定 |
| `intersectsCircleQuery(center, radius, shape)` | 圆形 vs ColliderShape 相交判定 |

它的设计意图是：让 `SpatialIndexManager` 和 `CollisionResolver` **共用同一套判定逻辑**。如果相交测试分散在多个文件中各写一份，迟早会出现"改了一处忘了另一处"的漂移问题。集中到一个 header-only 的工具文件中，既保证了一致性，也方便你在调手感时只改一处。

## 4. 常见问题与排错

在实际开发中，碰撞解析是最容易产出"诡异 bug"的模块之一。以下是本项目常见的几类问题和排查思路：

**薄墙不生效**：先在 Spatial Index 调试面板中确认对应 tile 的 `TileType` 是否包含正确的 `BLOCK_*` 标志。薄墙需要在 Tiled 编辑器中正确设置 tile 属性，漏设标志是最常见的原因。

**角色能穿过动态障碍**：检查三件事——(1) 障碍实体是否有 `SpatialIndexTag`；(2) 是否挂载了 `AABBCollider` 或 `CircleCollider`；(3) `sync_dynamic_grid_during_movement` 是否开启（关闭时多实体同帧碰撞可能失效）。

**角色在墙前一段距离就停住**：可能是碰撞器的 `offset` 或 `size` 设置不当，导致包围矩形比视觉精灵大。在调试面板中开启碰撞器包围盒显示，对比视觉和碰撞边界。

**边缘抖动（jitter）**：当速度很大或帧率不稳定时，`dt` 的波动可能导致角色在 tile 边界附近反复进出。`StaticTileGrid` 的 sweep 使用了 epsilon 缩减（`0.001f`）来缓解此问题，但如果速度远超预期（比如 debug 时手动设置了极高速度），仍然可能出现。

## 课后练习

### 练习 1（推荐）

**题目：把圆形碰撞器的静态检测从 bounding-rect 升级为 circle-vs-tile-AABB 精确检测**

目前 `SpatialIndexManager::checkCollision(center, radius)` 的静态部分使用碰撞器的包围矩形做简化判定，这意味着在 tile 拐角处，圆形碰撞器可能被"过早阻挡"——明明圆形能贴着拐角通过，但包围矩形比圆形"胖"一圈，提前触发了碰撞。

- **目标**：在不改变对外 API 的前提下，让圆形碰撞器在拐角/窄通道处更贴合直觉
- **验收标准**：
  - `ctest --test-dir build --output-on-failure` 通过
  - 至少新增 1 个单元测试覆盖"bounding rect 误判"场景（例如：圆能贴着角通过，但 bounding rect 会判为碰撞）

## 小结

本节我们把"移动与碰撞"从散落的 `if/else` 里剥离出来，形成了一个清晰的工程闭环：

- **`MovementSystem`** 负责积分（`target_pos`），并在必要时做帧内动态网格同步
- **`CollisionResolver`** 负责轴分解解析（`resolved_pos`），AABB/Circle 通过模板统一
- 静态瓦片用两种语义表达阻挡：**SOLID**（区域判定）与**薄墙**（边界 sweep）
- 动态实体通过 spatial index 的 broadphase/narrowphase 参与阻挡
- **`collider_shape.h`** 把碰撞形状抽象与相交判定集中到一处，避免散落漂移
- 调试面板把薄墙/网格/包围盒画出来，排错可以从"看见"开始
