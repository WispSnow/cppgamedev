# 存档与流程收尾：存档服务、场景流转与打磨方向

过去几节课，我们已经把"世界状态"拼到一个可玩的闭环里：
- [地图管理器](25-地图管理器.md)：`MapManager` 支持加载/卸载、预加载、快照（snapshot）与离线推进——地图的动态实体可以被序列化保存下来
- [游戏场景初始化与系统编排](26-游戏场景初始化与系统编排.md)：`GameScene` 作为组合根（composition root），按照严格顺序装配系统与依赖
- [物品栏与快捷栏](29-物品栏与快捷栏.md)：背包/快捷栏通过 `SyncRequest` 事件保持"数据层 ↔ UI 层"的一致性
- [游戏时间与昼夜](31-游戏时间与昼夜.md)：`GameTime` 是全局"权威状态 + 事件源"，也是存档必须保存的关键状态之一

但到目前为止，还缺一个"工程收尾级别"的能力：**玩家退出游戏后再回来，世界还在不在？**

这就是存档。

在教学项目里，存档有两个特别容易犯的错误：
1. **只保存玩家数据，不保存地图动态状态**（作物/宝箱/资源点等），导致读档后"我种的草莓不见了"
2. **把存档逻辑散落到各处**，UI/Scene/系统随手拼 JSON，耦合快速失控

因此这节课的重点不是"教你写 JSON"，而是把存档当作一个**系统边界**来设计：

> 用 `SaveService` 作为唯一入口，把"流程闭环"和"数据闭环"讲清楚，并给出一组可持续扩展的打磨方向。

## 2. 本节目标与问题定义

本节目标一句话：
> 把存档做成一个清晰的系统边界：流程层只负责"组织交互与场景流转"，数据层只负责"格式与版本"，而世界层通过 snapshot 把地图动态状态纳入持久化。

把它拆成 4 个必须回答的问题：

### 2.1 谁来负责"保存/加载"的统一入口？

如果 TitleScene、PauseMenu、DebugPanel 都能直接读写存档文件，你很快会遇到：
- 3 套 JSON key 拼写、3 套错误处理逻辑、3 套未来不兼容的可能
- 任何字段改名都要全局搜索替换，还极容易漏改

我们需要一个"边界对象"（boundary）：
- **对外**只暴露两个方法：`saveToFile(path)` / `loadFromFile(path)`
- **对内**封装全部复杂度：从 ECS 抓取持久化数据（capture）与应用回世界（apply）

这就是 `SaveService` 的定位——它是《迷你农场》中保存/加载的**唯一入口**。

### 2.2 存档格式怎么设计才能"允许演进"？

存档格式不可避免会变：你会新增字段、合并字段、重命名字段，甚至拆分文件。

如果没有版本意识，最常见的结果是：
- 老存档加载崩溃，或者读出一堆默认值，世界状态比不加载还糟糕
- 为了兼容旧版本到处写 `if/else`，Demo 变成"历史包袱展览"

因此本项目的最小版本策略是：
- 存档必须带 `schema_version`
- **允许加载**：`schema_version <= 当前版本`（新增字段用默认值兜底）
- **拒绝加载**：未来版本（避免用旧代码误读新格式）

### 2.3 保存什么？不保存什么？

存档最大的工程风险不是"漏了一个字段"，而是**把边界搞混**：
- 把"资源/配置/蓝图"（data-driven 资源）也塞进存档 → 存档膨胀且不可维护
- 把"运行时瞬态状态"（例如 ActionLockTag / DirtyTag）保存下来 → 读档后卡在奇怪的状态

因此这节课会给出一张明确的"保存对象清单"，用它约束当前实现和未来扩展。

### 2.4 流程怎么串起来才不会打破解耦？

存档功能永远不是一个孤立按钮：
- 标题界面的 Load → 选择 slot → 进入 `GameScene` 并在 `init` 阶段加载
- 游戏内 Pause 的 Save/Load → 选择 slot → 回到游戏世界（或提示错误）

我们需要一条稳定的"流程闭环"，让 UI/Scene 只负责组织流程，不直接操纵世界细节。

## 3. 核心概念（两条闭环 + 三类职责边界）

### 3.1 两条闭环：Flow loop + Data loop

你可以把整节课的内容压缩成两张图。建议你随时对照阅读。

#### Flow loop（流程闭环）

![Flow loop：场景流转闭环](diagrams/L30_flow_loop.png)

读图要点：
- `SaveSlotSelectScene` 是一个**复用 UI**，通过 `Mode::Save` / `Mode::Load` 区分用途——同一个组件服务两条流程，避免重复代码。
- TitleScene 和 PauseMenuScene 只负责"组织交互与场景流转"，**不直接写 JSON**。
- 流程串联的方式是 **callback**：`SaveSlotSelectScene` 接收一个回调函数 `on_select_`，选完 slot 后调用它，让调用方（Title 或 Pause）决定下一步做什么。这种设计让 slot 选择 UI 完全不知道 `SaveService` 的存在。

#### Data loop（数据闭环）

![Data loop：数据闭环](diagrams/L30_data_loop.png)

读图要点：
- 保存路径的第一步**不是** serialize，而是 `snapshotCurrentMap()`——`SaveService` 先主动调用 `MapManager`，把当前地图的动态实体写回 `WorldState` 的持久容器。这一步漏掉，就会丢失"当前地图上的改动"。
- `SaveService` 是流程层的唯一入口（边界），内部封装了 capture / apply + 文件读写。
- `SaveData` 只关心格式与版本（schema），不关心 ECS 细节、加载顺序或 UI 状态。

### 3.2 三类职责边界：谁负责什么

你可以用三句话来约束自己的设计，在添加新的持久化内容时反复对照：

1. **SaveService 是边界**
   - 谁想保存/加载，都必须通过 `SaveService`，而不是自己读写 JSON。
   - 它的构造函数接收四个依赖：`Context`（事件分发器等）、`entt::registry`（ECS）、`WorldState`（世界持久层）、`MapManager`（地图加载/卸载）、`BlueprintManager`（蓝图数据）。

2. **SaveData 是格式**
   - 它只描述"存档里有什么字段、字段怎么序列化/反序列化、版本怎么检查"。
   - 它不依赖 ECS，不引用系统，不操纵世界——是一个纯粹的数据传输对象（DTO）。

3. **MapManager snapshot 是持久层**
   - 它负责把"当前地图的动态实体状态"（耕地/作物/资源点等）写回到 `WorldState` 的持久容器里。
   - 这是保证"保存前不丢状态"的关键环节。

## 4. 架构/数据流：保存、加载、版本与排错

### 4.1 `SaveData`：格式层应该长什么样？

你可以把 `SaveData` 想成一个"持久化 DTO"：
- 它的字段来自"你决定要保存的东西"
- 它的行为主要是：`serialize` / `deserialize` + schema version 校验

在《迷你农场》里，`SaveData` 的字段分成三组：

**1. 元信息（meta）**
- `schema_version`：格式版本号（当前版本为 2）
- `timestamp`：保存时间（Unix 时间戳字符串），用于 slot 列表展示与调试定位
- `world_file`（可选）：用于一致性校验——确认存档和当前运行的世界配置匹配

**2. 全局权威状态**
- `game_time`：day / hour / minute / time_scale / paused——`TimeSystem` 推进的那份权威状态

**3. 世界状态**
- `player`：地图名、位置、方向/动作、HP / 金币、背包（inventory）、快捷栏（hotbar）
- `maps[]`：每张地图的持久状态——已打开的宝箱、已耕种的格子、已浇水的格子、作物列表、资源节点列表、最后更新的天数

重点是：`SaveData` 本身**不应该包含"运行时资源"**：
- 不保存 Blueprint / 配置 / 贴图路径（这些属于资源系统与数据驱动层，启动时重新加载即可）
- 不保存 ECS entity id（id 是运行时分配的，不是持久化身份）
- 不保存 DirtyTag / ActionLockTag / 临时动画状态（这些是瞬态，读档后应从零开始）

#### 保存对象清单

| 类别 | 例子 | 是否保存 | 理由 |
| --- | --- | --- | --- |
| 权威状态 | GameTime.day / hour / minute | 保存 | 所有时间相关系统的恢复基准 |
| 玩家核心 | map_name / position / hp / gold | 保存 | 读档必须可复现位置与进度 |
| 玩家背包 | inventory slots + active_page | 保存 | 玩法进度的一部分 |
| 快捷栏映射 | hotbar inventory_slot_indices + active_slot | 保存 | UI / 系统一致性需要它 |
| 地图持久状态 | opened_chests / tilled_tiles / wet_tiles / crops / resource_nodes | 保存 | 当前世界的"改动痕迹" |
| 资源 / 配置 | blueprint JSON / item catalog | 不保存 | 启动时从资源系统重新加载 |
| 瞬态状态 | ActionLockTag / DirtyTag / 手持工具引用 | 不保存 | 读档后应重新计算 / 清零 |

#### 存档 JSON 长什么样？（最小示例）

打开 `saves/slot0.json`，你会看到类似这样的结构：

  },
  "player": {

> 注意：这只是简化示例，实际字段以 `save_data.h` 中的定义为准。关键是理解这三层结构：**meta → 全局状态 → 世界状态**。

### 4.2 保存（Save）：为什么"保存前 snapshot 当前地图"不能省？

这是本节课的**第一条关键不变量**：

> **保存之前，必须先 snapshot 当前地图。**

为什么？来看一个具体场景：
1. 玩家在"农场"地图上耕了 3 块地、种了 2 棵草莓
2. 这些耕地和作物是运行时实体——只存在于当前 `registry` 中
3. `WorldState` 里保存的是"持久层容器"，它并不实时反映每一帧实体的最新状态
4. 如果你直接 capture 而不先 snapshot，`WorldState` 里拿到的是**上一次 snapshot 时的旧数据**——那 3 块地和 2 棵草莓就丢了

`snapshot` 的作用就是：**把运行时实体状态"写回"持久层**，确保 capture 时拿到的是最新数据。

![Save pipeline：保存链路](diagrams/L30_save_pipeline.png)

正确的保存链路（`SaveService::saveToFile` 内部实现）：

1. **`MapManager::snapshotCurrentMap()`**——把当前地图的动态实体状态写回 `WorldState`
2. **`SaveService::capture()`**——从 `registry` + `WorldState` 抓取所有需要保存的数据，组装成 `SaveData`
3. **`SaveData::serialize()`**——把 `SaveData` 转成 JSON
4. **文件写入**——使用"临时文件 + 原子替换（rename）"策略，避免写到一半崩溃导致存档损坏

你只需要记住一条结论：**只保存玩家数据是不够的。保存前必须 snapshot 当前地图。**

### 4.3 加载（Load）：恢复顺序与 UI 同步边界

加载看起来像"把 JSON 读回来"，但它真正的难点在于：**恢复顺序**。

如果你先恢复了玩家位置，但目标地图还没加载——玩家站在虚空里。如果你先加载了地图，但没清理旧状态——新旧实体混在一起。恢复顺序不对，结果往往比不读档还糟。

![Load pipeline：加载恢复顺序 + UI 同步边界](diagrams/L30_load_pipeline.png)

在《迷你农场》里，`SaveService::apply` 把恢复分成三层：

**第 1 层：全局状态层**
- 先恢复 `GameTime`（因为之后的系统可能依赖它做分支——比如昼夜判断、离线生长天数计算）

**第 2 层：世界持久层**
- 清空所有现有地图的持久状态容器（旧快照、旧宝箱记录等）
- 把存档里的 `maps[]` 数据转成快照写回 `WorldState`
- 这里有一个工程细节值得注意：`apply` 会用一个临时 `registry` 来重建动态实体（耕地精灵、作物等），计算好 AutoTile mask、生成好组件数据后再序列化为快照——这样 `MapManager` 在后续加载地图时就能正确恢复它们

**第 3 层：运行时世界层（地图 + 玩家）**
- 卸载当前地图 → 加载存档指定的目标地图
- 找到玩家实体，恢复位置、朝向、动作等外显状态
- **清理不应持久化的瞬态状态**：手持工具/种子引用、ActionLockTag 等——否则读档后可能卡在"挥锄头"动画出不来

#### 为什么 load 后要触发 SyncRequest？

背包与快捷栏有两套"数据 + 表现"：
- ECS 里的真实数据（`InventoryComponent` / `HotbarComponent`）
- UI 里显示的 slot 列表（包括拖拽高亮等状态）

load 之后，我们整体替换了 ECS 中的数据，但 UI 不会自动知道数据被替换了。因此 `apply` 的最后一步是触发三个同步事件：

- `InventorySyncRequest`：让背包 UI 把所有 slot 重绘
- `HotbarSyncRequest`：让快捷栏 UI 刷新引用关系
- `HotbarActivateRequest`：让快捷栏恢复到存档记录的 active slot

这和 [物品栏与快捷栏](29-物品栏与快捷栏.md) 的结论完全一致：**UI 一致性不是免费得到的，需要你明确声明同步边界。**

### 4.4 Slot 列表摘要：为什么不要在 UI 里随手 parse JSON？

`SaveSlotSelectScene` 需要显示每个存档位的信息：
- Day N
- 保存时间（人类可读的时间戳）

但它**不需要**加载整个世界，也**不应该**走 `SaveService` 的完整加载路径。

《迷你农场》的做法是提供一个极小的辅助函数：

`tryReadSlotSummary(path)` → `std::optional<SlotSummary>`

它只做三件事：
1. 打开 JSON 文件
2. 读取 `schema_version`（做基本校验）和 `game_time.day`、`timestamp` 字段
3. 返回一个 `SlotSummary { day, timestamp }` 结构

文件不存在返回 `nullopt`（slot 为空），解析失败或版本不支持也返回 `nullopt`（slot 无效）。

这样做的工程意义：
- 避免 JSON key 在 `SaveSlotSelectScene`、`SaveService`、`SaveData` 三处 hardcode
- 存档格式演进时，摘要读取逻辑只需改一处
- slot 列表的展示不依赖 `SaveService`，不需要构建完整的世界依赖链

### 4.5 版本策略：如何让存档"可演进但不失控"？

本项目的最低限度版本策略（足够用于教学 Demo，也足够覆盖大多数小型项目）：

| `schema_version` 值 | 处理方式 | 理由 |
| --- | --- | --- |
| 缺失 | 拒绝加载 | 文件可能不是我们的存档 |
| `> 当前版本` | 拒绝加载 | 旧代码不应尝试解读未来格式 |
| `<= 当前版本` | 允许加载 | 为新增字段提供默认值 / optional 处理 |

当你未来要新增持久化字段时，推荐的安全顺序是：
1. 在 `SaveData` 里新增字段（尽量 `optional` 或带默认值）
2. `serialize` 时写出新字段
3. `deserialize` 时能在"字段缺失"时给出合理默认值（不崩溃）
4. 只有当你确定字段"必须存在"时，才把它变成硬要求并升级 `SAVE_SCHEMA_VERSION`

> 小贴士：如果你不确定一个字段未来会不会改名或拆分，先把它做成 optional。等到它稳定下来、被多个系统依赖后，再考虑变成必要字段。

### 4.6 流程场景串联：TitleScene / PauseMenuScene / SaveSlotSelectScene

有了 `SaveService` 作为后端边界，接下来看前端流程怎么组织。

#### TitleScene：新游戏与读档入口

TitleScene 提供两个按钮：
- **Start**：用从 `game_time_config.json` 加载的初始 `GameTime` 创建 `GameScene`——这是一个全新的世界
- **Load**：Push 一个 `SaveSlotSelectScene`（`Mode::Load`），让玩家选择 slot

当玩家在 `SaveSlotSelectScene` 选中一个 slot 后，回调函数会创建一个带 `load_slot_` 参数的 `GameScene`。`GameScene` 在 `init()` 阶段检测到有 `load_slot_`，就会调用 `save_service_->loadFromFile(slotPath(*load_slot_))`。

如果加载失败，`GameScene` 不会卡死——它会请求 Scene 栈替换回 `TitleScene`，并通过 `error_message_` 把错误原因传递给标题界面展示。

#### PauseMenuScene：游戏内存读档

PauseMenuScene 提供四个按钮：Resume / Save / Load / Title。

- **Save**：Push `SaveSlotSelectScene`（`Mode::Save`）。玩家选中 slot 后，回调里调用 `save_service_->saveToFile(slotPath)`。如果 slot 已有存档，`SaveSlotSelectScene` 会先弹出覆盖确认对话框。
- **Load**：Push `SaveSlotSelectScene`（`Mode::Load`）。选中 slot 后调用 `save_service_->loadFromFile(slotPath)`，成功后在下一帧自动 Pop 掉 PauseMenuScene 回到游戏。
- **Title**：Pop 回到 `TitleScene`。

注意 `PauseMenuScene` 并不拥有 `SaveService`——它通过构造函数接收一个非持有（non-owning）引用，真正的所有权在 `GameScene`。这是依赖注入的典型用法：**使用者不创建资源，只使用资源。**

#### SaveSlotSelectScene：复用的关键

`SaveSlotSelectScene` 支持 10 个存档位（0–9），用 2×5 网格布局展示。它的核心设计是**回调驱动**：

- 构造时接收 `SlotSelectCallback on_select` 和 `Mode mode`
- `init()` 时调用 `refreshSlotButtons()` 扫描所有 slot 文件，用 `tryReadSlotSummary` 读摘要并更新按钮标签
- 玩家点击 slot 后：
  - Load 模式：直接调用 `on_select_(slot)`
  - Save 模式且 slot 已有存档：弹出覆盖确认，确认后才调用 `on_select_(slot)`

整个 Scene 不知道自己是在做"读档"还是"存档"——它只知道"用户选了第 N 个 slot，我该通知谁"。这种解耦让同一个 UI 组件同时服务于 TitleScene 和 PauseMenuScene 的不同流程。

### 4.7 快速排错 checklist（读档失败看哪里）

当 Load 失败时，不要盲改代码。先把错误归到以下五个层次中的某一层，再有针对性地排查：

**1. 文件层**
- 文件不存在 / 无法打开（路径、权限、slot 编号是否越界）
- JSON 解析失败（文件损坏 / 半写入——检查是否正确使用了"临时文件 + 原子替换"）

**2. 版本层**
- 缺少 `schema_version` 字段
- `schema_version` 大于当前代码支持的版本

**3. 数据层**
- 缺少关键字段（game_time / player / player.map_name）
- 字段类型不对（应该是数组的写成了对象、应该是字符串的写成了数字）

**4. 世界层**
- 地图加载失败：`map_name` 不存在或 world 文件不包含该地图
- 玩家实体找不到：地图加载后没生成 `PlayerTag`（通常是地图数据问题，而非存档问题）

**5. 表现层**
- UI 未同步：检查 load 完成后是否触发了 `InventorySyncRequest` / `HotbarSyncRequest`
- 读档后卡动作：检查 `apply` 是否清理了 `ActionLockTag`、手持工具引用等瞬态状态

> 调试技巧：`SaveLoadDebugPanel` 提供了一个免流程的快速入口——你可以跳过 Title/Pause 的 UI 流程，直接输入 slot 号或文件路径进行 Save/Load，并实时看到成功/失败信息。

## 6. 练习

### 练习 1（P1）：`world_file` 一致性校验（数据校验练习）

**目标：**
为存档增加"世界文件一致性校验"：如果存档声明的 `world_file` 与当前运行世界不一致，则拒绝加载并给出可定位的错误信息。

**验收标准：**
- 读取到 `world_file` 且与当前不一致时，`loadFromFile` 返回 false，并输出明确错误（能定位到是 world mismatch）
- 不影响正常存档加载（旧存档没有 `world_file` 时可按"兼容默认值"处理，或明确拒绝但需讲清策略）

**提示线索：**
- 存档格式：`src/game/save/save_data.*`（`world_file` 已作为可选字段存在）
- 加载入口：`src/game/save/save_service.*`（在 `apply` 的第一步做校验）
- 世界文件路径来源：`WorldState` 的初始化流程

### 练习 2（P2）：Slot 列表性能打磨（缓存或异步）

**目标：**
`SaveSlotSelectScene` 打开时需要读取多个 slot 的摘要。为它增加缓存（或异步读取）以减少卡顿，并保证 UI 不出现"错误的旧数据"。

**验收标准：**
- 反复打开/关闭 slot 选择界面时，摘要读取不出现明显卡顿（或至少避免重复 IO）
- 缓存失效策略清晰：例如 Save 成功后刷新对应 slot，或简单地"每次进入 scene 刷新一次"

**提示线索：**
- `src/game/scene/save_slot_select_scene.*`
- `src/game/save/save_slot_summary.*`
- 如果选择异步：注意线程安全与资源管理；不要引入复杂的任务系统——保持小而清晰

## 7. 小结与未来拓展方向

### 7.1 本节小结

你现在应该能回答三个"工程化问题"：

1. **存档的系统边界在哪里？** `SaveService` 是唯一入口，UI/Scene 不直接写 JSON。边界越清晰，未来改格式/加字段/换存储方式时改动就越少。

2. **保存前为什么必须 snapshot 当前地图？** 因为当前地图的动态实体只存在于运行时 registry 中，不 snapshot 就会丢状态。这是一类"数据在两个容器间不同步"的典型 bug。

3. **schema_version 的最小策略是什么？** 允许加载旧版本（缺失字段给默认值），拒绝加载未来版本（旧代码不应猜测新格式），缺少版本号则拒绝（可能不是我们的文件）。

### 7.2 扩展方向（不作为本课程内容）

到这里，《迷你农场》的核心架构已经全部串联起来。如果你想继续打磨这个项目，下面列出几个值得探索的方向：

- **自动存档**：定时 / 切地图 / 睡觉时自动触发保存，配合"回滚点"防止误操作
- **存档压缩/加密/云同步**：涉及平台差异与安全策略，适合有后端经验后再尝试
- **增量存档与冲突合并**：diff-based 存档 + 多端同步，属于进阶工程话题
- **更完整的 Load UX**：统一 Title 与 Pause 的错误提示策略（弹窗 / 通知 / 日志），提升玩家体验
- **更多玩法系统**：NPC 日程 / 任务 / 商店 / 季节——每新增一个系统，就要回来检查"它有没有需要持久化的状态？如果有，加到 SaveData 的哪一层？"
- **更多地图与美术**：更多 Tiled 地图、更丰富的瓦片集、更复杂的触发器——地图越多，预加载和 snapshot 策略就越重要
