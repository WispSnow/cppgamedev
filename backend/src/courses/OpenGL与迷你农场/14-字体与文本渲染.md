# 字体与文本渲染：从 Font 到 TextRenderer 的工程化问题

上节课我们建立了资源系统的工程化心智模型：`ResourceManager` 作为 Facade 统一了纹理/音频/字体/UI 预设的加载与缓存，`resource_mapping.json` 把路径变成了数据，`Resource` 调试面板把缓存与内存成本变成了可观测的指标。

这节课我们要把资源系统里最"看不见但很关键"的一块补齐——**字体与文本渲染**。

想象你现在要在游戏里做这些事：
- 标题界面显示"开始游戏"按钮文字
- 物品栏里每个格子要显示数量
- 时钟 UI 要显示当前时间
- NPC 头顶要弹出对话气泡

看起来只是"把字画出来"，但你很快会发现：为什么中文 kerning 不生效？为什么 atlas 内存一直涨？为什么改了字号但按钮没跟着变大？为什么世界文本跟着相机走、UI 文本又不跟？

这些问题的根源在于：**文本渲染不是"画字"，而是一条从字符到像素的完整数据管线**，中间涉及整形、光栅化、缓存、坐标空间和失效传播。这节课就是把这条管线讲清楚。

## 本节目标与问题定义

核心问题用一句话概括：

> 在《迷你农场》中，文本渲染如何从 `FontManager/Font`（FreeType 字形渲染 + HarfBuzz 字形整形）走到 `TextRenderer`（文本布局缓存 + UI/World 两条绘制通路），并通过 `config/text_render.json` 与调试面板把效果和成本变成可复现的输入/输出。

本节完成后你应该能回答这四个问题：

1. **分工**：FreeType、HarfBuzz、FontManager、TextRenderer、GLRenderer 分别负责什么？
2. **为什么需要 HarfBuzz**：为什么不能"一个字符画一个字形"，HarfBuzz 到底解决了什么？
3. **缓存代价**：Font / Glyph / Layout 三层缓存分别省什么、花什么？
4. **排查入口**：文本不显示 / 样式不对 / 内存增长 / 控件尺寸不更新时，第一步应该看哪里？

## 核心概念

### 字符不是字形：`text` 必须先变成 `glyph placements`

渲染文本时，我们真正要画的是"**字形（glyph）**"，而不是"字符（character）"。这不是文字游戏——两者之间有本质差异：

- 同一段文本在不同语言/方向下，glyph 的选择与顺序可能完全不同（例如阿拉伯语从右到左）
- kerning（字距微调）会让相邻字形的间距变化——比如 "AV" 这两个拉丁字母靠得比 "AI" 更近
- 连字（ligature）会把多个字符合并成一个 glyph——比如 "fi" 在某些字体里合成一个字形

因此文本渲染的第一步不是"画"，而是：

> **整形（shaping）**：把 `UTF-8 文本` 变成 `glyph 序列 + 每个 glyph 的 advance（步进）和 offset（偏移）`

![字符 vs 字形示意](diagrams/L12_char_vs_glyph.png)

### FreeType vs HarfBuzz：两个库，各管一半

初学者最容易混淆的就是 FreeType 和 HarfBuzz 的分工。一句话记住：

- **HarfBuzz**：决定"**用哪些 glyph、摆在哪里**"——输入是 UTF-8 文本，输出是 glyph 序列和每个 glyph 的位置信息（advance/offset），会处理 kerning、连字、RTL 方向等排版规则
- **FreeType**：决定"**glyph 长什么样**"——负责加载字体文件（`.ttf`），并把指定的 glyph 渲染成位图（bitmap），同时提供度量信息（ascender/descender/行高等）

打个比方：HarfBuzz 是排字工人，决定每个铅字的位置和顺序；FreeType 是铸字工人，负责把铅字的模子刻出来。

在《迷你农场》中，这两个库由不同模块驱动：

| 模块 | 驱动的库 | 职责 |
| --- | --- | --- |
| `TextRenderer` | HarfBuzz | 调用 `hb_shape()` 做整形，产生 glyph 序列与位置 |
| `Font` | FreeType + HarfBuzz | 持有 `FT_Face`（FreeType face）和 `hb_font_t`（HarfBuzz font）；当 TextRenderer 请求某个 glyph 时，调用 FreeType 把它渲染成位图并写入 atlas |
| `FontManager` | — | 管理 `Font` 实例的集合，按 `(font_id, pixel_size)` 做缓存 |

注意 `Font` 同时持有 FreeType 和 HarfBuzz 的句柄——FreeType 的 face 用于渲染位图，HarfBuzz 的 font 用于在整形时查询字体特性。两者通过 `hb_ft_font_create()` 关联起来。

### Glyph Atlas：字形图集是怎么回事

在讲三层缓存之前，先把 **glyph atlas（字形图集）** 这个概念讲清楚——它是文本渲染的核心数据结构。

每次需要绘制一个新字形时，`Font` 会调用 FreeType 把它渲染成一小块位图，然后把这块位图"贴"到一张较大的 OpenGL 纹理上。这张大纹理就是 **atlas**。绘制文字时，只需用 UV 坐标从 atlas 中取出对应区域——这避免了"每个字形一张纹理"带来的大量纹理切换开销（[精灵批处理与着色器](11-精灵批处理与着色器.md) 讲过批处理的核心思想，这里是同一个道理）。

Atlas 的空间分配方式是**行式排列**：

1. 从左上角开始，一行行地放入字形位图
2. 每行的高度由该行中最高的字形决定
3. 当一行放不下新字形时，换到下一行
4. 当整页放不下时，创建新的 atlas 页

Atlas 页的尺寸根据字号自适应：小字号（≤24px）用 512×512，中等字号（≤60px）用 1024×1024，大字号用 2048×2048。每个字形周围有 1px 的 padding，防止纹理采样时产生边缘渗透。

```cpp
// src/engine/resource/font_manager.cpp
int Font::calculateAtlasDimension(int pixel_size) {
    if (pixel_size <= 24)  return 512;
    if (pixel_size <= 60)  return 1024;
    return 2048;
}
```

**关键直觉**：atlas 是按需增长的——只有第一次绘制某个字形时才会写入。这意味着刚启动时 atlas 很小，随着你打开各种 UI、触发不同对话，atlas 会逐步填满。你可以在 `Resource` 调试面板中观察到这个增长过程。

### 三层缓存：Font / Glyph / Layout

文本系统的主要成本来自两类工作：整形 + 布局计算（CPU）、glyph 位图 + atlas 纹理（显存/内存）。《迷你农场》把缓存拆成三层来分别应对：

**第一层：Font cache（由 `FontManager` 管理）**

- 缓存键：`(font_id, pixel_size)` —— 同一个字体文件在不同字号下是不同的缓存条目
- 缓存内容：`Font` 对象（打开字体文件、创建 FreeType face + HarfBuzz font、准备度量信息）
- 省什么：避免重复打开和解析字体文件
- 花什么：每个 Font 对象持有 FreeType/HarfBuzz 资源 + glyph atlas 纹理

**第二层：Glyph cache（由 `Font` 管理）**

- 缓存键：`glyph_index`（FreeType 的字形索引）
- 缓存内容：`FontGlyph` 结构体——包含 atlas 纹理句柄、UV 坐标、尺寸、bearing（基线偏移）和 advance（步进宽度）
- 省什么：避免重复光栅化（FreeType 渲染位图是有成本的）
- 花什么：atlas 纹理的显存会随字形数量增长

```cpp
// src/engine/resource/font_manager.h
struct FontGlyph {
    GLuint texture{0};          // atlas 页的纹理句柄
    glm::ivec2 size{0};         // 字形位图尺寸
    glm::ivec2 bearing{0};      // 从基线到字形左上角的偏移
    float advance{0.0f};        // 绘制下一个字形时的步进距离
    glm::vec4 uv_rect{0.0f};    // 在 atlas 中的 UV 坐标 [u0, v0, u1, v1]
};
```

**第三层：Layout cache（由 `TextRenderer` 管理）**

- 缓存键：`(font_id, size, text, layout_options)` 的组合
- 缓存内容：`TextLayout`——预计算的 glyph 位置序列 + 文本总尺寸 + 行数
- 省什么：避免重复整形（HarfBuzz shaping）和布局计算
- 花什么：缓存占用内存；容量可通过 `layout_cache_capacity` 配置（默认 256），采用 LRU 策略淘汰最久未使用的条目

你可以这样理解取舍：
- 文本重复出现（UI 固定 label、时钟显示）→ Layout cache 很有价值，避免每帧重复整形
- 字符集更大（多语言 / 玩家输入 / 日志）→ Glyph cache & atlas 容易增长，需要关注内存

### 样式配置：`config/text_render.json` 把"观感"变成可复现输入

《迷你农场》把"文本长什么样"从代码里抽出来，放进 `config/text_render.json`。这和 [资源系统](13-资源系统.md) 中 `resource_mapping.json` 的思路一致——**把数据从代码中剥离，让修改不需要重新编译**。

配置文件包含三部分内容：

1. **全局 shaping 参数**：文本方向（`ltr`）、语言（`zh-Hans`）、HarfBuzz 特性（`kern=1` 启用字距微调）
2. **Layout cache 容量**：`layout_cache_capacity`，控制缓存条目上限
3. **文本样式**：按 style key（如 `ui/default`、`world/default`）组织，每个样式描述颜色、阴影、布局参数

```json
{
  "text_renderer": {
    "direction": "ltr",
    "language": "zh-Hans",
    "features": ["kern=1"],
    "layout_cache_capacity": 256,
    "default_style_keys": { "ui": "ui/default", "world": "world/default" },
    "styles": {
      "ui/default": {
        "color": { "start_color": "#FFFFFFFF", "end_color": "#FFFFFFFF", "use_gradient": false },
        "shadow": { "enabled": true, "offset": [1.0, 1.0], "color": "#000000FF" },
        "layout": { "letter_spacing": 0.0, "line_spacing_scale": 1.0, "glyph_scale": [1.0, 1.0] }
      }
    }
  }
}
```

**style key 的命名约定**：以 `ui/` 开头的用于 UI 文本，以 `world/` 开头的用于世界文本。`default_style_keys` 指定了两条通路各自的默认样式——当调用方不指定 style 时，就会用这里配置的默认值。

### 可观测性：两块调试面板就是"课堂仪表盘"

运行后按 `F5` → `Engine Debug Panels`，有两个面板与文本渲染直接相关：

**`Resource` 面板（字体部分）**

上节课我们已经用这个面板观察过纹理和音频的缓存状态。在字体这块，它展示的信息包括：

| 指标 | 含义 |
| --- | --- |
| 字体条目数 | 当前加载了多少个 `(font_id, pixel_size)` 组合 |
| 字形总数 | 所有字体的 glyph cache 条目总计 |
| atlas 页数 | 总共分配了多少张 atlas 纹理 |
| 估算内存 | `atlas 页数 × 页宽 × 页高 × 4 字节`（RGBA） |

**`Text` 面板**

这个面板可以**实时编辑**所有 `ui/*` 和 `world/*` 样式的参数：颜色（支持渐变）、阴影开关/偏移/颜色、字距（letter spacing）、行距缩放、字形缩放。修改后立刻生效——你会看到屏幕上的文字跟着变。

这两个面板配合起来，就能把文本渲染从"凭感觉调"变成"可度量、可实验"。

## 架构与数据流

### 总览：从字符串到屏幕像素

理解完各个概念后，我们把它们连成一条完整的数据流。当代码调用 `drawUIText("开始游戏", font_id, 16, ...)` 时，背后发生了这些事：

1. **查找样式**：`TextRenderer` 根据 style key 从配置中获取 `TextRenderParams`（颜色/阴影/布局参数）
2. **查找/创建布局**：以 `(font_id, size, text, layout_options)` 为键查 Layout cache；未命中则进入整形流程
3. **整形（shaping）**：调用 `hb_shape()` 得到 glyph 序列和位置信息（advance/offset，26.6 定点数格式，需除以 64 转换为像素）
4. **查找/创建字形**：对每个 glyph index，在 `Font` 的 glyph cache 中查找；未命中则调用 FreeType 渲染位图并写入 atlas
5. **计算目标矩形**：结合 glyph 的 bearing、advance 和布局参数（字距/字形缩放），算出每个字形的目标位置和尺寸
6. **绘制**：对每个字形，用 atlas 的 UV 坐标和目标矩形，通过 `GLRenderer` 绘制（先画阴影，再画正文）

### UI vs World：两条绘制通路

在《迷你农场》中，文本绘制分两条通路，对应不同的坐标空间和渲染阶段：

| | UI 文本 | 世界文本 |
| --- | --- | --- |
| API | `drawUIText()` | `drawText()` |
| 坐标空间 | 屏幕空间（逻辑分辨率） | 世界空间（会被相机变换） |
| 渲染阶段 | UI pass（`drawUITexture`） | Scene pass（`drawTexture`） |
| 默认样式 | `ui/default` | `world/default` |
| 视锥剔除 | 不剔除（屏幕空间始终可见） | 会剔除（超出相机视野不绘制） |
| 典型用途 | 按钮文字、物品数量、时钟 | 对话气泡、世界提示文字 |

**排查要点**：如果文字位置不对、抖动、或被意外裁剪，第一步要确认你的文本走的是 UI 还是 World 通路。UI 文本不受相机影响——如果你发现文字跟着画面滚动，说明它可能误走了 World 通路。

### UI 文本：为什么要把"测量"与"绘制"分开

在 UI 系统里，"先测量尺寸，再决定布局，再绘制"是基本规律。`UILabel` 就是这个规律的典型实现：

- **测量阶段**：调用 `getTextSize(text, font_id, font_size, ...)` 获取文本的像素尺寸，用于计算控件大小和布局位置
- **绘制阶段**：调用 `drawUIText(text, font_id, font_size, position, ...)` 把文字画到屏幕上

这里有一个必须点名的约束：

> `drawUIText` / `drawText` 依赖字体已经在缓存中。如果字体没有预加载，绘制会失败并在日志里给出提示。

这也是为什么 UI 侧通常会在测量阶段通过 `getTextSize(..., font_path)` 触发字体加载——**测量不仅是为了拿尺寸，也是在为后续"能画出来"做准备**。如果你只调 `drawUIText` 而从未通过任何途径加载过字体，绘制会静默失败。

### 覆写机制：`TextRenderOverrides` 让组件可以"微调"而不改全局样式

`config/text_render.json` 里定义的样式是全局的 base style，但 UI 组件往往需要在此基础上做局部调整——某个按钮的文字要用不同颜色、某个 label 要关闭阴影。如果每次都定义一个新 style key，配置文件会迅速膨胀。

《迷你农场》通过 `TextRenderOverrides` 解决这个问题：

```cpp
// src/engine/utils/defs.h
struct TextRenderOverrides {
    std::optional<FColor> color{};
    std::optional<bool> shadow_enabled{};
    std::optional<glm::vec2> shadow_offset{};
    std::optional<FColor> shadow_color{};
    std::optional<glm::vec2> glyph_scale{};
};
```

使用 `std::optional` 意味着每个字段"有值"才覆盖——这是一种**稀疏覆写**设计。`TextRenderer` 在绘制时会把 base style 和 overrides 合并：

- overrides 中有值的字段覆盖 base style 中对应的值
- overrides 中没有值的字段保持 base style 不变
- 设置 `color` 时会自动关闭渐变（`use_gradient = false`）

这保证了两个需求共存：**全局样式统一修改时所有组件跟着变**，同时**单个组件可以做微调**。

其中只有 `glyph_scale` 会影响布局（改变了字形的绘制尺寸），其他覆写（颜色/阴影）只影响视觉效果，不需要触发重新测量。

### 失效机制：`layout_revision` 如何让 UI 保持一致

![测量→布局→绘制时序 + layout_revision 失效传播](diagrams/L12_measure_draw_revision.png)

你需要建立一个关键直觉：文本系统的缓存不是"存了就不变"的——**字体可以被卸载，样式可以被修改**。如果缓存失效了但 UI 组件不知道，就会出现"文字变了但控件尺寸没变"的错位。

《迷你农场》用一个简单的版本号 `layout_revision` 来解决这个问题：

**谁递增 `layout_revision`？**

`TextRenderer` 在以下情况下递增版本号：
- 文本方向（direction）改变
- 语言（language）改变
- HarfBuzz 特性（features）改变
- 某个 style 的 layout 参数改变（字距/行距/字形缩放）
- 字体被卸载（`FontUnloadedEvent`）或全部清空（`FontsClearedEvent`）

**谁监听 `layout_revision`？**

`UILabel`、`UIButton` 等 UI 组件在每帧 update 时检查：

```
if (text_renderer.getLayoutRevision() != last_layout_revision_) {
    重新测量文本尺寸;
    更新控件大小;
    last_layout_revision_ = text_renderer.getLayoutRevision();
}
```

**字体卸载事件如何传播？**

这里用到了[事件系统](06-事件系统.md)讲过的事件系统：

1. `ResourceManager` 在 `unloadFont()` / `clearFonts()` 时 enqueue 事件（`FontUnloadedEvent` / `FontsClearedEvent`）
2. `TextRenderer` 监听这些事件，清理对应的布局缓存（避免旧 layout 指向已卸载字体的 glyph）
3. `TextRenderer` 递增 `layout_revision`
4. 下一帧 UI 组件检测到版本号变化，重新测量

整个链路是**被动检测 + 事件驱动**的——UI 组件不需要主动订阅字体事件，只需要每帧检查一个整数就够了。这比让每个 UI 组件都去监听字体事件简单得多。

## 演示：动手验证

### 演示 1：字体 atlas 可观测性

1. 运行游戏，进入游戏场景
2. 按 `F5` → `Engine Debug Panels` → 勾选 `Resource`
3. 找到 Fonts 部分，记下当前的 glyph 数量和 atlas 页数
4. 打开暂停菜单（Esc）、背包（Tab）、与 NPC 对话——这些操作会触发新的文字绘制
5. 再看 Fonts 部分——glyph 数量应该增长了（新字形被按需加载并写入 atlas）

这个实验建立的直觉是：**字形是按需加载的，atlas 会增长**。不是启动时就把所有字形都渲染好，而是第一次用到时才写入。

### 演示 2：样式实时调参

1. 按 `F5` → `Engine Debug Panels` → 勾选 `Text`
2. 在 "UI" 标签页中找到 `ui/default` 样式
3. 试试这些操作，观察屏幕上 UI 文字的变化：
   - 切换阴影开关（`shadow.enabled`）——文字的立体感消失/出现
   - 拖动阴影偏移（`shadow.offset`）——阴影的位置跟着动
   - 调整字距（`letter_spacing`）——文字变疏或变密
   - 调整字形缩放（`glyph_scale`）——注意观察控件（按钮/标签）的尺寸是否跟着变化

最后一项特别重要：当你改变 `glyph_scale` 时，`layout_revision` 会递增，UI 组件会重新测量——这就是失效机制在起作用。

### 演示 3：配置驱动 + 可复现

1. 打开 `config/text_render.json`
2. 做一个修改，例如：
   - 把 `"features"` 从 `["kern=1"]` 改成 `["kern=0"]`（关闭字距微调）
   - 或者把阴影 `"enabled"` 从 `true` 改成 `false`
   - 或者把 `"layout_cache_capacity"` 改成一个很小的值（如 `8`）
3. 重启游戏，观察效果变化

**核心价值**：配置文件就是课堂可复现的实验输入——你想演示某个效果，只要改 JSON 重启即可，不需要重新编译。

## "踩坑清单"：常见问题与排查

### 问题 1：文本不显示（空白）

最常见的原因是**字体没有加载到缓存中**。`drawUIText` / `drawText` 不会自动加载字体——它要求字体已经通过某种途径被缓存。

**排查路径**：
1. 打开 `F5` → `Resource` 面板，看 Fonts 部分是否有对应的字体条目
2. 检查日志中是否有"字体未找到"之类的提示
3. 确认 UI 组件是否在测量阶段调用了 `getTextSize(text, font_id, font_size, font_path)`——传入 `font_path` 才会触发按需加载
4. 如果是通过 `ResourceManager::getFont()` 加载的，确认传入的 `font_id` 和 `pixel_size` 是否匹配

### 问题 2：样式修改后文字变了但控件尺寸没变

这通常是 `layout_revision` 的传播断了。排查要点：

1. 确认修改的参数是否真的影响布局——只有 layout 参数（字距/行距/字形缩放）的变化才会触发 `layout_revision` 递增；纯颜色/阴影改变不会
2. 确认 UI 组件是否正确监听了 `layout_revision`（`UILabel` 已经内置了这个逻辑，自定义组件需要自己实现）
3. 在 `Text` 面板中修改 `glyph_scale`，如果控件尺寸跟着变了，说明机制正常；如果没变，说明该组件没有检查 `layout_revision`

### 问题 3：atlas 内存持续增长

字形一旦写入 atlas，在字体卸载前**不会被释放**。如果你加载了大量不同的文本（比如玩家输入、日志滚动），glyph cache 和 atlas 会一直增长。

**排查路径**：
1. 打开 `Resource` 面板，观察 atlas 页数和估算内存
2. 如果页数异常多，检查是否有不必要的字号组合——记住 `(font_id, pixel_size)` 的每个组合都是一个独立的 Font 对象，有独立的 atlas
3. 考虑场景切换时是否需要卸载不再使用的字体（`ResourceManager::unloadFont()`）

### 问题 4：世界文本位置偏移或抖动

确认你的文本走的是 World 通路（`drawText`）还是 UI 通路（`drawUIText`）：
- World 通路的坐标是世界空间，会受相机变换影响——如果相机有平滑跟随或插值，文字可能出现轻微抖动
- UI 通路的坐标是屏幕空间，固定不动

如果是世界文本需要像素对齐，参考 [精灵批处理与着色器](11-精灵批处理与着色器.md) 的 pixel snap 技巧。

## 小结

这节课的关键要点：

1. **分工明确**：HarfBuzz 负责整形（决定用哪些 glyph、摆在哪里），FreeType 负责光栅化（把 glyph 变成位图）。两者通过 `Font` 对象关联，分别由 `TextRenderer` 和 `Font` 驱动。
2. **三层缓存有代价**：Font cache 省解析、Glyph cache 省光栅化、Layout cache 省整形。但 atlas 会按需增长、layout cache 有容量上限——理解代价才能做好预算。
3. **配置驱动 + 可观测**：`config/text_render.json` 把样式变成可复现输入，`Text` 面板让你实时调参，`Resource` 面板让你看到 atlas 的真实成本。从"凭感觉调"升级为"可度量"。
4. **UI 与 World 两条通路**：坐标空间不同、渲染阶段不同、剔除策略不同。排查文本问题的第一步，永远是确认走的是哪条通路。

下节课（输入系统）我们会进入**输入系统**：从 SDL 事件到动作映射与状态机，并讨论 UI 场景下输入的占用与转发策略。

这节课你可能已经注意到一个问题——`Text` 调试面板和 UI 按钮都需要响应键鼠输入，它们之间不会冲突吗？当输入系统可控以后，UI 的交互（按钮点击、面板拖拽、调试菜单）就不再是"碰运气"，而是可预测、可测试的工程系统。
