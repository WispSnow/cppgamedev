# UI 布局与预设：Stack/Grid、九宫格与可复用样式

上节课我们搭好了 UI 框架的基础骨架：
- 每个 Scene 挂一个 `UIManager`，UI 的生命周期跟着场景走
- `UIManager` 管理一棵 `UIElement` 树，用 logical mouse 驱动 `Normal/Hover/Pressed` 交互状态机
- hover/click 等交互自然触发 `ui_hover/ui_click` 语义化音效（对齐[音频系统](16-音频系统.md)的约定）

骨架有了，但只要你开始做"真实 UI"——比如 Inventory 面板、快捷栏、暂停菜单——两个工程化问题会立刻浮出水面：

1. **怎么排（Layout）**：一排 10 个 slot、一列 4 个按钮，总不能每个都手写绝对坐标。改一个尺寸就得连锁改十几处——这不是工程，是体力活。
2. **长什么样（Style）**：按钮的皮肤、面板的边框、slot 的背景……如果散落在代码各处，换套 UI 素材就意味着全局搜索替换。这也不是工程，是事故等着发生。

本节课就来解决这两件事：用 **Layout 容器** 替代手工坐标，用 **Presets + Nine-slice** 把样式变成可配置数据。

## 本节目标与问题定义

> 把 UI 的"怎么排（Layout）"和"长什么样（Presets + Nine-slice）"抽离成可复用模块，并用 Debug 面板提供一个可观测、可调参的实验台。

学完本节，你应该能回答：
- **Layout 的职责边界**：什么场景用 anchor/pivot 就够了？什么场景必须用 Stack/Grid？
- **Stack/Grid 的直觉**：Stack 的"主轴/交叉轴"怎么理解？Grid 的"索引→行列→坐标"怎么映射？
- **Nine-slice 的最小规则**：为什么面板拉伸不失真？`margins` 如何决定最小尺寸与 3×3 切片？
- **Preset 的数据流**：`resource_mapping.json → ResourceManager → UIPresetManager → UI → Renderer` 这条链路上每一环各负责什么？
- **Debug 如何帮助验证**：如何用 `UI Presets` 面板快速确认"预设加载了/参数生效了"，而不是靠猜？

## 核心概念一：Layout 容器——把"排布规则"从业务 UI 里抽出来

### 为什么需要 Layout 容器

在没有 Layout 容器时，一个暂停菜单的 UI 代码可能是这样的隐性逻辑：先摆背景，再摆标题，再一个个摆按钮——每个按钮的位置都由"上一项的位置 + 高度 + 间距"手工计算。

这类代码的问题不是"写不出来"，而是三个致命缺陷：
- **复用差**：另一个菜单又得抄一遍"纵向排列"逻辑
- **改动脆弱**：改一个按钮高度，就得连锁调整后面所有坐标
- **意图不透明**：读代码的人看不到"这是一列纵向列表"，只能看到一堆数字

TinyFarm 的解法是 `UILayout`：你只告诉容器**规则是什么**（Stack 还是 Grid、间距多少、对齐方式），容器自己负责把规则落到每个子节点的 `position/size` 上。

### Layout 容器 vs Anchor/Pivot：什么时候用哪个

这是个关键的分界线：

- **Anchor/Pivot** 解决"一个元素相对父元素怎么挂"。比如 HUD 角落的时钟图标——它只需要锚定在右上角，不需要跟别的元素一起排列。
- **Layout 容器** 解决"**一组子元素**按规则怎么排"。快捷栏的 10 个 slot、暂停菜单的 4 个按钮——它们之间存在排列关系。

两者并不冲突：Layout 容器本身也是 `UIElement`，它可以用 anchor/pivot 决定"自己在父元素里挂在哪"，然后在内部用布局规则决定"子元素怎么排"。

![Anchor/Pivot vs Layout 对比](diagrams/L16_anchor_vs_layout.png)

> **设计细节**：`UILayout` 继承自 `UIElement`，但本身只是一个极薄的语义标记——实际的布局计算通过 `onLayout()` 虚函数完成。`UIElement` 基类提供了 `invalidateLayout()` / `ensureLayout()` 的脏标记与懒求值机制（[UI 框架基础](17-UI%20框架基础.md) 已介绍），`UILayout` 的子类只需要覆写 `onLayout()` 来描述自己的排列规则。

> 关联阅读：`src/engine/ui/layout/ui_layout.*`、`src/engine/ui/ui_element.*`

### UIStackLayout：线性排列的"主轴/交叉轴"思维

StackLayout 的核心直觉只有一句话：**选一个方向当主轴，沿主轴把可见子元素依次排开**。

两个轴的概念：
- **主轴（main axis）**：元素排列的方向。`Vertical` 时主轴是 Y（从上到下），`Horizontal` 时主轴是 X（从左到右）
- **交叉轴（cross axis）**：与主轴垂直的方向

![StackLayout 主轴/交叉轴示意图](diagrams/L16_stack_layout.png)

StackLayout 的可配参数：

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `Orientation` | 主轴方向 | `Vertical` |
| `Spacing` | 主轴方向相邻子元素的间距（只计算可见子元素） | `0` |
| `Alignment` | 内容在**主轴方向**的整体对齐：Start / Center / End | `Start` |
| `Padding` | 容器给内容留白，决定 content bounds 的起点与可用长度 | `{0,0,0,0}` |
| `AutoResize` | 容器在主轴方向按内容自动扩展尺寸 | `false` |

它的排列算法分两步走：

**第一步——测量**：遍历可见子元素，沿主轴方向累加它们的 requested size，加上 `(visible_count - 1) × spacing` 得到总内容长度。

**第二步——放置**：根据 Alignment 计算主轴起点偏移，然后从起点开始，逐个把子元素"码"上去：

```text
visible = children.filter(isVisible)
total_length = sum(main_size(child)) + spacing * (visible.count - 1)

start = content_start + alignment_offset(content_size, total_length, alignment)
cursor = start

for child in visible:
    child.main_pos = cursor
    child.cross_pos = content_start.cross   // 当前固定为 Start
    cursor += main_size(child) + spacing
```

注意 Padding 的作用：`content_size = layout_size - padding`，所有排列都在 content bounds 之内。Padding 不影响容器自身大小，但会缩小子元素可用的排列区域。

> **AutoResize 机制**：当 `auto_resize` 开启时，放置完所有子元素后，Layout 会回过头来把自己在主轴方向的尺寸调整为"内容总长度 + 两端 padding"。HotbarUI 的 slot 容器就用了这个特性——slot 数量可能变化，容器跟着自动伸缩。

当前版本的边界（适合作为练习方向）：
- `Alignment` **只作用于主轴**（整体的 Start/Center/End 偏移）
- 交叉轴固定为 Start（Vertical 时靠左，Horizontal 时靠顶）
- "交叉轴 fill（让子元素在交叉轴拉伸铺满）"尚未实现

典型落地点：
- `PauseMenuScene`：按钮纵向列表（Vertical Stack，spacing = 6）
- `HotbarUI`：slot 横向排列（Horizontal Stack，Center 对齐，AutoResize 开启）
- `TimeClockUI`：HUD 文本行/图标行（Stack 嵌套组合）

> 关联阅读：`src/engine/ui/layout/ui_stack_layout.*`、`src/game/scene/pause_menu_scene.cpp`、`src/game/ui/hotbar_ui.cpp`

### UIGridLayout：网格排列的"索引 → 行列 → 坐标"

GridLayout 的直觉同样一句话说清：**给定列数，把第 i 个可见元素放到 `(row = i / cols, col = i % cols)` 的格子里**。

![GridLayout 索引到行列映射](diagrams/L16_grid_layout.png)

GridLayout 的可配参数：

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `columns` | 固定列数（每行放几个格子） | `5` |
| `cell_size` | 强制格子大小（如果设置了，所有子元素统一用这个尺寸） | `{0,0}` |
| `spacing` | 格子间距（x/y） | `{0,0}` |
| `padding` | 内容区域留白 | `{0,0,0,0}` |

索引到坐标的映射：
```text
row = index / columns
col = index % columns

pos.x = content_start.x + col * (cell_w + spacing_x)
pos.y = content_start.y + row * (cell_h + spacing_y)
```

> **cell_size 的两种模式**：当 `cell_size` 的两个分量都大于 0 时，Grid 会强制把每个子元素的尺寸统一设成 `cell_size`（通过调用 `child->setSize()`）。这对于 Inventory 的 slot 格子特别有用——所有 slot 必须一样大。当 `cell_size` 为 `{0,0}` 时，则保留每个子元素自己的 requested size，此时不同格子可能有不同大小（但间距计算仍以每个子元素的实际尺寸为准）。

> **当前限制**：Grid 只支持固定列数，行数由可见子元素数量隐式决定。不支持"固定行数"或"auto-wrap"。不可见子元素会被跳过，不占格子位——这意味着隐藏一个 slot 会导致后续 slot 前移，而不是留下空位。

典型落地点：
- `InventoryUI`：5 列 × 4 行的背包 slot（`cell_size = {32,32}`，`spacing = {6,6}`）
- `HotbarUI`：也可以视为 1 行的 Grid（但实际用了 Horizontal Stack）

> 关联阅读：`src/engine/ui/layout/ui_grid_layout.*`、`src/game/ui/inventory_ui.cpp`

## 核心概念二：Nine-slice（九宫格）——让 UI 拉伸不变形

### 问题与直觉

UI 面板和按钮通常有边框和圆角。当你需要不同尺寸的面板时，如果直接拉伸整张贴图，边框会被压扁、圆角会变形——这就是"拉伸失真"。

Nine-slice 的解法很优雅：

> 用 `margins(left/top/right/bottom)` 把一张贴图切成 3×3 共 9 块。**四个角不缩放**，**四条边单轴拉伸**，**中心双轴拉伸**。

![Nine-slice 3×3 切片示意图](diagrams/L16_nine_slice.png)

因为角块始终保持原始像素不变，边框和圆角无论面板怎么拉伸都不会变形。

### 最小尺寸规则

Nine-slice 有一个容易踩的坑——如果目标尺寸比 margins 之和还小，中间的 patch 就会出现负宽/负高，渲染结果会出问题。因此存在一个**最小尺寸约束**：

```text
min_width  = left + right
min_height = top + bottom
```

渲染时会做 clamp：
```text
final_width  = max(target_width,  min_width)
final_height = max(target_height, min_height)
```

> **实际影响**：如果你发现某个面板"怎么缩小都不会小于某个尺寸"，那多半就是 nine-slice 的 minimum-size clamp 在起作用。这不是 bug，而是一个保护机制——确保九宫格的角块不会重叠。

### 在 TinyFarm 中的三层实现

Nine-slice 在《迷你农场》里贯穿三层，各司其职：

**数据层 —— `render::Image`**
- `Image` 可选携带 `NineSliceMargins`（left/top/right/bottom 四个 float 值）
- 采用 **lazy 缓存**策略：首次渲染时才构建 `NineSlice` 切片并缓存在 `nine_slice_cache_` 中
- 当 source rect 或 margins 发生变化时标记 `nine_slice_dirty_`，下次渲染自动重建
- 这样避免了每帧重复计算九宫格切片

**算法层 —— `render::NineSlice`**
- 接收 source rect 和 margins，切出 9 个 `Rect`（存在 `std::array<Rect, 9>` 中）
- 构建时会做完整性校验：margins 非负、source 尺寸正数、margins 之和不超过 source 尺寸
- 计算并记录 `min_size_`，供渲染层做 clamp

**渲染层 —— `Renderer::drawUIImage`**
- 这是调用方唯一需要关心的入口——UIPanel/UIButton 只调用 `drawUIImage()`
- 内部检测 `image.ensureNineSlice()` 的返回值：如果有有效的 NineSlice，自动走九宫格绘制路径（`drawUINineSliceInternal`）；否则走普通绘制
- 调用方**完全不需要知道**这张图是否启用了九宫格——渲染器透明处理

> **细节注意**：九宫格渲染时会**强制关闭水平翻转**（`flip_horizontal = false`），因为对九块独立切片做翻转会导致角/边错位，产生视觉错误。如果你需要翻转的 UI 元素，不要对它使用 nine-slice。

> 关联阅读：`src/engine/render/image.*`、`src/engine/render/nine_slice.*`、`src/engine/render/renderer.cpp`

## 核心概念三：Presets——把"样式"变成数据

Layout 解决了"怎么排"，Nine-slice 解决了"拉伸不变形"。但还剩一个问题：按钮在不同状态显示什么图片？用什么字体？播什么音效？面板用哪张贴图做背景？

如果这些信息散落在各处 C++ 代码里，换一套 UI 风格就意味着改十几个文件。**Preset（预设）** 就是把这些样式信息统一收到 JSON 文件里，让代码只负责"用预设"，而不负责"定义预设"。

### 两种 Preset

| 类型 | 定义文件 | 用途 |
|------|----------|------|
| **Button preset** | `ui_button_presets.json` | 按钮在不同状态（normal/hover/pressed/disabled）的图片、九宫格、label 样式、音效 |
| **Image preset** | `ui_image_presets.json` | 可复用的 UI 图片（面板背景、slot、气泡、光标等），含九宫格配置 |

### 数据入口与加载链路（对齐 [资源系统](13-资源系统.md)）

Preset 的加载入口与其他资源完全一致——还是 [资源系统](13-资源系统.md) 介绍的 `resource_mapping.json`：

```text
resource_mapping.json
  ├── "ui_button_presets" → "assets/data/ui_button_presets.json"
  └── "ui_image_presets"  → "assets/data/ui_image_presets.json"
```

启动时 `ResourceManager` 读取映射，把路径交给 `UIPresetManager`：
- `UIPresetManager::loadButtonPresets(path)` —— 解析 JSON，为每个 key 构建 `UIButtonSkin`
- `UIPresetManager::loadImagePresets(path)` —— 解析 JSON，为每个 key 构建 `render::Image`

加载完成后，Preset 以 **哈希 ID** 为键缓存在 `unordered_map` 中，UI 组件按需查询。

> **加载是全量替换**：每次调用 `loadButtonPresets` / `loadImagePresets` 都会先清空已有缓存再重新加载，而不是增量合并。这意味着如果你有多个 preset 文件，需要把它们合并到一个文件中（或修改加载逻辑）。

![Presets 数据流](diagrams/L16_preset_data_flow.png)

> 关联阅读：`assets/data/resource_mapping.json`、`src/engine/resource/resource_manager.cpp`、`src/engine/ui/ui_preset_manager.*`

### Key 与 0xID：为什么 Debug 面板要同时显示两者

Preset 在 JSON 里用**字符串 key** 命名（如 `"primary"`、`"inventory_slot"`）。运行时为了高效索引，key 会被哈希成 `entt::id_type`（显示为 `0x...`）。

这产生了一个实际问题：调试时你看到的是 `0x3A7B21C4`，完全不知道对应哪个 preset。所以 `UIPresetManager` 内部维护了一份 `id → key` 的反向映射表，Debug 面板会同时显示两者：

> `primary (0x3A7B21C4)`

这样在课堂讲解或团队协作时，不必对着一串十六进制数猜来猜去。

### Button preset（UIButtonSkin）能配置什么

一个 Button preset 的完整结构：

| 字段 | 含义 |
|------|------|
| `images.normal/hover/pressed/disabled` | 每个状态一张图片（`path` 指定纹理，`source` 指定裁剪区域） |
| `nine_slice` | 可选；**一次配置，自动传播到所有状态图片** |
| `label` | 默认文本样式：字体路径、字号、颜色（RGBA）、偏移量、默认文本 |
| `overrides.hover/pressed/disabled` | 对特定状态的 label 局部覆盖（颜色/偏移量） |
| `sounds` | 事件音效覆盖（按事件名映射） |

关于 **`sounds` 字段**的三种写法：
- 值为路径字符串 → 播放该音效
- 值为 `null` 或空字符串 → **禁用**该事件音效
- 不写该事件 → 使用默认行为（`hover → ui_hover`、`click → ui_click`，由 `resource_mapping.json` 定义）

> **设计要点——Nine-slice 的统一传播**：Button preset 的 `nine_slice` margins 只需写一次。`UIPresetManager::registerButtonPreset()` 会自动把这个 margins 传播到 normal/hover/pressed/disabled 的所有图片上——无论是从 JSON 加载还是通过 API 注册，都走同一个入口，避免了重复配置与不一致。

> **UIButton 的工厂模式**：UIButton 的构造函数是私有的，只能通过静态方法 `UIButton::create(context, preset_key, ...)` 创建。创建时会从 `UIPresetManager` 查找 preset，如果找不到或 normal_image 无效，返回 `nullptr`。调用方需要检查返回值——这是一种"快速失败"的防御策略。

> **Label 的自动视觉反馈**：如果 preset 没有为 hover/pressed/disabled 指定 label 覆盖，UIButton 会自动提供合理的默认反馈：hover 时亮度提升 1.15 倍，pressed 时文字下移 2 像素，disabled 时转为灰度。这让简单的 preset 无需写繁琐的 overrides 也能有及格的视觉反馈。

> 关联阅读：`assets/data/ui_button_presets.json`、`src/engine/ui/ui_button.*`

### Image preset（render::Image）能配置什么

Image preset 比 Button preset 简单得多：

| 字段 | 含义 |
|------|------|
| `path` | 纹理路径 |
| `source` | source rect（裁剪区域），支持数组 `[x,y,w,h]` 或对象 `{x,y,w,h}` |
| `flipped` | 是否水平翻转 |
| `nine_slice` | 可选；给面板/slot/气泡这类"可拉伸皮肤"使用 |

Image preset 典型用途：面板背景（`inventory_panel`）、slot 背景（`inventory_slot`）、选中高亮（`quick_bar_selected`）、对话气泡（`dialogue_bubble`）、光标（`cursor`）。

> **几乎都带 nine-slice**：翻看 `ui_image_presets.json` 你会发现，除了 `cursor` 之外，所有 Image preset 都配置了 nine-slice margins。这反映了一个工程事实：游戏中可复用的 UI 图片，大多需要适配不同尺寸。

> 关联阅读：`assets/data/ui_image_presets.json`、`src/engine/render/image.*`

### Debug 面板：把"不可见的配置"变成可观测系统

`F5 → Engine Debug Panels → UI Presets` 是本课的实验台。

**Buttons tab**：
- 列出所有已加载的 button preset（key + 0xID）
- 选中一个 preset 后，查看它的图片（四个状态）、九宫格参数、label 样式
- **支持运行时编辑**：可以直接修改 label 的 color（拾色器）和 offset（拖拽条），修改立即生效

**Images tab**：
- 列出所有已加载的 image preset
- 查看纹理路径、裁剪区域、九宫格信息
- 用于核对"这个 preset 加载对了吗？纹理路径对了吗？"

> **为什么修改能"立即生效"？** 因为 UIButton 在每帧渲染时都会通过 `getPreset()` 从 `UIPresetManager` 的内存缓存中读取 skin 数据。Debug 面板直接修改的就是这份内存数据，所以所有使用该 preset 的按钮都会在下一帧立刻反映变化。

> **但修改不会持久化**：Debug 面板只操作内存中的 `UIPresetManager` 数据，不会写回 JSON 文件。要把调整持久化，你需要手工编辑 `assets/data/ui_*_presets.json` 并重启。

> 关联阅读：`src/engine/debug/panels/ui_preset_debug_panel.*`

## 真实 UI 是怎么"组装"的：布局 + 预设的组合模式

前面把 Layout、Nine-slice、Presets 分别讲清楚了，现在看看它们在真实 UI 中是怎么配合工作的。

### HotbarUI：预设 + Stack + 防御式回退

`HotbarUI` 是一个典型的"面板 + 布局 + 预设"组合：

1. 从 `UIPresetManager` 查找 `quick_bar_panel` Image preset，用作面板皮肤（带 nine-slice）
2. 创建一个 `UIPanel`，根据 slot 数量和间距动态计算面板尺寸
3. 面板内放一个 **Horizontal StackLayout**（居中对齐、AutoResize 开启）
4. Stack 里放 10 个 `UIItemSlot`，每个 slot 的背景来自 `quick_bar_slot` Image preset

值得注意的一个工程模式：HotbarUI 对**每个 preset 查找都准备了硬编码的回退 Image**。如果 preset 没加载（比如 JSON 文件路径写错了），UI 不会崩溃，而是用一个灰色方块凑合渲染。这种"防御式回退"在游戏开发中很常见——UI 系统不应该因为一张丢失的贴图就让整个游戏挂掉。

### InventoryUI：Grid + 按钮工厂 + 拖拽面板

`InventoryUI` 展示了 GridLayout 的典型用法：

1. 外层是一个 `UIDraggablePanel`（可拖拽面板），皮肤来自 `inventory_panel` Image preset
2. 面板内放一个 **UIGridLayout**（列数 5，cell_size = {32,32}，spacing = {6,6}）
3. Grid 里放 20 个 `UIItemSlot`，背景来自 `inventory_slot` Image preset
4. 面板右上角放一个 `UIButton::create(context, "close")`——关闭按钮
5. 面板底部放翻页按钮 `"page_left"` / `"page_right"`——这些都是无 label 的图标按钮

### PauseMenuScene：全覆盖式 UI + 嵌套布局

暂停菜单是最复杂的真实案例，展示了布局嵌套与预设组合：

1. **全屏遮罩层**：一个半透明黑色 UIPanel（`{0,0,0,0.6}`）+ UIInputBlocker，用 anchor 铺满整个屏幕
2. **主面板**：居中定位的 UIPanel（`anchor={0.5,0.5}`、`pivot={0.5,0.5}`）
3. **按钮区域**：一个 Vertical StackLayout（spacing = 6），包含 4 个用 `"primary"` preset 创建的按钮（Resume / Save / Load / Title）
4. **控制区域**：另一个 Vertical StackLayout，包含音量和速度控制行——每行内部用普通 UIPanel 手工布局图标按钮和 label

所有按钮的皮肤、九宫格、label 样式、音效都来自 preset——代码里没有任何"这个按钮用 xxx.png"的硬编码。换一套 UI 素材？改 JSON 就行。

> 关联阅读：`src/game/ui/hotbar_ui.cpp`、`src/game/ui/inventory_ui.cpp`、`src/game/scene/pause_menu_scene.cpp`

### 练习 1：补齐 StackLayout 的"交叉轴 Fill/对齐"最小实现

- 目标（任选其一，建议从 A 开始）：
  - A) **cross-axis fill**：Vertical stack 时，让 child 的宽度按父 content bounds 自动拉伸（Horizontal stack 则拉伸高度）
  - B) **cross-axis alignment**：在交叉轴上支持 Start/Center/End（不需要同时做 fill）
- 验收标准（满足 3 项即可）：
  - 现有 UI（Inventory/Hotbar/PauseMenu/TimeClock）布局不回归、不崩溃
  - Vertical stack 的按钮列在不同容器宽度下依然"对齐且整齐"（无需在业务 UI 里手工调每个 child 的 x）
  - 与 `padding/margin` 的交互符合直觉（padding 影响可用区域）
  - （加分）能通过一个最小 demo 清晰看到对齐/拉伸差异
- 提示线索：
  - Layout 容器：`src/engine/ui/layout/ui_stack_layout.*`（重点看 `onLayout()` 里交叉轴的 `child.cross_pos = content_start.cross` 那一行）
  - 子元素布局字段：`src/engine/ui/ui_element.*`（anchor/pivot/requested size 的含义）
  - 参考 UI：`src/game/scene/pause_menu_scene.cpp`、`src/game/ui/time_clock_ui.cpp`

## 小结 + 下节课预告

本节你把 UI 的两条工程化主线串起来了：

- **Layout 容器**：Stack/Grid 让 UI 从"手工堆坐标"升级为"声明式布局"——你只描述规则（方向、间距、列数），容器自动排列子元素
- **Nine-slice**：一组 margins 把贴图切成 3×3，角不变、边拉伸、中心填充——面板和按钮可以自由缩放而不变形
- **Presets**：Button preset 和 Image preset 把皮肤/字体/音效等样式信息收进 JSON，代码只负责"用"不负责"定义"——换风格改数据就行，不用动代码
- **Debug 面板**：把"不可见的配置系统"变成可观测、可调参的实验台，大幅缩短调试周期

这三件事加在一起，构成了一个完整的 UI 工程化闭环：数据驱动样式（Presets）→ 自动化排布（Layout）→ 稳定拉伸（Nine-slice）→ 实时验证（Debug 面板）。

下节课我们回到"世界侧"的工程化：用空间索引把"查询附近实体/命中检测/交互判定"做成稳定高效的基础设施。
