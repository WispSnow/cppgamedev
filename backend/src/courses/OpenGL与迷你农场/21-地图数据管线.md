# 地图数据管线：Tiled（.tmj/.tsj）到运行时实体

前两节课我们一直在做一件事——**消费地图语义**：

- “空间索引” 搭好了 `SpatialIndexManager`，让玩法系统能查到"这一格是 SOLID 还是 WATER"、"附近有哪些动态碰撞体"；
- “碰撞解析与移动” 在 `CollisionResolver` 里，把 `TileType::SOLID` 和 `TileType::BLOCK_*`（薄墙）转化为"可行位移"，解决了穿墙、卡边、滑动等工程问题。

但如果你回头想一想，会发现有一个关键问题我们一直绕过去了：

> 这些 `SOLID`、薄墙、可耕地、水域、触发器、灯光……它们最初是从哪来的？
> 我在 Tiled 编辑器里改了一行配置，运行时是怎么变成 ECS 实体、组件和空间索引数据的？

换句话说：“空间索引”解决了"怎么查"，“碰撞解析与移动”解决了"怎么用"，而本节课要回答的是——**怎么来**。

这节课的目标就是把这条从**制作侧（Tiled）**到**运行时（ECS + SpatialIndex）**的数据管线（pipeline）完整串起来。

## 本节目标

> 理解《迷你农场》如何把 Tiled 导出的 `.tmj/.tsj` 地图数据解析为"可渲染/可交互/可查询"的运行时世界，并能定位"我要加新关卡语义/新对象类型/新 tile 属性"应该从哪里入手。

你完成本节后，至少能回答三类工程问题：

1. **内容制作问题**：一条语义应该写在 `.tmj` 的哪一层、哪个 properties 里？还是写在 `.tsj` 的 tile properties 里？判断标准是什么？
2. **扩展点问题**：我要加一种新的 object type（比如 `quest_giver`），应该改哪些文件？哪些属于引擎通用层，哪些属于游戏扩展层？
3. **排错问题**：为什么"瓦片阻挡没生效 / 灯光没生成 / 触发器不触发"？如何快速定位是"制作侧配置写错"还是"解析/构建阶段"出了问题？

## 核心概念

本节建立 4 个心智模型，它们是理解整条管线的基础：

1. **三类文件**：`.tmj`（map）/ `.tsj`（tileset）/ `.world`（可选：世界布局）——数据从哪来
2. **三类图层**：tile layer / object layer / image layer——数据的粒度与用途
3. **一条 ID 链**：tile layer 的 `gid` 如何定位到 tileset 里的具体 tile——索引的核心机制
4. **语义的落点**：同一份地图数据最终落到两类运行时结构——ECS 实体（可渲染/可交互）与 SpatialIndex（可查询/可碰撞）

### 1. Tiled 的三类文件：Map / Tileset / World

在《迷你农场》约定的资源结构里（见 `docs/map_data_pipeline.md`），制作侧产出三类文件，各自回答一个问题：

**Map（`.tmj`）**：`assets/maps/*.tmj`
- 回答"这一关长什么样"：地图尺寸（宽×高×瓦片大小）、图层列表（tile/object/image layers）、tileset 引用（每个 tileset 的 `firstgid`）、map/layer 级的 properties。
- 一张 `.tmj` 就是一张完整地图的"蓝图"。

**Tileset（`.tsj`）**：`assets/maps/tileset/*.tsj`
- 回答"每个瓦片是什么"：纹理图片路径、每个 tile 的 properties（如 `tile_flag`）、动画帧定义、碰撞形状、自动图块规则（wangsets）。
- 多张 `.tmj` 可以共享同一个 `.tsj`——比如所有室外地图都引用 `Fence Wood.tsj`，栅栏的碰撞语义只需配置一次。

**World（`.world`，可选）**：`assets/maps/*.world`
- 回答"世界里有哪些 map，它们怎么拼起来"：每张地图的世界坐标与尺寸，用于计算邻接关系。
- 这部分信息会在 [世界状态](24-世界状态.md)（WorldState）深入，这节课只需知道它存在。

<img src="https://theorhythm.top/gamedev/TF/L19_tiled_file_trio.webp" style='width: 960px;' />

> **一句话记忆**：`.tmj` 管"布局"，`.tsj` 管"语义"，`.world` 管"拼接"。

### 2. 三类图层：不同粒度的数据容器

一张 `.tmj` 里的 `layers[]` 数组可以包含三种类型的图层，它们的信息密度和适用场景完全不同：

**(1) Tile Layer（`tilelayer`）**——密度最高，每格一个数字

一张 tile layer 覆盖整个地图网格，`data` 字段是一个扁平数组，按行优先排列。每个元素是一个 `gid`（全局 tile ID），`0` 表示空格。一张地图通常会叠加多个 tile layer 来实现分层渲染，例如 `ground → ground2 → dirt → prop → fence`。

适合表达：地表贴图、装饰物、静态阻挡语义（SOLID/薄墙/水域/可耕地等）。

**(2) Object Layer（`objectgroup`）**——密度中等，每个对象一条记录

每个 object 有自己的坐标、形状（point 或 rect）、`type`/`name` 字段和 properties。point 对象（`width=0, height=0`）通常表示出生点；rect 对象（有宽高）通常表示交互区域。

适合表达：玩家出生点、NPC/动物、地图切换触发器、休息区、灯光等"离散对象"。

**(3) Image Layer（`imagelayer`）**——密度最低，一个大图

整层只挂一张图片，用于远景或背景装饰（parallax 或静态背景）。

<img src="https://theorhythm.top/gamedev/TF/L19_layer_types.webp" style='width: 960px;' />

> **选型原则**：如果语义是"逐格覆盖"的（地面、阻挡），用 tile layer；如果语义是"离散放置"的（NPC、触发器），用 object layer。

### 3. `gid`：把网格上的数字还原成 tileset 里的具体 tile

Tile layer 的 `data` 里存的不是"tileset 里第几个 tile"，而是一个 **全局 ID（gid）**。为什么？因为一张地图可以引用多个 tileset，它们的 tile 编号需要"拼"成一个不重叠的全局编号空间。

规则很简单：

- map 文件的 `tilesets[]` 列表中，每个 tileset 带一个 `firstgid`（该 tileset 在全局编号中的起始值）。
- 一个 `gid` 落在哪个 `firstgid` 区间，就属于哪个 tileset。
- `local_id = gid - firstgid`，即可定位到 tileset 内部的具体 tile。

用一个具体例子来说明。假设一张地图引用了两个 tileset：

```text
tilesets[0]: "Grass Spring"   firstgid = 1     (960 tiles → 占用 gid 1~960)
tilesets[1]: "Fence Wood"     firstgid = 961   (60 tiles  → 占用 gid 961~1020)
```

当 tile layer 的 `data` 里出现 `gid = 965` 时：
- 965 > 961 → 属于 `Fence Wood`
- `local_id = 965 - 961 = 4` → 这是 `Fence Wood` 的第 4 号 tile
- 查该 tile 的 properties，发现 `tile_flag = "SOLID"` → 运行时写入 `TileType::SOLID`

概念级伪代码：
```text
tileset = choose_tileset_by_firstgid(gid)   // 找到 gid 所属的 tileset
local_id = gid - tileset.firstgid            // 算出 tileset 内的本地编号
tile_json = tileset.tiles[local_id]          // 取出该 tile 的完整描述
```

这里不展开 flip bit（翻转标志位）等细节；你只需要记住：**`gid → (tileset, local_id)` 是 tile layer 数据的"索引主线"**。

<img src="https://theorhythm.top/gamedev/TF/L19_gid_resolution.webp" style='width: 960px;' />

### 4. Properties：同一套自定义字段，在不同作用域生效

Tiled 的 custom properties 是一个极为灵活的机制——同一种"键值对"结构可以挂在四个不同的作用域（scope）上：

| 作用域 | 粒度 | 典型用法 |
|--------|------|----------|
| **map properties** | 整张地图 | 室内环境光覆盖（`ambient`）|
| **layer properties** | 整层 | 标记某层为碰撞语义层（`collider`/`solid`）|
| **object properties** | 单个对象 | 触发器的 `target_map`/`target_id`、chest 的奖励 id |
| **tile properties** | 单个 tile（在 `.tsj` 里）| `tile_flag = "SOLID,BLOCK_N"` |

<img src="https://theorhythm.top/gamedev/TF/L19_properties_scope.webp" style='width: 960px;' />

这套机制的价值在于：**语义不必绑死在 layer 名字或文件名上**。你可以在不改动 layer 结构的前提下，通过 properties 逐步演进出更丰富的 schema。比如给 tile 增加一个 `tile_flag = "ARABLE"`（可耕地），不需要新建 layer，只需在 `.tsj` 的对应 tile 上加一条 property。

## 架构与数据流

理解了制作侧的数据模型之后，接下来的关键问题是：**这些数据在运行时是怎么变成实体和空间索引的？**

整个加载流程可以划分为两个阶段，它们之间有一条清晰的分界线：

1. **加载阶段（Load Phase）**：读 `.tmj/.tsj` → 解析 JSON → 建实体 → 写入空间索引。这个阶段需要理解 Tiled 的数据格式。
2. **运行阶段（Runtime Phase）**：系统只做消费与更新（移动/碰撞/交互/渲染）。**运行时系统完全不知道 Tiled JSON 的存在**——它们只看 ECS 组件和空间索引。

这条分界线非常重要：它意味着"加载"是一次性的格式转换，转换完成后 Tiled 的概念就彻底消失了。

### 1. 运行时主链路：从 GameScene 到可渲染/可交互/可查询

从入口开始，《迷你农场》的地图数据管线是一条"入口 → 元数据 → 编排 → 解析 → 构建 → 落点"的链路。每一段有明确的职责边界：

| 模块 | 角色 | 职责 |
|------|------|------|
| `GameScene` | 入口 | 读取配置、创建各模块并触发加载 |
| `MapLoadingSettings` | 配置 | 把 `map_loading_config.json` 解析为运行时设置（预加载模式 `off/neighbors/all`、timing log 开关） |
| `WorldState` | 元数据 | 持有所有地图的 id / 文件路径 / 世界坐标 / 邻接关系，为 `MapManager` 提供"加载谁、文件在哪"的查询入口（深入留到 [世界状态](24-世界状态.md)） |
| `MapManager` | 编排器 | 决定"加载谁"，编排完整的加载流程：卸载旧地图 → 快照恢复 → 创建加载器 → 调用加载 → 配置相机 → 预加载邻居 |
| `LevelLoader` | 引擎加载器 | 解析 `.tmj/.tsj`，遍历 layers 并分派到 tile / object / image 三条处理路径 |
| `BasicEntityBuilder` | 通用构建器 | 把 tile/object 的 JSON 描述转成一组通用 ECS 组件（Transform / Sprite / Collider / Animation / Audio…） |
| `EntityBuilder` | 游戏扩展构建器 | 在通用构建之上，解释游戏特有的对象语义（`actor` / `animal` / `map_trigger` / `rest` / `light`…），挂载游戏组件 |
| `SpatialIndexManager` | 落点 | 接收 tile types 与瓦片/碰撞体实体，成为 [空间索引](19-空间索引.md)/L18 玩法系统的查询入口 |

<img src="https://theorhythm.top/gamedev/TF/L19_map_loading_pipeline.webp" style='width: 960px;' />

这条链路的关键设计意图是**单向流动、逐层转换**：Tiled JSON → TileInfo/ObjectJSON → ECS 组件 → 空间索引。每一段只关心"把上游的数据翻译成下游能消费的格式"，不做回溯，也不保留上游的原始结构。

### 2. 引擎通用层与游戏扩展层的边界

这节课你会反复用到一个判断标准——"这件事应该由引擎层做，还是游戏层做？"

**引擎层（`src/engine/`）负责"通用转换"：**
- 读取/解析 Tiled JSON（`.tmj/.tsj`），这与任何具体游戏无关
- 把"通用概念"变成通用组件（Transform / Sprite / Collider / Animation…）
- 把静态语义写入空间索引（TileType、瓦片实体）

对应核心模块：
- `src/engine/loader/level_loader.*`——Tiled 格式的通用适配层
- `src/engine/loader/basic_entity_builder.*`——JSON/TileInfo → 通用组件
- `src/engine/component/tilelayer_component.h`——`TileType` 枚举与 `TileInfo` 结构
- `src/engine/spatial/spatial_index_manager.*`——空间索引的写入入口

**游戏层（`src/game/`）负责"语义解释"：**
- 定义"这个项目里有哪些 object type 和玩法语义"
- 将 object layer 的 `type`/`properties` 解释为游戏组件（MapTrigger / RestArea / Light…）
- 维护"世界级信息"（地图 id、邻接、触发器列表、快照状态）

对应核心模块：
- `src/game/loader/entity_builder.*`——游戏内容的扩展点
- `src/game/world/map_manager.*`——加载编排器
- `src/game/world/world_state.*`——世界元数据

> **一句话记忆**：`LevelLoader` 是"引擎对 Tiled 的通用适配层"，`EntityBuilder` 是"游戏内容的扩展入口"。当你想加新 object type 时，改的是 `EntityBuilder`，而不是 `LevelLoader`。

<img src="https://theorhythm.top/gamedev/TF/L19_extension_points.webp" style='width: 960px;' />

### 3. 让"加载"变成可观测系统：Conventions / Cache / Diagnostics

地图加载这类"制作侧 → 运行时"的管线，最容易出两类问题：

1. **magic string 漂移**：同一字段名在不同文件里写法不一致。比如 tileset 里写 `tile_flag`，但构建器里读 `tileFlag`——拼写不匹配就静默跳过。
2. **静默失败**：制作侧配置写错（比如 `tile_flag` 写成 `SLOID`），运行时不会崩溃，只是"没效果"。你可能要花很久才发现"栅栏为什么不挡人了"。

《迷你农场》用三件套来对抗这两类问题：

**(1) 约定常量集中管理（Conventions）**

所有 layer 名字、property 键名、object type 字符串、tile flag token 都集中定义在两个头文件里：

- 引擎层：`src/engine/loader/tiled_conventions.h`——通用字段名（`tile_flag`、`obj_type`、`anim_id` 等）和 layer 名约定（`collider`、`solid`）
- 游戏层：`src/game/loader/tiled_conventions.h`——游戏特有的 object type（`actor`、`animal`、`map_trigger`、`rest`、`light`）、trigger 属性名（`self_id`、`target_map`…）、light 名字（`point`、`spot`、`emissive`）

这样做的好处是：如果你要加新 token 或改名，只需要改一个地方，编译器会帮你找到所有引用点。

**(2) JSON 安全读取与缓存（Cache）**

- `src/engine/loader/tiled_json_helpers.h`：提供 `jsonStringOr()` / `jsonIntOr()` / `jsonFloatOr()` 等 safe getter，当字段缺失或类型不符时返回默认值而非崩溃。这组工具避免了"因一个 tile 的属性写错而导致整张地图加载失败"的脆弱行为。
- `src/engine/loader/tiled_json_cache.h`：`.tmj` 和 `.tsj` 的全局缓存（各有容量上限），同一个文件不会被重复读盘和解析。在频繁的地图切换中，这能显著减少加载延迟。

**(3) 未知 token 诊断（Diagnostics）**

- `src/engine/loader/tiled_diagnostics.h` 定义了三种诊断记录：`UnknownTileFlagToken`（tile flag 拼写错误）、`UnknownObjectType`（object type 未注册）、`UnknownLightName`（light name 不识别）。
- 加载过程中遇到未知 token 不会中断，而是收集到诊断列表并输出 warning。
- `Map Inspector` 调试面板（`F5 → Game Debug Panels → Map Inspector`）能直接显示这些 unknown token 报告，包含 tileset 路径和 tile id，帮你快速定位到制作侧的错误位置。

> **排错经验**：当某个语义"在游戏里没效果"时，首先打开 `Map Inspector`，检查 `Unknown Tokens` 部分——八成是拼写错误。

建议按"入口 → 编排 → 加载器 → 构建器 → 落点"的顺序阅读源码：

1. `src/game/scene/game_scene.cpp`——找到地图在何时加载、`MapManager` 在哪里创建。

4. `src/engine/loader/level_loader.*`——理解 `loadLevel()` / `preloadLevelData()` 的分阶段逻辑，以及它如何把三类 layer 分派到不同的处理路径。
5. `src/engine/loader/basic_entity_builder.*`——理解 `configure()` + `build()` 的两步法：先配置数据源，再按固定顺序构建组件（Transform → Sprite → Collider → Render → Animation → Audio）。
6. `src/game/loader/entity_builder.*`——object layer 的"游戏扩展点"（深入细节留到 [关卡载入器与实体建造者](22-关卡载入器与实体建造者.md)）。
7. `src/engine/component/tilelayer_component.h` + `src/engine/spatial/spatial_index_manager.*`——tile 语义如何从 `TileInfo` 写入空间索引，并被 [空间索引](19-空间索引.md)/L18 的系统消费。
8. （可选）`src/game/debug/map_inspector_debug_panel.*`——Map Inspector 的观测入口（unknown token / JSON cache / tile flags 分布）。

## 课后练习

### 练习 1（推荐）
**题目：实现 "Map Validator（加载后验证器）"，让关卡配置错误更早暴露**

背景：目前项目已经能报告未知 `tile_flag` / `object.type` / `light.name`，但更多"制作侧错误"仍然可能以"游戏里没效果"的形式出现——比如 trigger 指向不存在的地图、必需的碰撞层缺失、object 缺少必需字段。

目标：在地图加载完成后，输出一份结构化报告（日志或 debug 面板均可），覆盖你认为最有价值的 5–10 条校验项。

- 验收标准：
  - 运行游戏加载地图后能看到 Map Validator 报告（日志或 `Map Inspector` 的新 section）
  - 报告至少覆盖以下方向中的 3 类：
    - 必需图层 / 必需 properties 是否存在（例如 collider/solid 语义层）
    - object layer：缺少必需字段（type/name/shape）或字段值不合法
    - tileset：tile properties 取值不合法、纹理 / 动画帧缺失等
    - 与 `WorldState` / 邻接相关的引用失效（例如 trigger 指向不存在的 map）
  - 可选（加分）：支持 strict mode（遇到 error 直接阻止进入地图）
  - `ctest --test-dir build --output-on-failure` 通过（允许你为 validator 新增 1–2 个测试）
- 提示线索（模块/文件）：
  - `src/game/world/map_manager.cpp`（最合适的触发位置：`loadMap()` 完成后）
  - `src/engine/loader/level_loader.*`（你能拿到 map/tileset JSON，做更精准的检查）
  - `src/game/debug/map_inspector_debug_panel.*`（展示入口）
  - `src/engine/loader/tiled_diagnostics.h`（可复用 unknown token 报告的数据结构）
- 提交方式：GitHub PR（一个作业一个 PR，描述"新增了哪些校验 / 如何验证 / 如何扩展"）

### 练习 2（可选挑战）
**题目：为 object properties 做一个"类型安全的读取器"，并用它改造 1–2 个对象构建分支**

背景：object layer 的 properties 非常灵活（键值对，什么都能写），但直接手写 JSON 访问容易产生三类问题：字段名拼写漂移、默认值不一致、报错信息不统一。当 10 种 object type 各自手写解析逻辑时，这些问题会成倍放大。

目标：为游戏层提供 `getStringProp` / `getIntProp` / `getEnumProp` 这类工具函数，并用它替换掉 `EntityBuilder` 中至少 1–2 个分支的手工解析逻辑。

- 验收标准：
  - 新增一个"小而独立"的 properties reader（只服务 game 层，不污染 engine 通用层）
  - 对缺失字段 / 类型不符能输出统一、可定位的错误信息（包含 map name / object id / type / name）
  - 至少为 1 个对象类型增加 1 个单元测试，覆盖"不合法配置"的报错（参考现有 tests 风格）
  - `ctest --test-dir build --output-on-failure` 通过
- 提示线索（模块/文件）：
  - `src/game/loader/entity_builder.cpp`（从 `buildMapTrigger` 或 `buildRestArea` 之类入手最合适）
  - `src/game/loader/tiled_conventions.h`（字段名与枚举 token 的集中位置）
  - `src/engine/loader/tiled_json_helpers.h`（如果你想复用通用 safe getter，注意保持引擎/游戏层边界）

## 小结与下节课预告

本节你应该形成一个稳定的**地图数据管线心智模型**：

- **制作侧**：`.tmj` 通过 layers（tile/object/image）和 properties（map/layer/object/tile 四级作用域）描述关卡语义；`.tsj` 为每个 tile 附加碰撞、动画与自定义属性。
- **运行时**：`MapManager` 编排加载流程，`LevelLoader` 解析 Tiled JSON 并分派到三类 layer 处理路径，`BasicEntityBuilder` / `EntityBuilder` 把数据翻译成 ECS 组件，最终 `SpatialIndexManager` 接收静态语义供玩法系统查询。
- **工程保障**：约定常量集中管理防漂移、JSON safe getter 防崩溃、全局缓存防重复 I/O、diagnostics + `Map Inspector` 让加载过程可观测可排错。

下节课我们会把镜头拉近到"构建器"本身：

> `LevelLoader` 与 `EntityBuilder` 是如何分工的？它怎么把 object layer 里的多种对象（角色、动物、触发器、灯光……）做成一条可扩展、可测试的构建流水线？

换句话说：本节课讲了"管线从头到尾怎么走"，下节课要讲的是——"当你想加新 object type 时，如何只改游戏层代码，而不破坏引擎通用层"。
