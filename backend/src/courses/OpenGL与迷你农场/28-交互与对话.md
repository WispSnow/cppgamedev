# 交互与对话：从空间查询到事件分发

上节课我们完成了玩家控制与相机的闭环——玩家能移动、能面向某个方向、相机能跟随并限制在地图边界内。但到目前为止，玩家只是在世界里"走来走去"，跟场景中的 NPC、宝箱、休息点没有任何互动。

> 移动和朝向只是"底盘"，交互才是让玩家与世界产生关系的第一步。

本节会把之前多节课的积木拼起来，形成一条完整的交互链路：

| 前置知识（课号） | 本节复用的能力 |
| --- | --- |
| [输入系统](15-输入系统.md) | 动作映射：`interact`（默认 `F`），通过 `isActionPressed` 轮询 |
| [空间索引](19-空间索引.md) | 一次查询拿到"可能被碰到的候选实体" |
| [事件系统](06-事件系统.md) | 用 `trigger/enqueue` 把系统解耦 |
| [UI 框架基础](17-UI%20框架基础.md) | UI 只订阅事件，不直接依赖玩法系统 |
| [玩家控制与相机](27-玩家控制与相机.md) | 玩家朝向（`StateComponent::direction_`）驱动目标选择 |

你可以这样理解 [玩家控制与相机](27-玩家控制与相机.md) 和 [交互与对话](28-交互与对话.md) 的关系：
- **[玩家控制与相机](27-玩家控制与相机.md)** 解决的是：输入 → 移动/朝向（玩家能控制自己的角色）
- **[交互与对话](28-交互与对话.md)** 解决的是：输入 → 交互请求 → 世界响应 → UI/Scene（玩家能与世界产生内容）

本节的演示效果也很直观：
- 面对 NPC 按 `F`：出现对话气泡，再按 `F` 推进下一句，走远自动关闭
- 面对宝箱按 `F`：宝箱打开，并弹出短通知气泡（和对话不同频道）
- 面对休息点按 `F`：push `RestDialogScene`（交互不仅能驱动 UI，也能驱动场景控制流）

## 本节目标与问题定义

本节目标一句话：

> 建立一个可复用的"交互闭环"：把 `F` 键的交互意图转成 `InteractRequest`，再由多个订阅者系统各司其职地消费，并通过事件驱动 UI 或 Scene。

把目标展开成一条链路：

> `F`（交互意图） → 选出"玩家面对的目标" → 发出 `InteractRequest` → 各系统按职责响应（对话/宝箱/休息） → 通过事件驱动 UI 或 Scene

我们用 4 个问题来驱动理解：
1. **交互目标应该怎么选？** 为什么不是"找最近"，而是"找面向的一格（facing probe）"？
2. **交互逻辑应该放在哪里？** 为什么 `InteractionSystem` 不应该知道"对话/开箱/休息"的细节？
3. **一个请求如何让多个系统响应而不互相耦合？** `InteractRequest` 为什么是扩展点？
4. **UI 如何被玩法驱动但仍保持解耦？** `DialogueBubble` 为什么只订阅事件而不直接引用玩法系统？

### 为什么要这么绕一圈（工程动机）

想象一下，如果我们把所有交互逻辑——对话、开箱、休息、未来可能的告示牌、商店、传送点——全都塞进 `InteractionSystem` 的 `update()` 里：

```text
if (target has DialogueComponent) { ... 对话逻辑 ... }
else if (target has ChestComponent) { ... 开箱逻辑 ... }
else if (target has RestArea) { ... 休息逻辑 ... }
// 未来每加一种交互对象，这里就多一个 else if
```

这条路在内容量少的时候还行，但随着游戏功能增加，这个函数会快速膨胀成一个"巨型 if-else"——改一个分支容易误伤其他分支，测试也变得困难。

事件总线式设计把这个问题一分为二：
- **`InteractionSystem`**：只负责"选目标 + 发 `InteractRequest`"
- **订阅者系统**（`DialogueSystem/ChestSystem/RestSystem/...`）：各自关心自己的 component 并独立响应

UI 同样用事件订阅保持"弱依赖"：`DialogueBubble` 不直接引用任何玩法系统，只依赖事件契约。这对教学 demo 和长期维护都更稳。

## 核心概念

### 3.1 交互闭环的两层稳定结构

先建立一个全局的心智模型——把"交互"拆成两层：

| 层级 | 角色 | 职责 | 稳定性 |
| --- | --- | --- | --- |
| 上游 | `InteractionSystem` | 选目标 + 发 `InteractRequest` | 高（几乎不需要改） |
| 下游 | 订阅者系统（Dialogue/Chest/Rest/...） | 消费请求 + 产出效果 | 低耦合（各自独立演进） |

当你新增一种交互对象时（比如告示牌/商店/钓鱼点），优先策略始终是：

> 新增一个订阅者系统（+ 新 component），而不是去改 `InteractionSystem`。

这条原则贯穿本节所有代码。

### 3.2 交互不是"找最近"，而是"找玩家面对的目标"

很多俯视角游戏的交互更像"指向并确认"，而不是"范围内最近"。本项目采用 **facing probe**（面向探测）：

1. 取玩家当前朝向（上/下/左/右，来自 `StateComponent::direction_`）
2. 在玩家前方一格（`TILE_SIZE`）生成一个 probe rect
3. 给 probe rect 加一点 padding（`PROBE_PADDING_PX = 4.0f`），容忍轻微偏移
4. 用空间索引查询 probe 覆盖到的候选实体
5. 按规则过滤 + 按优先级选出目标

简化后的决策逻辑：
```text
if F pressed:
  if current map has active dialogue target:
    // 对话进行中 → 优先推进/结束当前对话
    target = that entity
  else:
    // 否则做 facing probe → 寻找新目标
    target = chooseFacingTarget(player)

  if target != null:
    trigger InteractRequest(player, target)
```

**为什么用 facing probe 而不是最近距离？**
- **更符合直觉**：玩家面对谁，就和谁交互；不会出现"跟身后的人说话"
- **更可控**：交互范围限制为"一格"，大幅降低误触概率
- **更可扩展**：即使后续增加更多可交互对象，也只是"probe 命中了更多候选"，而不是"全局距离排序算法变复杂"

#### 3.2.1 候选目标的两种来源

面对一格时，你可能命中两类交互目标：
- **动态实体（dynamic colliders）**：NPC、宝箱……它们有碰撞形状，存在于空间索引的动态网格中。查询方式是 `SpatialIndexManager::checkCollision(probe_rect)`
- **tile 交互点（tile entity）**：例如休息区（`RestArea`），更像"地图上的标记格子"，属于某个 tile layer。查询方式是 `SpatialIndexManager::getTileEntityAtWorldPos(probe_world_pos, layer_id)`

这解释了 `chooseFacingTarget` 里一个常见的结构模式：**先查 dynamic colliders，如果没找到合适的动态实体，再查特定 tile layer 的交互点**。代码中的体现：

```cpp
// 先在动态碰撞候选中找 NPC / 宝箱
if (best_npc == entt::null && best_chest == entt::null) {
    // 都没找到，才去查 REST tile layer
    if (auto rest = spatial_index_manager_.getTileEntityAtWorldPos(
            probe_world_pos, game::defs::spatial_layer::REST);
        rest != entt::null && registry_.valid(rest)) {
        // ...
        return rest;
    }
}
return best_npc != entt::null ? best_npc : best_chest;
```

最终优先级：**NPC 对话 > 宝箱 > 休息点**。

### 3.3 InteractRequest：事件总线式扩展点

`InteractRequest` 是整个交互架构的核心枢纽。它的结构极简——只有两个字段：

```cpp
struct InteractRequest {
    entt::entity player{entt::null};
    entt::entity target{entt::null};
};
```

它的定位是**扩展点**：
- `InteractionSystem` 发请求（`dispatcher_.trigger(InteractRequest{player, target})`）
- 任意数量的系统都可以订阅它
- 每个订阅者只处理自己关心的 component，互不侵入

你可以把每个订阅者的心智模型记成一句话：

> **"我只关心 target 身上有没有某个 component；有我就处理，没有我就忽略。"**

以 `DialogueSystem` 为例：

```cpp
void DialogueSystem::onInteractRequest(const InteractRequest& event) {
    // 1. 基本校验
    if (event.target == entt::null || !registry_.valid(event.target)) return;
    // 2. 只关心有 DialogueComponent 的目标
    auto* dialogue = registry_.try_get<DialogueComponent>(event.target);
    if (!dialogue || dialogue->dialogue_id_ == entt::null) return;
    // 3. 额外门控（冷却、睡眠等）
    if (dialogue->cooldown_timer_ > 0.0f) return;
    // 4. 执行对话逻辑
    // ...
}
```

`ChestSystem` 和 `RestSystem` 的模式完全一样——检查自己的 component（`ChestComponent`/`RestArea`），有就处理，没有就 return。

#### 3.3.1 两类事件的语义差异

在 [事件系统](06-事件系统.md) 我们提过 `trigger` 与 `enqueue` 的差别。在交互链路中，一个实用的经验法则是：

| 事件类型 | 代表事件 | 倾向用法 | 原因 |
| --- | --- | --- | --- |
| 请求事件（command-like） | `InteractRequest` | `trigger` | 让响应者在同一帧立刻处理，形成闭环 |
| UI 通知事件（view-like） | `DialogueShow/Move/HideEvent` | `enqueue` | 统一在 dispatcher 更新阶段分发，不会影响同帧系统更新顺序 |

这不是唯一正确答案，但它能同时保证两件事：
1. 交互请求的响应更"即时"，玩家不会感觉"慢了一拍"
2. UI 事件不会在系统 update 中间"插队"，减少顺序型 bug

### 3.4 为什么要"优先推进当前对话"

交互系统里有一条重要的 UX 规则：

> 当对话已经开始时，`F` 应该推进/结束当前对话，而不是重新做一次目标选择。

这条规则在 `InteractionSystem::update()` 中体现为一个**两段式策略**：

```cpp
void InteractionSystem::update() {
    if (!input_manager_.isActionPressed("interact"_hs)) return;
    // ...
    // 阶段 1：如果有 active 对话 → 优先发给它
    if (auto target = findActiveDialogueTarget(current_map); target != entt::null) {
        dispatcher_.trigger(InteractRequest{player, target});
        return;
    }
    // 阶段 2：否则做 facing probe → 寻找新目标
    if (auto target = chooseFacingTarget(player, current_map); target != entt::null) {
        dispatcher_.trigger(InteractRequest{player, target});
    }
}
```

为什么不每次都重新选目标？原因很现实：
- 玩家在对话时可能微移一步或轻微改变朝向；如果重新选目标，可能误选到旁边的宝箱或休息点
- 对话推进是一个**连续操作**，最好保持目标稳定，给玩家"正在跟这个 NPC 说话"的确定感

`findActiveDialogueTarget` 的实现也很直接——遍历当前地图上所有有 `DialogueComponent` 的实体，找到 `active_ == true` 的那个：

```cpp
entt::entity InteractionSystem::findActiveDialogueTarget(entt::id_type current_map) const {
    auto view = registry_.view<DialogueComponent, MapId>();
    for (auto entity : view) {
        if (view.get<MapId>(entity).id_ != current_map) continue;
        if (view.get<DialogueComponent>(entity).active_) return entity;
    }
    return entt::null;
}
```

#### 3.4.1 架构模式：双重守门（defense-in-depth validation）

你会发现 `InteractionSystem::chooseFacingTarget` 和 `DialogueSystem::onInteractRequest` 中存在**重复的条件检查**（`cooldown > 0`、`SleepRoutine::is_sleeping_`、`dialogue_id` 有效性）。

这不是代码重复，而是事件驱动架构中常见的**双重守门**模式：

- **上游（InteractionSystem）**：做前置过滤，避免向事件总线发出明显无效的请求——减少不必要的事件广播和后续处理
- **下游（DialogueSystem）**：不信任上游，重新校验——即使未来有其他上游也能安全处理

一句话记忆：

> 发送者负责"别乱发"，接收者负责"不管谁发的都要自保"。

### 3.5 对话推进：从一次交互到一个轻量状态机

对话不是一次性弹窗——它有一个最小的三段状态机：

| 状态 | 触发条件 | 行为 |
| --- | --- | --- |
| **start** | 目标无 active 对话时按 `F` | 设 `active_=true`，`current_line_=0`，显示第 1 行 |
| **advance** | 已有 active 对话时再按 `F` | `current_line_++`，显示下一行（如果还有） |
| **end** | 已到最后一行时按 `F` | 关闭对话（`active_=false`，`current_line_=0`），隐藏气泡 |

![对话状态机](diagrams/L26_dialogue_state_machine.png)

除了状态机本身，对话还要处理两个现实约束：

**冷却（cooldown）**：避免按键抖动导致一帧推进多次。每次交互后设置 `cooldown_timer_ = cooldown_`（默认 `0.35s`），`DialogueSystem::update` 每帧递减计时器。`InteractionSystem` 和 `DialogueSystem` 都会检查 `cooldown_timer_ > 0.0f`——前者不发请求，后者不处理请求（双重守门）。

**距离门控（distance gating）**：玩家走远后自动关闭，避免"隔空对话"。具体阈值用命名常量 `DIALOGUE_CLOSE_DISTANCE_FACTOR`（`= 1.4f`）表示，含义是"允许比触发距离再远 40% 才关闭"——之所以留余量，是为了避免玩家稍微挪动就断开对话，手感会很差。这比写一个裸的 `1.4f` 更容易理解和调整。

### 3.6 事件驱动 UI：DialogueBubble + channel

对话气泡/通知气泡看起来像 UI，但它们的触发时机完全来自玩法系统。这是 [交互与对话](28-交互与对话.md) 中最重要的解耦模式之一：

**玩法系统侧（生产者）**：
- `DialogueSystem`、`ChestSystem`、`ItemUseSystem` 只负责 `enqueue` 三种 UI 事件：`DialogueShowEvent`（显示文本）、`DialogueMoveEvent`（更新位置）、`DialogueHideEvent`（隐藏）
- 这些事件都携带 `world_position`（世界坐标）和 `channel`（频道号）

**UI 侧（消费者）**：
- `DialogueBubble` 监听这三种事件
- 收到 `ShowEvent` 时：设置文本、设置世界坐标、显示
- 收到 `MoveEvent` 时：更新世界坐标（每帧由 `update` 转成屏幕坐标）
- 收到 `HideEvent` 时：隐藏
- 坐标转换在 `update` 中完成：`context.getCamera().worldToScreen(world_position_)`

为了避免不同类型的提示互相覆盖，我们约定了 **3 个 channel**（`GameScene::initUI` 会创建 3 个 `DialogueBubble` 实例，各绑不同 channel）：

| Channel | 用途 | 典型发送者 |
| --- | --- | --- |
| `0` | 对话 | `DialogueSystem` |
| `1` | 短通知（拾取/开箱） | `ChestSystem`、`PickupSystem` |
| `2` | 物品提示（使用/消耗） | `ItemUseSystem` |

理解 channel 最好的方式：**把它当成"UI 的三个独立槽位"**。同一时刻对话和通知可以同时存在——你正在跟 NPC 说话时打开了旁边的宝箱，对话气泡和开箱通知互不影响。

每个 `DialogueBubble` 实例在创建时绑定一个 channel，事件处理函数里做的第一件事就是检查频道是否匹配：

```cpp
void DialogueBubble::onShowEvent(const DialogueShowEvent& evt) {
    if (evt.channel != channel_) return;  // 不是我的频道，忽略
    setWorldPosition(evt.world_position);
    setText(/* 处理换行后的文本 */);
    setVisible(true);
}
```

#### 3.6.1 事件发射的胶水层：`system_helpers.h`

你在 `DialogueSystem`、`ChestSystem` 等系统中会频繁看到 `helpers::computeHeadPosition` 和 `helpers::emitDialogueBubbleShow/Move/Hide` 这些调用——它们都定义在 `src/game/system/system_helpers.h`。

这个头文件的定位是**跨系统共享的轻量工具函数**：

- `computeHeadPosition`：根据实体的 `Transform` + `Sprite` pivot 计算"头顶位置"（用于气泡锚点）。如果实体有 `SpriteComponent`，取 `position_.y - size_.y * pivot_.y`；否则默认偏移 `-16px`
- `emitDialogueBubbleShow/Move/Hide`：封装了事件结构体的构造与 `enqueue`，让各系统不必手动拼字段

为什么要抽出来？因为多个系统都要做同样的"算头顶 + 发事件"操作，把它们集中在一处可以避免重复代码，也让"事件契约"有一个明确的落脚点——如果事件结构变了，只改 helper 就行。

### 3.7 数据驱动对话脚本：dialogue_id → lines[]

对话文本放在 `assets/data/dialogue_script.json`，是一个极简的字典结构：

```json
{
  "friend_greeting": [
    "你好！今天天气真不错。",
    "最近农场怎么样？",
    "有空来我家坐坐！"
  ],
  "shopkeeper_intro": [
    "欢迎光临！",
    "看看有什么需要的？"
  ]
}
```

- key：对话 id（string），在加载时会被哈希成 `entt::id_type`
- value：字符串数组，每个元素是一行对话

NPC 如何绑定脚本？
- NPC 蓝图（blueprint）里写 `dialogue_id`（string）
- 运行时 `EntityFactory` 把这个 string 哈希后写入 `DialogueComponent::dialogue_id_`
- `DialogueSystem` 在初始化时调用 `loadDialogueFile` 加载对话表到 `dialogue_table_`
- 交互触发时，用 `dialogue_id_` 在表中查找对应的文本行

一个实用的**"新增 NPC 对话流程"**（不改代码）：
1. 在 `assets/data/dialogue_script.json` 增加一个 key 和若干行文本
2. 在对应 NPC 的 blueprint JSON 中把 `dialogue_id` 设为同样的字符串
3. 运行游戏，面对 NPC 按 `F` 验证能显示并推进

### 4.1 数据流总览（一次交互的完整闭环）

#### 4.1.1 目标选择的规则表

三种交互目标走的是同一条管线（probe → query → filter → pick），只是门控规则不同：

| 目标类型 | 候选来源 | 必要 component | 典型门控/过滤 | 消费者 |
| --- | --- | --- | --- | --- |
| NPC 对话 | dynamic colliders | `DialogueComponent` + `MapId` | 同地图、`dialogue_id` 有效、冷却=0、非睡眠 | `DialogueSystem` |
| 宝箱 | dynamic colliders | `ChestComponent` + `MapId` | 同地图、未开启 | `ChestSystem` |
| 休息点 | tile entity（REST layer） | `RestArea` + `MapId` | 同地图 | `RestSystem` |

### 4.2 chooseFacingTarget：把"面向一格"变成"可交互目标"

`chooseFacingTarget` 的逻辑可以按三个阶段来读：

**阶段 1 — 计算 probe：** 由"玩家当前位置 + 朝向"得到前方一格的 probe rect。具体做法是先用 `toOffset(direction)` 把朝向转成 `(0,-1)/(0,1)/(-1,0)/(1,0)` 的偏移量，乘以 `TILE_SIZE` 得到世界坐标，再通过 `getRectAtWorldPos` 得到对应 tile 的矩形，最后加 padding。

**阶段 2 — 空间查询：** 用 `SpatialIndexManager::checkCollision(probe_rect)` 拿到覆盖 probe 的所有动态碰撞实体。

**阶段 3 — 优先级挑选：** 遍历候选，分别收集"最近的 NPC"和"最近的宝箱"。如果两者都没找到，才去查 REST tile layer。最终返回优先级最高的（NPC > Chest > Rest）。

这三个阶段是一个通用结构——你会在很多玩法里复用同样的模式，只是"规则"和"优先级"不同。

### 4.3 三个订阅者系统各自做了什么

#### DialogueSystem：对话推进与事件发射

`DialogueSystem` 的职责分两块：

**事件处理（`onInteractRequest`）**：收到请求后，检查目标是否有 `DialogueComponent` 且满足门控条件。如果是新对话就 `startDialogue`；如果是已有对话就 `advanceDialogue`；如果到最后一行就 `endDialogue`。每次状态变化都通过 `helpers::emitDialogueBubbleShow/Hide` 发出 UI 事件。

**帧更新（`update`）**：递减所有 `DialogueComponent` 的冷却计时器；检查 active 对话的距离门控（超过阈值则自动关闭）；如果对话仍然 active，发出 `MoveEvent` 更新气泡位置。

#### ChestSystem：开箱 + 短通知

`ChestSystem` 收到 `InteractRequest` 后，检查目标是否有 `ChestComponent` 且未开启。如果满足条件：
1. 用 `ItemCatalog` 查询奖励物品的显示名，拼成通知文本
2. 通过 `helpers::emitDialogueBubbleShow`（`channel=1`）显示短通知
3. 对每个奖励 `trigger AddItemRequest`（物品入背包）
4. 播放开箱动画
5. 标记 `opened_ = true`，并把状态写入 `WorldState` 的地图持久化数据（这连接了 [地图管理器](25-地图管理器.md) 讲的快照机制）

通知的显示时长由 `NOTIFICATION_SECONDS = 2.0f` 控制，`update` 中每帧递减计时器，到期后自动隐藏。

#### RestSystem：交互驱动场景控制流

`RestSystem` 是最简洁的订阅者——收到请求后，检查目标有 `RestArea` component，然后直接 `trigger PushSceneEvent`，把 `RestDialogScene` 压入场景栈。

这里的教学价值在于：**交互的结果不一定是 UI 变化，也可以是场景控制流的变化**。同一套 `InteractRequest` 机制既能驱动对话气泡，也能 push 一个全新的 Scene。

### 4.4 UI 侧：为什么 DialogueBubble 不直接依赖玩法系统

`DialogueBubble` 的职责是"展示"，而不是"知道玩法"：
- 它只订阅 `DialogueShow/Move/HideEvent`（过滤 channel）
- 它只关心：显示什么文本、锚点在哪里（世界坐标）、如何转到屏幕坐标

这样做的好处是双向的：
- **玩法侧**可以自由演进（增加宝箱通知、物品提示……），只要复用同一组事件契约即可
- **UI 侧**也可以被替换（换皮肤/换字体/换布局），不影响任何玩法逻辑

一句话总结这个解耦模式：

> 玩法系统 `enqueue` 事件，UI 订阅并渲染；channel 做分流。两边通过事件契约相连，但彼此不 `#include`。

### 4.5 顺序敏感点：交互依赖"本帧最新空间索引"

交互系统会做空间查询，因此它隐含依赖两个系统先执行：
1. `MovementSystem`（玩家位置已更新）
2. `SpatialIndexSystem`（空间索引已重建）

这是 [游戏场景初始化与系统编排](26-游戏场景初始化与系统编排.md) 讲过的典型"顺序型依赖"。当你遇到"按了 F 但交互好像慢一拍"或"选错了目标"的现象时，优先检查 `GameScene` 中的 update 顺序：

> `MovementSystem` → `SpatialIndexSystem` → ... → `InteractionSystem`

确认空间索引在交互之前更新完毕。

## 练习

### 练习 1：升级换行策略

- **目标**：把 `DialogueBubble` 的换行策略从"按字符数"升级为"按像素宽度测量"，避免不同字体/中英文混排导致溢出。
- **验收标准**：
  - 给 `DialogueShowEvent.text` 填入一段较长的中英文混排文本，气泡不会超出背景宽度
  - 仍然支持 `\n` 作为强制换行
- **提示线索**：
  - `src/game/ui/dialogue_bubble.cpp`（当前 `onShowEvent` 中的简易换行逻辑）
  - `engine::render::TextRenderer`（如果有测量接口，优先复用）
- **建议实现路线**（避免过度工程化）：
  1. 保持现有 API 不变，只替换"分行算法"
  2. 把每行的宽度上限定义成一个明确的像素值（可从气泡背景宽度推导）
  3. 逐字/逐 token 累加像素宽度，超过上限就换行（遇到 `\n` 强制换行）
- **常见坑**：
  - CJK 字符宽度不是等宽；按字符数分行在中文/混排时更容易溢出
  - 不要在每帧重新做测量：优先在收到 `DialogueShowEvent` 时计算一次并缓存分行结果
  - 不要引入复杂文本排版系统——demo 规模更看重可读性与可维护性

### 练习 2（可选）：引入交互类型标记

- **目标**：引入一个极简的 `InteractionType` component，用它来标记"可交互实体类型"，减少 `InteractionSystem` 对具体 component 的硬编码。
- **验收标准**：
  - `InteractionSystem` 不再通过 `try_get<DialogueComponent/ChestComponent/...>` 直接判断类型，而是读取你引入的标记 component 来决定优先级
  - 仍保持 demo 规模：不做通用注册表/反射/脚本化派发
- **提示线索**：
  - `src/game/system/interaction_system.*`
  - `src/game/factory/entity_factory.cpp`（NPC/宝箱等实体创建处）
  - `src/game/component/*`（放新 component 的位置）
- **建议控制在"一个枚举 + 两处写入 + 一处读取"的规模**：
  - 枚举：`InteractionType::{Dialogue, Chest, Rest, ...}`
  - 写入：实体创建时给目标实体加上该 component（NPC、宝箱、休息点）
  - 读取：`InteractionSystem` 在候选筛选阶段读 type 决定优先级（并保持规则表清晰）

## 小结

本节我们把"交互"拆成了两个稳定层：
- **InteractionSystem（上游）**：选目标 + 发 `InteractRequest`——对"做什么"一无所知
- **订阅者系统（下游）**：对话 / 宝箱 / 休息——各自消费请求并通过事件驱动 UI 或 Scene

你应该带走的 3 条心智模型：
1. **交互目标选择**：probe → query → filter → pick（+ fallback to tile entity）
2. **交互架构的职责边界**：`InteractionSystem` 只发请求，具体行为全在订阅者——扩展新交互 = 新增订阅者 + 新 component
3. **UI 解耦的关键是事件契约**：玩法 `enqueue`，UI 订阅并渲染；channel 做分流，让不同类型的提示互不干扰

下节课会把"宝箱/拾取产生的物品变化"讲完整：物品栏与快捷栏如何同步、拖拽映射如何保持状态一致，以及 UI 如何持续地跟随 ECS 事件更新。
