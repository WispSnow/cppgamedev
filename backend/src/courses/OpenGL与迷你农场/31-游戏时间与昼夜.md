# 游戏时间与昼夜：时间事件驱动的环境变化

在上节课我们已经见过时间事件的"消费侧"：
- 作物生长以"天"为粒度——`DayChangedEvent` 到来时推进生长阶段
- 调试面板可以"一键快进 1 天"，不用等真实时间流逝就能验证整条玩法闭环

但有一个问题一直悬而未决：**这些时间事件到底是谁产生的？它在哪一帧被分发？为什么我们推荐用事件而不是直接改数值？**

这就是本节课要解答的核心。本节的主线不是"做一个时钟 UI"，而是把时间变成一个**可复用的系统 API**：

> **TimeSystem 负责"推进时间 + 产生事件"；其他系统只消费事件或读取 GameTime，而不是互相直接调用。**

一旦时间是事件源，你就能用同一条链路同时驱动：
- **玩法**：作物生长、NPC 日程、离线推进……
- **观感**：昼夜环境光变化、路灯显隐、室内外策略分支……
- **UI/调试**：时钟显示、快进、暂停、加速……

这种"一个事件源，多个消费者"的模式，正是 [事件系统](06-事件系统.md) 事件系统中讲过的观察者思想在实际项目中的落地。

## 2. 本节目标与问题定义

本节目标一句话：
> 建立一个"权威时间状态 + 事件输出"的时间系统，并用它驱动昼夜光照与光源显隐，让时间成为多个系统共享的低耦合节拍器。

把目标拆成三个问题，每个都对应一个你一定会遇到的坑。

### 2.1 时间的"权威状态"放哪里？

想象一下：如果作物系统自己记了一份时间，UI 又从另一处读取，昼夜光照系统算的是第三份。你迟早会遇到：
- UI 显示"白天"，但环境光已经变暗了
- 你手动快进了一天，作物没长、灯没亮——因为有些系统根本没收到通知
- 调试时改了小时数值，结果跟没改一样

**根本原因**：多个数据源会互相矛盾，且手动修改单个数据源不会通知其他人。

解决方式是：**只有一处权威时间状态（Single Source of Truth）**。

《迷你农场》把它放到 ECS 的 `registry.ctx()` 中：
- `GameTime` 是全局共享的"时间模型"——day、hour、minute、time_of_day、time_scale，全部集中在一个结构里
- `TimeSystem` 是唯一负责推进它的系统（后面还会看到 `AdvanceTimeRequest` 如何与它配合）

这样，任何系统想读时间，只需要 `registry.ctx().find<GameTime>()`，拿到的一定是同一份数据。

### 2.2 如何把"时间变化"变成可组合的系统 API？

假设你把"时间变化"做成直接调用：TimeSystem 每到整点就调一下 `CropSystem::onHourChanged()`，再调一下 `DayNightSystem::onHourChanged()`。这条路能走多远？

- 新加一个需要响应时间的系统（比如 NPC 日程），就要改 TimeSystem
- 系统顺序/初始化稍一变动，调用链就断了
- 想在测试里单独验证 CropSystem，得先把 TimeSystem 也搭起来

**事件解耦的价值**：TimeSystem 不知道消费者是谁，只输出三种事件：
- `HourChangedEvent`（整点）
- `DayChangedEvent`（跨天）
- `TimeOfDayChangedEvent`（时段切换）

消费者通过 `dispatcher.sink<T>().connect()` 订阅。加新系统？写一个 `connect`，不动 TimeSystem 一行代码。

### 2.3 "夜晚"到底是玩法概念，还是视觉概念？

这是一个容易踩的坑——很多项目会无意中把"夜晚"写出三套阈值：
- **玩法时段**（TimeOfDay::Night）可能是 20:00→4:00，影响 UI 显示、AI 行为
- **视觉过渡**（sunrise/sunset）可能是 5:00→7:00 / 17:00→19:00，影响环境光渐变
- **路灯显隐**可能想更早更晚（比如 18:00→6:00，日落前就开灯）

如果这三组数值散落在不同文件的 hardcode 里，改一个忘一个，结果就是"太阳已经落山了但路灯还没亮"这种视觉穿帮。

[游戏时间与昼夜](31-游戏时间与昼夜.md) 的设计原则是：

> **玩法时段和视觉暗时段是两个独立概念。** 它们可以不一致，但必须"数据驱动 + 明确边界"——分别放在 `game_time_config.json` 和 `light_config.json` 中，互不干扰。

## 3. 核心概念

### 3.1 `GameTime`：权威时间状态

`GameTime` 就是一张"全局时间仪表盘"，存放在 `registry.ctx()` 中。来看它包含什么：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `day_` | int | 当前天数（从 1 开始） |
| `hour_` | float | 当前小时（0.0–24.0，浮点以支持平滑过渡） |
| `minute_` | float | 当前分钟（0.0–60.0） |
| `time_scale_` | float | 时间倍率（1.0 = 正常，加大可加速） |
| `paused_` | bool | 时间暂停开关 |
| `time_of_day_` | TimeOfDay | 当前玩法时段（Dawn/Day/Dusk/Night） |
| `config_` | TimeConfig | 从 `game_time_config.json` 加载的配置 |
| `emissive_dark_start/end_hour_` | float | 从 `light_config.json` 加载的"视觉暗时段"窗口 |

`GameTime` 的初始化发生在 `GameScene::initRegistryContext()` 中——这是 [游戏场景初始化与系统编排](26-游戏场景初始化与系统编排.md) 讲过的"组合根"阶段：

```cpp
// GameScene::initRegistryContext()
game_time_ = GameTime::loadFromConfig("assets/data/game_time_config.json");
game_time_->loadEmissiveVisibilityFromLightConfig("assets/data/light_config.json");
registry_.ctx().emplace<GameTime>(*game_time_);
```

注意这里做了两步加载：先读玩法时间配置，再读视觉时间配置——正是上面"两个概念、两个配置文件"原则的体现。

它最大的好处是：**读取成本极低**，任何系统都可以在 update 中拿到统一的时间视图，不需要额外的依赖注入或跨系统调用。

### 3.2 TimeSystem：唯一的"推进者"与事件源

TimeSystem 每帧做两件事：
1. **推进数值**：把 delta_time 换算成游戏分钟，累加到 minute → hour → day
2. **在边界处发出事件**：整点发 `HourChangedEvent`，跨天发 `DayChangedEvent`，时段变化发 `TimeOfDayChangedEvent`

你不需要记住每一行实现，但下面这段"心智版伪代码"值得内化：

```text
minute += delta * scale * minutes_per_real_second
while minute >= 60:
  minute -= 60
  hour += 1
  enqueue HourChanged{day, hour}
  if hour >= 24:
    hour -= 24
    day += 1
    enqueue DayChanged{day}

new_period = calculateTimeOfDay(hour)
if new_period != old_period:
  time_of_day = new_period
  enqueue TimeOfDayChanged{day, hour, new_period}
```

这里有几个值得留意的细节：

**为什么用 `while` 而不是 `if`？** 当 `time_scale` 很大或快进时，一帧可能跨越多个小时甚至多天。`while` 循环确保每个整点都会产生一次 `HourChangedEvent`，这对作物系统等逐小时结算的消费者至关重要——漏发一次事件就意味着少长一个周期。

**`calculateTimeOfDay` 如何处理跨天？** Night 的时段是 20:00→4:00（start > end），需要特殊处理。`GameTime` 内部的逻辑是：如果 `start > end`，则当 `hour >= start || hour < end` 时判定为该时段。这是一个经典的"跨日时间窗口"判定模式，`isDarkForEmissives()` 也使用同样的逻辑。

### 3.3 `trigger` vs `enqueue`：事件什么时候被分发？

这是一个容易被忽视但影响调试体验的关键点。

《迷你农场》的默认约定是：
- **控制流类事件**（Quit / Scene push/pop）用 `trigger`——立即同步生效
- **数据类事件**（时间/动画/音效）多用 `enqueue`——帧尾统一分发

在本项目中，`dispatcher.update()`（即 enqueue 事件的分发点）放在 `render()` 之后（见 `src/engine/core/game_app.cpp`）。这意味着：

> TimeSystem 在本帧 enqueue 的时间事件，在本帧画面呈现之后才被分发；消费者的响应结果通常在**下一帧**才完全可见。

这不是 bug，而是一种**稳定性策略**：
- **避免递归触发**：如果事件在 update 链路中立即分发，消费者的响应又可能触发新事件，导致时序混乱甚至无限循环
- **让逻辑更可预测**：把大量数据事件变成"下一帧输入"，每帧的状态变化有明确的边界

如果你在调试中发现"时间改了但灯还没亮"，先别急着怀疑 bug——等一帧再看，很可能是 enqueue 延迟的正常表现。想彻底搞清楚这个机制，请回顾：`docs/events.md`。

<img src="https://theorhythm.top/gamedev/TF/L29_frame_timeline.webp" style='width: 960px;' />

### 3.4 "视觉暗时段"：`emissive_visibility.dark_time`

本节一个重要的架构成果是把"路灯什么时候亮"从 hardcode 变成配置。

**配置位置**：`assets/data/light_config.json` 的 `emissive_visibility.dark_time`

```json
"emissive_visibility": {
    "dark_time": {
        "start": 18.0,
        "end": 6.0
    }
}
```

这个窗口表示"视觉上足够暗、需要开灯"的时间段（18:00→次日 6:00），它跟玩法的 `TimeOfDay` 是独立的——Dusk 从 16:00 就开始了，但路灯到 18:00 才亮，这更符合现实感。

`GameTime` 把它解析成一个统一判定函数：

```cpp
bool GameTime::isDarkForEmissives() const;
```

所有需要判断"现在该不该开灯"的地方（初始化时、运行期切换时）都调用这同一个函数。如果以后想调阈值，只改 JSON 配置，不需要到代码里到处搜 `18` 或 `6`。

## 4. 架构与数据流

本节的系统交互可以拆成**三条链路**，每条链路有明确的输入、输出和边界。先看全景图：

<img src="https://theorhythm.top/gamedev/TF/L29_three_chains_overview.webp" style='width: 960px;' />

### 4.1 链路一：时间源——`TimeSystem → 时间事件`

**输入：**
- 每帧的 delta_time（来自 GameApp 的主循环）
- `AdvanceTimeRequest`（来自 RestDialogScene 或调试面板——"请帮我快进 N 小时"）

**输出：**
- `HourChangedEvent` / `DayChangedEvent` / `TimeOfDayChangedEvent`

**关键边界：**
- TimeSystem **不直接调用**任何消费者；消费者只通过事件订阅来响应
- 手动设置 `GameTime.day_/hour_/minute_` 只改数值，**不会自动补发事件**——调试面板里也明确提示了这一点

**`AdvanceTimeRequest` 的处理方式值得注意**：TimeSystem 收到请求后，不是一次性把时间跳到目标值，而是**逐小时循环推进**，每推进一小时就 enqueue 一次 `HourChangedEvent`。这样即使快进 24 小时，作物系统也能收到 24 次整点事件，每一次都有机会推进生长阶段。这保证了快进和自然流逝走的是**同一条事件链路**——不需要为快进写特殊逻辑。

### 4.2 链路二：环境光——`DayNightSystem → GlobalLightingState → LightSystem`

这条链路的目标是：**把"时间"变成渲染输入，而不是把渲染逻辑写到玩法系统里。**

**数据流（三步）：**

1. **DayNightSystem** 每帧读取 `GameTime`（hour + minute），根据 `light_config.json` 中的配置计算：
   - **环境光（ambient）**：通过关键帧插值——配置中定义了 6 个时间点的颜色（凌晨深蓝、正午明亮、黄昏暖橙），系统在相邻关键帧之间做平滑插值
   - **太阳方向光**：用正弦弧线模拟太阳轨迹（6:00 东方升起 → 12:00 正午最高 → 18:00 西方落下），并在 sunrise/sunset 过渡期用 smoothstep 做淡入淡出
   - **月亮方向光**：与太阳相位相反，sunset 时升起、sunrise 时落下

2. 结果写入 `registry.ctx<GlobalLightingState>()`——这是游戏层和引擎层之间的"光照契约"

3. 引擎侧 `engine::LightSystem` 读取 `GlobalLightingState`，把 ambient 和启用的方向光提交给 Renderer

**室内/室外分支：**

不是所有地图都应该受昼夜影响。`WorldState` 中的 `MapInfo` 提供了两个关键字段：
- `in_world`：标记地图是室内还是室外
- `ambient_override`：室内地图可以指定自己的固定环境光颜色

DayNightSystem 在 update 时会检查当前地图：如果是室内，直接使用 `ambient_override`，跳过太阳/月亮的计算。这样玩家进入房间后，光照不会跟着外面的昼夜变化而闪烁——室内永远是一个稳定的光照环境。

你需要记住的不是公式，而是边界：
> **DayNightSystem 负责"把时间变成全局光照参数"；engine::LightSystem 负责"把光照参数变成渲染提交"。** 游戏逻辑不碰渲染 API，渲染系统不知道"几点了"。

<img src="https://theorhythm.top/gamedev/TF/L29_daynight_lighting_chain.webp" style='width: 960px;' />

### 4.3 链路三：光源显隐——`TimeOfDayLightSystem → LightDisabledTag`

这条链路的目标是：让地图里的路灯、火把、窗户光在夜晚亮起、白天熄灭，但**不让引擎层知道"夜晚"这个概念**。

**实现策略非常 ECS：**

1. **数据层**：地图光源实体在 Tiled 编辑器中标记 `night_only=true` 或 `day_only=true`
2. **加载层**：`EntityBuilder::applyTimeVisibilityTags()` 在地图加载时，根据 Tiled 属性给实体挂上 `NightOnlyTag` / `DayOnlyTag`，并检查当前时间——如果加载时是白天而光源标记为 NightOnly，就预先挂上 `LightDisabledTag`，避免加载瞬间出现"白天路灯亮着"的穿帮
3. **运行层**：`TimeOfDayLightSystem` 监听 `HourChangedEvent`，每次整点变更时调用 `GameTime::isDarkForEmissives()` 判断当前是否处于暗时段，然后批量添加/移除 `LightDisabledTag`
4. **渲染层**：`engine::LightSystem` 收集光源组件时，排除带 `LightDisabledTag` 的实体——这些光源不参与光照计算

**为什么是 `LightDisabledTag` 而不是 `InvisibleTag`？**

引擎层定义了两个不同的标签：
- `InvisibleTag`——`RenderSystem` 跳过精灵渲染，实体在画面上**完全消失**
- `LightDisabledTag`——`LightSystem` 跳过光照提交，但**不影响精灵渲染**

路灯/火把的灯柱模型白天也应该可见，只是不发光。如果用 `InvisibleTag`，白天整个灯柱都看不见了。`LightDisabledTag` 精确地表达了**"关灯但不拆灯"**的语义。

**事件驱动 vs 每帧轮询：**

`TimeOfDayLightSystem` 不是每帧都遍历所有光源实体来判断显隐。它只在收到 `HourChangedEvent` 时才做一次遍历——因为光源显隐状态只可能在整点变更时发生变化。这样做的收益是：
- 逻辑更清晰：不需要每帧都"算一次是不是夜晚"
- 性能更自然：一天只遍历 24 次（整点数），而不是每帧都遍历

### 4.4 初始化与顺序：为什么 Time/Lighting 要尽早更新？

在 `GameScene::update` 中，你会看到一个很明确的顺序：

```text
1. remove_entity_system  ← 清理标记删除的实体
2. time_system           ← 推进时间、产生事件
3. day_night_system      ← 计算环境光/方向光
4. player_control_system ← 处理输入
5. ...（其他玩法系统）
6. movement / collision  ← 物理与空间索引
7. animation / UI        ← 渲染准备
```

时间和光照排在最前面，原因很直接：

> **让本帧所有系统都读到同一份"最新时间"，并且玩家在当前帧看到的光照反馈与行为决策尽量一致。**

如果你把 TimeSystem 放到最后，其他系统在本帧读到的时间就是"上一帧的"，会出现一帧的延迟错位。虽然一帧延迟肉眼很难察觉，但在快进场景下（一帧跨多小时），这种错位可能导致逻辑 bug。

另外，`GameScene::initRegistryContext()` 中把"视觉暗时段窗口"加载到 `GameTime` 的做法也值得注意：
- `game_time_config.json`：负责玩法时间（时段边界与速度）
- `light_config.json`：负责视觉时间（环境光关键帧与自发光显隐窗口）

这就是本节反复强调的"配置边界"原则：

> **一个配置负责一类语义，不要把玩法阈值和视觉阈值混到同一处。** 各改各的，互不干扰。

### 4.5 休息/睡觉：快进闭环

玩家在游戏中触发"休息"的完整链路是：

1. 玩家走到休息区，触发 `InteractRequest`
2. `RestSystem` 识别目标带有 `RestArea` 组件，push 一个 `RestDialogScene`（暂停主游戏）
3. 玩家在对话框中选择休息时长（1-24 小时），点确认
4. `RestDialogScene` 发出 `AdvanceTimeRequest{hours}`
5. `TimeSystem` 收到请求，逐小时推进时间，逐个 enqueue 事件
6. 各消费者响应事件：作物生长（DayChanged）、光照变化（DayNightSystem 读到新时间）、灯光显隐（HourChanged 触发 TimeOfDayLightSystem）

整条链路的精妙之处在于：休息和正常时间流逝走的是**完全相同的事件链路**。`AdvanceTimeRequest` 只是让 TimeSystem "加速模拟"了若干小时，每个小时该触发的事件一个都不少。这意味着你不需要为快进写任何特殊逻辑——同一套代码覆盖了正常流逝和快进两种场景。

### 4.6 演示/调试最佳实践

如果你想手动推动"作物生长/昼夜变化/灯光显隐"来验证链路，推荐方式：
1. 使用 `Game Time` 调试面板的"快进 1 小时/1 天"按钮——内部发的是 `AdvanceTimeRequest`，走完整事件链路
2. 调大 `time_scale`——让时间自然加速推进

**不推荐**：直接在调试面板里手动改 day/hour/minute 数值。因为这只改了 `GameTime` 的字段，不会触发任何事件——消费者不知道时间变了，作物不会长，灯也不会开。

这是一个值得内化的工程经验：

> **想要系统联动，就要驱动"事件源"，而不是只改"状态字段"。** 状态是结果，事件是驱动力。

## 5. 常见问题与排错

### Q1：时间在走，但环境光不变？
**检查顺序**：
1. 确认 `DayNightSystem` 已在 `GameScene::initSystems()` 中创建
2. 确认 `GameScene::update()` 中调用了 `day_night_system_->update()`
3. 检查当前地图是否是室内（`MapInfo.in_world == false`）——室内地图使用固定 ambient，不随昼夜变化

### Q2：灯应该亮但没亮？
**检查顺序**：
1. 确认 Tiled 地图中光源对象设置了 `night_only=true` 属性
2. 确认 `TimeOfDayLightSystem` 已创建并连接了 `HourChangedEvent`
3. 确认当前时间在 `emissive_visibility.dark_time` 窗口内（默认 18:00→6:00）
4. 用调试面板快进到整点——`TimeOfDayLightSystem` 只在整点才重新评估显隐

### Q3：快进后作物没长？
**可能原因**：
- 你是直接改了 `GameTime.day_` 数值，而不是通过 `AdvanceTimeRequest`——前者不触发事件
- `AdvanceTimeRequest` 的 hours 参数不够大（需要至少跨天才触发 `DayChangedEvent`）

### Q4：室内光照闪烁？
**可能原因**：
- 地图的 `in_world` 属性未正确设置为 `false`
- `ambient_override` 未在 Tiled 地图属性中配置——DayNightSystem 找不到覆盖值，退回了动态计算

## 8. 小结

本节课的要点：

1. **`GameTime` 是权威时间状态，`TimeSystem` 是唯一推进者**——所有系统读同一份数据，时间变化通过事件输出而非直接调用，想联动就驱动事件源、别手改字段
2. **用事件把时间变成"可组合的系统 API"**——玩法（作物/NPC）、观感（昼夜/灯光）、UI（时钟/调试）通过订阅同一组事件解耦协作，加新消费者不改时间系统
3. **明确区分"玩法时段"与"视觉暗时段"**——`game_time_config.json` 管玩法边界（Dawn/Day/Dusk/Night），`light_config.json` 管视觉边界（ambient 关键帧、emissive 显隐窗口），各负其责、数据驱动

下节课我们会把"时间"放到更大的闭环里：
> **存档与流程收尾**：当 GameTime 变成可保存的状态，你需要考虑读档后如何让"环境光/灯光显隐/日结算"在恢复时保持一致，以及离线推进如何与存档契合。
