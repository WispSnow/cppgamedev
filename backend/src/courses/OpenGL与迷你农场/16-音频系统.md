# 音频系统：音效/音乐、资源缓存与 2D 空间声

上节课我们把输入系统工程化成了"动作映射 + 状态机 + 逻辑鼠标坐标"，让玩家控制、世界交互与 UI 都能共享同一套稳定的输入语义。

但当你的游戏开始"能玩"之后，你很快会发现另一个体验层面的关键缺失：

> 没有声音反馈的交互很"空"：挥工具没有节奏感、拾取物品没有确认反馈、切换场景缺少氛围过渡——一切操作都像在"静音模式"下进行。

所以这节课要解决的不是"怎么调用一个播放 API"这种局部问题，而是：**如何把声音系统做成可复用、可配置、可观测的工程模块**，让它能被 UI、游戏系统稳定调用，并且能在开发阶段快速调参验证。

## 2. 本节目标与问题定义

本节核心问题可以总结为一句话：

> 用 `resource_mapping.json` 预加载音效/音乐缓存，用 `AudioPlayer`（miniaudio）管理播放实例；音效通过 `PlaySoundEvent → AudioSystem` 事件链路触发，并在 2D 世界里以相机为 listener 做"距离衰减 + 声像（pan）"；最后用 `config/audio.json` + Debug 面板形成调参闭环。

本节完成后你应该能回答这些问题：

- **资源与缓存**：为什么音频要"预加载成缓存"？`AudioManager` 与 `AudioPlayer` 各自负责什么？
- **事件驱动**：为什么音效要用事件（`PlaySoundEvent`）而不是到处直接调用 `AudioPlayer`？
- **空间声**：2D 空间声的最小模型是什么？`falloff_distance` 和 `pan_range` 的直觉含义是什么？
- **可观测性**：怎么验证"资源确实被预加载了""参数确实生效了"，而不是靠猜？

## 3. 核心概念

### 3.1 key-id：让"语义 key"成为稳定 API

《迷你农场》延续了 [资源系统](13-资源系统.md) 的资源系统约定：代码里使用 **语义 key 的 hash（key-id）**，而不是硬编码文件路径。

数据入口是 `assets/data/resource_mapping.json`，其中 `sound` 和 `music` 部分定义了所有音频资源的映射：

```json
{
  "sound": {
    "watering": "assets/audio/water_splash.wav",
    "hoe": "assets/audio/shovel-stab.wav",
    "harvest": "assets/audio/plant_harvest.wav",
    "axe": "assets/audio/chop-wood.wav",
    "ui_hover": "assets/audio/Fantasy_UI (1).wav",
    "ui_click": "assets/audio/Fantasy_UI (10).wav"
  },
  "music": {
    "title-bg-music": "assets/audio/02_spring_fairy_tale.ogg",
    "scene-bg-music": "assets/audio/01_spring_journey.ogg"
  }
}
```

运行时语义：`"ui_click"` / `"title-bg-music"` 表示"这是什么声音"，真实路径藏在映射里。代码只需要说"play ui_click"，不需要关心它到底是哪一份 wav 或 ogg。

好处：
- **替换资源不改代码**：想换一个点击音效？改映射文件即可
- **统一入口**：所有音频资源通过 `ResourceManager` 在启动时预加载，不会散落在各处

> **术语提示**：项目里同时存在 key-id 与 path-hash 两种用法；本课以 key-id 为主。约定速查：`docs/audio_system.md` 的"ID 语义"小节。

### 3.2 "缓存"与"播放实例"不是一回事

把音频系统拆成两层，是降低复杂度的关键：

| 层级 | 负责人 | 职责 | 类比 |
|------|--------|------|------|
| **缓存层** | `AudioManager` | 把音频文件解码成 PCM float samples，按 `entt::id_type` 缓存 | 纹理缓存（`TextureManager`） |
| **实例层** | `AudioPlayer` | 把缓存数据变成可播放的 `ma_sound` 实例，管理音量/淡入淡出/空间化 | DrawCall（运行时渲染实例） |

这个分层意味着：**同一份音效数据只需解码一次，但可以同时产生多个播放实例**。比如两个实体同时挥斧头，共享同一份斧头音效缓存，但各自有独立的播放实例（独立的音量、空间位置）。

这也是为什么缓存使用 `shared_ptr<AudioBuffer>`：播放期间必须保证底层数据不被释放。`AudioManager` 持有 `shared_ptr`，每个播放实例也通过 `shared_ptr` 引用同一份数据——只有当所有引用都释放后，内存才会被回收。

![缓存层 vs 实例层两层架构](diagrams/L14_cache_vs_instance.png)

### 3.3 事件驱动音效：把"触发"与"播放实现"解耦

音效的触发点很多：UI 点击、玩家挥工具、拾取物品、碰撞、宝箱开启……

如果每个系统都直接调用 `AudioPlayer`，你会遇到三个工程问题：
- **调用点分散**：难以统一控制开关、策略和音量
- **难做实体音效**：空间声需要 source/listener 坐标，谁来提供？
- **难以调试**：到底是哪个系统在疯狂播放音效？

因此《迷你农场》用事件做统一入口。事件的定义非常简洁：

```cpp
// src/engine/utils/events.h
struct PlaySoundEvent {
    entt::entity entity_{entt::null};      // 目标实体（空 = 全局音效）
    entt::id_type sound_id_{entt::null};   // 音效 ID
};
```

两个字段，表达了两层意图：
- `sound_id_`：播放"什么声音"
- `entity_`：在"谁身上"播放（空表示全局音效，有实体则做 2D 空间化）

#### AudioSystem：事件处理的 Guard 链

`AudioSystem` 订阅 `PlaySoundEvent` 后，用一系列 Guard 逐步判断播放策略：

```text
1. sound_id 为空？         → 忽略
2. 通过 AudioComponent 做一次 trigger_id → sound_id 映射
3. entity 为空？           → 全局音效
4. entity 无效？           → 降级为全局音效（+ 警告日志）
5. entity 缺少 Transform？ → 降级为全局音效（+ 警告日志）
6. 全部通过               → 2D 空间音效（source = Transform, listener = Camera）
```

> **一句话记住**：`AudioSystem` 的策略是"尽量播放，能空间化就空间化，不能就降级为全局音效"——绝不因为缺少位置信息就丢弃音效。

#### 实体音效表：AudioComponent

当事件携带了实体时，`AudioSystem` 不只是查实体位置——还会做一次 **"触发名 → 实际音效"的映射**：

```cpp
// src/engine/component/audio_component.h
struct AudioComponent {
    std::unordered_map<entt::id_type, entt::id_type> sounds_;
    // key:   触发名 hash（如 "axe" 的 hash）
    // value: 可播放的 sound id（对应 resource_mapping.json 中的 key hash）
};
```

好处：**同一个"砍树"动作在不同实体上可以播放不同的音效**，只需在蓝图/数据里配置 `AudioComponent` 即可——代码完全不变。比如玩家和 NPC 都有"axe"动作，但可以通过各自的 `AudioComponent` 映射到不同的音效资源。

#### 游戏侧触发范例：ActionSoundSystem

`ActionSoundSystem` 展示了游戏层如何以数据驱动的方式触发音效：

1. 检测实体 action 切换（例如 idle → axe）
2. 查 `ActionSoundComponent` 获取该 action 的触发配置
3. 通过**概率过滤**（`probability_`）和**冷却过滤**（`cooldown_seconds_`）后，enqueue `PlaySoundEvent`

```cpp
// src/game/system/action_sound_system.cpp（核心逻辑简化）
const auto& cfg = cfg_it->second;
if (cfg.probability_ < 1.0f) {
    const float roll = engine::utils::randomFloat(0.0f, 1.0f);
    if (roll > cfg.probability_) continue;
}

dispatcher_.enqueue(PlaySoundEvent{entity, trigger_id});

if (cfg.cooldown_seconds_ > 0.0f) {
    action_sounds.cooldown_remaining_seconds_[trigger_id] = cfg.cooldown_seconds_;
}
```

这避免了在每个动作逻辑里硬编码音效调用，也让"某些动作只有 30% 概率出声""同一动作 0.5s 内不重复"变成纯数据配置。

### 3.4 音乐（BGM）与音效（SFX）的工程语义不同

在工程层面，音乐与音效的差异不只是"时长"：

| 维度 | 音效（SFX） | 音乐（BGM） |
|------|-------------|-------------|
| 时长 | 短（< 1s ~ 数秒） | 长（数十秒 ~ 数分钟） |
| 并发 | 可叠加，同一帧可能触发多个 | 通常只有一首在播 |
| 循环 | 通常不循环 | 通常 loop |
| 触发方式 | 事件驱动（`PlaySoundEvent`） | 场景直接调用 |
| 切换需求 | 无 | 淡入/淡出、cross-fade |

`AudioPlayer` 为音乐提供了完整的生命周期控制（play/pause/resume/stop），并支持淡入淡出。场景切换 BGM 时使用 200ms 的短淡入让过渡更自然：

```cpp
// src/game/scene/title_scene.cpp
constexpr int MUSIC_FADE_IN_MS = 200;
context_.getAudioPlayer().playMusic(
    game::defs::audio::TITLE_BG_MUSIC_ID.value(), true, MUSIC_FADE_IN_MS);
```

当 `playMusic` 被调用时，如果已有音乐在播放且指定了淡入时间，旧音乐会按同样时长淡出——实现短暂的 cross-fade 效果。如果同一首曲子已经在播放中，调用会直接返回，不会重启。

![音乐生命周期](diagrams/L14_music_lifecycle.png)

> **常量收敛**：`src/game/defs/audio_ids.h` 把常用 BGM key 定义为 `constexpr entt::hashed_string`（如 `TITLE_BG_MUSIC_ID`、`SCENE_BG_MUSIC_ID`），避免字符串字面量散落在多个场景文件中。

### 3.5 2D 空间声：教学向"最小可用模型"

《迷你农场》的 2D 空间声是一个教学向的简化模型，只用两个维度就能建立有效的空间感：

- **listener**：相机位置（`Camera::getPosition()`）
- **source**：实体 Transform 的位置

核心直觉：
- **越远越小声**（距离衰减 → 控制音量）
- **左右位置影响声像**（pan → 控制左右声道平衡）

实际代码和下面的公式一一对应——这不是"示意"，而是 `AudioPlayer` 内部 `playSoundSpatialInternal` 的真实计算逻辑：

```text
delta = source - listener
distance = length(delta)

attenuation = clamp01(1 - distance / falloff_distance)   // 距离衰减
pan = clamp(delta.x / pan_range, -1, 1)                 // 左右声像
```

关键参数来自 `config/audio.json`：

```json
{
  "audio": {
    "spatial": {
      "falloff_distance": 320.0,
      "pan_range": 160.0
    }
  }
}
```

- **`falloff_distance`**：超过此距离音量为 0。值越大，声音"传得越远"
- **`pan_range`**：delta.x 达到此值时声像完全偏左/右。值越小，声像"偏得越快"

> **直觉验证**：以当前配置为例——`falloff_distance = 320`，一个音源在距相机 160 像素处，音量约为 50%；在 320 像素处完全静音。`pan_range = 160`，音源在相机右方 80 像素处，声像偏右 50%。

### 3.6 调参闭环：配置文件 + Debug 面板

音频系统最怕"凭感觉改，改完不知道有没有生效"。《迷你农场》的调参闭环是：

1. **运行时调参**：`F5` → `Engine Debug Panels` → `Audio`，拖动 Music/Sound 音量滑块，调整 falloff/pan 参数——**即时生效**
2. **持久化**：点击 `Save`，当前参数写回 `config/audio.json`
3. **重载验证**：重启游戏或点击 `Reload`，确认参数从文件正确读回
4. **缓存确认**：同时打开 `ResMgr` 面板，确认 sound/music 缓存条目存在（说明预加载成功）

这套闭环的价值在于：**你能把"听感调试"变成一个可重复的工程流程**，而不是"改数值 → 重启 → 再听 → 感觉不对 → 再改"的低效循环。

## 4. 架构与数据流

### 4.1 启动阶段：映射 → 预加载 → 缓存

![启动阶段流程](diagrams/L14_startup_flow.png)

启动时的关键顺序：

1. `GameApp::initResourceManager` 创建 `ResourceManager`，调用 `loadResources("assets/data/resource_mapping.json")`
2. `ResourceManager` 解析映射文件，遍历 `sound` 和 `music` 条目，逐一调用 `AudioManager::loadSound/loadMusic`
3. `AudioManager` 使用 miniaudio 的 `ma_decoder` 将文件解码为 float PCM samples，缓存在内存中
4. `GameApp::initAudioPlayer` 创建 `AudioPlayer`，构造时自动调用 `loadConfig("config/audio.json")` 读取运行时参数

> **顺序约束**：`loadResources` 必须早于 `AudioPlayer::create`——后者依赖前者建立的缓存。如果顺序反了，播放时会找不到缓存数据。

### 4.2 运行时（音效）：事件链路 + 空间化

![事件驱动时序图](diagrams/L14_event_sequence.png)

运行时音效的完整链路：

1. 游戏系统（Farm/Pickup/ActionSound 等）在逻辑更新时 `dispatcher.enqueue(PlaySoundEvent{...})`
2. 帧尾 `dispatcher.update()` 统一分发所有排队事件
3. `AudioSystem::onPlaySoundEvent` 被调用，执行 Guard 链：
   - 先通过 `AudioComponent` 做 trigger_id → sound_id 映射（没有 `AudioComponent` 则直接使用原始 sound_id）
   - 判断"全局音效 vs 实体音效（2D spatial）"——缺少 Transform 时自动降级为全局音效
4. 调用 `AudioPlayer::playSound` 或 `playSound2D`，后者会计算距离衰减和声像

> **设计要点**：游戏系统只负责"发生了什么声音事件"，不负责"怎么播、在哪里播"。这让音效的统一开关、调参、策略切换都收口在 `AudioSystem` 一处。

### 4.3 运行时（音乐）：场景触发 + 音乐控制

音乐的触发路径比音效简单——不走事件，而是由场景在进入时直接调用 `AudioPlayer::playMusic`：

- `TitleScene` 进入时：播放 `TITLE_BG_MUSIC_ID`（对应 `"title-bg-music"`）
- `GameScene` 进入时：播放 `SCENE_BG_MUSIC_ID`（对应 `"scene-bg-music"`）

两个场景都使用 `playMusic(id, true, MUSIC_FADE_IN_MS)` 形式调用，`MUSIC_FADE_IN_MS = 200`。`playMusic` 内部会检查：如果同一首曲子已经在播放中就直接返回；如果需要切歌，旧音乐会按淡入时长做淡出，形成短暂的 cross-fade。

> **为什么音乐不走事件？** 音乐与场景生命周期直接绑定（进入场景就播放），触发点少且明确，直接调用反而更清晰。课后练习 1 会引导你把音乐也改成事件驱动，体会两种方式的取舍。

### 4.4 可观测性：两个面板各看什么

| 面板 | 关注点 | 验证的是 |
|------|--------|----------|
| `ResMgrDebugPanel` | 缓存条目数量、内存占用、时长 | **资源层正确性**——预加载是否成功 |
| `AudioDebugPanel` | 音量滑块、空间参数、Test 按钮 | **播放层正确性**——参数是否生效 |

> **工程化思路**：把不可见的系统变成可观测系统。如果你怀疑"音效为什么不响"，先看 ResMgr 面板确认缓存存在，再看 Audio 面板确认音量不为零——绝大多数音频问题可以在这两个面板中定位。

## 5. 演示：动手验证

以下演示帮你建立对音频系统的直觉。建议边操作边对照上面的概念讲解。

### 演示 1：缓存可视化

1. 运行游戏
2. 按 `F5` → `Engine Debug Panels` → `ResMgr`
3. 展开 `Audio` 区域，查看 sound/music 缓存条目
4. 确认：每个 `resource_mapping.json` 中的 sound/music 条目都有对应的缓存记录，且内存占用和时长数值合理

### 演示 2：调参闭环

1. 按 `F5` → `Engine Debug Panels` → `Audio`
2. 拖动 `Music Volume` 滑块，感受 BGM 音量即时变化
3. 拖动 `Sound Volume` 滑块，然后触发音效（比如挥工具），确认音量变化
4. 调整 `Falloff Distance` 为一个较小的值（如 100），在世界中触发音效，感受远距离音效是否变得更弱
5. 点击 `Save` → 关闭游戏 → 打开 `config/audio.json` 确认参数已写入
6. 重新运行游戏 → 打开 Audio 面板，确认参数从文件正确读回

### 演示 3：音乐切换

1. 在标题场景中，确认 BGM 正在播放
2. 进入游戏场景，观察 BGM 的切换（应有短暂淡入/淡出过渡）
3. 返回标题场景，再次确认 BGM 切回
4.（可选）在 Audio 面板中点击 Pause/Resume/Stop，体验音乐生命周期控制

### 演示 4：2D 空间声直觉

1. 进入游戏场景，走到有可交互物体的位置
2. 使用工具触发音效（如砍树、锄地）
3. 改变角色位置，让音源与相机的相对位置变化，感受：
   - 远离时音量变小
   - 左右移动时声像偏移
4.（可选）在 Audio 面板调小 `Falloff Distance`，重复上述操作，感受衰减范围变化

## 7. 课后练习

### 练习 1：让音乐也走事件驱动

> 目的：让音乐播放也走"事件驱动"的同一条路，进一步解耦 Scene 与 AudioPlayer（和 `PlaySoundEvent` 对齐）。

- **目标**：
  - 新增音乐事件（任选一种形式）：
    - `PlayMusicEvent` / `StopMusicEvent`
    - 或统一为 `AudioCommandEvent`（含 command enum + 参数）
  - 场景不再直接调用 `AudioPlayer::playMusic/stopMusic`，而是 enqueue 事件，由 `AudioSystem` 统一处理
- **验收标准**（满足 3 项即可）：
  - Title / Game 场景进入时 BGM 会自动播放，切换场景时 BGM 行为正确（可淡入/淡出）
  - 连续触发多次播放事件不会崩溃；行为稳定（例如"最后一次事件生效"）
  - Debug 面板依然可播放/暂停/恢复（不要求改面板，但不能破坏现有功能）
- **提示线索**：
  - 事件定义：`src/engine/utils/events.h`（或新建事件头）
  - 事件处理：`src/engine/system/audio_system.*`
  - 触发点：`src/game/scene/title_scene.cpp`、`src/game/scene/game_scene.cpp`

## 8. 小结

这节课的要点：

1. **`resource_mapping.json` 让音频资源 key 成为稳定 API**——替换音效只需改映射文件，代码完全不变
2. **`AudioManager` 负责解码与缓存，`AudioPlayer` 负责播放实例与参数**——两层分工让复杂度可控，`shared_ptr` 保证播放期间缓存不被释放
3. **`PlaySoundEvent → AudioSystem` 把"触发"与"播放实现"解耦**——统一处理全局音效和实体音效，缺少 Transform 时自动降级而不是报错丢弃
4. **2D 空间声用"距离衰减 + pan"的最小模型建立直觉**——只需两个参数（`falloff_distance` + `pan_range`），由 `config/audio.json` 控制
5. **Debug 面板让音频系统可观测**——ResMgr 面板看缓存是否存在，Audio 面板调参数并保存/重载

下节课我们会进入 UI 框架基础：UIManager、元素树与交互状态。你会看到 UI 的 hover/click 如何自然地触发 `ui_hover`/`ui_click` 音效，以及为什么"可复用的交互组件"需要同样可复用的声音约定。
